# 3주차 Linux 실습 — 경로의 다음 상대와 ARP·ICMP

요약: 승인된 IPv4에 대해 기존 VM의 주소·경로·이웃을 조회하고 ping 2회를 직접 실행한다. 패킷은 허용된 제한 캡처 또는 제공 trace로 분석한다. 캡처 권한이 없어도 가능한 조회·ping은 진행하며 관리 설정은 바꾸지 않는다.

패킷을 읽을 때는 스터디 팀원이 만든 [WireSalmon](https://taerim0.github.io/WireSalmon/)을 사용해 보기를 권장한다. Wireshark를 사용해도 좋다. WireSalmon 공개 웹에서 내장 샘플이나 저장한 `.pcap`·`.pcapng` 파일을 열어 대화 흐름과 개별 패킷의 근거를 함께 살펴본다. 공개 웹은 실시간 캡처를 지원하지 않으므로 캡처는 아래 실습 절차를 따른다. 내장 샘플 분석과 본인이 직접 수행한 결과는 구분한다.

## WireSalmon에서 먼저 볼 샘플

[WireSalmon](https://taerim0.github.io/WireSalmon/)에서 언어를 **한국어**로 고른 뒤 상단 **샘플 열기**에서 아래 이름을 선택한다. 대화 목록에서 볼 대화를 고르고 **대화 흐름**을 따라간다. 패킷을 누르면 **봉투 구조**에서 주소와 필드를 펼쳐 볼 수 있다. **전체 패킷**에서는 다른 대화와의 시간 순서도 확인한다.

### 먼저 보기 · ARP 다음에 ping

**링크 계층 → ARP로 MAC 주소 알아내기**를 연다.

1. **MAC 주소 찾기: 192.168.0.1** 대화의 ARP 요청·응답을 누른다. Ethernet 목적지가 요청의 `ff:ff:ff:ff:ff:ff`에서 응답의 요청자 MAC으로 달라지는지 확인하고, ARP가 묻는 대상 IP와 응답이 알려 주는 MAC을 짝짓는다.
2. **핑: 192.168.0.1** 대화를 고른다. ICMP Echo 요청·응답의 출발/목적 IP, 식별 번호와 순번을 비교한다. **전체 패킷**에서 ARP 요청 → 응답 → Echo 요청 → 응답의 순서를 찾는다. 이 예제는 게이트웨이 자체가 IP 목적지인 경우다.
3. 아래 실제 조회·ping 결과와 비교한다. 샘플은 새 ARP가 있는 사례이며, 본인 캡처에는 캐시 때문에 새 ARP가 없을 수 있다. ARP가 안 보였다는 이유로 실패나 ARP 미사용을 단정하지 않는다.

### 선택 비교 · IP 목적지와 링크의 다음 상대

**한눈에 보기 → 와이파이에 접속해서 웹사이트 열기**에서 **핑: 8.8.8.8**의 Echo 요청을 누른다. IPv4 목적지는 `8.8.8.8`이지만 Ethernet 목적지는 앞선 **MAC 주소 찾기: 192.168.0.1**에서 알아낸 게이트웨이 MAC인지 대조한다. 이 샘플에서는 최종 목적지 IP와 다음 홉 MAC의 주인이 다르다. ICMP Echo에는 TCP/UDP 포트가 없다는 점도 확인한다. 샘플 주소로 직접 ping하지 않으며, 실제 실습은 아래에서 허용된 대상만 사용한다.

샘플은 기존 패킷 분석 시간에 필요한 것만 골라 본다. 같은 근거를 본인 캡처나 제공 trace로 확인했다면 반복하지 않아도 된다. 샘플은 코드로 만든 분석 예제다. 아래 Linux 직접 실습의 완료 근거로 바꾸어 적지 않는다. 필요한 패킷을 근거로 한 사람이 설명하고, 다른 사람은 조건 하나를 바꾸어 질문한다. 추가 기록 양식은 없다.

## 실습 전 결정 — 값부터 확인

기존 아올다 Linux VM에 접속한 뒤 진행자가 **통신을 허용한 IPv4 목적지**를 확인한다. 같은 가상 LAN의 허가된 상대 또는 허가된 게이트웨이가 적합하다. 외부 임의 주소, 다른 참가자 VM의 주소, 문서 예제 주소를 시험 대상으로 쓰지 않는다. 두 번째 VM은 이미 존재하고 같은 네트워크이며 양측 사용 권한이 확인된 경우에만 선택할 수 있다. 새 VM·보안 규칙을 만들 필요가 없다.

아래 명령에서 `TARGET`은 승인된 실제 IPv4로 **직접 바꾼 뒤** 실행한다. 꺾쇠 안 설명이나 [합성 예제](sample-trace.txt)의 `192.0.2.x`·`198.51.100.x`를 복사하지 않는다. 비밀번호·토큰은 기록하지 않는다. 실습 중 NIC 주소·IP·경로·방화벽·SSH 관리 설정·이웃 캐시를 변경하거나 캐시를 일괄 삭제하지 않는다.

```sh
TARGET='승인된-IPv4-주소로-교체'
ip -4 route get "$TARGET"
```

출력의 `dev`를 보고 실제 장치명을 적는다. `via`가 있으면 그것이 링크에서 다음에 보낼 IPv4이고, 없으면 목적지 자체가 다음 상대 후보다. `dev lo`이거나 `local` 경로면 이더넷 ARP 실험에 쓰지 않는다. `unreachable`·`prohibit` 등 오류가 나면 ping하지 말고 명령과 오류를 기록한다. `dev`가 가상 NIC여도 이더넷 형식인지 다음 단계에서 확인한다. `via`가 없다고 항상 같은 LAN에서 끝까지 전달된다는 뜻은 아니다.

## 필수 실험 A — 읽기 전용 주소·경로·이웃 카드

**예상:** 선택된 NIC, 내 IPv4·MAC, `via` 유무, 이웃 표에 예상되는 다음 상대 IPv4와 상태를 생각하거나 짧게 말한다. 자세한 메모는 선택이며 2주차 접두사 판단과 비교한다.

```sh
ip -br -4 addr
ip -4 route
ip -o link show
ip -4 route get "$TARGET"
ip -4 neigh show
```

`route get`의 `dev`·`src`·`via`, 해당 `ip -o link show` 행의 `link/ether`와 MAC을 찾아 카드에 옮긴다. `IFACE`를 **출력에서 확인한 `dev` 이름**으로 수동 입력하고 아래에서 재확인한다. 장치명은 VM마다 다르다. `link/ether`가 아니거나 `lo`라면 Ethernet/ARP 직접 관찰 범위에서 제외하고 제공된 패킷 예제로 전환한다.

```sh
IFACE='route-get에서-확인한-dev-이름으로-교체'
ip -o link show dev "$IFACE"
ip -4 neigh show dev "$IFACE"
```

이웃 표에서 `via`가 있으면 게이트웨이 IPv4 행을, 없으면 `TARGET` 행을 찾는다. 처음부터 행이 없거나 `STALE`인 것은 가능한 출발 상태다. `INCOMPLETE`·`FAILED`라면 성공한 MAC으로 적지 않는다. 인터페이스가 다르거나 값이 불명확하면 실행을 멈추고 진행자에게 확인한다.

**근거:** 실제 명령과 출력 일부, 읽은 `dev`·내 MAC·다음 상대 IPv4·이웃 상태를 기록한다. 이웃 표가 비면 `행 없음`이라고 적는다. 출력에서 불필요한 주소·호스트명은 공유 전에 가린다. **복구:** 이 실험은 조회만 하므로 구성 복구가 없다. 오류는 원문과 환경 상태를 남긴다.

## 필수 실험 B — 제한된 ping과 패킷 분석

승인된 대상·경로·NIC와 ping 실행 가능 여부를 확인한다. **허용 대상에 대한 ping·전후 이웃 조회는 직접 수행하고, 패킷 분석은 직접 캡처 또는 [제공 trace](sample-trace.txt) 중 하나로 진행한다.** 캡처 도구·권한이 없다는 이유로 가능한 ping까지 건너뛰지 않는다. 대상·접속·경로·ping 도구 자체가 준비되지 않았다면 해당 직접 수행만 보충으로 남긴다.

### 패킷을 직접 캡처할 수 있을 때

`tcpdump`·`timeout`과 캡처 권한이 확인됐다면 같은 VM에 셸 A(캡처), 셸 B(ping)를 연다. **아래 캡처를 먼저 시작한 뒤 다음 절의 ping을 실행한다.** 캡처가 불가능하면 이 절을 건너뛰고 다음 절에서 ping·이웃 조회를 실행한 뒤 제공 trace를 분석한다. 설치·권한 변경은 기본 실습에 포함하지 않는다.

캡처는 **선택한 NIC의 ARP와 해당 대상과의 ICMP**만 대상으로 하며 SSH 패킷을 수집하지 않는다. ARP에는 같은 NIC의 다른 ARP가 짧게 섞일 수 있으므로 공유 전에 검토한다. 실행 전에 새 ARP와 ICMP 요청·응답이 보일지 짧게 예상한다. 캐시가 있으면 새 ARP 요청이 없을 수 있다.

셸 A에 위에서 검증한 같은 `TARGET`·`IFACE`를 입력하고 시작·종료 시각을 확인한다. `-c 16`과 `timeout 12`는 패킷 수와 시간을 모두 제한한다. `-n`은 이름 조회를 막고 `-e`는 Ethernet 주소를 표시한다. 종료 코드 124는 시간 제한으로 끝났다는 뜻이며 실험 실패 판정이 아니다.

```sh
TARGET='위에서-승인받고-route-get한-IPv4로-교체'
IFACE='위에서-확인한-Ethernet-dev로-교체'
sudo -n timeout 12 tcpdump -eni "$IFACE" -c 16 -l "arp or (icmp and host $TARGET)"
```

`sudo -n`이 실패하면 비밀번호를 기록하거나 권한을 바꾸지 않는다. 진행자가 허용한 대화형 캡처 방식이 이미 있다면 그 절차를 따르고 조건을 기록한다. 그렇지 않으면 캡처를 중단하고 아래 직접 조회·ping과 제공 trace 분석으로 이어 간다.

### ping과 이웃 조회를 직접 수행하기

직접 캡처 중이면 시작 표시를 확인한 뒤 12초 안에 셸 B에서 실행한다. **캡처하지 않는 경우에는 같은 VM의 작업 셸 하나에서 실행하면 된다.** 각 셸의 변수는 공유되지 않으므로 승인 값·검증된 NIC를 다시 입력한다. 응답 유무와 전후 이웃 상태를 먼저 예상하고, 허가되지 않은 주소에는 실행하지 않는다.

```sh
TARGET='같은-승인-IPv4로-교체'
IFACE='같은-검증된-Ethernet-dev로-교체'
ping -4 -n -c 2 -W 2 -w 8 "$TARGET"
ip -4 neigh show dev "$IFACE"
```

위 ping 명령은 한 번만 실행한다(총 2패킷, 각 응답 대기 최대 2초, 전체 기한 8초). 전후 이웃 상태와 ping 결과를 비교한다. `INCOMPLETE`·`FAILED`·행 없음은 그대로 기록한다. ping 실패는 ICMP 차단·상대 미응답·경로·정책 등 여러 가능성을 남기며 응답 성공으로 표시하지 않는다.

### 패킷 분석과 완료 근거를 나누기

직접 캡처했다면 ARP·ICMP 행 번호 또는 실제 `0 packets`를 남긴다. 캡처를 실행하지 않았다면 `캡처 미실행`이라고 적고 [제공 trace](sample-trace.txt)의 A01\~A06·B01\~B04에서 프레임·ARP·ICMP를 분석한다. **캡처 미실행과 실제 캡처 결과 0개는 다르다.** 제공 trace의 주소·행 번호를 자기 VM의 관찰 값으로 옮기지 않는다.

캐시나 다른 트래픽의 갱신 때문에 ARP 요청이 없을 수 있다. 다른 ARP가 보이면 내 대상이라고 단정하지 않는다. 다른 망 목적지의 `via` 게이트웨이 행에서 본 MAC은 그 최종 서버의 MAC이 아니다. 게이트웨이 자체를 TARGET으로 골랐다면 이번 IP 목적지와 링크의 다음 상대는 같은 게이트웨이다.

실제 대상·경로·전후 이웃 상태·ping 결과는 개인 파일에 한 번 보관한다. 직접 캡처의 필터·시각·패킷 번호 또는 제공 trace의 사례·행 번호는 출처를 구분한다. **직접 조회·ping과 제공 trace 분석을 마쳤다면 필수 실습의 해당 항목을 충족하며, 직접 캡처를 별도 필수 보충으로 요구하지 않는다.** 조회·ping을 실행하지 못했다면 그 단계만 직접 수행 보충으로 남긴다.

구성을 바꾸지 않았으므로 별도 설정 복구는 없다. 캡처가 12초 뒤에도 끝나지 않으면 Ctrl+C로 중지한다. 공유 전 실제 IP·MAC·호스트명·다른 ARP와 민감한 값을 가린다.

## 관찰 결과를 해석할 때

기존 이웃 정보가 있으면 새 ARP 없이 ICMP가 오갈 수 있다. ARP 요청이 없었다는 이유로 캡처 실패나 ARP 미사용으로 판정하지 않는다. 게이트웨이 자체를 목적지로 골랐다면 그 결과만으로 게이트웨이 너머의 전달이나 외부 HTTP 상태를 확인할 수 없다.

캡처 실행 시간과 첫 패킷부터 마지막 패킷까지의 간격도 구분한다. 본인 출력과 패킷에서 확인한 값만 기록한다.

## 직접 실행 불가와 관찰 한계

| 상태 | 이어서 할 일 | 직접 수행 기록 |
| --- | --- | --- |
| 승인 대상·권한·VM 접속 없음 | 가상 패킷 예제의 같은 망/게이트웨이 사례에서 다음 MAC과 ICMP를 찾는다 | A/B 직접 실행 미완료 |
| `ip`·`ping` 없음 또는 대상·경로가 준비되지 않음 | 가능한 조회와 제공 trace 분석을 이어 간다. 무허가 요청·임의 설치는 하지 않는다 | 실행하지 못한 조회·ping만 보충 |
| `tcpdump`·`timeout` 없음 또는 캡처 권한 없음 | 허용 대상의 직접 조회·ping을 하고 패킷만 제공 trace로 분석한다 | 직접 조회·ping / 제공 패킷 분석을 구분. 직접 캡처 필수 보충 없음 |
| `dev lo`, `link/ether` 아님 | 해당 경로에서 Ethernet ARP를 요구하지 않는다. 적합한 허용 대상이 있는지 확인하고 패킷은 제공 trace로 분석한다 | 실제 조회·요청 여부와 제공 분석을 구분. 적합한 대상에 직접 요청하지 못했다면 보충 |
| ARP가 안 보임, 이웃 `STALE`/행 없음 | 캐시·GC·캡처 타이밍과 다른 가능성을 적는다. 캐시 flush·추가 무허가 ping을 하지 않는다 | 관찰된 그대로 기록 |
| ICMP Echo만 보이거나 응답 없음 | 캡처 위치·필터·대상 정책·상대 상태를 확인되지 않은 가설로 적는다 | 응답 성공으로 표시하지 않음 |

가상 NIC의 캡처는 해당 VM에서 보이는 트래픽만 보여준다. 물리 스위치나 다른 VM의 모든 프레임을 본 것으로 설명하지 않는다. 1주차 `lo` HTTP 캡처에서 Ethernet ARP가 없는 것은 정상적인 구분 사례다. [개인 기록지](PERSONAL_RECORD.md)에 직접 실행과 제공 예제 분석을 각각 체크한다.

명령 옵션의 근거: [ip route get](https://man7.org/linux/man-pages/man8/ip-route.8.html), [ip neigh show와 상태](https://man7.org/linux/man-pages/man8/ip-neighbour.8.html), [tcpdump의 인터페이스·필터·개수·링크 헤더 옵션](https://github.com/the-tcpdump-group/tcpdump/blob/master/tcpdump.1.in), [timeout 종료 상태](https://man7.org/linux/man-pages/man1/timeout.1.html).
