# 2주차 코드 읽기 — 주소 계산과 격리 실험

요약: Python 검산기의 입력·판단·출력을 따라 읽고, 셸의 준비·정상 확인·접두사 변경·복구·정리를 설명한다. 주소 계산과 실제 통신을 구분하며, 셸 실행은 진행자가 확인한 격리 Linux에서만 한다.

| 파일 | 읽어서 설명할 것 | 실행 범위 |
| --- | --- | --- |

Python은 아래 네 단계를 읽고 [C1·C2 카드](LINUX.md#3-24와-26을-손으로-계산하고-코드로-검산)를 검산한다. 셸은 먼저 맨 아래의 ‘실험 1·2·3’을 훑은 뒤 위쪽 관찰 함수와 정리 함수를 읽는다. 코드를 읽는 것만으로 직접 실습을 완료했다고 기록하지 않는다.

## Python — 입력에서 출력까지 네 단계

### 1. 주소 두 개를 이름에 연결한다

`main()`에서 `argparse`가 명령 뒤의 A·B 값을 받는다. `IPv4Interface`가 각 `주소/접두사`를 해석하며 잘못된 형식이면 실행을 멈추고 입력 오류를 알려준다.

```python
interface_a = args.a
interface_b = args.b
```

`interface_a.ip`는 A의 주소, `interface_a.network`는 A의 접두사로 계산한 범위다. `a`·`b`는 명령의 첫째·둘째 입력이며 네트워크에서 자동으로 찾은 호스트가 아니다.

### 2. 한 주소의 범위를 출력한다

`print_interface_summary()`는 A와 B에 한 번씩 호출한다. `network = interface.network`로 범위를 꺼내고 네트워크·마스크·범위 끝·호스트 범위를 출력한다.

`/24`·`/26`에서는 첫 주소 다음부터 마지막 주소 직전까지가 일반 호스트 범위다. `network.num_addresses > 2`가 이 분기를 고른다. `/31`·`/32`는 예외이므로 `else`에서 양 끝을 그대로 사용한다. 이 예외는 선택 확장이며 이번 카드의 기본 범위는 `/24`·`/26`이다.

### 3. 두 방향을 따로 판단한다

```python
b_is_in_a_network = interface_b.ip in interface_a.network
a_is_in_b_network = interface_a.ip in interface_b.network
```

첫 줄은 ‘B의 주소가 A의 범위 안인가?’이고 둘째 줄은 반대 방향이다. `in`의 결과는 `True` 또는 `False`다. A가 `.10/26`, B가 `.70/24`이면 첫 줄은 거짓, 둘째 줄은 참이다. A의 범위는 `.0~.63`, B의 범위는 `.0~.255`이기 때문이다.

### 4. 판단을 한국어 답으로 바꾼다

```python
if b_is_in_a_network:
    a_answer = "예"
else:
    a_answer = "아니요"

print(f"A 기준으로 B 포함: {a_answer}")
```

계산·판단과 출력 형식을 분리했다. B 기준도 같은 방식으로 별도 처리한다. `f"...{a_answer}..."`는 중괄호의 값을 문자열에 넣는 문법이다. 파일 마지막의 `if __name__ == "__main__":`는 이 파일을 직접 실행했을 때 `main()`을 시작한다.

‘포함: 예’는 주소 계산 결과다. 상대가 존재하는지, 어떤 경로를 고르는지, 응답하는지는 확인하지 않는다.

## 셸 — 두 노드를 어떻게 준비할까?

두 노드는 새 VM 두 대가 아니라 같은 Linux 안의 독립된 네트워크 공간이다. 네트워크 네임스페이스마다 주소·인터페이스·경로를 따로 볼 수 있다. veth는 이 두 공간을 잇는 가상 케이블의 양 끝으로 생각한다. [ip-netns 매뉴얼](https://man7.org/linux/man-pages/man8/ip-netns.8.html)

코드의 `ns_a`·`ns_b`는 공간 이름, `veth_a`·`veth_b`는 케이블 끝 이름이다. `suffix`는 실행마다 이름이 겹칠 가능성을 줄이려고 붙이는 값이다. 생성이 성공한 직후에만 `created_ns_a` 같은 표식을 `0`에서 `1`로 바꾼다. 정리할 때 이 실행이 무엇을 만들었는지 판단하기 위해서다.

| 코드에서 찾을 명령 | 목적 |
| --- | --- |
| `ip netns add "$ns_a"` | A 공간을 만든다. B도 별도로 만든다. |
| `ip link add "$veth_a" type veth peer name "$veth_b"` | 서로 이어진 가상 인터페이스 한 쌍을 만든다. |
| `ip link set dev "$veth_a" netns "$ns_a"` | A 쪽 인터페이스를 A 공간으로 옮긴다. B도 같은 순서다. |
| `ip -n "$ns_a" link set dev "$veth_a" up` | A 안에서 인터페이스를 켠다. 각 공간의 `lo`도 켠다. |
| `ip -n "$ns_a" address add 192.0.2.10/24 dev "$veth_a"` | A에 문서용 실험 주소를 붙인다. B에는 `.70/24`를 붙인다. |

관리자 권한·`ip`·`ping` 유무는 자원 생성 전에 확인한다. `ns_a`에는 방금 만든 이름을 사용하며 기존 SSH 관리 NIC를 넣지 않는다. 명령을 따로 따라 하기보다 [선택 실험 실행 안내](LINUX.md#5-선택-두-격리-노드에서-접두사-한-조건만-바꾸기)에 따라 전체 스크립트를 실행한다.

## 셸 — 정상·변경·복구를 따라 읽기

| 단계 | 코드에서 바뀌는 것 | 관찰과 예상 |
| --- | --- | --- |
| 실험 1 | A `.10/24`, B `.70/24` | 양쪽 주소·경로, A의 `route get`, A→B ping으로 기준 상태 확인 |
| 실험 2 | A의 `/24` 주소를 지우고 같은 주소를 `/26`으로 추가. B는 유지 | 기본·별도 경로를 추가하지 않았으므로 A의 `.70` 경로 조회와 ping 실패 예상 |
| 실험 3 | A를 다시 `.10/24`로 변경 | 경로 조회·응답이 기준 상태로 돌아오는지 확인 |
| 종료 | 이번 실행에서 만든 자원 삭제 | 실험 결과 복구와 별도로 남은 실습 자원을 정리 |

`show_state()`는 양쪽 주소·경로를 보여 준다. `ip -n "$ns_a" -4 route get 192.0.2.70`은 경로 조회이며 패킷 도달 증거가 아니다. `ip netns exec "$ns_a" ping -n -c 1 -W 2 192.0.2.70`은 A 공간에서 실제 ICMP 요청을 보낸다. `-n`은 숫자 주소 표시, `-c 1`은 한 번 요청, `-W 2`는 응답 대기 2초다. 출력의 송수신 수·종료 상태를 실제 값으로 확인한다.

실험 1·3에서 실패하면 스크립트는 중단하고 종료 정리로 간다. 실험 2의 경로·ping 실패는 비교하려던 조건이므로 `if/else`에서 기록하고 다음 복구 단계로 간다. 예상과 달리 응답하면 그 사실도 출력한다. 예상 문구를 실제 관찰로 옮겨 적지 않는다.

## 셸 — 낯선 문법을 이 코드에서 읽기

| 문법 | 이 코드에서의 뜻 |
| --- | --- |
| `run_show() { ...; }` | 함수 정의다. 정의할 때는 실행하지 않고 이름을 호출할 때 실행한다. |
| `"$ns_a"` | 변수 값을 하나의 인자로 전달한다. 따옴표를 임의로 없애지 않는다. |
| `"$@"` | 함수가 받은 인자들을 나뉜 상태 그대로 다음 명령에 전달한다. |
| `printf ' %q' "$@"` | 실제 실행 전 인자 경계를 읽을 수 있게 명령을 표시한다. |
| `if 명령; then ... else ... fi` | 명령 종료 코드가 0이면 앞쪽, 0이 아니면 뒤쪽을 실행한다. |
| `$?` | 바로 직전 명령의 종료 코드다. 다른 명령을 실행하기 전에 저장한다. |
| `local status` / `return "$status"` | 함수 안에서 상태를 보관하고 호출한 곳으로 돌려준다. 전체 종료는 `exit`다. |
| `>/dev/null 2>&1` | 확인용 명령의 일반 출력과 오류 출력을 숨긴다. 성공·실패 상태는 남는다. |
| `>&2` | 정리 실패 같은 메시지를 오류 출력으로 보낸다. |

`run_show()`는 먼저 명령을 표시하고 마지막 줄의 `"$@"`로 실행한다. 따라서 호출한 쪽은 실제 명령의 종료 상태를 받는다. `ping_and_report()`는 실패 직후 `$?`를 저장한 뒤 메시지를 출력하고 `return`한다. 먼저 `echo`를 실행하면 ping이 아닌 echo의 종료 상태를 읽게 된다.

## 셸 — 오류가 나도 정리 경로를 유지하기

`set -euo pipefail`에서 `-u`는 없는 변수 사용을 오류로 처리하고, `pipefail`은 파이프 중간 실패를 상태에 반영한다. 이 실험에는 파이프가 없지만 이후 명령을 추가할 때도 이 설정을 유지한다. `-e`에는 예외가 있어 ‘모든 실패에서 즉시 종료’라고 읽으면 안 된다. 이 스크립트의 실험 2처럼 `if`가 결과를 검사하는 명령은 실패를 직접 처리한다. [GNU Bash — set](https://www.gnu.org/s/bash/manual/html_node/The-Set-Builtin.html)

`trap cleanup EXIT`는 종료할 때 `cleanup()`을 호출하라는 약속이다. Ctrl+C의 `INT`는 130, `TERM`은 143으로 종료하도록 연결했다. 정리 함수는 다음 순서로 읽는다.

1. 원래 종료 상태를 `original_status`에 보관한다. `trap - EXIT`로 정리 중 종료가 다시 정리를 부르지 않게 한다.
2. 이번 실행의 veth 생성 표식과 기본 공간에 남아 있는지 확인한다. 이동 전에 실패했다면 그 veth부터 지운다.
3. 생성에 성공한 A·B 공간만 삭제한다. 모든 이름을 한꺼번에 지우지 않는다.
4. 삭제가 실패하면 정확한 자원 이름을 출력한다. 실험이 성공했어도 정리가 실패했다면 실패로 종료하며, 원래 실험이 실패했다면 그 상태를 보존한다.

이 정리 함수는 종료 절차를 밟을 때 실행된다. `SIGKILL`·시스템 중단처럼 trap이 실행될 수 없는 경우나 삭제 오류에서는 자원이 남을 수 있다. 다른 프로세스가 공간을 계속 사용해도 삭제가 바로 끝나지 않을 수 있다. 첫 출력의 이번 실행 이름과 `ip netns list`를 진행자와 대조한다. 이름을 확인하지 않은 일괄 삭제를 하지 않는다. [GNU Bash — trap](https://www.gnu.org/software/bash/manual/html_node/Bourne-Shell-Builtins.html) · [ip-netns의 삭제 조건](https://man7.org/linux/man-pages/man8/ip-netns.8.html)

## 읽은 뒤 서로 설명할 질문

1. C2에서 두 방향의 `in` 결과가 다른 이유를 주소 범위로 설명한다. 그 결과로 ping 성공까지 말할 수 있을까?
2. 실험 2는 어느 주소만 바꾸는가? `route get`과 `ping`은 각각 무엇을 확인하는가?
3. 실험 2의 예상 실패 뒤에도 복구가 실행되는 이유와 실험 1 실패 시 흐름을 비교한다.
4. B 공간 생성에 실패했다면 정리 대상은 무엇인가? 생성 여부를 기록하지 않았다면 무엇을 잘못 지울 수 있는가?
5. 접두사 복구와 자원 정리는 어떻게 다른가? 삭제 오류는 어디에 남는가?
