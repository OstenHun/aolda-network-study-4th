# 16주 상세 커리큘럼 — 개념을 함께 배우고 통신으로 확인하기

요약: 네트워크 초보자를 위한 Linux 기반 16주 범위 초안이다. 공통 운영안의 설명·질문·근거 확인과 개인 실습을 각 주제에 연결하며 진도에 따라 분량을 조정한다. 주차별 제작·실제 수행 상태는 별도로 확인한다.

## 대상과 학습 범위

네트워크를 처음 배우거나 기초를 다시 익히는 학습자를 위한 16주 학습 순서다. 주차는 학습 순서를 나타내며 실제 달력 일정은 학습 속도에 맞춰 정한다. 아래 실습은 학습 계획이며 수행 결과가 아니다.

공통 실습은 허용된 Linux 환경을 사용한다. 접속·도구·권한이 준비되지 않았다면 제공 자료 분석과 본인 직접 실행을 구분한다. 현재 읽을 수 있는 자료는 [학습 홈](index.html), 공식 출처는 [자료 안내](materials/REFERENCE_GUIDE.md)에서 찾는다.

## 매주 개념과 실습을 묶는 방법

매주 필요한 개념 3~5개를 함께 공부하고, 앞 주차의 질문·개념·실습 근거를 이번 주의 판단에 연결한다. 긴 강의 한 번이나 이전 자료의 존재만으로 개념을 익혔다고 간주하지 않는다.

중심 질문을 함께 찾고 한 사람이 근거를 들어 설명한 뒤 조건 변경과 실습으로 확인한다. 아래 표의 ‘예측·실행·관찰’은 실험에서 할 일을 뜻한다.

①②③은 주제별 학습 묶음이다. 실제 모임 수를 뜻하지 않는다. 필수 실험을 먼저 고르고 선택·보충 활동은 학습 속도에 맞춰 배치한다.

각 주차의 아래 완료 증거는 공동 설명·조건 변경·실습 확인에 연결한다. 본인 실행·분석·독립 설명을 확인하되 같은 원출력을 여러 문서에 옮기지 않는다. 제공 캡처 분석·직접 캡처·모형을 구분하고, 도구 접근이 막힌 것과 개념 설명이 막힌 것은 따로 남긴다. AI 설명·예시 출력·짝의 수행을 본인 실제 관찰로 기록하지 않는다.

### Linux를 쓰는 범위

처음에는 Linux 한 대 안에서 client/server를 함께 실행한다. 아올다 VM에서 시작하더라도 1주차는 VM 내부의 127.0.0.1 통신이며 개인 PC→VM의 외부 요청과 다르다. SSH는 실습 환경에 들어가는 준비 절차로 먼저 안내하고, 암호화·인증 원리는 6주차에 다시 배운다. VM 생성·할당 작업은 진행자가 준비하고 네트워크 개념을 배우기 전 개인별 생성 과제로 두지 않는다.

공통 기본 도구는 Linux 셸·python3·curl·ip·ss와 캡처 도구 tcpdump 또는 tshark다. 기존 Node/TypeScript 클라이언트는 상세 출력 비교용 선택 경로로 유지한다. GUI가 없는 VM에서는 패킷 파일을 만든 뒤 허용된 방법으로 개인 PC의 Wireshark에서 분석한다. 설치 패키지·배포판·캡처 권한은 환경 확인 후 주차 실행 안내에 정한다.

아올다 VM의 인터넷 접근·관리자 권한·다중 노드·파일 보존과 접속 방식은 실제 계정에서 확인한다. 특히 ARP·DHCP·VLAN·경로 변경은 원하는 관찰이 가능한 격리 환경이나 시뮬레이터를 사용한다. 문서 정본은 현재 프로젝트 폴더에 유지하며, 실습을 Linux로 바꾸기 위해 프로젝트를 임의로 이사하지 않는다.

### 1주차 — 요청 하나를 끝까지 따라가기

**핵심 질문:** 같은 주소에서 200·404·연결 실패는 왜 다를까? 선수 지식은 터미널 열기·폴더 이동·실행·중지부터 함께 익힌다.

| 회차 | 함께 배울 개념 | 관찰·실습 |
| --- | --- | --- |
| ① | 네트워크, client/server, 프로세스, IP·port, 루프백 | 기존 키트로 요청·응답을 만들고 메시지 변경, 양쪽 주소·포트 그리기 |
| ② | 프로토콜·계층의 역할, HTTP 응답과 TCP 통신의 구분 | 정상과 404의 출력·로그·패킷을 대조하고 왕복 흐름 설명 |
| ③ | 응용 오류와 통신 실패, 근거로 원인을 좁히는 방법 | 서버 중지·재시작, 짝이 바꾼 메시지·경로·포트 중 하나를 재현 |

- **완료 증거:** 양쪽 출력, 패킷 번호 또는 예제 분석 표시, 실제 값이 든 통신 그림. 404는 응답이고 서버 중지 시 실패는 다른 현상임을 설명한다.
- **환경·대안:** 아올다 Linux 한 대 + 기존 Python 서버 + curl 기본, 기존 Node/TypeScript 클라이언트 선택. 접속이 막히면 진행자가 확인한 출력·캡처를 함께 분석하고 개인 실행은 미완료로 남긴다. 캡처 권한이 없으면 자체 예제 캡처 분석으로 표시한다. 직접 실행할 때는 같은 Linux 호스트의 터미널 두 개를 사용한다.
- **선택·후속:** OSI 계층 이름 암기, VM 생성, TCP 상태 상세, 서브넷 계산은 첫 주 완료 조건에서 제외한다.
- **자료:** [1주차 개념 교재](materials/week-01/concepts.html), [실행 키트](labs/week-01/README.md), P01의 시작/HTTP 관찰 부분.

### 2주차 — IPv4 주소와 서브넷으로 상대를 구분하기

**핵심 질문:** 내 PC는 목적지가 같은 망에 있는지 어떻게 판단할까? 1주차의 IP와 포트 구분을 먼저 확인한다.

| 회차 | 함께 배울 개념 | 관찰·실습 |
| --- | --- | --- |
| ① | 인터페이스, IPv4, 루프백·사설·공인 주소, 기본 게이트웨이 | Linux의 ip addr·ip route로 주소·접두사·게이트웨이를 조회하고 VM·가상 라우터·외부 목적지를 그리기 |
| ② | 비트, 서브넷 마스크, CIDR, 네트워크 주소 | /24·/26의 작은 예제로 같은 서브넷 여부와 범위를 예측·검산 |
| ③ | 주소 범위와 실제 도달성의 차이 | 준비된 두 노드의 마스크 한 조건을 바꾸어 예상과 도달 결과 비교 |

- **완료 증거:** 자기 인터페이스 정보, 서브넷 예제 2개 풀이, 다른 망에는 게이트웨이가 필요한 이유. 같은 서브넷 계산만으로 통신 성공을 보장하지 않는다고 설명한다.
- **환경·대안:** Linux 조회 + 준비된 격리 구성/시뮬레이터. 도구 준비가 안 되면 실제 조회와 주소 카드 문제를 하고 구성 변경 실습은 미완료로 남긴다. SSH 접속에 사용하는 VM 인터페이스의 주소·마스크를 바꾸지 않는다.
- **선택·후속:** VLSM·주소 집계·많은 계산 문제, 준비된 VM→VM 비교. 공인 주소와 외부에서의 접근 가능성을 동일시하지 않는다.
- **자료:** R01의 IP Addressing 범위, [2주차 학습 홈](materials/week-02/index.html), [Linux 안내](labs/week-02/LINUX.md), [공개 시험·CCNA 연계](materials/week-02/CCNA_PRACTICE.md).

### 3주차 — 같은 망에서 다음 전달 상대 찾기

**핵심 질문:** 목적지 IP를 아는데 왜 MAC 주소와 ARP가 필요할까? 같은/다른 서브넷과 기본 게이트웨이 개념을 사용한다.

| 회차 | 함께 배울 개념 | 관찰·실습 |
| --- | --- | --- |
| ① | LAN/WAN, 케이블·무선 링크, 스위치·라우터·AP, Ethernet 프레임 | Linux VM의 가상 NIC와 개인 PC의 접속 경로를 그리고 IP 목적지와 링크의 다음 상대 구분 |
| ② | MAC, ARP 요청·응답, 이웃 캐시 | 허가된 LAN 상대·게이트웨이에 ping을 보내고 이웃 정보·ARP 관찰 조건 비교 |
| ③ | ICMP Echo, 도달성 관찰의 한계 | ICMP 결과와 1주차 HTTP 결과를 비교하고 ping 실패의 가설을 나누기 |

- **완료 증거:** 목적지 IP와 다음 홉 MAC을 표시한 그림, 이웃 정보와 ICMP/ARP 관찰 또는 제공 trace 분석. ARP 캐시가 있으면 새 요청이 안 보일 수 있고 ping 실패만으로 서버 중지를 단정할 수 없다고 설명한다.
- **환경·대안:** Linux의 ip neigh·ping·가상 NIC 캡처 또는 제공된 Ethernet/ARP·ICMP trace. 1주차 루프백에서 Ethernet ARP가 보일 것이라고 요구하지 않는다. VM에서 호스트 물리망의 모든 전달을 볼 수 있다고 가정하지 않는다.
- **선택·후속:** 캐시 초기화 실험은 격리 환경에서 준비한다. IPv6 이웃 탐색은 8주차에 비교한다.
- **자료:** R01의 Switching·Core Protocols 범위, P01의 Ethernet/ARP·ICMP. 조회·캡처 절차는 주차 준비 때 검증한다.

### 4주차 — TCP와 UDP는 무엇을 맡는가

**핵심 질문:** 데이터가 프로그램에 도착한다는 것은 어떤 의미일까? 1주차 HTTP 패킷과 IP·port를 다시 사용한다.

| 회차 | 함께 배울 개념 | 관찰·실습 |
| --- | --- | --- |
| ① | 소켓, 서버의 대기, 임시 포트, TCP 연결·종료 | 1주차 키트의 대기·연결 상태와 핸드셰이크를 출력·패킷에서 찾기 |
| ② | TCP 바이트 스트림·순서·ACK, UDP 데이터그램 | 제공된 작은 TCP/UDP 송수신 예제를 실행하고 메시지 경계·연결 유무 비교 |
| ③ | 재전송·손실과 애플리케이션의 처리 | 제공된 재전송 trace 또는 격리된 손실 데모 분석, 짝이 바꾼 포트 조건 재현 |

- **완료 증거:** TCP 흐름과 UDP 흐름 비교표, 소켓 상태·출력·패킷 대응. TCP의 전달 기능과 애플리케이션의 처리 성공을 구별하고, 정상 UDP 실행에서 손실을 반드시 볼 수 있다고 가정하지 않는다.
- **환경·대안:** Linux의 제공 소켓 코드 또는 검증한 nc 예제 + ss + 캡처 분석. nc 구현마다 옵션을 확인하며 새 언어 구현 과제는 요구하지 않는다. 재전송을 못 만들면 예제 분석으로 표시한다.
- **선택·후속:** 혼잡 제어·윈도 크기 계산·Linux netem 설정. 4주차 말에 1~4주 핵심 설명과 독립 재현을 점검한다.
- **자료:** R01의 Core Protocols 범위, P01의 TCP/UDP. 제공 소켓 코드와 nc 절차는 주차 준비 때 검증한다.

### 5주차 — 이름을 찾고 주소 설정을 받기

**핵심 질문:** URL의 이름과 내 PC의 주소 설정은 각각 어디서 올까? IPv4·UDP·client/server를 연결한다.

| 회차 | 함께 배울 개념 | 관찰·실습 |
| --- | --- | --- |
| ① | DNS 이름·레코드·재귀 질의·캐시 | Linux의 dig/nslookup으로 지정한 실습용 이름을 질의하고 서버·A/AAAA 응답 읽기 |
| ② | DNS 결과와 서비스 접속의 차이 | 같은 서버의 이름·IP 지정 결과와 출력 비교, 준비된 이름 오류 사례 진단 |
| ③ | DHCP 임대, 주소·마스크·게이트웨이·DNS 옵션 | Linux VM의 주소 설정 출처 확인, 제공 DHCP trace/시뮬레이션으로 메시지 순서 설명 |

- **완료 증거:** DNS 질의·응답과 실제 요청 결과, Linux 주소 설정 정보, DHCP 순서 그림. 이름 해석 성공·통신 성공·서버 응답을 별도 증거로 설명한다.
- **환경·대안:** Linux 조회·질의 + 제공된 DHCP 캡처. 관리자 권한·외부 질의가 막히면 제공 캡처를 분석한다. 아올다 게스트의 설정 방식은 실제 출력·설정으로 확인한다.
- **선택·후속:** MX/PTR·권한 서버·TTL 비교·DHCP 서버 설정. 접속 중인 VM의 임대를 강제로 해제하거나 공유망에 DHCP 서버를 띄우지 않는다.
- **자료:** R01의 DNS·Core Protocols 범위, P01의 DNS/DHCP. 질의 대상과 명령은 주차 준비 때 검증한다.

### 6주차 — HTTP를 다시 보고 암호화·인증 이해하기

**핵심 질문:** HTTPS에서 관찰할 수 있는 것과 암호화되는 것은 무엇일까? TCP·DNS와 1주차 요청을 다시 연결한다.

| 회차 | 함께 배울 개념 | 관찰·실습 |
| --- | --- | --- |
| ① | HTTP 메서드·경로·헤더·상태·본문 | 첫 주 요청을 항목별로 읽고 200/404와 준비된 응용 오류를 비교 |
| ② | TLS 암호화·서버 인증·인증서, HTTPS | 통제된 HTTP/HTTPS 요청의 패킷과 클라이언트 관찰을 비교하고 읽을 수 있는 필드 표시 |
| ③ | SSH의 원격 셸, 호스트 확인·사용자 인증, 안전한 원격 접속 | 허가된 테스트 서버가 준비되면 SSH·HTTP 접속 비교. 미준비면 제공 접속 기록과 TLS trace로 설명 |

- **완료 증거:** HTTP 메시지 표시와 HTTPS 관찰 범위, 서버 신원 확인과 사용자 인증의 구분. SSH와 TLS가 서로 다른 프로토콜임을 설명한다. 원격 직접 접속 여부는 별도 표시한다.
- **환경·대안:** Linux의 curl/openssl/ssh 중 검증한 도구 + 허가된 테스트 대상 또는 제공 trace. 브라우저의 HTTP/3·QUIC 결과를 TCP 실험과 섞지 않고 이번 실습 프로토콜을 기록한다. 인증서 검증을 꺼 성공시키는 것을 완료 기준으로 삼지 않는다.
- **선택·후속:** 캐시·쿠키·HTTP/2·HTTP/3·WebSocket, SSH 키 생성·전송. 인증 정보는 기록하지 않는다.
- **자료:** P01의 HTTP/TLS, R02의 필요한 SSH 설명, R01의 Application Protocols.

- **선택·후속:** 메트릭 상세·정책 라우팅·복잡한 다중 경로. SSH 관리 경로나 아올다 공용 라우터를 실습용으로 변경하지 않는다.
- **자료:** R01의 Routing 범위, P02의 시뮬레이터 입문. ip route 조회·경로 변경 절차는 주차 준비 때 검증한다.

| 회차 | 함께 배울 개념 | 관찰·실습 |
| --- | --- | --- |
| ① | 지연·대역폭·처리량·손실, 기준선·반복 측정 | 같은 요청을 여러 번 실행하고 클라이언트 전체 시간·서버 처리·패킷 시각 비교 |
| ② | 애플리케이션 지연과 전달 지연, 관측 위치 | 서버 응답 지연 한 조건을 추가해 정상과 비교. 망 지연은 준비된 격리 데모/trace에서 분석 |
| ③ | 프록시·로드밸런서, round robin·상태 확인·failover | 준비된 프록시와 서버 2프로세스의 응답 식별자를 관찰하고 한 서버 중지 결과 비교 |

- **완료 증거:** 측정 조건·횟수·단위, 양쪽 로그와 시각, 분산/실패 결과. 총 경과 시간을 순수 망 지연으로 단정하거나 로드밸런서가 모든 장애를 자동 복구한다고 설명하지 않는다.
- **환경·대안:** Linux의 준비된 서비스·프록시 구성. 서버 두 프로세스는 한 Linux 호스트에서 서로 다른 포트로 실행할 수 있다. 새 프레임워크 구현은 필수가 아니다. 미준비면 제공 자료로 분석 범위를 표시한다.
- **선택·후속:** QoS·shaping·prioritization, SNMP·NetFlow·Prometheus/Grafana, 게이트웨이 HA·HSRP/VRRP, MTU 심화. 필수는 기준선·단일 원인 비교·관측 근거다.
- **자료:** P08, R01의 Traffic Management·Load Balancing·High Availability·Observability.

<a id="week-15"></a>
### 15주차 — 검증한 절차 하나를 자동으로 반복하기

**핵심 질문:** 사람이 하던 확인을 자동화해도 같은 결론을 낼 수 있을까? 먼저 정상·실패 확인 절차가 있어야 한다.

| 회차 | 함께 배울 개념 | 관찰·실습 |
| --- | --- | --- |
| ① | 입력·출력·시간 제한·오류 구분·재현성 | 200/404/연결 실패의 수동 확인 절차와 기대 증거를 먼저 정리 |
| ② | 스크립트·API·설정과 검증의 차이 | 제공 Python 또는 기존 TypeScript 예제를 조금 바꿔 상태·시간·오류를 파일로 수집 |
| ③ | 반복 실행·수동 대조·변경 범위 | 정상→한 장애→복구를 같은 입력으로 반복하고 수동 관찰과 비교 |

- **완료 증거:** 입력·코드·실제 결과, 수동과 자동 비교, 시간 제한과 오류 분류. 404를 연결 실패로 합치지 않고 인증 정보를 결과에 쓰지 않는다.
- **환경·대안:** 기존 Linux·테스트 서비스. 새 언어 학습 부담이 크면 제공 코드의 입력·조건만 변경하고 각자 실행·설명한다.
- **선택·후속:** Ansible로 설정 재현 또는 Terraform의 계획 검토 중 한 경로. 자원 변경·삭제나 두 도구 동시 습득을 필수로 요구하지 않는다. NETCONF/YANG·대규모 장비 자동화는 후속 심화다.
- **자료:** P09 또는 기존 TypeScript 키트, R01의 Shell/Scripting·APIs·Automation. 도구 심화 자료는 선택 경로가 정해진 뒤 검증한다.

### 16주차 — 처음 보는 작은 장애를 진단하고 설명하기

**핵심 질문:** 정답을 모르는 상황에서 어떤 증거를 먼저 확인할까? 배운 개념을 다시 연결한다.

| 회차 | 함께 배울 개념 | 관찰·실습 |
| --- | --- | --- |
| ① | 증상·가설·관찰·변경·복구의 순서 | 정상 기준선을 확인하고 진행자가 준비한 단일 장애의 가설·확인 순서 작성 |
| ② | 계층별 증거와 가장 작은 변경 | 이름·바인딩/포트·서버 중지·경로·정책 중 한 원인을 찾아 허가된 환경에서 복구 |
| ③ | 독립 재현·근거 전달·남은 불확실성 | 짝과 사례를 바꿔 재현하고 개인 설명·팀 구성도·다음 학습 목록 정리 |

- **완료 증거:** 예상·실제 출력/로그/패킷·배제한 가설·수정·복구·재현, 처음과 마지막 통신 그림 비교. 환경 접근 제한과 관찰하지 못한 부분도 기록한다.
- **환경·대안:** Linux 한 대의 기본 사례부터. VM 간 통신·VLAN·라우팅은 해당 실습을 실제 수행한 팀의 확장 사례로 사용한다. 제공 자료로 진단한 경우 직접 복구 완료라고 쓰지 않는다.
- **선택·후속:** 두 원인이 겹친 문제, VM·프록시를 포함한 작은 서비스 구성. 졸업 조건은 완성 앱이나 자격증 합격이 아닌 기본 통신의 설명·진단·재현이다.
- **자료:** 지금까지의 개인 기록·실행 키트·구성도. 마지막 학습 범위 점검에 R01을 다시 사용한다.

## 진행 속도와 준비 기준

### 진도 조정

4·8·12주차 종료 때 각자 핵심 질문 설명, 근거 찾기, 조건 하나 변경 재현을 확인한다. 한 명이라도 선수 개념이 막히면 다음 주 첫 20분에 그 개념을 다시 실험하고 선택 과제를 줄인다. 설치·접속 문제가 원인이면 대체 관찰을 제공하고 환경 미완료를 따로 관리한다.

두 회차 이상 같은 선수 개념이 막히면 다음 주의 선택 심화를 복습으로 바꾸고 필수 실험을 하나로 줄인다. 그래도 해결되지 않으면 주차를 늘리거나 뒤의 필수 범위를 줄이는 안을 팀과 정하고 학습 계획에 반영한다. 16주라는 숫자를 맞추기 위해 기본 설명을 건너뛰지 않는다. 8주차 복습과 16주차 종합 시간은 우선 확보한다.

### 실습 전 준비

실습마다 허용된 대상·도구·권한·기준선·중단 조건·복구 경로를 확인한다. 시뮬레이터와 클라우드 실습은 준비된 환경이나 대체 관찰 자료를 사용한다. 직접 실행과 제공 자료 분석은 구분한다.
