# 15주차 교재 · 수신 완료와 처리 성공을 구별하기

요약: TCP 바이트 스트림 위의 메시지 경계를 프로그램이 정하는 이유를 설명한다. EOF·시간제한의 다른 의미와 수동/자동 HTTP 판정의 조건을 읽고, 처리 여부를 모를 때 재시도 횟수와 멱등성을 함께 판단한다.

[개인 공부 정리](README.md#personal-notes)에서는 이 교재의 핵심·혼동 구별을 주요 질문과 내 답에 연결한다. 먼저 설명하고 해설과 비교한 뒤, 확인한 근거와 고친 이해를 기존 개인 노트에 보완한다.

## 먼저 연결할 개념

[4주차 TCP](../week-04/CONCEPTS.md)의 순서 있는 바이트 스트림은 앱의 메시지 구획을 보존하지 않는다. [6주차 HTTP](../week-06/CONCEPTS.md)는 헤더·본문 길이 등으로 경계를 정했다. 이번 LF 예제는 HTTP가 아닌 별도 학습 프로토콜이다. [실습과 코드 지도](LINUX.md#code-reading)를 함께 편다.

## W15-K1 · recv 한 번은 메시지 하나가 아니다

**기억 문장: TCP는 바이트를 전달하고, 프로그램은 약속한 규칙으로 메시지의 끝을 찾는다.** `recv(n)`은 최대 n바이트를 읽는 호출이다. n바이트를 채우거나 메시지 끝까지 기다린다는 보장은 없다. `sendall`도 앱의 메시지 처리 완료를 보장하지 않는다.

이 예제의 약속은 **UTF-8 본문 최대 256바이트 + LF(`0a`)**, 한 연결에 한 메시지다. 본문에는 LF/CR을 넣지 않는다. 서버는 `recv(3)`의 조각을 `bytearray`에 누적하고 LF를 찾은 뒤 본문 전체를 디코딩한다. 한글 한 글자의 UTF-8 바이트가 조각 사이에 나뉠 수 있어서 조각마다 디코딩하지 않는다.

```text
보낸 바이트:  h e l l o LF
읽기 예시 A: [h e l] [l o LF]  → 누적 뒤 LF 발견
읽기 예시 B: [h] [e l] [l] [o LF] → 같은 메시지
```

위 분할은 설명용이다. 실제 호출별 길이는 서버의 `recv` 로그에서 읽는다. 서버가 최대 3바이트씩 읽게 했으므로 6바이트 입력은 적어도 두 번 읽지만, 이것으로 TCP 세그먼트가 둘이라고 판단할 수 없다. 짧은 입력은 여러 메시지가 한 호출에 들어올 수도 있다. 지속 연결이라면 첫 경계 뒤의 남은 바이트를 다음 메시지용으로 보관해야 한다. 이번 서버는 한 메시지 응답 뒤 연결을 닫으므로 연속 메시지 전송을 지원하지 않는다.

길이가 정해진 메시지·길이 접두사·구분자·연결 종료도 각각 경계 규칙이 될 수 있다. 규칙마다 누적/남은 바이트 처리가 필요하다. LF는 이번의 선택이며 모든 프로토콜의 규칙이 아니다. 근거: [Python Using a Socket](https://docs.python.org/3.14/howto/sockets.html#using-a-socket).

## W15-K2 · EOF와 timeout은 서로 다른 관찰이다

**기억 문장: EOF는 상대가 보내기를 끝냈다는 관찰이고, timeout은 정한 시간 안에 기다리던 일이 끝나지 않았다는 관찰이다.** 양수 크기의 `recv`에서 `b''`를 받으면 수신 방향의 EOF다. 상대가 `shutdown(SHUT_WR)`로 보내기만 끝냈다면 이쪽은 응답을 보낼 수 있다.

| 입력 조건 | 서버가 볼 수 있는 것 | 이번 프로토콜의 판단 |
| --- | --- | --- |
| `line` | `hello` 뒤 LF | `frame_ok` · 메시지 완료 |
| `eof` | LF 없이 `hello`, 그 뒤 `b''` | `eof_incomplete` · 경계 전 종료 |
| `hold` | LF 없이 `hello`, 보내기도 끝내지 않음 | 수신 시작 약 2초 뒤 `timeout` |

EOF 자체가 항상 오류는 아니다. EOF를 메시지 경계로 정한 다른 프로토콜에서는 완료일 수 있다. 이번 LF 규칙에서는 LF 전 EOF가 미완료다. 빈 본문에 LF만 보내면 정상적인 빈 메시지다. 아무것도 보내지 않은 채 닫는 것과 구별한다.

서버의 `read_line`은 `monotonic()`으로 수신 마감 시각을 정하고 매번 남은 시간을 `settimeout`에 넣는다. 조금씩 보내며 호출마다 시간을 새로 얻는 문제를 피한다. 약 2초는 수신 단계 제한이며 OS 스케줄링 오차·수신 후 응답 대기·쓰기 시간은 별도다. 클라이언트의 연결/송신 제한과 응답 수신 마감도 각각 구별한다. 모든 실행의 총 시간이 정확히 인자 값 이하라는 뜻은 아니다.

응답을 기다리던 클라이언트가 timeout으로 닫아도 서버는 이미 요청을 받았거나 처리 중일 수 있다. 서버의 `received`는 경계 판정 결과, `reply_written`은 로컬 쓰기 성공이며 클라이언트 수신 증명이 아니다. 클라이언트 출력과 같은 메시지의 서버 로그를 함께 본다. 근거: [recv](https://docs.python.org/3.14/library/socket.html#socket.socket.recv), [settimeout](https://docs.python.org/3.14/library/socket.html#socket.socket.settimeout), [shutdown](https://docs.python.org/3.14/library/socket.html#socket.socket.shutdown).

## W15-K3 · 자동화는 먼저 정한 관찰과 판정을 반복한다

**기억 문장: 자동 기록의 성공 조건을 수동 절차와 같게 정하고, 횟수·대기·오류를 제한한다.** 1주 Handler의 `/echo?message=w15`는 200과 같은 message의 JSON, 없는 경로는 404와 오류 JSON을 돌려준다. 서버를 중지하면 HTTP 응답을 못 받을 수 있다. 404와 연결 실패는 같은 사건이 아니다.

`check_http.py`는 루프백의 지정 포트로 같은 GET을 최대 5번, 기본 3번 수행한다. 각 시도는 새 연결이고 다음 시도 전 0.2초 쉰다. 재시도는 없으며 `attempt`는 예정된 점검 번호다. `status`·`outcome`·본문·오류 종류·`elapsed_ms`를 JSON Lines, 즉 한 줄에 JSON 하나로 기록한다. 상태를 읽은 뒤 본문이 끊기거나 timeout이 나면 `status`가 있어도 `http_success`로 세지 않는다. 본문 상한은 64KiB다.

| 관찰 | 자동 판정 | 수동 대조 |
| --- | --- | --- |
| 완전한 2xx 응답 | `http_success` | 상태뿐 아니라 예상 message·서버 로그 확인 |
| 완전한 404 응답 | `http_error`, `status=404` | `curl`에 404 상태/본문. `--fail` 없이 종료 코드 0일 수 있음 |
| 응답 전 연결 거절 등 | `communication_error`, 보통 `status=null` | curl의 비0 종료 코드·상태000, 리스너/로그 조회 |
| 응답 대기 초과 | `timeout` | 어느 단계까지 관찰했는지와 서버 로그 대조 |

`http_success`는 전송·상태에 대한 이 코드의 분류다. 다른 서비스를 점검할 때는 업무 내용 검증이 더 필요하다. 경과 시간은 연결 시도 직전부터 응답 본문 읽기/오류와 정리까지이며 DNS/TLS를 쓰지 않는 루프백 HTTP다. 14주차의 전체 요청 시간과 대응하되 수동/자동은 별도 요청이므로 시간이 완전히 같을 필요는 없다. `HTTPConnection`의 timeout은 개별 블로킹 작업의 제한이지 실행 전체 마감이 아니다. 이 작은 서버의 짧은 응답에 쓰며 악의적인 지속 전송/대규모 수집기로 확대하지 않는다.

### timeout 뒤에 다시 보내도 될까

가공 사례: 수량을 1 늘리는 요청을 서버가 처리했는데 응답만 늦었다. 클라이언트가 timeout만 보고 다시 보내면 2 늘어날 수 있다. **멱등성**은 같은 요청을 여러 번 적용해도 의도한 서버 효과가 한 번과 같다는 성질이다. 응답 시간·로그 줄까지 같다는 뜻은 아니다. ‘수량을 7로 설정’과 ‘수량을 1 증가’의 차이를 생각한다.

멱등적인 조회 GET은 반복할 수 있어도 무제한 재시도가 안전한 것은 아니다. 횟수 정책의 산술 예로 **최초 1회 + 추가 최대 2회 = 총 최대 3회**를 들 수 있다. 이는 RFC의 권장 횟수가 아니며, RFC 9110 §9.2.2는 실패한 자동 재시도를 다시 자동 재시도하지 말 것을 권고한다. 실제 정책에는 시도 사이 대기·중단 기한과 해당 서비스의 계약이 필요하다. 변경 요청은 멱등성 보장이나 원래 요청이 적용되지 않았음을 확인할 근거 없이는 자동 재시도하지 않는다. 중복 방지 키도 서버의 저장·동시 처리·유효 기간 계약이 있어야 한다. 이번 코드는 이를 구현하지 않는다. 근거: [RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2).

## 재시도 횟수와 전체 시간 예산을 함께 보기

4주에서 TCP ACK와 앱 처리를 나눴고 이번에는 응답 timeout만으로 미처리를 확정할 수 없음을 배웠다. 14주의 느린 요청에서 기다림을 짧게만 줄인 뒤 재시도를 늘리면 시도 수가 오히려 커질 수 있다.

아래는 **실제 실행하지 않는 가공 상한 계산**이다. 클라이언트→서비스A→서비스B→저장 서비스에서 앞 세 호출 계층이 각각 최초 포함 최대3회를 독립적으로 시도한다. 매 시도는 다음 계층의 호출을 만들고 계속 재시도 가능한 실패가 돌아오며 공유 deadline·재시도 예산·중복 제거가 없다고 가정한다.

```text
최하위 호출 수 상한 = 3 × 3 × 3 = 27회
한 계층에서만 최대3회로 제한하고 나머지는1회라면 = 3회
```

27은 이 조건의 상한이지 모든 요청의 실제 시도 수가 아니다. 성공·재시도 불가 오류·마감 도달로 더 일찍 멈출 수 있다. 어느 계층이 재시도를 소유하는지 정하고 나머지 호출의 재시도와 곱해지는지 확인한다. backoff는 다음 시도 전 기다리는 간격, jitter는 그 대기를 흩어 동시 재시도를 줄이는 방식이다. 기다리는 동안도 전체 시간 예산은 소모된다. [AWS의 Retries·Jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)와 연결한 자체 예다.

전체 deadline은 한 요청의 시작부터 끝까지 쓸 수 있는 마감이다. 시도별 최대0.4초·시도 사이 대기0.2초·최초 포함 최대3회라면 단순 합의 상한은 `3×0.4+2×0.2=1.6초`다. 요청 전체 예산이1초라면 이 설정만으로 전체 마감을 보장할 수 없다. 남은 예산을 전달해 각 시도/대기를 제한하고 부족하면 시도 상한에 도달하기 전에도 멈춰야 한다. DNS·연결·TLS·수신 중 어디부터 시간을 재는지도 확인한다.

이 수치는 권장 설정이 아니다. 변경 요청은 서버의 처리 여부·멱등성 계약을 먼저 확인하고 무제한 반복·여러 계층의 중첩 재시도를 피한다. 이번 `check_http.py`는 예정된 점검을 반복하며 재시도·엄격한 전체 deadline을 구현한 코드가 아니다. 부하·실제 backoff/jitter 구현은 후속 심화로 남긴다.

**오프라인 연결 질문:** 27회의 조건이 성립하는지, 1초 전체 예산과 시도별0.4초가 왜 다른지 설명한다. [분리 해설](ANSWERS.md#retry-budget)은 먼저 답한 뒤 읽는다.

## 헷갈리는 두 구별

1. **수신 조각 / 메시지 / TCP 세그먼트:** `recv` 길이는 앱이 읽은 바이트 수다. LF는 앱의 경계이고 TCP 패킷 분할과 일대일로 대응하지 않는다.
2. **시간제한 초과 / 처리 실패:** 기다림이 끝났다는 사실만으로 서버가 아무것도 하지 않았다고 결론내리지 않는다. HTTP 404 수신도 통신 자체의 실패와 구별한다.
