# 15주차 분리 해설 · 관찰과 결론 사이의 조건

요약: 복습 8문항과 개발 질문의 필수 요소·흔한 오답·근거를 제공한다. 수신 호출·메시지·세그먼트를 구별하고 EOF·시간제한·HTTP 판정의 조건을 확인한다. 직접 수행·독립 이해는 실제 근거로 따로 확인한다.

<span id="retry-budget"></span>

## 오프라인 연결 질문 · 재시도와 시간 예산

매 시도가 다음 계층의 호출을 만들고 각 계층이 최초 포함3회씩 끝까지 시도하는 조건이면 최하위 상한은3³=27회다. 최초1회+추가2회이므로 계층별 숫자를4로 세지 않는다. 한 계층에서만 최대3회로 제한하고 나머지가1회면 최하위도3회다. 공유 deadline·조기 성공·재시도 불가 오류·중복 제거가 있으면 실제 횟수는 더 작을 수 있다.

시도별0.4초와 사이 대기0.2초의 단순 합은 최대1.6초로 전체1초 예산과 다르다. 전체 시작 시각/마감을 정하고 남은 시간을 다음 호출과 대기에 반영해야 한다. 최대3회는3회 보장이 아니며 남은 시간이 부족하면 일찍 멈추거나 해당 시도의 제한을 줄인다. 응답을 못 받아도 서버 처리 가능성은 남으므로 멱등성·중복 방지 계약 없이 변경 요청을 자동 재시도하면 안 된다.

이 계산은 [교재의 가공 예](CONCEPTS.md#retry-budget)이며 `check_http.py`가 재시도·전체 deadline을 구현했다는 뜻이 아니다. 기존 Q8의 조건 변경으로 사용하고 별도 실습/제출을 추가하지 않는다.

## Q1 · 호출과 메시지

이 프로토콜은 LF까지 한 메시지이며 관찰한 recv 호출은 두 번이다. TCP 세그먼트 수는 이 로그만으로 모른다. TCP는 앱의 send/recv 호출 경계를 보존하지 않는다. **흔한 오답:** sendall 1회이니 반드시 recv 1회 또는 세그먼트 1개다. [K1](CONCEPTS.md#W15-K1)의 경계 규칙과 실제 recv 길이가 근거다.

## Q2 · UTF-8

LF를 찾은 뒤 누적한 본문을 한 번 디코딩한다. 개별 조각이 불완전한 문자 바이트를 담아도 누적 후에는 복원할 수 있다. 잘못된 UTF-8이면 invalid_utf8로 분류한다. 상한 256은 **본문 바이트 수**, LF는 별도 1바이트다. **흔한 오답:** 글자 수 256 또는 recv마다 문자열로 바꾸면 언제나 된다. 빈 본문+LF도 정상이다.

## Q3 · 보내기 종료

eof는 LF를 보내지 않고 `shutdown(SHUT_WR)` 한다. 서버는 LF 전 `recv`의 `b''`로 eof_incomplete를 반환한다. 클라이언트는 수신 방향을 열어 두어 오류 판정 응답을 받는다. EOF를 경계로 약속한 다른 프로토콜에서는 완료일 수 있다. **흔한 오답:** EOF는 언제나 모든 양방향 통신 실패다. [K2](CONCEPTS.md#W15-K2)·client 종료 조건과 server의 not chunk 분기가 근거다.

## Q4 · 수신 마감

read_line 진입에서 monotonic()+2를 정하고 매 recv 전에 남은 시간을 계산한다. remaining이 0 이하이거나 recv에서 TimeoutError면 timeout이다. 받은 바이트마다 2초를 새로 주지 않는다. 이 마감은 수신 단계에만 적용되며 응답 대기/쓰기·연결·OS 지연은 별도다. HTTP timeout은 개별 블로킹 대기 제한이다. **흔한 오답:** 모든 프로그램은 인자 시간 안에 정확히 끝나며 timeout이면 서버가 처리하지 않았다.

## Q5 · 직접 수행 근거

필수 변경은 ending만 line→eof→line이다. 본문 hello·포트·서버를 유지한다. 정상/원복은 reply 안 frame_ok와 hello·종료0, 변경은 eof_incomplete·종료1과 서버 recv0을 대조한다. 호출별 조각 길이는 실제 로그를 따른다. **흔한 오답:** 제공 사례를 자기 실행 결과로 쓰거나 원복 명령만 있고 재확인이 없다. 환경이 막혔다면 제공 분석과 남은 직접 수행을 나눈다.

## Q6 · 판정 정책

모순이 아니다. `--fail` 없는 curl은 완전한 404 응답도 전송 성공으로 종료0일 수 있다. 자동 코드는 완전한 2xx만 http_success로 분류하여 404는 http_error·종료1이다. 서버 중지의 communication_error·status null은 HTTP 응답 이전 실패다. 상태를 이미 읽었더라도 본문이 잘리거나 시간제한을 넘으면 성공으로 세지 않는다. **흔한 오답:** 모든 종료1은 연결 실패이며 404는 서버에 닿지 않았다. [K3](CONCEPTS.md#W15-K3)·check_once 분기가 근거다.

## Q7 · 같은 입력과 관찰 위치

정상 경로 `/echo?message=w15`와 각 단계 count3을 유지한다. 수동 상태·본문·종료 코드, 자동 attempt/status/outcome/error/elapsed_ms와 서버의 같은 경로·message 로그를 대조한다. 새 연결의 별도 요청들이라 경과 시간은 정확히 같을 필요가 없다. 중지에서는 리스너 부재를 보고 복구 후 200/message/로그를 확인한다. **흔한 오답:** 실패 한 줄만으로 방화벽을 원인으로 확정하거나 3회로 p99·실서비스 가용성을 주장한다. O05의 기록 부분이며 독립 원인 진단은 추가 관찰이 필요하다.

## Q8 · 불확실성과 상한

서버 처리 후 응답만 늦었을 수 있으므로 미처리로 단정할 수 없다. ‘1 증가’는 중복 적용 때 효과가 늘지만 ‘7로 설정’은 같은 목표값을 반복 적용해도 의도한 효과가 같다. 후자는 멱등성의 작은 사례이지 동시성·모든 부수 효과까지 보장한다는 뜻은 아니다. 최초1+추가2는 총3회다. 이는 횟수 계산 예이며 RFC 권장 횟수가 아니다. RFC는 실패한 자동 재시도를 다시 자동으로 시도하지 말 것을 권고한다. 재시도에는 대기·전체 중단 기한/조건도 필요하며 변경 요청은 멱등성 보장이나 원래 요청의 미적용 확인 없이 자동 반복하지 않는다. **흔한 오답:** 멱등이면 무한 반복해도 부하나 위험이 없거나 응답/로그까지 같아야 한다. [RFC9110 §9.2.2](SOURCES.md)의 제한이 근거다. 이번 점검 코드는 예정된 GET 반복이며 오류 재시도는 없다.

## W15-D1\~D3 · 개발 질문 확인

- **D1 설명:** 404 응답과 응답 전 실패의 관찰을 구별한다. 상태·본문·종료 코드·서버 로그를 같은 조건으로 대조해야 자동 결과를 해석할 수 있다. 성공 문자열 하나만 보는 답은 보충한다.
- **D2 조건 변경:** line은 LF, eof는 보내기 종료, hold는 둘 다 없어서 서로 다른 분기다. EOF를 완료로 바꾸려면 프로토콜 약속·빈 입력·상한·코드와 해설을 함께 바꿔야 한다. 이번 필수 실습은 준비된 입력 한 가지 변경이다.
- **D3 다음 판단:** 동일 요청의 수신/처리 기록·서버의 상태 확인 방법·멱등 계약을 먼저 찾는다. 수신 로그만으로 영구 업무 처리 완료를 증명할 수 없다. 총 시도/대기/중단 조건과 모르는 부분을 말한다.

이 문항들은 자체 작성했다. 실제 기업 기출이나 참가자 수행 결과가 아니다. 해설 읽기와 본인 직접 변경·독립 설명을 구별한다.
