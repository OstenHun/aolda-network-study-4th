네트워크와 호스트·프로세스

네트워크는 장치들이 데이터를 교환하는 체계입니다. 이번에는 Linux 한 대의 네트워크 기능으로 두 프로그램이 통신합니다. 호스트는 컴퓨터, 프로세스는 실행 중인 프로그램입니다. 터미널 창 두 개가 호스트 두 대를 뜻하지는 않습니다.

클라이언트·서버와 IP·포트

curl은 요청을 시작하고 Python 서버는 받아 응답합니다. IP는 통신 위치를, TCP 포트는 그 주소의 통신 끝점을 구분합니다. 127.0.0.1은 명령을 실행하는 환경 자신입니다. SSH 뒤의 Linux와 개인 PC에서 이 주소가 가리키는 곳은 다릅니다.

같은 Linux 내부 / 임시 포트는 설명용 값
curl 127.0.0.1:51000 → 서버 127.0.0.1:8080
curl 127.0.0.1:51000 ← 서버 127.0.0.1:8080

프로토콜·계층과 HTTP

프로토콜은 함께 따르는 통신 규칙입니다. HTTP는 요청·응답의 형식, TCP는 이번 메시지의 전달, IP는 주소를 다룹니다. 역할을 나눠 보면 연결 실패와 HTTP 오류를 구별할 수 있습니다. OSI 이름 암기는 이번 주 완료 조건이 아닙니다.

HTTP: 무엇을 요청하고 어떤 응답을 받았나?
  ↓ TCP: 어떤 포트 사이에 연결했나?
  ↓ IP: 어느 주소인가?
  ↓ 이번 전달 위치: Linux 내부 lo

아래는 주석용 예시이며 실측이 아닙니다. >와 <는 curl의 방향 표시입니다.

> GET /echo?message=hello HTTP/1.1  ← 요청 메서드·경로·버전
< HTTP/1.1 200 OK                  ← 응답 상태
< Content-Type: application/json; charset=utf-8
< Content-Length: 20              ← 본문 바이트 수
<                                 ← 빈 줄 뒤 본문
{"message": "hello"}
오해 확인: 파일이 있으면 서버가 실행 중일까?

파일은 실행할 내용이고 프로세스는 실행 중인 프로그램입니다. listening과 실제 요청·응답으로 실행 상태를 확인합니다. 파일이 남아도 서버를 중지하면 요청을 받지 못합니다.

01 / 첫 번째 실험

내가 보낸 문장은 어디로 갈까?

클라이언트는 요청하는 프로그램, 서버는 요청을 받아 응답하는 프로그램입니다. 서로 다른 컴퓨터일 필요는 없습니다.

127.0.0.1은 명령을 실행하는 Linux 자신을 가리키는 루프백 주소입니다. 8080은 이번 서버가 요청을 기다리는 TCP 포트입니다. 클라이언트에도 OS가 고른 임시 포트가 생깁니다.

HTTP는 요청과 응답의 형식을 정하는 응용 프로토콜입니다. 이번에는 GET /echo?message=hello로 경로와 메시지를 보내고, 상태 코드·헤더·본문을 받습니다. 그 HTTP 메시지를 이번 키트에서는 TCP 연결로 전달합니다. IP는 상대 주소, 포트는 그 주소에서 통신을 구분하는 번호입니다.

터미널 A · 서버를 시작하고 그대로 둡니다

python3 labs/week-01/server.py

터미널 B · 요청을 한 번 보냅니다

curl -v --http1.1 --noproxy '*' --max-time 5 'http://127.0.0.1:8080/echo?message=hello'
echo $?

세 군데를 찾아 연결하세요

  1. curl의 연결 설명과 서버 로그의 client에서 IP·임시 포트를 찾습니다.
  2. curl의 < HTTP/1.1 상태 줄과 JSON 본문을 확인합니다.
  3. 서버의 response 로그에서 같은 요청의 경로와 클라이언트 포트를 찾습니다.

hello를 다른 단어로 바꾸고 다시 실행하세요. 어떤 값이 달라졌고 어떤 값이 유지되나요?

출력을 읽을 때 놓치기 쉬운 점

선택 Node 클라이언트의 elapsed_ms는 프로그램에서 잰 경과 시간입니다. 서버 처리와 로컬 실행 비용도 포함하므로 네트워크에서만 걸린 시간이나 왕복 시간(RTT)으로 단정하지 않습니다. 이번 키트는 매 요청 연결을 닫습니다. 실제 HTTP 서비스는 연결을 재사용할 수도 있습니다.

02 / 두 번째 실험

없는 경로를 요청해 봅시다

서버는 그대로 두고 요청의 경로만 바꿉니다. 실행 전에 “연결 정보·상태 코드·본문 중 무엇이 나올까?”를 예상하세요.

curl -v --http1.1 --noproxy '*' --max-time 5 'http://127.0.0.1:8080/missing'
echo $?

정상 요청과 비교해 서버 로그가 생기는지, HTTP 상태 코드가 있는지 확인합니다. curl 바로 다음에 echo $?로 종료 코드를 확인하세요. --fail 없는 curl은 404를 받아도 전송 완료 시 0입니다. HTTP 상태와 종료 코드는 다릅니다. 선택 Node 키트는 404에 2를 반환합니다.

실험 후 설명 대조하기

이 키트의 404는 Python 서버가 없는 경로에 대해 보낸 HTTP 응답입니다. 요청·응답 통신은 이루어졌지만 요청한 자원이 없습니다. 실제 시스템에서는 프록시 등 중간 서비스가 응답할 수도 있으므로, 이번에는 서버 로그까지 대조합니다.

같은 현상을 그림으로 정리하기

아래는 설명용 모형입니다. 상태를 골라도 실제 요청·캡처는 실행되지 않습니다. 표시 내용은 예상 동작이며 여러분의 관찰 결과가 아닙니다.

연결 후 정상 응답을 받습니다

양쪽 출력과 패킷에서 같은 흐름을 찾아보세요. 임시 포트와 실제 시간은 실행 결과로 채웁니다.

관찰 / 정상 흐름부터

출력과 패킷을 맞춰봅시다

프로그램 로그는 프로그램이 남긴 기록이고, 캡처는 선택한 네트워크 인터페이스(통신 통로)에서 관찰한 패킷입니다. 두 증거를 같은 주소·포트로 연결합니다.

서버 A·요청 B 외에 같은 Linux의 셸 C를 더 엽니다. 권한이 확인된 경우만 아래 명령을 사용합니다. 파일명은 매번 새로 정합니다.

sudo tcpdump -i lo -nn -s 0 -w week-01-linux-run-01.pcap 'host 127.0.0.1 and tcp port 8080'
  1. C의 캡처 시작 표시 뒤 B에서 정상 요청을 한 번 보냅니다. 그 흐름을 먼저 찾고 시간이 남으면 새 파일로 404·중지·복구도 비교합니다.
  2. C에서 Ctrl+C로 저장을 마칩니다. pcap은 Linux의 현재 폴더에 생깁니다.
  3. 진행자가 안내한 SFTP 또는 scp로 PC에 가져와 Wireshark에서 엽니다. 반출·읽기 권한이 없으면 진행자에게 알립니다.
  4. 표시 필터 tcp.port == 8080. 필요하면 해당 포트를 HTTP로 Decode As 합니다.
  5. Follow → TCP Stream, Statistics → Flow Graph에서 요청·응답 방향·상태를 보고 서버 로그의 임시 포트와 대조합니다.

이번에 찾을 것

송·수신 IP와 포트, 요청 경로, 상태 코드, 요청·응답의 패킷 번호.

이번 증거로 말할 수 없는 것

실제 LAN의 ARP·스위치·라우터 경유. 루프백 캡처로 외부 망 구조를 증명하지 않습니다.

제공 예제 캡처를 처음부터 분석하는 안내 →

HTTP 메시지 하나가 패킷 하나와 항상 일치하지 않습니다. 분할·재조립될 수 있으므로 패킷 개수를 정답으로 외우지 마세요.

캡처가 안 되면 어떻게 진행하나요?

인터페이스, 시작 시점, 포트 필터, 캡처 권한을 확인합니다. 아래 예제는 Windows에서 기록한 패킷이며 Linux 캡처가 아닙니다. 계속 막히면 이번 키트의 실제 예제 캡처를 사용하세요. 이 예제의 포트는 59995입니다. 표시 필터는 tcp.port == 59995, 필요하면 해당 포트를 HTTP로 Decode As 합니다. 예제에서는 정상 요청·응답이 4·8번, 404 요청·응답이 17·21번 패킷입니다. 예제 분석으로 기록하고 직접 캡처는 미완료로 남깁니다. 다른 프로토콜은 Kurose·Ross 제공 캡처도 참고할 수 있습니다. 예제의 주소·구성이 우리 실험과 같다고 가정하지 않습니다.

03 / 세 번째 실험

서버를 멈추고 다시 시작하기

  1. 터미널 A에서 Ctrl+C로 이번 Python 서버를 종료합니다.
  2. B에서 첫 hello 요청을 그대로 실행합니다. 실패 패킷도 비교할 여유가 있고 권한이 준비됐다면 같은 Linux의 C에서 먼저 새 캡처를 시작합니다.
  3. curl 오류 문구와 바로 다음 echo $?의 종료 코드를 기록합니다. HTTP 상태 줄이 있는지 별도로 확인합니다.
  4. A에서 같은 포트로 서버를 다시 시작하고 B에서 같은 hello 요청을 재실행합니다. 200·본문·새 서버 로그를 확인합니다. C에서 캡처 중이었다면 Ctrl+C로 마칩니다.

이 실험에서는 서버 실행 여부 하나만 바꿉니다. 캡처 권한이 없으면 직접 요청·출력 비교를 먼저 하고 제공 예제를 별도 분석합니다. 실제 오류 코드와 패킷을 기록하고 404와 비교하세요.

1. 404이면 서버에 도달하지 못했을까요?

퀴즈 1 힌트

HTTP 상태 줄과 Python response 로그가 있는지 보세요.
