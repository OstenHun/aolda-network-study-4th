먼저 풀었는지 확인

문제에 자기 답을 쓴 다음 10분 동안 비교한다. 틀린 답은 지우지 말고 바꾼 이유를 덧붙인다.

  1. HTTP 요청·응답이 오가는 호스트는 VM 한 대이며, 이를 주고받는 주요 응용 프로세스는 curl과 Python 서버 둘이다. 개인 PC는 SSH 명령 입력과 화면 표시를 한다. 전체 환경에는 PC와 VM 두 호스트가 있지만 해당 HTTP는 VM 안에서 진행한다. 확인 질문: “터미널 창과 호스트는 왜 같지 않을까?”
  2. 응답은 127.0.0.1:8080 → 127.0.0.1:53120. 53120은 이 예시의 클라이언트 임시 포트이며 다음 요청에서 같을 필요 없다. 서버 로그 client와 캡처로 확인한다. 확인 질문: “두 IP가 같아도 방향을 구별한 근거는?”
  3. PC 자신의 루프백을 요청했으므로 VM 고장을 단정할 수 없다. curl을 실행한 셸의 호스트와 SSH 접속 대상을 확인하고, VM 안에서 서버 listening과 같은 URL 요청을 대조한다. 확인 질문: “같은 URL 문자열이 왜 다른 곳을 가리킬까?”
  4. 메서드는 GET, 경로는 /missing, 상태 코드는 404, 본문은 JSON 오류 데이터다. HTTP 응답을 받았으므로 이번 요청을 TCP 연결 실패라고 부를 수 없다. 자체 서버 로그까지 맞으면 이 서버가 처리했다는 근거가 보강된다. 404를 만든 다른 중간 서비스 가능성은 일반 환경에서 별도 확인한다.
  5. 기본 curl에 --fail이 없으면 HTTP 오류 응답도 전송 완료로 0을 반환할 수 있다. pwd 뒤의 $?는 pwd의 결과이므로 curl 결과를 잃는다. HTTP 상태와 프로세스 종료 코드는 서로 다른 출처다. 선택 Node의 404=2는 키트의 정책이다.
  6. 7은 curl 연결 실패 종료 코드다. HTTP 상태가 아니다. 다른 호스트·포트 오타·서버 미실행 등도 확인해야 한다. 중지 → 같은 명령 실패 → 같은 포트 재시작 → 복구의 통제된 비교가 가설을 강화한다. 오류 문구 하나로 모든 환경의 원인을 확정하지 않는다.
  7. 같은 Linux의 추가 셸 C에서 허가된 lo 캡처를 한다. pcap은 Linux에 생기고 승인된 파일 전달로 개인 PC에 가져와 Wireshark로 연다. PC Wi-Fi에는 SSH 트래픽이 보일 수 있어도 VM 내부 루프백 HTTP를 그대로 보는 것은 아니다.
  8. 제공 파일에 맞춰 tcp.port == 59995로 바꾼다. 제공 Windows 캡처 분석으로 기록하며 자기 Linux 실행·직접 캡처와 구분한다. 번호는 파일 안에서만 의미가 있다.
  9. 어떤 변경이 영향을 주었는지 분리하기 어렵다. 기준 /echo 성공으로 돌아간 뒤 메시지만, 또는 경로만 바꾼다. 포트 선택 시 서비스 포트라는 변수 하나를 서버·URL·필터에 일관되게 적용한다. 설정 세 곳을 맞추는 것과 독립 변수 세 개를 바꾸는 것은 다르다.
  10. TCP로 전달되어도 HTTP는 404 등을 반환할 수 있다(상태 줄). HTTP 메시지는 나뉘거나 재조립될 수 있다(Follow TCP Stream). listening은 로컬 대기 상태이고 외부 접근은 별도 요청·바인딩·경로·정책 확인이 필요하다. 이번 주는 외부 접근을 실습했다고 쓰지 않는다.

진행자가 확인할 설명

정확한 용어를 한두 번 틀리는 것보다 “PC의 루프백과 VM의 루프백을 합침”, “404를 응답 없음으로 설명함”, “짝 결과를 직접 수행으로 적음”을 우선 수정한다. 이 세 혼동은 그림·개인 실습 출력·팀 활동의 설명에서 각각 확인한다. 교재 2·4·7절로 돌아가고, 환경이 되는 참가자는 해당 요청을 한 번 더 실행한다.

정답 암기가 보이면 “내가 경로 대신 포트만 바꾸면 다음에 무엇을 확인할까?”를 묻는다. 스터디장도 다른 참가자와 같은 기준으로 짝의 확인을 받는다.

개발 질문 해설

핵심 정리의 자체 문항을 먼저 설명한 뒤 비교한다.

  1. W01-D1: VM의 200·404는 HTTP 응답이다. PC의 loopback은 PC 자신이므로 그 실패가 VM 서버 중지를 증명하지 않는다. 일반 서비스의 중간 프록시 가능성과 이번 직접 요청 모형을 구별한다.
  2. W01-D2: 아니다. 서버 바인딩·대기 소켓, PC→VM 경로와 정책·실제 대상 포트를 확인해야 한다. URL 한 부분을 바꾼 사실만으로 도달성이 보장되지 않는다.
  3. W01-D3: curl 실행 호스트·정확한 URL을 먼저 맞추고 VM의 서버 로그·대기 주소/포트와 비교한다. 1주차의 VM 내부 요청과 PC 외부 요청은 다른 실험이다.

흔한 오답: ‘404는 TCP 실패’, ‘localhost는 언제나 내 PC’, ‘IP만 맞으면 성공’. 설명 확인: 위치·실패 단계·근거를 함께 말하면 개념 답안이 충족된다. 직접 실습 완료는 개인 증거로 별도 확인한다.
