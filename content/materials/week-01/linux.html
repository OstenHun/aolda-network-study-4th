1주차 Linux 실행 안내

같은 Linux VM에서 Python 서버와 curl을 실행해 정상 응답·404·연결 실패·복구를 비교한다. lo에서 캡처한 패킷과 출력을 대조하며, 안내의 예시와 자신이 실행한 결과를 구분한다. 개인별 준비와 수행은 별도로 확인한다.

개념 교재 →팀 활동 →
이 페이지의 목차
WireSalmon 샘플 분석읽기 순서와 준비 — 모임 전 20~40분터미널이 처음이라면 — 명령을 넣기 전에1. 서버 시작 — 셸 A2. 정상 요청 — 셸 B3. 경로 변경 — 셸 B4. 중지와 복구 — A와 B5. lo 캡처와 PC 분석 — 추가 셸 C6. 짝이 정한 조건으로 다시 실행하기 — 15분환경이 막힐 때종료와 완료 증거

패킷을 읽을 때는 스터디 팀원이 만든 WireSalmon을 사용해 보기를 권장한다. Wireshark를 사용해도 좋다. WireSalmon 공개 웹에서 내장 샘플이나 저장한 .pcap·.pcapng 파일을 열어 대화 흐름과 개별 패킷의 근거를 함께 살펴본다. 공개 웹은 실시간 캡처를 지원하지 않으므로 캡처는 아래 실습 절차를 따른다. 내장 샘플 분석과 본인이 직접 수행한 결과는 구분한다.

WireSalmon에서 먼저 볼 샘플

WireSalmon에서 언어를 한국어로 고른 뒤 상단 샘플 열기에서 아래 이름을 선택한다. 대화 목록에서 볼 대화를 고르고 대화 흐름을 따라간다. 패킷을 누르면 봉투 구조에서 주소와 필드를 펼쳐 볼 수 있다. 전체 패킷에서는 다른 대화와의 시간 순서도 확인한다.

먼저 보기 · HTTP 요청과 정상 응답

한눈에 보기 → 와이파이에 접속해서 웹사이트 열기를 연다. DHCP·DNS·TLS의 자세한 분석은 이번 순서에서 건너뛰고, 대화 목록의 웹 페이지 요청: example.com을 고른다.

  1. 대화 흐름에서 GET /와 200 OK의 방향을 찾는다. 요청한 쪽과 응답한 쪽의 IP·포트를 짝짓는다.
  2. HTTP 메시지에서 요청 경로·Host, 응답 상태·헤더·본문을 읽는다. 본문이 든 패킷으로 이동해 HTTP 메시지 하나와 패킷 하나가 항상 같은 단위인지 살펴본다. 이 샘플의 응답 헤더와 본문은 서로 다른 패킷에 담겨 있다.
  3. 아래 VM 실습의 루프백 HTTP와 비교한다. 샘플의 원격 서버 주소·80번 포트는 예제 값이며 본인 VM의 주소·포트와 섞지 않는다.

선택 비교 · 404와 연결 거부

한눈에 보기 → 뭔가 잘 안 되는 네트워크를 연다. 웹 페이지 요청: example.com에서 GET /old-page와 404 Not Found를 찾고, TCP 통신: 203.0.113.20 (포트 8080) 대화의 SYN 뒤 RST·ACK와 비교한다. 전자는 HTTP 응답이 왔고 후자는 연결이 거부되어 HTTP 응답이 없다는 점을 패킷으로 설명한다. 응답이 없다는 사실만으로 서버 중지나 방화벽을 단정하지 않는다. 이 주소로 직접 요청을 보내는 과제는 아니다.

샘플은 기존 패킷 분석 시간에 필요한 것만 골라 본다. 같은 근거를 본인 캡처나 제공 trace로 확인했다면 반복하지 않아도 된다. 샘플은 코드로 만든 분석 예제다. 아래 Linux 직접 실습의 완료 근거로 바꾸어 적지 않는다. 필요한 패킷을 근거로 한 사람이 설명하고, 다른 사람은 조건 하나를 바꾸어 질문한다. 추가 기록 양식은 없다.

읽기 순서와 준비 — 모임 전 20~40분

개념 교재를 읽은 뒤 이 안내에 따라 실습한다. 네 상태의 상세 예상·출력·패킷은 개인 실습 기록이나 별도 증거 파일에 남긴다. 함께 찾을 질문을 설명할 때 필요한 근거를 보여 준다. 추가 메모는 자유롭게 하며 원본 출력을 다시 옮기지 않는다.

실습은 다음 순서로 진행한다. 아래 번호는 모임 횟수가 아니라 실습 단계를 뜻한다.

  1. 1~4단계: 정상 응답, 404 응답, 서버 중지 뒤 연결 실패, 재시작 뒤 복구를 비교한다.
  2. 5단계: 정상 요청이 오간 패킷을 캡처하고 분석한다.
  3. 6단계: 짝과 조건 하나를 정해 바꾸고, 각자 같은 실험을 다시 실행한다.

안내에 나온 기대 결과는 제공 코드로 예상한 동작이다. 자신이 실행해서 얻은 결과와 구분해 기록한다.

개념 학습과 Linux 실습은 준비 속도에 맞춰 나누어 진행한다.

실습은 본인에게 허용된 Linux VM에서 진행한다. 접속 주소·계정·인증 방식은 환경 안내를 따른다. 이 HTTP 실습을 위해 VM을 새로 만들거나 방화벽을 바꿀 필요는 없다.

시작하기 전에 다음을 확인한다. 막히는 항목은 진행자와 함께 점검한다.

  • 내 VM에 접속할 수 있는가?
  • Python과 curl이 준비되어 있는가?
  • 패킷을 캡처할 권한과 도구가 있는가?
  • 캡처 파일을 개인 PC로 가져올 수 있는가?
개인 PC: 자료 읽기·SSH 창·마지막 Wireshark 분석
    └ 접속 → Linux 한 대
                A: Python 서버 / B: curl / C: lo 캡처(추가 셸)
                server.py와 pcap도 이 Linux에 위치

실행할 파일은 VM에도 있어야 한다. 개인 PC에서 내려받은 파일이 Linux VM에 자동으로 복사되지는 않는다. 진행자가 안내한 SFTP 또는 scp로 실습 파일을 VM에 옮긴다. 접속 주소와 파일 위치도 진행자 안내를 따른다.

실습에 필요한 파일을 Linux에 옮긴 뒤 파일 위치를 확인한다.

터미널이 처음이라면 — 명령을 넣기 전에

터미널은 명령을 입력하고 결과를 보는 창이다. 셸은 입력한 명령을 해석해 실행하는 프로그램이다.

아래 코드 상자의 명령을 한 줄씩 입력하고 Enter를 누른다. 화면에 보이는 $ 같은 입력 대기 표시(프롬프트)는 복사하지 않는다.

터미널 창 A·B·C는 같은 VM의 셸을 구별하는 이름이다.

명령·키 이번에 사용할 뜻
pwd 지금 명령을 실행하는 폴더의 절대 경로 확인
ls 지금 폴더의 파일·하위 폴더 확인
cd 폴더이름 그 하위 폴더로 이동. 실제 이름으로 바꿈
cd .. 바로 위 폴더로 이동
mkdir -p labs/week-01 실습 파일을 둘 하위 폴더 준비
Ctrl+C 그 창에서 실행 중인 명령 중지. 복사 단축키가 아님

Linux에 옮긴 폴더 이름이 aolda-week-01이라면, 그 폴더가 보이는 위치에서 cd aolda-week-01로 이동한다. 각 셸의 현재 폴더는 따로 관리되므로 A와 B에서 각각 pwd와 ls로 위치를 확인한다.

ls labs/week-01/server.py가 파일 이름을 출력하면 서버를 실행할 위치가 준비된 것이다. No such file or directory가 나오면 파일을 아직 옮기지 않았거나 현재 폴더가 다르다. 서버를 시작하기 전에 진행자와 파일 위치를 확인한다.

두 번째 창도 같은 승인된 Linux에 접속한다. 브라우저 기반 환경에서 두 셸을 여는 방법은 진행자의 안내를 따른다. 첫 창의 서버를 종료하고 그 자리에 curl을 입력하면 서버와 클라이언트가 동시에 실행되지 않는다.

  • 프로젝트 폴더를 받았다면 Linux에서 그 루트로 cd한다. 아래 명령은 그 위치 기준이다.
  • server.py 하나만 받았다면 현재 폴더 아래 mkdir -p labs/week-01로 폴더를 준비하고 파일을 그곳에 둔다. 그러면 아래 명령을 바꾸지 않아도 된다.
  • A와 B에서 다음을 확인한다. hostname만 같다고 같은 VM이 보장되지는 않으므로 접속 대상도 대조한다.

Python 3.10 이상과 curl이 기본이다. 없는 도구는 진행자가 배포판·권한에 맞춰 준비한다. Node는 선택이며 기본 실습 때문에 설치하지 않는다. 준비가 5분 이상 막히면 마지막 오류 표의 대안으로 전환한다.

1. 서버 시작 — 셸 A

코드가 어떻게 응답을 만드는지 궁금하면 코드 읽기 안내를 함께 본다. 처음에는 정상 요청을 한 번 실행한 뒤 코드의 다섯 단계와 출력을 연결하면 된다.

예측: 파일만 있을 때와 프로세스가 실행 중일 때 무엇이 다를까?

python3 labs/week-01/server.py

A가 대기하며 프롬프트가 돌아오지 않는 것이 정상이다. listening의 127.0.0.1과 8080을 적는다. A는 그대로 두고 B로 이동한다. 이 로그는 외부 PC 접근의 증거가 아니다.

다음은 형태를 익히는 예상 출력이다. listening은 요청을 기다리기 시작했다는 뜻이다. 실제 A 화면의 줄은 개인 실습 기록이나 별도 증거 파일에 보관한다.

{"event": "listening", "address": ["127.0.0.1", 8080]}

2. 정상 요청 — 셸 B

정상 요청의 결과를 먼저 예상하고 짝과 이유를 이야기한다. ss의 Local Address:Port에서 서버 대기 포트를 찾는다.

ss -lnt
curl -v --http1.1 --noproxy '*' --max-time 5 'http://127.0.0.1:8080/echo?message=hello'
echo $?
부분 뜻
ss -lnt 대기 중인 TCP 소켓을 숫자 주소·포트로 조회
-v 연결 설명·요청·응답 헤더 표시
--http1.1 이번 HTTP 버전을 명시
--noproxy '*' 프록시를 사용하지 않음. 따옴표 유지
--max-time 5 전체 요청 시간 최대 5초
URL의 작은따옴표 셸의 특수 문자 해석을 피함
echo $? 바로 직전 명령 종료 코드. 다른 명령보다 먼저 실행

정상 요청의 기대 결과는 HTTP 200과 {"message": "hello"} 본문이다. 셸 A에는 같은 요청의 path와 status를 담은 로그가 새로 남을 것으로 예상한다.

curl 출력에서 >는 보낸 헤더, <는 받은 헤더, *는 도구의 연결 설명을 나타낸다. 본문은 표준 출력(stdout), 상세 설명은 표준 오류(stderr)로 나와 한 화면에 섞여 보인다. 본문 끝에 줄바꿈이 없어 다음 프롬프트가 붙어 보일 수도 있다.

출력은 다음 순서로 읽는다.

  1. 셸 B에서 < HTTP/1.1 200 OK 상태 줄과 {"message": "hello"} 본문을 찾는다.
  2. echo $?로 바로 직전 curl 명령의 종료 코드를 확인한다. 정상적으로 전송을 마쳤다면 0을 예상한다.
  3. 셸 A로 돌아가 event가 response인 새 로그에서 path와 status를 대조한다.

JSON의 중괄호를 외울 필요는 없다. client는 요청한 쪽의 IP와 임시 포트, path는 요청 경로, status는 HTTP 상태다. 숫자나 출력 순서가 예시와 다르면 자신의 화면 그대로 기록한다.

E1에 실제 명령·B의 상태/본문/종료 코드·A의 response 줄을 붙인다. A의 client에 있는 임시 포트로 통신 그림을 채운다. 짧은 연결은 ss 조회 전에 끝날 수 있어 임시 포트는 서버 로그·캡처에서 찾는다.

메시지만 hello에서 again으로 바꿔 재실행한다. 어떤 값이 바뀌었는지 기록한 뒤 기준 hello로 돌아온다.

3. 경로 변경 — 셸 B

E2에 HTTP 응답·서버 로그 유무를 예측한다. 서버는 켜 둔다.

curl -v --http1.1 --noproxy '*' --max-time 5 'http://127.0.0.1:8080/missing'
echo $?

기대: HTTP 404와 오류 본문, A에 새 response 로그. 이 curl에는 --fail이 없으므로 전송 완료 시 404도 종료 코드 0이다. HTTP 상태와 종료 코드는 다른 칸에 쓴다. 선택 Node 클라이언트의 404 종료 코드 2와 구분한다. 짝에게 응답 존재의 근거를 상태 줄과 서버 로그에서 하나씩 보여준다.

4. 중지와 복구 — A와 B

E3 예상 후 A에서 Ctrl+C로 자신이 시작한 서버만 중지한다. B에서 E1과 같은 요청을 한다.

curl -v --http1.1 --noproxy '*' --max-time 5 'http://127.0.0.1:8080/echo?message=hello'
echo $?

다른 리스너가 없다면 연결 실패와 HTTP 응답 없음을 예상한다. 연결 거부 시 curl 7, 시간 초과는 28 등 실제 코드를 적는다. 중지된 서버는 새 로그를 남길 수 없다. “HTTP 7”이라고 쓰지 않는다.

E4 예상 후 A에서 python3 labs/week-01/server.py로 재시작하고 B에서 위 명령을 그대로 실행한다. 200·본문·A의 새 로그로 복구를 확인한다. 재시작할 때 메시지나 포트를 함께 바꾸지 않는다.

5. lo 캡처와 PC 분석 — 추가 셸 C

같은 Linux의 C에서 허가된 캡처 권한이 준비된 경우에만 실행한다. sudo 사용 권한이 없으면 제공 예제로 진행한다. 실행마다 run-01을 run-02 등 새 이름으로 바꿔 이전 증거를 보존한다.

sudo tcpdump -i lo -nn -s 0 -w week-01-linux-run-01.pcap 'host 127.0.0.1 and tcp port 8080'

-i는 위치, -nn은 숫자 표시, -s 0은 잘림 없는 수집, -w는 파일 저장이다. 마지막 따옴표 안은 캡처 필터다. 처음에는 정상 요청 한 흐름만 찾아도 된다. 시간이 남으면 다음 순서로 네 상태를 다시 실행해 비교한다.

  1. C의 캡처 시작 표시 뒤 B에서 요청한다. 중지 실험에서는 A만 멈추고 C는 유지한다.
  2. 정상 → 404 → A 중지 후 정상 URL → A 재시작 후 같은 URL 순서 뒤 C에서 Ctrl+C.
  3. Linux에서 ls -l week-01-linux-run-01.pcap으로 파일과 크기를 확인한다. 읽기 권한 문제는 진행자에게 승인된 반출을 요청한다.
  4. 진행자가 안내한 SFTP 또는 scp로 PC에 가져온다. 원격 절대 경로는 C의 pwd로 확인한다. 이미 SSH 별칭이 준비된 경우 PC 터미널에서 쓰는 형식은 scp 실습별칭:/실제/Linux/경로/week-01-linux-run-01.pcap .이다. 별칭·경로를 실제 값으로 교체한다.
  5. PC Wireshark에서 파일을 연다. 표시 필터 tcp.port == 8080을 사용한다. 캡처 필터와 문법이 다르다. 필요하면 Analyze → Decode As → 해당 포트 HTTP.
  6. 요청 패킷 선택 → Follow → TCP Stream에서 메시지를, Statistics → Flow Graph에서 방향을 찾는다. 실제 번호·IP·포트·경로·상태를 적는다.

제공 Windows 캡처 분석 안내의 포트는 59995, 필터는 tcp.port == 59995다. 예제 분석은 자기 Linux 직접 캡처와 구분하고 서로 다른 실행의 출력·패킷을 하나로 합치지 않는다. 직접 캡처가 막혀도 패킷 분석은 수행한다.

lo는 Linux 내부 통신이다. PC Wi-Fi, VM 가상 NIC, 라우터, ARP, 보안 그룹 경유의 증거로 쓰지 않는다. 번호·개수·임시 포트는 고정 정답이 아니다.

6. 짝이 정한 조건으로 다시 실행하기 — 15분

팀 안의 짝 또는 3인 그룹에서 진행한다. 한 사람이 조건을 정하면 다른 사람이 자기 Linux에서 예상·명령·실행·설명을 하고 교대한다. 3인은 실행·근거 확인·설명 역할을 바꾸며 모두 직접 수행한다. 시간이 부족하면 마치지 못한 실험을 개인 보충으로 남긴다. 다음 중 하나만 선택한다.

  • 메시지: hello → pair. 경로·포트 유지.
  • 경로: /echo?message=hello → /missing?message=hello. 쿼리(message=hello)와 포트는 유지한다.
  • 포트: 자기 서버 중지 → python3 labs/week-01/server.py --port 8081, URL :8081, 캡처·표시 필터 8081. 서비스 포트라는 변수 하나를 세 설정에 일관되게 반영한다.

명령을 서로 복사하기 전에 예상과 변경 이유를 말한다. 각자 자신의 출력으로 재현 여부를 기록하고, 끝에 기준 포트·URL로 복구한다. 한 사람의 수행을 두 사람의 직접 수행으로 적지 않는다.
