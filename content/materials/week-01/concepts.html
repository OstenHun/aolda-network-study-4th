1. 네트워크 — 무엇이 연결되어 있나?

네트워크는 장치들이 연결되어 데이터를 주고받는 체계다. 인터넷은 여러 네트워크가 연결된 큰 네트워크다. 모든 네트워크 통신이 인터넷을 거치는 것은 아니다.

이번에는 Linux 한 대 안에서 두 프로그램이 운영체제의 네트워크 기능으로 통신한다. 같은 컴퓨터 안에서 데이터를 주고받는 루프백 경로를 쓰므로 외부 케이블이나 무선 연결이 필요하지 않다. 요청을 보내는 도구는 curl, 요청을 받아 응답하는 프로그램은 Python 서버다. 이들이 주고받는 요청·응답의 규칙인 HTTP는 5~6절에서 살펴본다.

먼저 생각하기: 인터넷이 끊겨도 같은 컴퓨터의 두 프로그램이 통신할 수 있을까?

같은 내용을 문자 그림으로 보기
일반적인 외부 통신:  내 호스트 ── 링크·중간 장치 ── 다른 호스트
이번 실험:          [ Linux 호스트: curl → 루프백 → Python 서버 ]

캡처 도구는 통신 중 오가는 데이터 단위인 패킷을 기록한다. “패킷 하나 = 화면의 문장 하나”는 아니다. 하나의 HTTP 메시지가 TCP의 전송 단위인 세그먼트 여러 개로 나뉘어 전달되고, 받는 쪽에서 다시 합쳐질 수 있다.

Linux에서 루프백을 관찰할 때 선택하는 네트워크 인터페이스(데이터를 주고받는 통로)의 이름은 lo다.

관찰할 곳: Linux의 lo 캡처와 요청/응답 주소.

오해 확인: Wi-Fi에서 보이지 않는다고 통신이 없었던 것은 아니다.

자기 설명: 이번 실험만으로 인터넷 연결 상태를 확인했다고 말할 수 없는 이유는?

2. 호스트와 프로세스 — 컴퓨터와 프로그램은 다른 단위다

호스트는 통신에 참여하는 컴퓨터다. 가상 머신(VM)도 자기 운영체제와 네트워크 환경을 갖춘 호스트로 볼 수 있다. 프로세스는 실행 중인 프로그램이다. server.py는 디스크에 저장된 파일이고, python3 server.py로 실행하면 Python 서버 프로세스가 생긴다. curl 명령도 요청을 보내는 프로세스를 실행한다.

터미널은 명령을 입력하고 출력을 보는 창이고, 셸은 그 명령을 해석해 실행하는 프로그램이다. SSH로 원격 컴퓨터에 접속하면 내 PC의 터미널에서 원격 Linux의 셸을 사용할 수 있다.

먼저 생각하기: 터미널 두 개를 열면 컴퓨터가 두 대가 될까?

같은 내용을 문자 그림으로 보기
개인 PC                             원격 Linux VM 한 대
┌ SSH 터미널 창 A ── 명령 입력 ────> 셸 A → Python 서버 프로세스
└ SSH 터미널 창 B ── 명령 입력 ────> 셸 B → curl 프로세스
                                     두 프로세스 사이 HTTP는 VM 내부

창이 개인 PC에 보여도 SSH 접속 뒤 명령은 Linux에서 실행된다. A와 B가 같은 호스트인지 접속 대상과 hostname, uname -s를 확인한다. 패킷 분석 도구인 Wireshark는 개인 PC에서 사용할 수 있다. Linux에서 캡처한 패킷을 pcap 파일로 저장해 PC로 가져온 뒤 분석한다.

실행할 파일도 명령을 실행하는 Linux에 있어야 한다. 개인 PC에서 내려받기만 한 파일은 원격 Linux에서 바로 실행할 수 없다.

관찰할 곳: pwd는 현재 폴더, ls는 파일, hostname은 호스트 이름을 보여준다. 호스트 이름만 같다고 같은 VM이 보장되지는 않으므로 접속 대상도 대조한다.

오해 확인: Python 파일이 있어도 서버를 실행하지 않았다면 요청을 받을 프로세스가 없다.

3. 클라이언트와 서버 — 요청을 기준으로 한 역할

이번 통신에서 curl은 요청을 시작하는 클라이언트이고 Python 프로그램은 요청을 받아 응답하는 서버다. “서버”는 기계를 가리킬 때도 있지만 여기서는 서버 프로세스를 뜻한다. 같은 호스트에서 두 역할을 수행할 수 있고, 어떤 프로그램은 다른 통신에서는 클라이언트 역할을 할 수도 있다.

먼저 생각하기: 클라이언트와 서버는 반드시 서로 다른 컴퓨터일까?

4. IP·포트·루프백 — 어느 위치의 어떤 통신인가?

IP 주소는 네트워크에서 통신 위치를 구분하는 주소다. 한 호스트에 여러 IP 주소가 있을 수 있으므로 주소 하나가 언제나 컴퓨터 한 대를 뜻하지는 않는다. TCP 포트는 그 주소에서 데이터를 보내거나 받는 지점, 즉 통신 끝점을 구별하는 번호다.

포트는 물리적인 케이블 구멍도, 프로세스의 식별 번호인 프로세스 ID도 아니다. 주소를 건물, 포트를 창구에 비유할 수 있지만 프로그램 하나가 여러 포트를 사용할 수도 있다. 아래 URL은 요청을 보낼 주소와 처리할 경로를 함께 적은 것이다. ? 뒤의 쿼리 매개변수는 서버에 추가로 전달하는 값이다.

먼저 생각하기: IP가 같으면 같은 프로그램일까?

같은 내용을 문자 그림으로 보기
http://127.0.0.1:8080/echo?message=hello
│      │         │    │    └ 쿼리 매개변수: message에 hello 전달
│      │         │    └ 경로: 이 서버에 어떤 처리를 요청하는가
│      │         └ 서버 TCP 포트
│      └ 목적지 IP: 명령을 실행하는 환경 자신의 루프백
└ HTTP 사용

같은 Linux 내부 / 설명용 임시 포트 51000
요청  127.0.0.1:51000 ───────> 127.0.0.1:8080
응답  127.0.0.1:51000 <─────── 127.0.0.1:8080

클라이언트의 임시 포트는 보통 운영체제가 고르므로 요청할 때마다 달라질 수 있다. 실제 값은 서버 로그의 client에서 요청한 쪽의 IP와 함께 확인한다. IP가 같더라도 포트 번호와 통신 방향을 보면 두 끝점을 구분할 수 있다.

서버가 요청을 기다리는 TCP 포트는 ss -lnt로 확인한다. 옵션 -l은 대기 중인 포트, -n은 숫자 표시, -t는 TCP를 뜻한다. 짧은 curl 연결은 조회 전에 끝날 수 있으므로 클라이언트의 임시 포트는 서버 로그나 캡처에서 찾는다.

루프백 127.0.0.1은 명령이 실행되는 네트워크 환경 자신을 가리킨다. 개인 PC에서 실행한 curl의 127.0.0.1과 SSH 뒤 Linux에서 실행한 curl의 127.0.0.1은 다른 곳이다. 이번 주는 컨테이너·별도 네트워크 네임스페이스를 사용하지 않는다.

오해 확인: 서버 포트 8080과 클라이언트 포트가 같을 필요는 없다.

자기 설명: 개인 PC에서 VM의 127.0.0.1 서버를 보겠다고 같은 URL을 입력하면 왜 다른 곳을 확인하게 되는가?

5. 프로토콜과 계층 — 서로 다른 질문을 나눠 다룬다

프로토콜은 통신 상대가 함께 따르는 메시지 형식과 처리 규칙이다. 계층은 통신에 필요한 일을 역할별로 나눠 이해하는 방법이다. 이번에는 HTTP·TCP·IP가 답하는 세 질문을 구분하고, 패킷을 관찰할 위치도 확인한다.

역할이번 예확인할 질문
응용HTTP어떤 요청을 했고 어떤 상태·본문을 받았나?
전송TCP두 끝점 사이 연결에서 데이터를 주고받았나?
인터넷IP어느 주소로 보냈나?
링크에 해당하는 전달이번에는 호스트 내부 lo어느 인터페이스에서 관찰했나?

먼저 생각하기: “통신 성공”이라고 하면 무엇이 성공한 걸까?

같은 내용을 문자 그림으로 보기
보내는 응용: HTTP 메시지
               ↓ TCP가 바이트 전달을 담당
               ↓ IP 주소를 사용
          이번에는 Linux 내부 루프백
               ↑ 받는 쪽에서 메시지 해석

TCP 연결이 성립해도 요청한 경로가 있을지는 HTTP 응답을 봐야 한다. HTTP 404를 받았다면 HTTP 메시지를 전달할 통신은 이루어진 것이다. 반대로 연결이 거부되었다면 이번 요청의 HTTP 상태가 없을 수 있다. 모든 HTTP 버전이 TCP를 쓰는 것은 아니지만 이 키트의 HTTP/1.1은 TCP를 사용한다.

OSI는 통신의 역할을 일곱 계층으로 나누어 설명하는 참조 모형이다. TCP/IP 모형은 실제 사용하는 프로토콜 묶음과 연결해 역할을 설명한다. 지금은 계층 이름을 모두 외울 필요가 없다. 정확한 계층 경계와 TCP 재전송은 나중에 배운다.

오해 확인: HTTP 오류와 IP 전달 실패는 같은 뜻이 아니다.

6. HTTP 요청·응답 — 각 줄이 뜻하는 것

HTTP 요청에는 무엇을 요청하는지, 응답에는 처리 결과가 담긴다. 먼저 요청 줄·헤더·빈 줄·본문을 구분해 보자. 헤더는 메시지를 읽는 데 필요한 정보이고, 본문은 전달하는 데이터다.

먼저 생각하기: hello를 again으로 바꾸면 요청 주소의 어느 부분과 응답의 어느 부분이 달라질까?

다음은 curl -v 형식을 단순화해 설명을 붙인 예시이며 실제 측정 결과가 아니다. >와 <는 curl의 방향 표시이며 HTTP 메시지 자체의 문자가 아니다. 버전·날짜·헤더 순서는 환경마다 다를 수 있다.

> GET /echo?message=hello HTTP/1.1    요청: 메서드 / 경로와 쿼리 / 버전
> Host: 127.0.0.1:8080               요청 헤더: 대상 호스트·포트
>
< HTTP/1.1 200 OK                    응답: 버전 / 상태 코드 / 설명
< Content-Type: application/json; charset=utf-8
< Content-Length: 20                본문 바이트 수 (문자 수와 다를 수 있음)
< Connection: close                 이 키트는 응답 뒤 연결을 닫음
<                                    빈 줄 뒤 본문
{"message": "hello"}                 JSON 형식의 데이터

GET은 이 실습에서 값을 요청하는 메서드, 즉 요청의 종류다. /echo는 서버 코드가 정한 경로이며 반드시 디스크 파일 이름은 아니다. 이 키트의 서버는 /echo 요청에는 200과 메시지를, 그 외 경로에는 404와 오류 본문을 돌려준다. JSON은 "message": "hello"처럼 이름과 값을 짝지어 데이터를 표현하는 형식이다.

서버 쪽의 설명용 로그:

{"event":"response","client":["127.0.0.1",51000],"path":"/echo?message=hello","status":200,"bytes":20}

client의 포트를 캡처에서 찾은 요청 출발지 포트와 맞춰 본다. path와 status는 curl 출력과 대조한다. 서버 로그는 서버 프로그램이 남긴 기록이고, 캡처는 선택한 네트워크 인터페이스에서 관찰한 기록이다. 둘은 서로 다른 증거이므로 한쪽 기록을 양쪽에 복사해 적지 않는다.

처음 curl -v 화면을 읽을 때는 *로 시작하는 연결 설명 → >로 시작하는 보낸 요청 → <로 시작하는 받은 응답 → 헤더가 아닌 본문 순서로 찾는다. 상세 설명과 헤더는 보통 표준 오류(stderr), 본문은 표준 출력(stdout)에 나와 한 화면에서 섞여 보일 수 있다. echo $?의 숫자는 HTTP 상태 줄이 아니라 curl 실행 결과다.

예측: hello를 again으로만 바꾸면 무엇이 바뀔까? 본문과 요청 주소의 쿼리 부분은 바뀌지만 서버 포트는 유지될 것으로 예상한다. 실제 임시 포트·시각은 실행 뒤 적는다.

오해 확인: HTTP 200만으로 다른 서비스의 모든 기능이 정상이라고 일반화하지 않는다.

7. 네 상태를 비교하는 방법

정상 응답, 없는 경로에 대한 404, 서버 중지 뒤 연결 실패, 재시작 뒤 복구를 비교한다. 아래 표는 코드와 명령으로 예상한 동작이다. 자신의 출력은 파일로 보관하고, 함께 설명·토론하며 예상과 달랐던 점을 짧게 남긴다.

먼저 생각하기: 404 응답을 받은 경우와 연결 자체에 실패한 경우에는 어떤 기록이 다를까?

조건HTTP 상태이 서버의 새 response 로그기본 curl 종료 코드의 기대
실행 중 /echo200있음전송 완료 시 0
실행 중 /missing404있음--fail 없는 전송 완료 시 0
서버 중지, 같은 URL응답 없음중지된 프로세스는 남기지 못함연결 거부라면 7, 시간 초과는 28
같은 포트로 재시작, /echo200있음전송 완료 시 0

화면에서 먼저 구별할 두 줄은 다음과 같다. 이것은 찾아볼 형태를 보여주는 예시이며 오류 문구와 헤더의 실제 표현은 환경에 따라 다르다.

없는 경로:     < HTTP/1.1 404 Not Found       ← 서버가 보낸 HTTP 응답
서버 중지 뒤:  curl: (7) Failed to connect... ← curl이 보고한 연결 오류; HTTP 상태 줄 아님

404에서는 응답 본문과 서버의 새 response 로그도 찾아본다. 서버 중지 뒤에는 새 응답 로그가 없고 < HTTP/ 상태 줄도 기대하지 않는다. 다만 연결 오류 하나만으로 서버 중지가 원인이라고 확정하지 않는다. 같은 호스트·주소·포트를 확인하고 재시작 후 같은 명령이 복구되는지 비교한다.

HTTP 상태는 서버가 보낸 응답의 값이고, 종료 코드는 도구가 셸에 보고하는 실행 결과다. 종료 코드는 curl 바로 다음 줄의 echo $?로 확인한다. 사이에 다른 명령을 실행하면 그 명령의 결과를 보게 된다. 선택 Node 클라이언트는 자체 정책으로 200을 0, 404를 2, 연결 오류를 1로 보고한다. 같은 통신이라도 도구의 종료 코드 정책은 다를 수 있다.

실패했을 때는 “서버가 없다”고 바로 결론 내리지 말고 바꾼 조건부터 확인한다. 셸 A에서 서버를 중지했는가? A와 B가 같은 호스트인가? URL과 서버 포트가 같은가? 재시작한 뒤 같은 요청에 다시 응답이 오는가? 조건 하나만 바꾸고 결과를 비교하면 원인을 더 분명하게 설명할 수 있다. 방화벽을 끄거나 다른 프로세스를 종료할 필요는 없다.
