# 1주차 CCNA 연계 연습 해설

요약: 외부 원문 3문항·자체 보충 2문항·사이트 인용 1문항의 자체 해설이다. HTTP·TCP·포트의 역할을 실습과 연결하며, 공식 해답이나 실제 수행 결과를 대신하지 않는다.

| --- | --- | --- |

## C4 — B

같은 IP라도 목적지 포트가 다르면 같은 대기 소켓을 가리키지 않는다. `ss -ltn`과 URL을 비교하고 8080으로 다시 요청한다.

- A: HTTP 경로보다 연결할 목적지 포트부터 확인한다.
- C: 8081은 URL의 포트이며 HTTP 상태 코드가 아니다.
- D: 같은 호스트 안에서도 요청하는 curl과 응답하는 서버 역할은 구별된다.

이 문제에는 서버 설정과 URL이 주어졌다. 일반 상황에서 오류 하나로 서버 중지나 포트 오타를 확정하지 않는다. 근거: [교재](CONCEPTS.md)와 [Linux 실습](../../labs/week-01/LINUX.md)의 주소·포트 확인.

## C5 — C

이번 HTTP/1.1 실험에서는 TCP를 통해 HTTP 응답을 받았다. 응용 계층의 404는 TCP 연결 실패와 구별한다.

- A: 상태 줄과 서버 로그라는 관찰에 맞지 않는다.
- B: 전송 성공은 요청한 자원의 존재나 응용 처리 성공을 보장하지 않는다.
- D: 이번 요청의 로그는 이후 요청 결과를 보장하지 않는다.

근거: [RFC 9110 §15.5.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.5.5)와 키트의 경로 분기. 일반 HTTP의 404에는 자원 존재를 공개하지 않으려는 경우도 있지만 이 문제는 키트의 없는 경로 상황이다.

## C6 — TCP와 UDP의 전달 특성

TCP는 연결 상태를 관리하며 순서를 지키는 신뢰성 있는 바이트 스트림을 제공한다. UDP 자체에는 전달·순서·중복 방지 보장이 없으며, 필요한 기능은 상위 프로토콜이나 응용이 구현할 수 있다. TCP도 영구적인 장애를 넘어 전달 성공을 보장하지는 않는다.

원문 보기 중에서는 B가 출제 의도에 가장 가깝다고 판단한다. 다만 UDP가 항상 더 빠르다는 표현은 일반 법칙으로 외우지 않는다. 실제 속도와 지연은 망 상태·구현·응용 요구사항에 달려 있다. 사이트의 표나 투표를 공식 정답으로 취급하지 않는다.

검토 근거: [RFC 9293 §2.2](https://www.rfc-editor.org/rfc/rfc9293.html#section-2.2), [RFC 768](https://www.rfc-editor.org/rfc/rfc768.html). 이번 주에는 키트의 HTTP/1.1이 TCP를 사용한다는 점만 연결하고, 재전송·흐름 제어·UDP 비교 실험은 4주차로 넘긴다.
