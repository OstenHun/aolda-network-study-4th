1주차 제공 캡처 분석 — 네 상태를 패킷에서 찾기

Windows 개발 환경에서 수집한 예제 pcapng로 200·404·연결 거부·복구의 패킷 근거를 찾는다. 직접 Linux 캡처와 구분하며, 이 파일의 번호와 포트를 자기 실습에 복사하지 않는다.

이 자료를 쓰는 때Wireshark에서 찾는 순서먼저 답하고 근거 확인하기개인 실습 기록에 옮길 때

이 자료를 쓰는 때

자기 Linux에서 lo 직접 캡처가 막혀도 패킷 읽기 활동은 진행한다. 예제 캡처 파일을 내려받아 Wireshark에서 열고, 관찰한 값은 개인 실습 기록이나 별도 증거 파일에 제공 예제 분석임을 표시한다. 팀 활동의 다룬 질문과 근거에는 확인한 파일·패킷 위치를 짧게 남긴다. 캡처를 열지 않고 아래 표만 읽은 경우에는 패킷 분석을 완료했다고 표시하지 않는다. 자기 Linux의 curl 출력과 이 Windows 캡처는 서로 다른 실행이다.

이 파일은 Windows 루프백에서 Python 서버와 선택 Node 클라이언트로 수집한 예제다. 서버 포트는 59995이며 Linux 실습 기본값 8080과 다르다.

Wireshark에서 찾는 순서

  1. week-01-local.pcapng을 저장해 Wireshark로 연다. 화면 위 표시 필터에 tcp.port == 59995를 넣는다. tcp.port == 8080은 자기 Linux 실습용이며 이 파일에서는 결과가 없다.
  2. 목록의 No. 열로 아래 표의 번호를 찾는다. Source/Destination은 모두 127.0.0.1이므로 포트와 화살표 방향도 함께 본다. 요청 쪽 임시 포트는 네 번의 시도에서 각각 59996·59997·59998·59999다.
  3. HTTP로 보이지 않으면 해당 TCP 패킷에서 Analyze → Decode As → HTTP를 선택해 포트 59995를 지정한다. 요청 패킷을 선택한 뒤 Follow → TCP Stream을 열면 그 연결의 요청과 응답을 이어서 볼 수 있다. 패킷 번호는 목록에서, 메시지 내용은 Stream과 패킷 상세에서 확인한다.
  4. 4→8, 17→21, 27→28, 32→36 순으로 확인한다. HTTP 헤더와 본문은 서로 다른 패킷에 표시될 수 있다. 아래 번호 하나가 HTTP 응답의 모든 바이트를 담는다는 뜻은 아니다.
상황 요청 쪽에서 찾기 상대 쪽에서 찾기 판단할 근거
정상 4: 59996 → 59995, GET /echo?message=hello 6: HTTP 200 헤더, 8: 200과 JSON 본문 요청 경로와 200 응답이 같은 포트 쌍에 있다
없는 경로 17: 59997 → 59995, GET /missing 19: HTTP 404 헤더, 21: 404와 오류 본문 서버가 응답했으므로 연결 실패가 아니다
서버 중지 뒤 27: 59998 → 59995, TCP SYN 28: 59995 → 59998, TCP RST/ACK 연결 거부이며 이 시도에는 HTTP 상태 줄이 없다
재시작 뒤 32: 59999 → 59995, GET /echo?message=again 34: HTTP 200 헤더, 36: 200과 JSON 본문 같은 서버 포트로 다시 응답을 받았다

RST만으로 어떤 프로세스를 누가 중지했는지는 알 수 없다. 이 자료의 서버 중지·재시작은 예제의 실행 조건이다. 실제 장애에서는 프로세스 상태와 로그도 함께 확인한다.

먼저 답하고 근거 확인하기

  1. 정상과 404의 클라이언트 임시 포트는 각각 무엇인가? 두 상태 모두 HTTP 응답을 받았다는 근거 번호를 하나씩 고른다.
  2. 404 시도에서 17번과 21번의 방향은 어떻게 다른가? 404를 서버에 연결할 수 없음으로 적어도 되는가?
  3. 중지 뒤 27번 다음의 28번은 어떤 TCP 표시를 갖는가? 이 시도에서 HTTP 404나 200을 찾을 수 있는가?
  4. 복구 시 서버 포트는 유지되는가? 메시지 값과 임시 포트는 정상 시도와 같은가?

확인 기준: 정상의 임시 포트는 59996, 404는 59997이다. 8번과 21번에서 각각 200·404 응답 본문을 확인할 수 있다. 17번은 클라이언트에서 서버로, 21번은 서버에서 클라이언트로 간다. 중지 뒤 28번에는 RST/ACK가 있고 HTTP 응답은 없다. 복구는 서버 포트 59995를 유지하지만 임시 포트가 59999이고 메시지는 again이다. 이 마지막 메시지 변경은 제공 예제의 조건이므로 자기 Linux E4의 기준 hello와 동일한 실행으로 합치지 않는다.

개인 실습 기록에 옮길 때

파일명, Windows 루프백 예제, 서버 포트 59995, 내가 확인한 패킷 번호·주소·양쪽 포트·HTTP 상태 또는 상태 없음, 직접 캡처가 막힌 이유를 적는다. 자기 Linux의 실제 포트·번호·출력 칸은 별도로 유지한다. 예제 분석은 패킷 읽기 증거가 되지만 자기 Linux 직접 캡처나 E1~E4 직접 실행의 증거는 아니다.
