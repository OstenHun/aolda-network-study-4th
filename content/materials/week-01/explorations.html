1주차 선택 탐구

진행 방식

먼저 예상하고, 과제의 비교 대상만 바꿔 실행하거나 같은 흐름을 다시 분석한다. 상세 명령·출력·패킷과 수정한 설명은 개인 실습 기록이나 별도 증거 파일에 추가한다. 함께 찾을 질문을 설명할 때 필요한 근거를 보여 준다. 추가 메모는 선택이다. 명령·설정을 바꾼 과제는 끝에 기준 상태로 돌아온다.

A. 도구의 성공 기준 — 10분

서버 실행 상태에서 기본 /missing 요청 뒤 종료 코드를 기록한다. 같은 curl 명령에 --fail만 추가하고 다시 비교한다. 상태가 404라는 사실은 같은데 종료 코드와 본문 출력은 어떻게 다른가? 곧바로 echo $?를 확인한다. 다른 옵션·URL은 유지한다.

예상 해설(실행 뒤 읽기): 기본 전송 완료는 0, --fail은 HTTP 오류에서 22를 반환하고 오류 본문 표시도 달라질 수 있다. 실제 출력으로 확인한다. curl의 --fail과 Exit codes 부분만 5분 읽는다.

B. 메시지 길이와 바이트 — 15분

ASCII 메시지 hello를 hellohello로만 바꿔 요청한다. JSON 본문과 Content-Length를 비교한다. 헤더를 포함한 전체 길이인가, 본문의 길이인가? 선택으로 URL의 message를 %ED%95%9C%EA%B8%80로 바꾸어 UTF-8 바이트와 눈에 보이는 글자 수의 차이를 본다. 이 문자열은 “한글”의 URL 인코딩이며 인코딩 계산은 필수가 아니다.

예상 해설: JSON 문법·공백도 본문 바이트에 포함된다. Content-Length는 문자 개수가 아니다. Python 서버의 protocol_version 설명을 5분 읽는다.

C. Node 출력과 curl 출력 — 20분

Node가 이미 준비된 경우만 키트 안내 (Markdown 원문)의 client.mts를 실행한다. 같은 200·404에서 connected/response/body와 curl 출력이 어떤 사실을 공통으로 보고하는지 표로 쓴다. Node의 404 종료 코드는 2이며 curl 기본 동작과 다르다. elapsed_ms를 순수 망 지연이라고 부르지 않는다. TypeScript 문법 공부나 설치를 위해 기본 실습을 중단하지 않는다.

D. 한 흐름을 더 깊게 읽기 — 15분

필수 정상 요청 한 흐름의 주소·포트·요청·응답을 이미 확인한 뒤, 자기 캡처 또는 제공 캡처에서 그 흐름의 패킷 목록과 Follow TCP Stream 표시를 비교한다. 화면의 메시지 전체가 한 패킷에 있다고 단정할 수 있는가? 헤더와 본문이 나뉘거나 재조립 표시가 있는지, 못 찾았다면 어디까지 보았는지도 기록한다. 시간이 남으면 404 흐름에도 같은 질문을 적용한다. Wireshark Follow Stream을 5분 읽는다. TCP 재전송·혼잡제어 계산은 후속 주차로 남긴다.
