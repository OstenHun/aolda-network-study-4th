# 경로표·다음 홉·왕복 경로

요약: 경로표에서 목적지와 일치하는 가장 긴 접두사를 고르고 다음 홉으로 전달한다. 각 라우터는 자기 표를 사용하며 응답에는 반환 경로가 필요하다. TTL과 traceroute는 도달성을 판단하는 일부 근거다.

## 경로를 배우는 일과 전달하는 일

2주차에는 주소가 어느 범위에 속하는지, 3주차에는 다음 홉의 MAC을 어떻게 찾는지 배웠다. 이번에는 목적지가 달라질 때 **어느 출구와 다음 홉을 고르는지** 읽는다. 인터페이스는 패킷을 내보내는 장치이고 다음 홉은 그 링크에서 다음으로 받을 IP 장비다.

라우팅 정보 학습·설정은 경로 후보를 얻는 일이다. 직접 연결 경로는 인터페이스의 주소/접두사에서 생기고, 정적 경로는 관리자가 지정한다. 동적 라우팅은 다른 장비와 정보를 교환해 경로를 배우며 10주차에 다룬다. **전달**(forwarding)은 패킷마다 현재 전달표에서 다음 홉을 골라 보내는 일이다. 경로를 배운 방법과 그 경로로 패킷을 전달하는 동작을 구별한다. 실제 장비의 라우팅 정보와 전달표가 표현상 분리될 수 있지만 여기서는 준비된 유효 경로 한 표를 읽는다.

## W07-K1 · 목적지에 맞는 가장 긴 접두사

**기억 문장: 같은 표의 유효 후보에서 목적지와 일치하는 접두사 중 가장 긴 것을 고른다.** `/24`는 앞 24비트를 비교하므로 `/16`보다 좁은 주소 범위다. 숫자가 커서 더 빠르다는 뜻은 아니다.

다음은 주소 계산용 가공 표다. 단일 IPv4 유니캐스트 표이며 정책 규칙·동일 접두사 경쟁·비활성 경로는 제외한다. 다음 홉은 각 해당 출력 링크에서 직접 도달 가능하다고 가정한다.

| 목적지 접두사 | 다음 홉/출구 | 범위 |
| --- | --- | --- |
| `0.0.0.0/0` | `192.0.2.1` / net0 | 모든 IPv4 주소 |
| `203.0.0.0/16` | `192.0.2.2` / net0 | `203.0.0.0`~`203.0.255.255` |
| `203.0.113.0/24` | `192.0.2.3` / net0 | `203.0.113.0`~`203.0.113.255` |
| `192.0.2.0/24` | 직접 연결 / net0 | `192.0.2.0`~`192.0.2.255` |

`203.0.113.20`은 `/0`, `/16`, `/24`와 일치하고 `/24`를 고른다. `203.0.114.20`은 위 `/24` 밖이므로 `/16`을 고른다. `198.51.100.20`은 `/0`만 일치한다. 기본 경로(default)는 더 구체적인 경로가 없을 때 쓰는 `/0`이다. 기본 경로가 반드시 인터넷 연결이거나 통신 성공이라는 뜻은 아니다.

일치하는 경로가 하나도 없고 기본 경로도 없다면 전달할 수 없다. `/24`가 선택된 뒤 실제 다음 홉이 응답하지 않는다고 언제나 덜 구체적인 `/16`으로 자동 재시도하는 것은 아니다. 메트릭은 접두사 길이와 다른 판단 요소다. 정책 라우팅·복수 표·경로 후보 설치·동일 접두사 선택은 이번 단일 표 가정 밖이다. [RFC 1812 §5.2.4.3 (1)(2)](https://www.rfc-editor.org/rfc/rfc1812.html#section-5.2.4.3)과 [실습 A](LINUX.md#linux-query)로 근거를 잇는다.

## W07-K2 · 왕복은 각 방향의 경로가 필요하다

**기억 문장: 내 경로표는 출발하는 다음 구간을 알려 주며 응답이 돌아오는 길까지 보장하지 않는다.** 다음은 시뮬레이터의 고정 구성이다. 모든 주소는 문서용 예제다.

```text
A 192.0.2.10/24
  │ LAN-A
R1 192.0.2.1/24
   198.51.100.1/30
  │ TRANSIT 198.51.100.0/30
R2 198.51.100.2/30
   203.0.113.1/24
  │ LAN-B
B 203.0.113.20/24
```

A는 다른 망인 B로 보낼 때 `192.0.2.1`을 다음 홉으로 고른다. R1은 `203.0.113.0/24 via 198.51.100.2`를, R2는 직접 연결된 LAN-B를 고른다. 응답의 목적지는 A다. B는 `203.0.113.1`로, R2는 `192.0.2.0/24 via 198.51.100.1`로, R1은 LAN-A로 보낸다. R2에서 이 정적 경로만 지우면 요청은 B까지 가도 응답은 R2에서 길을 잃는다. 이 구성의 R2에는 기본 경로가 없다.

| 구간 | IP 목적지 | Ethernet 목적 MAC을 찾을 상대 |
| --- | --- | --- |
| A→R1 | B `203.0.113.20` | R1의 LAN-A 인터페이스 |
| R1→R2 | B `203.0.113.20` | R2의 TRANSIT 인터페이스 |
| R2→B | B `203.0.113.20` | B |

일반적인 Ethernet 라우팅에서 들어온 프레임을 벗기고 다음 링크의 프레임으로 보낸다. 이 예제는 NAT·터널을 제외하므로 종단 출발/목적 IP는 유지되지만 IPv4 TTL·헤더 체크섬 등은 바뀐다. 모든 비트가 그대로라는 뜻은 아니다. ARP는 해당 링크의 다음 홉 주소를 알아내는 데 쓰며 멀리 있는 최종 서버의 MAC을 전체 경로에서 계속 쓰지 않는다. 시뮬레이터는 이웃 대응표를 미리 제공하므로 실제 ARP 패킷·MAC 갱신을 재현하지 않는다.

반환 경로는 요청 경로와 달라도 된다. 이 작은 선형 구성에서는 같은 두 라우터를 거꾸로 지나지만 일반 망의 대칭성을 보장하지 않는다. 반환 경로가 있어도 방화벽·서버 대기 상태 등은 따로 확인해야 한다. [실습 B](LINUX.md#simulator)에서 한 방향의 성공과 왕복 결과를 나눠 본다.

## W07-K3 · 홉·TTL과 관찰 한계

**기억 문장: TTL은 끝없이 순환하는 패킷의 수명을 제한하며 경로의 응답을 모두 보장하지 않는다.** IPv4 라우터는 전달할 때 TTL을 적어도 1 줄인다. 0이 되면 버린다. 일반적인 유니캐스트에서는 ICMP Time Exceeded를 보내지만 ICMP 오류 금지 조건·정책·제한 때문에 항상 보인다고 가정하지 않는다. TTL의 역사적 시간 의미와 오래 머문 패킷 처리는 [RFC 1812 §5.3.1](https://www.rfc-editor.org/rfc/rfc1812.html#section-5.3.1)에 있다. 여기서는 전달마다 1 감소하는 모형으로 읽는다. DNS 캐시의 TTL과 다른 필드다.

A가 초기 TTL 2로 B를 향해 보내면 R1에서 1, R2에서 0이 되어 B에 도착하지 못한다. TTL 3이면 R1에서 2, R2에서 1로 B에 도착한다. B의 응답은 별도 초기 TTL을 갖는 새 패킷이다. L2 스위치 하나를 지났다고 IPv4 TTL이 반드시 1 줄어드는 것은 아니다.

traceroute는 보통 초기 TTL을 1부터 늘리며 제한된 탐색 패킷을 보낸다. 중간 장비의 ICMP Time Exceeded와 목적지의 종료 응답을 보고 응답 주소·왕복 시간을 표시한다. Linux 기본 방식은 보통 UDP이며 ICMP/TCP 방식도 있다. 방식·포트·부하 분산·정책에 따라 실제 앱과 다른 경로/결과가 나올 수 있다.

`*`는 해당 탐색의 응답이 시간 안에 오지 않았다는 뜻이다. 중간 라우터가 전달은 하면서 ICMP를 제한하거나 응답의 반환 경로가 다를 수 있다. 연속 별표만으로 위치를 확정하지 않는다. 각 줄의 시간은 내 PC에서 해당 응답까지의 왕복 시간이며 바로 전 링크만의 지연이 아니다. `ip route get`은 로컬 커널의 경로 조회, traceroute는 탐색 응답 관찰, TCP/HTTP는 실제 서비스 확인이다. [가공 기록](LINUX.md#trace)과 [traceroute DESCRIPTION](https://man7.org/linux/man-pages/man8/traceroute.8.html#DESCRIPTION)을 대조한다.

## 핵심 3개·혼동 2개·개발 사례 1개

핵심은 W07-K1 최장 접두사, K2 왕복 경로, K3 TTL과 관찰 범위다. 위 절이 정의의 정본이다. 성립 조건과 반례까지 함께 설명한다.

| 혼동 | 조건을 붙인 설명 |
| --- | --- |
| “경로가 있으니 서비스가 된다” | 로컬 다음 홉 선택과 왕복 전달·정책·서비스 상태는 각각 확인한다 |
| “목적 IP가 멀리 있으니 그 MAC을 찾는다” | Ethernet에서는 선택한 다음 홉의 MAC을 해당 링크에서 찾는다 |

개발 사례 W07-D1~D3은 “TCP 연결이 안 된다 → 반환 경로 하나가 없다면? → 어떤 출력으로 가설을 구별할까?”다. [공동 질문](WORKSHEET.md)에서 탐색하고 [분리 해설](ANSWERS.md#development)로 확인한다. 다음 주에는 DNS→TCP→TLS→HTTP를 경로·캐시와 함께 연결한다. 동적 경로 학습과 OSPF 설정은 10주차로 넘긴다.
