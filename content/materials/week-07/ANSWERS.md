# 분리 해설 · 왕복 경로로 판단하기

요약: 복습의 필수 답안 요소·흔한 오답·확인 근거를 정리한다. 개발 질문은 경로 선택과 반환 경로를 구별하고 다음 진단으로 이어 간다. 예제 분석으로 직접 수행을 대신하지 않는다.

## Q1 · 일치하는 가장 긴 접두사

순서대로 `/24 via 192.0.2.3`, `/16 via 192.0.2.2`, `/0 via 192.0.2.1`이다. 목적지의 앞 비트가 일치하는 후보만 남긴 뒤 접두사 길이를 비교한다. `203.0.114.20`은 `203.0.113.0/24` 범위 밖이다. 흔한 오답은 기본 경로를 우선하거나 가장 작은 다음 홉 주소를 고르는 것이다. [W07-K1](CONCEPTS.md#longest-prefix)의 단일 유효 표 가정 안에서 판단한다.

## Q2 · 조회와 실제 전달

`via`는 다음 홉, `dev`는 출력 인터페이스, `src`는 선택한 출발 주소다. 직접 연결이면 via가 없을 수 있다. 조회는 패킷을 보내지 않아 다음 홉의 실제 응답·반환 경로·정책·서버 대기를 보장하지 않는다. 두 목적지가 같은 기본 경로를 쓰는 것은 정상일 수 있다. 출력 일치가 목적지 주소까지 같다는 뜻은 아니다. [ip-route get](https://man7.org/linux/man-pages/man8/ip-route.8.html#DESCRIPTION)과 본인 조회를 대조한다.

## Q3 · 종단 IP와 링크의 다음 홉

두 구간 모두 IP 목적지는 B다. A→R1의 프레임은 R1의 LAN-A MAC으로, R1→R2는 R2의 TRANSIT MAC으로 전달한다. 프레임의 출발 MAC도 해당 송신 인터페이스에 맞게 바뀐다. NAT·터널 없는 가정이며 IPv4 TTL·체크섬까지 고정이라는 답은 틀리다. 일반 L2 스위치 전달 자체는 라우터의 IP TTL 감소와 다르다. [왕복 구성](CONCEPTS.md#round-trip)·[3주차](../week-03/topics/03-next-hop.md)를 근거로 한다.

## Q4 · 요청이 도착해도 응답은 막힐 수 있다

A→R1→R2→B 요청은 도착한다. 응답은 B의 기본 경로로 R2에 도착하지만 R2에 A 범위의 경로·기본 경로가 없어 `NO_ROUTE`다. A의 표만 반복 조회해서는 원인을 다 볼 수 없다. `restore` 뒤 R2 표에 `192.0.2.0/24 via 198.51.100.1`이 돌아왔는지, 다시 probe해 양방향 전달과 `ROUND_TRIP OK`가 보이는지 모두 확인한다. [실습 B](LINUX.md#simulator)의 실제 본인 출력이 직접 수행 근거다.

## Q5 · 라우터 두 대를 지나는 TTL

초기 2는 R1에서 1, R2에서 0이 되어 폐기된다. 초기 3은 R1에서 2, R2에서 1이 되어 B에 도착한다. 응답은 새 패킷의 별도 초기 TTL로 시작한다. DNS TTL은 캐시 유효 시간이며 IP 홉 수 제한과 다른 값이다. 실제 ICMP가 항상 보인다는 답은 피한다. 시뮬레이터는 전달당 1 감소만 모델링하며 ICMP를 보내지 않는다. [W07-K3](CONCEPTS.md#ttl)에서 조건을 확인한다.

## Q6 · 별표가 허용하는 결론

확실한 사실은 해당 TTL의 탐색에 제한 시간 안에 응답을 받지 못했다는 것이다. 홉 2 장비 단절, 전체 TCP/HTTP 실패, 모든 패킷의 동일 경로를 확정할 수 없다. 중간 응답 제한·반환 경로·분산 등을 구별할 추가 관찰이 필요하다. 각 시간은 별도 탐색의 왕복 시간이며 차이 3.6ms가 한 링크의 지연이라고 단정할 수 없다. [제공 분석](LINUX.md#trace)·[traceroute 설명](https://man7.org/linux/man-pages/man8/traceroute.8.html#DESCRIPTION)을 근거로 한다.

## Q7 · 정적 설정과 패킷 전달

정적 설정은 관리자가 경로 정보를 넣는 일, 전달은 현재 표에서 패킷의 다음 홉을 고르는 일이다. 경로 학습 방식이 달라도 전달 판단이 필요하다. 더 구체적인 유효 경로가 선택된 뒤 다음 홉이 실패했다고 덜 구체적인 경로로 반드시 재시도하지 않는다. 경로 설치/활성 상태·정책·장비 구현을 구별해야 한다. 시뮬레이터는 ARP·실제 ICMP·큐잉·정책·NAT·동적 경로 학습 등을 생략한다. 단순 모형을 실제 커널과 같다고 설명하지 않는다.

## Q8 · 근거와 수행 범위

Linux는 두 목적지와 `get`의 via/dev/src 또는 경로 부재를, 시뮬레이터는 변경 전후 표·요청 도착/반환 실패·복구 뒤 왕복 성공을 짚는다. 제공 출력만 읽었다면 분석만 확인하고 직접 실행은 보충한다. 복구 후에도 실패하면 같은 프로세스에서 원본 구성을 복구했는지 표를 먼저 비교하고, 정방향/반환 중 어느 단계가 실패했는지 출력으로 나눈다. 원본 재다운로드·재실행 후에도 실패하면 환경/명령을 확인하고 실제 OS 경로를 임의로 바꾸지 않는다.

## 개발 질문 W07-D1~D3

**D1 원리:** 이름·인증서가 맞아도 연결 도달성이 보장되지 않는다. 클라이언트 선택 경로·다음 홉·목적지 쪽 대기/정책·반환 경로를 서로 다른 근거로 확인한다. 본인 경로 조회만으로 전체 왕복을 확정하는 것이 흔한 오답이다.

**D2 조건 변경:** R2 반환 경로 한 항목만 삭제하면 요청은 B에 도착해도 왕복은 실패한다. 노드마다 응답의 목적지 A를 기준으로 다시 조회한다. 복구는 표와 왕복 결과로 확인하며 “삭제했으니 정방향도 모두 실패”라고 뭉뚱그리지 않는다.

**D3 다음 진단:** 중간 별표만 있으면 응답 제한/반환 경로와 실제 전달 장애 가설을 나눈다. 허가된 환경에서 양끝 출력·경로표·서비스 로그를 비교하고 필요하면 탐색 방식을 확인한다. TCP 연결 전 실패와 TLS 이름 검증 실패·HTTP 오류를 [6주차](../week-06/CONCEPTS.md)처럼 단계별로 구별한다. 권한 없는 장비 설정 변경은 다음 관찰이 아니다.

## 확인 범위와 다음 복습
