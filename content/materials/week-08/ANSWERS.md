# 8주차 분리 해설 · 조건과 근거

요약: RTT 계산의 가정, 세 전송 모형의 수신 규칙, IPv6 관찰 범위로 답을 확인한다. C08 진단은 정답 문장보다 최초 가설·구별 근거·재현·복구를 보며 해설 노출과 직접 수행을 구별한다.

[문제](REVIEW.md)를 먼저 풀고 읽는다. 아래 자체 해설은 실제 기업 기출이나 참가자의 수행 결과가 아니다. 핵심 정의는 [교재 W08-K1\~K3](CONCEPTS.md)가 소유한다.

## Q1 · 전체 흐름

주소·다음 홉/왕복 경로 준비→DNS 주소 찾기→TCP 연결→TLS 신원 검증/보호 준비→HTTP 요청/응답이다. DNS 캐시만 있으면 주소 찾기 비용을 생략하되 새 TCP/TLS는 필요하다. 같은 origin의 사용 가능한 TLS 연결을 재사용하면 해당 요청을 위한 DNS/TCP/TLS 준비 없이 HTTP를 보낼 수 있다. 필수 요소는 각각 무엇을 확인하는지와 재사용 조건이다. DNS 성공을 서비스 성공으로 쓰는 답은 보충한다. [K1](CONCEPTS.md#request-flow).

## Q2 · RTT 계산

(a) D+3R=30+180=**210ms**, (b) 3R=**180ms**, (c) R=**60ms**, (d) **추가 네트워크 왕복 0회**다. (d)를 실제 총 지연 0ms로 쓰지 않는다. 시작/끝은 요청 직전부터 첫 응답 바이트까지이며 로컬 캐시 사용은 네트워크 요청 자체를 생략하는 별도 경우다. DNS 전체 비용 D와 서버 RTT R을 구별하고 TLS 1.3 전체 핸드셰이크·클라이언트 관점·순차 단계 가정을 밝혀야 한다. 처리/본문 전송·손실·ARP/NDP 등은 제외한다. TLS 재개/0-RTT·HTTP/3의 일반 공식으로 쓰지 않는다.

## Q3 · 캐시와 연결

304는 재검증 요청에 대한 네트워크 응답이므로 이 조건에서는 1R이 든다. 저장한 본문을 다시 쓸 수 있어도 요청 왕복은 했다. 신선한 저장 응답을 재검증 없이 사용하는 경우와 구별한다. DNS TTL은 저장한 이름/주소 정보의 유효성과 관련되며 이미 열린 연결을 그 시점에 자동 종료하는 타이머가 아니다. 연결 재사용 가능성은 별도로 확인한다. [K1](CONCEPTS.md#request-flow), [6주차 캐시](../week-06/CONCEPTS.md#캐시-재검증은-응답-내용을-다시-받을지-묻는다).

## Q4 · 손실 1

stop-and-wait `{1}`: 1을 확인하기 전 2·3은 아직 보내지 않았다. GBN `{1,2,3}`: 순서 밖 2·3을 버렸고 ACK 0만 돌아와 1 이후가 미확인이다. SR `{1}`: 2·3을 버퍼에 보관하고 개별 ACK를 보냈으므로 1만 보낸다. 1이 와야 보관한 2·3도 순서대로 위에 전달한다. 필수 요소는 집합과 그 이유다. stop-and-wait의 2·3을 재전송으로 세면 틀리다. 실제 TCP ACK는 다음 기대 바이트를 누적으로 나타내므로 패킷 단위 ACK n과 수치까지 같게 읽지 않는다. TCP=GBN/SR로 단정하지 않는다. [K2](CONCEPTS.md#reliable-models).

## Q5 · 손실 3

세 모형 모두 `{3}`이다. 앞의 0\~2는 확인됐고 GBN에서도 뒤에 미확인 전송이 더 없다. SR이 언제나 엄격히 적은 재전송을 한다는 결론은 반례로 깨진다. 재전송 수·버퍼/타이머 비용·전체 완료 시간은 다른 비교 항목이며 이 한 시간축으로 실제 TCP 성능을 판정하지 않는다.

## Q6 · IPv6

접두사는 `2001:db8:8:1::/64`이며 `2001:db8:8:2::20`은 포함되지 않는다. `::1/128`은 같은 호스트의 루프백, `fe80::1`은 링크 로컬 범위의 예, `::/0`은 IPv6 기본 경로다. IPv4 Ethernet ARP와 IPv6 ICMPv6 NDP를 구별한다. L1/L2는 같은 호스트 Echo이며 이웃 NS/NA나 외부 경로를 검증하지 않는다. E1/E2는 가정한 같은 링크 이웃의 NS/NA다. 이웃 표·NS/NA·Echo를 각각 구분하고 가공 trace를 본인 캡처로 쓰지 않는다. 주소 접두사 계산만으로 실제 on-link/도달성을 보장한다고 쓰면 보충한다. [K3](CONCEPTS.md#ipv6).

## Q7 · 최초 진단을 확인하는 기준

정답은 받은 단일 조건에 따라 다르다. HTTP 404가 있다면 해당 요청의 HTTP 응답을 받은 것이며 잘못된 경로 등을 조사한다. 연결 거부라면 HTTP 응답 전 실패이므로 실제 요청 포트와 서버 listener를 대조한다. 이것만으로 서버 중지와 다른 포트 요청을 구별할 수는 없다. 서버 로그 부재도 단독 원인 확정은 아니다. 최소 두 가설과 둘을 가르는 관찰을 실제 출력에서 짚어야 한다. [실습 B](LINUX.md#diagnosis)의 최초 진단 시점과 해설/도움 노출을 구분한다. 제공 분석만이면 독립 직접 진단 완료가 아니다.

## Q8 · 재현과 복구

본인 테스트 서비스/요청 한 조건을 바꾸어 동일 증상→정상 조건 복귀→정상 URL 200·본문·서버 로그→본인 서버 종료/대기 해제를 확인한다. 포트 불일치를 재현하면서 서버와 URL을 함께 바꾸면 비교 조건이 사라지므로 재검토한다. 남의 프로세스를 종료하거나 정책/관리 경로를 고친 것은 이 실습 범위가 아니다. 이 평문 루프백 HTTP로 DNS 질의·TLS 신원·외부 왕복 경로까지 검증했다고 쓰지 않는다. 최초 진단은 독립이어도 재현 때 도움을 받았다면 그 항목은 도움 후 보충 필요로 나눈다.

## W08-D1\~D3 · 설명→조건 변경→진단

**D1:** 첫 요청의 D+3R과 같은 TLS 연결에서의 R을 비교한다. 주소 찾기·연결 준비·보호 준비·요청 응답의 교환과 생략 이유를 설명한다. “두 번째니까 빠르다”만으로는 부족하다.

**D2:** DNS 주소는 남고 연결이 닫혔다면 새 TCP/TLS가 필요해 3R이다. 신선한 HTTP 저장 응답 사용이 허용되면 추가 네트워크 왕복이 없을 수 있다. 304 재검증과 로컬 캐시 사용은 다르다.

**D3:** 실패가 이름 해석·TCP 연결·TLS 검증·HTTP 응답 중 어디에서 관찰됐는지 먼저 나눈다. 본 사례의 404/연결 거부는 HTTP 상태·종료 코드·대기 포트·실제 URL·서버 로그로 가른다. [5주 DNS/Host](../week-05/LINUX.md), [6주 TLS 이름](../week-06/LINUX.md#tls-lab), [7주 반환 경로](../week-07/LINUX.md#simulator)는 다른 가능한 진단 근거이며 모두를 이번에 직접 수행했다고 쓰지 않는다.

## C08 결과의 범위

전체 흐름/RTT·전송 모형·IPv4/IPv6·독립 단일 장애 진단을 각각 확인한다. 상태는 독립 확인/도움 후 보충 필요/미확인으로 나눈다. 정답을 읽은 사실·짝의 설명·과거 실습 완료가 이번 새 조건의 독립 수행을 대신하지 않는다. 제공 분석이 허용된 IPv6 trace와 직접 수행이 필요한 장애 재현의 범위를 구별한다. 새 팀 기록이나 추가 발표를 요구하지 않는다.
