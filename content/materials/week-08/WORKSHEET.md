# 함께 찾을 질문 · 같은 주소를 다시 열면

요약: 캐시와 열린 연결의 조건으로 HTTPS 흐름을 설명한다. 공식 지정 절을 함께 읽고 한 명이 설명한 뒤 조건을 바꾼다. 손실 모형·IPv6 비교와 각자의 C08 단일 장애 진단으로 확인한다.

## 먼저 이전 개념으로 예상하기

DNS가 주소를 돌려줬는데 TCP가 실패했다면 무엇이 아직 미확인인가? [5주차](../week-05/CONCEPTS.md)·[7주차](../week-07/CONCEPTS.md)에서 이름·왕복 경로를 다시 본다. 4주차의 ACK가 앱 성공을 뜻하는지도 말해 본다. [학습 홈](README.md) · [핵심 3개](CONCEPTS.md).

## 중심 질문 · W08-D1

**같은 HTTPS URL을 두 번째 요청할 때, DNS→TCP→TLS→HTTP 중 어떤 교환이 필요할까?** 첫 요청은 DNS 캐시·HTTP 캐시·열린 연결이 없고, 두 번째는 같은 origin의 TLS 연결이 사용 가능하다. 두 번째에 쓸 신선한 HTTP 저장 응답은 없다고 가정한다. [교재의 D=20ms, R=80ms 조건](CONCEPTS.md#request-flow)에서 각 요청 비용과 생략 이유를 설명한다.

함께 [RFC 8446 §2 그림 1](https://www.rfc-editor.org/rfc/rfc8446.html#section-2)의 ClientHello→서버 flight→Finished/응용 데이터 순서와 [RFC 9111 §4](https://www.rfc-editor.org/rfc/rfc9111.html#section-4)의 저장 응답 사용 조건을 찾는다. flight는 한쪽이 연속해 보내는 메시지 묶음이다. 공식 전체 문서를 읽기보다 이 두 판단에 필요한 부분을 찾는다. 한 사람이 시간축으로 설명한 뒤 다른 사람이 아래 조건 하나를 바꾼다.

## 조건 변경 · W08-D2

**DNS 캐시는 남아 있지만 열린 연결이 닫혔다. HTTP 저장 응답도 없다면 어디부터 다시 할까?** 반대로 신선한 저장 응답으로 처리할 수 있으면 어떨까? “두 번째라서 빠르다” 대신 어떤 교환을 센 것인지 말한다.

## 다음 관찰 · W08-D3

**DNS 응답 뒤 요청이 실패했다. 서버 중지와 HTTP 경로 오류를 무엇으로 구별할까?** 클라이언트 종료 코드·HTTP 상태·서버 대기 포트·요청 로그 가운데 어떤 순서로 볼지 이유를 붙인다. [실습 B](LINUX.md#diagnosis)에서는 정답을 가린 사례 하나를 각자 확인한다. 답은 먼저 읽지 않고 [분리 해설](ANSWERS.md#development)에서 나중에 대조한다.

## 보조 질문 · 필요할 때 선택

- [손실 시간축](CONCEPTS.md#reliable-models)에서 1 대신 마지막 3만 손실되면 GBN/SR의 재전송 집합은 어떻게 달라질까? 창·ACK·타이머 가정은 유지한다.
- `::1` 요청이 성공했는데 외부 IPv6가 된다고 말할 수 있을까? [IPv6와 관찰 범위](CONCEPTS.md#ipv6)에서 주소·링크·경로의 조건을 찾는다.

질문마다 설명자를 교대하며 다른 사람도 짧은 계산·출력 해석·조건 변경을 한다. 모든 보조 질문을 별도 발표로 만들지 않는다. 자세한 명령·출력은 개인 파일에 한 번 보관한다.

## C08을 기존 활동 안에서 확인하기

전체 흐름 그림과 RTT 계산, 세 전송 모형, IPv4/IPv6 비교를 [복습 Q1\~Q6](REVIEW.md)에서 확인한다. 정답을 숨긴 단일 장애 진단·재현은 [실습 B와 Q7\~Q8](LINUX.md#diagnosis)에서 한다. 개별 설명은 기존 활동의 2분 설명으로 나누고 새 발표를 추가하지 않는다. 해설 노출·도움 여부, 제공 분석·직접 실행을 구별한다.
