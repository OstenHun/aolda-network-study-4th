# 전체 요청·신뢰 전송·IPv6 교재

요약: 요청마다 필요한 단계는 캐시와 연결 상태에 따라 달라진다. 손실 복구의 교육 모형을 ACK·버퍼 조건으로 비교하고 IPv6의 주소·범위·이웃 탐색을 IPv4와 구별한다.

## 출발 전에 갖춰진 것

주소와 접두사, 다음 홉·왕복 경로가 준비돼 있어야 한다. DHCP로 주소를 받았더라도 HTTP 요청마다 DHCP 임대를 다시 얻는 것은 아니다. Ethernet에서 다음 홉의 링크 주소가 필요할 수 있지만 이웃 캐시가 있으면 매번 ARP/NDP 교환이 보이지 않는다. [5주차](../week-05/CONCEPTS.md)와 [7주차](../week-07/CONCEPTS.md)의 관찰 범위를 다시 쓴다.

## W08-K1 · 캐시와 열린 연결이 필요한 단계를 바꾼다

**기억 문장: 같은 URL이라도 DNS 캐시·HTTP 캐시·열린 연결은 각각 다른 비용을 생략한다.** DNS는 이름에서 주소를 찾고, TCP는 연결을 만들며, TLS는 신원과 보호 조건을 확인한다. HTTP는 그 연결 위에서 자원을 요청한다. DNS 성공이 TCP/TLS/HTTP 성공을 보장하지 않는다.

```text
주소·경로 준비
  → DNS: 이름의 주소 찾기 (사용할 캐시가 없다면)
  → TCP: 주소·포트로 연결 (쓸 수 있는 연결이 없다면)
  → TLS: 신원 검증·보호 준비 (새 HTTPS 연결이라면)
  → HTTP: 요청·응답 (신선한 저장 응답으로 처리할 수 없다면)
```

이 시간축은 **TCP 기반 HTTPS, HTTP/1.1, TLS 1.3 전체 핸드셰이크**의 자체 계산 모형이다. 시작은 이름으로 작은 객체 하나를 요청하기 직전, 끝은 첫 응답 바이트 수신이다. 주소·경로는 준비됐고 DNS 비용 D=20ms, 서버 RTT R=80ms가 주어진다. DNS 비용은 재귀 과정 전체를 합쳐 주어진 값이며 R과 같을 필요가 없다. TLS 재개·0-RTT·HelloRetryRequest·프록시·병렬 전송·손실·처리·본문 전송·ARP/NDP 비용은 제외한다.

```text
0ms     DNS 시작
20ms    주소 확보 → TCP SYN
100ms   SYN-ACK 수신 → ACK와 TLS ClientHello 전송
180ms   TLS 서버 flight 수신·검증 → Finished와 HTTP 요청 전송
260ms   첫 HTTP 응답 바이트 수신
```

TCP 준비를 클라이언트가 SYN-ACK를 받아 마지막 ACK를 보낼 수 있는 시점까지 1R로 센다. 서버의 ESTABLISHED 시점과 혼동하지 않는다. TLS 1.3에서 클라이언트가 서버 flight를 받은 뒤 Finished와 요청을 함께 보낼 수 있다는 가정으로 TLS 준비 1R, 요청/첫 응답 1R을 더한다. [RFC 8446 §2 그림 1](https://www.rfc-editor.org/rfc/rfc8446.html#section-2)과 [4주차 연결 시간](../week-04/CONCEPTS.md), [6주차 비용](../week-06/CONCEPTS.md#request-cost)을 잇는다.

| 요청 직전 조건 | 추가 네트워크 대기 모형 | D=20ms, R=80ms |
| --- | --- | --- |
| DNS 캐시 없음·새 연결·HTTP 캐시 없음 | D+3R | 260ms |
| 사용할 DNS 주소 있음·새 연결·HTTP 캐시 없음 | 3R | 240ms |
| 같은 origin의 사용 가능한 TLS 연결 있음·HTTP 캐시 없음 | R | 80ms |
| 재사용이 허용된 신선한 HTTP 저장 응답으로 처리 | 0회 네트워크 왕복 | 로컬 처리까지 0ms라는 뜻은 아님 |
| 열린 TLS 연결·저장 응답 재검증 필요 | R | 304여도 80ms |

DNS 캐시만 있어도 TCP/TLS 수립은 필요할 수 있다. 반대로 열린 연결을 실제로 재사용하면 보통 그 요청을 위해 DNS를 다시 찾지 않는다. DNS TTL 만료가 열린 연결을 즉시 끊는다는 뜻도 아니다. 캐시 사용 여부·연결 재사용 가능 여부를 명시한 조건에서만 계산한다. HTTP 재검증의 304는 네트워크 요청에 대한 응답이며 로컬 캐시 적중과 다르다. [RFC 1034 §3.6](https://www.rfc-editor.org/rfc/rfc1034.html#section-3.6), [RFC 9111 §4·§4.3](https://www.rfc-editor.org/rfc/rfc9111.html#section-4).

## W08-K2 · 재전송 범위는 ACK와 버퍼 규칙에 달린다

**기억 문장: 같은 데이터 하나가 사라져도 무엇을 확인하고 보관했는지에 따라 다시 보낼 범위가 달라진다.** 4주차의 번호·ACK(수신 확인)·타이머를 재사용한다. 타이머가 끝났다는 사실만으로 데이터와 ACK 중 무엇이 사라졌는지 확정할 수 없다.

다음은 자체 제공 모형이다. 데이터 단위 번호 0·1·2·3 중 **1의 첫 전송만 손실**되고 ACK는 손실되지 않는다. 순서가 바뀌는 다른 원인은 없다. 파이프라이닝 창은 4이며 네 단위를 먼저 보낸다. 번호 순환·체크섬 오류·혼잡 제어·빠른 재전송은 제외한다. ACK 0의 귀환 뒤 1의 복구 타이머가 끝나도록 충분히 기다린다. SR의 2·3 ACK는 각 타이머 만료 전에 온다. 시간축의 간격은 실측 시간이나 같은 완료 시간을 뜻하지 않는다.

| 규칙 | stop-and-wait | Go-Back-N (GBN) | Selective Repeat (SR) |
| --- | --- | --- | --- |
| 미확인 전송 | 한 단위 | 창 안에서 여러 단위 | 창 안에서 여러 단위 |
| ACK n 의미 | n을 받음 | n까지 연속 수신 | n 자체를 받음 |
| 순서 밖 2·3 수신 | 1 확인 전에는 아직 안 보냄 | 보관하지 않고 버림 | 창 안의 2·3을 버퍼에 보관 |
| 타이머 | 현재 단위 | 가장 오래된 미확인 단위 기준 하나 | 미확인 단위별 |

```text
stop-and-wait
송신 0 → 수신 0 → ACK 0 → 송신 1 ×
  → 1 타이머 만료 → 재전송 1 → ACK 1
  → 처음 전송 2 → ACK 2 → 처음 전송 3 → ACK 3

GBN (창 4)
송신 0,1,2,3 → 수신 0, [1 손실], 2·3 버림
  ← ACK 0, ACK 0, ACK 0
  → 1의 타이머 만료 → 미확인 1,2,3 재전송
  ← ACK 1, ACK 2, ACK 3

SR (창 4)
송신 0,1,2,3 → 수신 0, [1 손실], 2·3 보관
  ← ACK 0, ACK 2, ACK 3
  → 1 타이머 만료 → 1만 재전송
  ← ACK 1 → 보관한 2·3까지 순서대로 위에 전달
```

재전송 집합은 차례로 `{1}`, `{1,2,3}`, `{1}`이다. stop-and-wait에서 뒤의 2·3은 첫 전송이다. SR은 2·3을 수신·ACK했어도 순서 있는 상위 전달은 1을 기다린다. 이 조건에서 SR이 중복 전송을 줄인다는 것과 모든 환경에서 가장 빠르다는 주장은 다르다. 버퍼·타이머 관리 비용과 다른 손실 조건도 있다. [제공 원문](../../labs/week-08/loss-timeline.txt)을 내려받아 송신/수신 사건을 대조한다.

이 모형은 [Kurose·Ross 3.4](https://gaia.cs.umass.edu/kurose_ross/videos/3/)의 신뢰적 전송 학습 범주를 따른다. **실제 TCP는 바이트 번호와 누적 ACK를 사용하며 위의 패킷 번호 ACK와 다르다.** TCP의 선택 확인·빠른 손실 복구 같은 추가 동작을 고려하지 않고 “TCP=GBN” 또는 “TCP=SR”로 외우지 않는다. TCP ACK는 앱 처리·DB 저장의 확인이 아니다. [RFC 9293 §3.4](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.4). 창 크기의 처리량 계산은 14주차로 넘긴다.

## W08-K3 · 주소 범위와 이웃 탐색을 IPv6로 다시 읽는다

**기억 문장: IPv6에서도 목적지와 다음 홉을 구별하지만 주소 표기와 이웃 탐색 프로토콜이 다르다.** IPv4는 32비트, IPv6는 128비트 주소다. IPv6는 16비트씩 여덟 묶음을 16진수로 적고 `:`로 나눈다. 각 묶음의 앞 0을 생략할 수 있고 연속된 0 묶음은 `::`로 한 번만 줄인다.

```text
2001:0db8:0008:0001:0000:0000:0000:0010
                    ↓ 같은 주소
2001:db8:8:1::10/64
접두사: 2001:db8:8:1::/64 (앞 64비트)
```

`2001:db8:8:1::20`은 위 /64에 포함되며 `2001:db8:8:2::20`은 포함되지 않는다. 접두사 포함 계산만으로 실제 on-link 판단·도달성을 확정하지 않는다. Linux의 경로/인터페이스 조건을 함께 본다. /64는 이 예제의 접두사이며 모든 IPv6 경로가 /64인 것은 아니다. [RFC 4291 §2.2·§2.3](https://www.rfc-editor.org/rfc/rfc4291.html#section-2.2). `2001:db8::/32`는 문서용 주소다. 실제 외부 요청 대상으로 사용하지 않는다. [RFC 3849 §2](https://www.rfc-editor.org/rfc/rfc3849.html#section-2).

| 비교 | IPv4 | IPv6 |
| --- | --- | --- |
| 자기 자신 | 127.0.0.1 (127/8 루프백 범위 중 예) | ::1/128 |
| 링크 로컬 범위 | 169.254.0.0/16 | fe80::/10, 다른 링크로 라우팅하지 않음 |
| 기본 경로 | 0.0.0.0/0 | ::/0 |
| Ethernet 이웃 주소 확인 | ARP | ICMPv6의 NDP |

루프백과 링크 로컬을 같은 통신 범위로 보지 않는다. `::1`은 같은 호스트, `fe80::...`는 특정 링크의 이웃에 쓰며 어떤 인터페이스인지 구별해야 할 수 있다. `::`는 미지정 주소로 `::1`과 다르다. IPv6 주소가 보이거나 AAAA 레코드가 있다는 것만으로 외부 IPv6 통신 성공이 확인되는 것은 아니다. [RFC 4291 §2.5.2·§2.5.3·§2.5.6](https://www.rfc-editor.org/rfc/rfc4291.html#section-2.5.6), [IPv4 링크 로컬 RFC 3927 §1](https://www.rfc-editor.org/rfc/rfc3927.html#section-1).

NDP(Neighbor Discovery Protocol)는 같은 링크의 이웃과 라우터를 찾고 도달 상태를 확인하는 IPv6 기능 묶음이다. 주소 확인에 Neighbor Solicitation(NS)·Neighbor Advertisement(NA)를 쓰며 Ethernet에서는 이웃의 링크 주소를 알아낸다. ARP의 이름만 바꾼 것은 아니다. 라우터·접두사 발견 등 역할도 포함한다. 루프백 `::1` 통신에서 실제 Ethernet 이웃의 NS/NA를 요구하지 않는다. [RFC 4861 §3·§3.1](https://www.rfc-editor.org/rfc/rfc4861.html#section-3), [실습 A](LINUX.md#ipv6-lab).

## 혼동 두 가지와 개발 사례

| 혼동 | 조건을 붙인 설명 |
| --- | --- |
| DNS 캐시·연결 재사용·HTTP 캐시는 모두 같은 생략이다 | 주소 찾기·연결 준비·응답 재사용을 각각 나눈다. 304는 요청 왕복이 필요하다 |
| 교육 모형과 제한된 관찰로 실제 동작 전체를 단정한다 | TCP를 GBN/SR과 같다고 하지 않고, ::1 성공으로 Ethernet NDP·외부 IPv6까지 확인했다고 하지 않는다 |

W08-D1\~D3은 “같은 주소의 두 번째 HTTPS가 무엇을 생략할까 → 연결만 끊기면? → 실패 단계를 가를 근거는?”이다. [공동 질문](WORKSHEET.md)과 [분리 해설](ANSWERS.md#development)을 연결한다. 다음 주에는 IP 경로가 같아도 링크의 VLAN·전달 상태가 달라질 수 있는지를 묻는다.
