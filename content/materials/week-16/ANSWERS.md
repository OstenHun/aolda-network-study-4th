# 16주차 분리 해설 · 관찰이 지지하는 결론

요약: 복습과 개발 질문의 필수 답안 요소·흔한 오답·근거를 연결한다. 계산은 가정에 따른 자체 검산이며 실측이 아니다. 이 해설은 실제 주입 장애의 정답 카드나 참가자의 독립 이해 증명이 아니다.

## Q1 · 표현 대신 원인을 다르게 고른다

두 문장은 대체로 서버 부재라는 같은 원인을 가리킨다. 예를 들어 ‘원래 대상에 대기하는 서버가 없다’와 ‘HTTP 서버에는 연결됐지만 요청 경로가 다르다’를 비교할 수 있다. 앞 가설은 연결 실패·리스너 부재를, 뒤 가설은 HTTP 응답·해당 경로 로그를 예상한다. 상태·본문·리스너·로그의 관찰 위치를 맞춘다. 이 예시가 실제 주입 원인이라는 뜻은 아니다.

필수 요소는 원인이 다른 두 설명과 서로 다른 예상이다. ‘ping을 해 본다’만 말하고 HTTP 실패 원인을 전부 구별했다고 하면 부족하다. [K1](CONCEPTS.md#W16-K1)·[실습 A2](LINUX.md#diagnosis).

## Q2 · 기록 부재와 요청 부재는 다르다

확인된 것은 선택한 로그에 해당 기록이 없다는 사실이다. 실제 대상 호스트/프로세스·출력 파일·필터·단계 구간이 맞는지, 코드가 어느 시점에 로그를 찍는지 확인한다. 현재 Handler는 응답 쓰기 뒤 로그를 찍으므로 그 전 실패도 고려한다. 클라이언트의 주소/포트/경로와 서버 리스너를 먼저 대응하고, 필요하면 허가된 해당 위치의 패킷/다른 로그를 본다. 로그가 없다는 이유만으로 방화벽 DROP이나 DNS 실패를 확정하는 것은 오답이다.

## Q3 · 원래 증상과 입력으로 돌아간다

무엇이 원인이었는지 알기 어려우며 다른 URL의 성공은 원래 요청의 복구를 보장하지 않는다. 변경 전 값·두 가설·구별 관찰을 찾고 허가된 조건 하나를 바꾼 근거를 대조한다. 원래 호스트·scheme·주소/포트·path·기대 본문·클라이언트 옵션·횟수로 상태/본문/시간/로그를 다시 확인한다. 되돌릴 수 없는 추가 변경을 추측으로 실행하지 않는다. [K2](CONCEPTS.md#W16-K2).

## Q4 · 한 패킷의 지연과 연속 흐름을 구별한다

`L=1,500×8=12,000 bit`. 전송 지연은 첫 링크 `12,000/20,000,000=0.6 ms`, 둘째 `1.2 ms`다. store-and-forward 가정에서 합은 `0.6+1.2+5+1=7.8 ms`다. 연속 흐름의 이상적 병목 상한은 `min(20,10)=10 Mbps`다. 한 패킷의 도착 지연에는 전파·처리도 들어가며 여러 패킷은 링크마다 겹쳐 진행할 수 있으므로 단일 패킷 비율을 장기 처리량으로 쓰지 않는다.

단위·저장 후 전달·큐잉/손실/오버헤드 제외 조건이 필수다. ms를 초처럼 쓰거나 지연 역수를 곧바로 링크 처리량이라 하면 보충한다. [14주 교재](../week-14/CONCEPTS.md).

## Q5 · byte를 bit로 바꾼다

`RTT=0.05 s`. BDP는 `40,000,000×0.05=2,000,000 bit=250,000 byte=0.25 MB`다. 윈도 상한은 `100,000×8/0.05=16,000,000 bit/s=16 Mbps`로 대역폭40 Mbps보다 작다. 단순 모형의 상한은16 Mbps다. MB는 십진 단위로 썼다.

실제 처리량은 혼잡/수신 윈도 변화·손실/재전송·다른 병목·프로토콜 오버헤드·처리/앱 제한 등의 영향을 받는다. 같은 RTT가 유지되고 유효 윈도와 병목만 제약하는 이상화된 계산이다. 16 Mbps를 실측이나 보장으로 쓰는 것은 오답이다. [14주 계산](../week-14/CONCEPTS.md).

## Q6 · EOF가 경계를 대신하지 않는다

LF 전의 `b''`는 수신 방향 EOF이고 이 키트에서는 `eof_incomplete`다. TCP 스트림이 메시지 경계를 제공하지 않으므로 여러 recv를 누적한다. 연결당 한 메시지·본문 최대256 UTF-8 byte이며 LF까지 완성한 byte를 디코딩한다. 지속 연결·여러 메시지 처리 키트가 아니다. 서버 수신은 monotonic 마감에서 남은 시간을 계산하고, HTTP 점검기의 timeout은 개별 블로킹 작업의 제한이다. 클라이언트 timeout·서버수신·로컬쓰기·클라이언트수신은 구별한다.

전체 TCP 구현은 요구하지 않는다. [15주 실습 A·코드 지도](../week-15/LINUX.md)와 실제 본인 line→eof→line 출력·원복을 재사용한다. 해설만 읽어 코드 변경을 직접 했다고 쓰지 않는다.

## Q7 · 판정의 계약을 확인한다

`http_success`는 점검기가 상태와 본문 읽기를 성공으로 분류한 것이다. 기대 message까지 검사하는 코드는 아니므로 원래 echo 요청의 정상 기준을 별도로 대조한다. O01 실제 자원/왕복 구성도, O02 DNS/TLS 신원·양끝 요청, O03 전용 정책 변경/복구, O04 분산/제외/복귀, O05 두 가설의 독립 진단을 세 줄로 모두 증명할 수 없다. [운영 근거 지도](CHECKPOINT.md#operations)에서 실제 앞 근거를 찾는다. 3/3을 장기 가용성·p99로 일반화하지 않는다.

## Q8 · 도움받은 시도와 독립 확인을 나눈다

해당 시도는 도움받은 수행이다. 실제 Linux에서 실행했다는 사실은 남길 수 있지만 독립 진단으로 승격하지 않는다. 다음에는 처음 보는 배운 범위의 단일 장애로 두 가설·관찰 선택·최소 변경·복구를 도움 없이 확인한다. 공식 자료·명령 도움말 조회는 가능하다.

제공 사례는 분석 근거, Linux 실습은 해당 환경의 직접 근거, 참가자 설명은 독립 이해의 근거다. AI 로컬 재현과 팀원 수행을 본인 수행으로 옮기지 않는다. 필수 직접 수행·O01\~O05가 빠졌으면 부분 완료와 보충 행동을 남긴다. [C16](CHECKPOINT.md).
