# 16주차 함께 찾을 질문 · 증거로 가설을 좁히기

요약: 요청 실패의 원인을 바로 고르지 않고 서로 다른 두 가설과 구별할 관찰을 찾는다. 짧은 공식 절과 교재를 함께 읽고 설명자를 교대한다. 실제 장애는 정답을 가린 별도 실습에서 각자 조사한다.

## 먼저 앞 개념을 꺼내 보기

13주차에서 서버가 보는 주소와 클라이언트가 요청한 주소는 언제 다른가? 14주차에서 TCP 연결은 빠른데 전체 응답은 느렸다면 무엇이 아직 미확인인가? 15주차에서 HTTP 404와 `status=null`은 어떻게 다른가? 기억이 막히면 [돌아갈 교재](README.md#막히면-돌아갈-곳)를 읽는다.

<span id="W16-D1"></span>

## W16-D1 · 중심 질문

같은 서비스에서 요청이 실패했다. **서로 다른 원인 가설 두 개를 세우고, 둘을 구별할 관찰 하나를 고른다면 무엇을 볼까?** ‘네트워크 문제’처럼 넓은 이름 대신 어느 위치의 어떤 조건이 달라졌다고 생각하는지 말한다. 아직 관찰하지 않은 결과를 실제 출력처럼 쓰지 않는다.

함께 [공식 출처의 필수 두 절](SOURCES.md#함께-읽을-필수-범위)에서 HTTP 상태와 대기 제한을 읽고, [K1·K2](CONCEPTS.md)에서 관찰 위치를 대조한다. 한 사람이 관찰을 고른 이유를 설명하면 다른 사람은 ‘다른 프로세스가 같은 포트를 열고 있다면?’처럼 조건 하나를 바꾼다. 다음 질문에서는 설명자를 교대한다.

<span id="W16-D2"></span>

## W16-D2 · 조건을 바꾸면

숫자 주소의 HTTP 요청에서 이름을 쓰는 HTTPS 요청으로 바뀌었다. 정상 기준과 관찰에 무엇을 추가해야 할까? 서버 로그 한 줄이 없다는 이유만으로 요청이 오지 않았다고 결론 내릴 수 있을까? [K1의 계층별 증거](CONCEPTS.md#W16-K1)와 5\~6주차를 재사용한다. 선택 보조 질문이다.

<span id="W16-D3"></span>

## W16-D3 · 다음 판단

작은 변경 뒤 자동 점검에 `http_success`가 세 줄 나왔다. 원래 증상 해결·업무 성공·과정 전체 완료 가운데 무엇을 더 확인해야 할까? [K3](CONCEPTS.md#W16-K3)와 [종료 점검](CHECKPOINT.md)으로 확인한다. 자세한 정답은 설명을 마친 뒤 [분리 해설](ANSWERS.md#development)에서 읽는다.

## 직접 확인으로 이어 가기

공동 탐구는 관찰을 고르는 연습이다. [실습 A](LINUX.md)에서는 각자 미리 보지 않은 단일 장애를 받고 자기 가설·관찰·변경·복구를 설명한다. 다른 사람의 명령을 그대로 따라 했다면 도움받은 부분을 밝히고 새 조건에서 보충한다. 별도 발표자료나 팀 입력 양식은 만들지 않는다.
