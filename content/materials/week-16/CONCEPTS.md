# 16주차 핵심 교재 · 원인과 증거를 연결하기

요약: 정상 기준과 관찰 위치를 고정하고 서로 다른 가설을 증거로 구별한다. 허가된 최소 변경 뒤 같은 요청으로 복구를 확인한다. 관찰하지 못한 범위와 도움받은 수행을 남겨 진단·운영·학습의 완료를 나눈다.

<span id="W16-K1"></span>

## W16-K1 · 증상은 출발점이고 원인은 가설이다

**기억 문장: 실패했다는 사실과 왜 실패했는지는 다른 주장이다.** 가설은 ‘이 조건이 달라져서 이 증상이 생겼다’는 임시 설명이다. 경쟁 가설은 같은 증상을 설명하지만 서로 다른 원인을 가리킨다. 관찰을 고를 때는 두 가설 아래 예상이 달라지는지 본다.

```text
같은 입력·관찰 위치의 정상 기준
             ↓ 차이
실패 증상 → 가설 A / 가설 B → 예상이 다른 관찰
                                    ↓
                            지지 / 배제 / 아직 모름
```

정상 기준에는 실행 호스트·URL의 scheme/host/port/path·본문 기대·시간제한·클라이언트 옵션을 포함한다. scheme은 HTTP인지 HTTPS인지를 나타내는 URL 앞부분이다. IP나 포트 하나만 같다고 같은 요청은 아니다. 비밀값을 요청 꼬리표나 로그에 넣지 않는다.

| 관찰 위치·출력 | 알 수 있는 범위 | 아직 알 수 없는 것 |
| --- | --- | --- |
| 이름 조회 결과 | 그 조회의 주소 응답 | TCP 연결·TLS 신원·HTTP 정상 여부 |
| `ss -ltnp`의 로컬 주소:포트 | 그 호스트에서 대기 중인 소켓·보이는 프로세스 | 다른 호스트에서의 도달성·정책 통과·올바른 업무 처리 |
| curl 상태·본문·종료 코드 | 그 요청에서 받은 HTTP 결과와 도구의 판정 | 오류의 모든 원인·장기 가용성 |
| 서버의 해당 요청 로그 | 그 로그를 찍는 코드 위치에 도달한 사실 | 클라이언트 수신·영구 저장·업무 성공 |
| 양끝 로그/필요한 패킷 | 해당 위치·구간의 요청/응답 대응 | 관찰하지 않은 다른 계층·외부 경로의 상태 |

예를 들어 HTTP 404가 왔다면 HTTP 응답을 받았다. 곧바로 ‘서버가 꺼졌다’고 말할 근거는 아니다. 그렇다고 의도한 프로그램이 응답했는지까지 자동 보장하지는 않는다. 클라이언트 요청·리스너 소유자·응답 본문·서버 로그를 함께 본다. 로그가 없을 때도 다른 파일/호스트를 보거나 로그 분기 전 실패했을 수 있다. **로그 없음은 선택한 위치에 기록이 없다는 관찰**부터 뜻한다.

숫자 주소 HTTP 루프백 요청에는 DNS 질의·TLS·클라우드 ingress 통과가 포함되지 않는다. 원격 HTTPS에서는 이름→대상 주소→왕복 경로/정책→TCP→TLS 신원→HTTP를 추가 확인한다. 캐시와 열린 연결이 있으면 일부 단계가 생략될 수 있다. 근거는 [RFC 9110의 404](SOURCES.md)와 5\~6·13주 교재다.

## W16-K2 · 관찰 뒤 가장 작은 변경을 한다

**기억 문장: 한 번에 한 조건을 바꾸면 어느 가설을 확인했는지 설명하기 쉽다.** 변경 전 현재 값과 정상 값을 비교하고 대상·권한·원복 명령을 확인한다. ‘되면 좋겠다’며 서버·경로·정책을 한꺼번에 바꾸면 무엇이 원인이었는지 알기 어렵고 새 장애가 생길 수 있다.

```text
현재 값과 근거 → 허가된 한 조건 변경 → 같은 원래 요청
                       │                    │
                 예상과 다르면 중단     정상 기준과 대조
                       └── 알려 둔 복구 경로 ──┘
```

복구는 프로그램이 떠 있다는 말에서 끝나지 않는다. 원래 실패한 URL·본문 조건·관찰 위치·점검 횟수로 다시 요청하고 상태·본문·시간·같은 요청의 서버 로그를 대조한다. 복구용 새 진단 요청과 정상 재확인 요청은 구별한다. 진단하려고 다른 포트를 조회할 수 있지만 마지막에는 원래 요청이 정상이어야 한다.

이 원칙은 허가된 작은 학습 환경에 적용한다. 실제 사고에서 긴급 완화가 필요하면 원인 확정과 서비스 회복을 분리해 기록할 수 있지만, 이번 필수는 복합 장애나 운영 사고 대응이 아니다. 관리 SSH·기본 경로·공용 방화벽을 실습 때문에 임의 변경하지 않는다.

대기 초과만으로 서버 미수신/미처리를 확정하지 않는다. [15주 소켓](../week-15/CONCEPTS.md)의 서버 수신→로컬 쓰기→클라이언트 수신은 서로 다르다. `check_http.py --timeout`은 연결 시도 같은 개별 블로킹 작업의 제한이며 전체 실행의 엄격한 마감이 아니다. curl의 `--max-time`은 한 curl 전송의 총시간 제한이다. 실패 시 횟수·대기를 무제한 늘리지 않는다. [공식 API·curl](SOURCES.md)의 범위로 해석한다.

## W16-K3 · 정상화와 학습 완료에는 각각 근거가 필요하다

**기억 문장: 한 요청의 성공·한 장애의 복구·전체 필수 수행은 서로 다른 범위다.** `check_http.py`는 HTTP 상태·본문 읽기·오류를 기록한다. `http_success`라도 기대한 message가 다르면 이번 echo 서비스의 정상 기준은 충족하지 못한다. 실제 업무 서비스라면 별도의 업무 계약·저장 결과도 필요하다.

정상/장애/복구 각 3회는 이 사례를 비교하는 작은 관찰이다. 3회 성공으로 p99·장기 가용성·부하 수용량을 추정하지 않는다. 프록시가 한 VM의 두 프로세스로 분산한 결과를 호스트 장애 검증으로 쓰지도 않는다.

[공통 종료 점검](CHECKPOINT.md)은 앞선 증거를 다시 찾는 지도다. 계산·코드 설명을 새 문서에 다시 베끼지 않는다. 앞 근거가 충분하면 재사용하고 막힌 부분만 새 조건으로 설명한다. 해설을 보고 맞힌 것은 독립 설명과 구별하며 실제 Linux·참가자 직접 수행이 없으면 그 부분을 보충한다. 공식 문서/도움말 조회는 가능하지만 AI가 제시한 답·명령을 그대로 실행한 것은 독립 진단의 근거로 삼지 않는다.

## 헷갈리는 구별 두 가지

1. **증상이 사라짐 / 원인을 뒷받침함:** 여러 설정을 한꺼번에 바꿔 요청이 성공해도 원인을 특정하기 어렵다. 서로 다른 두 가설의 예상과 변경 전후 관찰을 남긴다.
2. **HTTP 성공 / 업무 성공·독립 이해:** 상태·본문·해당 요청의 서버 로그를 비교하고, 자기 말로 다른 조건을 설명한다. 제공 출력·다른 사람의 실행은 본인 직접 수행이 아니다.
