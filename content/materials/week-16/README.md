# 16주차 · 처음 보는 작은 장애를 진단하기

요약: 기존 서비스의 정상 기준을 잡고 배운 범위의 단일 장애를 각자 조사·복구한다. 두 원인 가설을 관찰로 구별하고 같은 요청으로 정상화를 확인한다. 앞선 계산·코드·운영 근거를 재사용해 공통 과정의 남은 보충을 찾는다.

<span id="weekly-study"></span>

## 개인 공부와 오프라인 확인

오프라인 모임 전까지 아래 범위를 공부하고 실습을 시도한다. 모임은 그 주의 학습을 마무리하는 자리로, 막힌 이유와 조건을 바꾼 결과를 설명하고 남은 보충을 정한다. [공동 질문](WORKSHEET.md)은 개인 공부의 출발점으로 쓰고, 모임에서는 근거를 비교한다. 별도 사전 모임이나 발표 자료는 필요하지 않다.

- **개념·문제:** 경쟁 가설·관찰의 정보 차이, 최소 변경·같은 입력 복구, C16과 O01~O05의 증거/보충 범위. [교재](CONCEPTS.md) → [공식 지정 절](SOURCES.md) → [복습](REVIEW.md) 순서로 읽고, 먼저 답한 뒤 [해설](ANSWERS.md)과 비교한다.
- **실습·분석:** 개인 공부에서는 정상 실행·도구·앞 근거만 준비하고 미노출 사례의 원인/주입/정답은 읽지 않음. 오프라인에서 각자 진단→최소 변경→같은 입력 복구. [실행 안내](LINUX.md)의 필수/선택과 제공 분석/직접 수행 구분을 따른다.
- **모임에 가져올 것:** 본인의 근거에서 고른 출력·풀이와 아직 설명이 막힌 질문. 개인 학습 노트에 한 번 정리하고 원시 로그·pcap은 파일 링크로 연결해도 된다. 새 제출 양식은 만들지 않는다.

### 개인 공부를 정리할 때

기존 개인 학습 노트에 아래 세 가지를 중심으로 정리한다. 모임 전에는 현재 답과 막힌 지점을 남기고, 모임 뒤에는 확인한 차이와 보충할 부분을 고친다. 정해진 개수·분량이나 새 제출물은 없다.

- **주요 질문과 내 답:** [공동 질문](WORKSHEET.md)과 아래 확인 질문에 먼저 내 말로 답한다. 이유·성립 조건과 공식 자료·실습 근거를 연결하고, [분리 해설](ANSWERS.md)은 시도 뒤에 비교한다.
- **헷갈리는 개념 비교:** [핵심 설명](CONCEPTS.md)에서 증상과 원인, 응답 복구와 업무 성공의 역할·관찰 위치·성공 범위를 비교한다. 두 개념이 다른 결론을 내는 예를 들어 본다.
- **이번 주 꼭 기억하고 이해할 핵심 개념:** [핵심 정리](CONCEPTS.md)의 W16-K1~K3를 길잡이로 용어·역할·동작 순서를 추린다. 필요한 공식은 식·단위·성립 조건과 적용 이유를 함께 설명한다. 예제 주소·일회성 출력값을 외우는 목록으로 만들지 않는다.

실습 근거는 해당 질문·개념 아래에 예상·실제 관찰·수정한 이해와 함께 연결한다. 제공 분석과 직접 실행을 구별하고 관찰하지 않은 결과는 채우지 않는다. 입력 화면을 썼다면 이동 전에 답안을 내려받는다. [전체 개념 색인의 정리 방법](../CONCEPT_INDEX.md#personal-study)은 다른 주차에도 같은 방식으로 쓸 수 있다.

### 오프라인에서 확인할 질문

1. **중심 질문:** 서로 다른 두 원인 가설에서 예상이 갈리는 관찰 하나를 스스로 고를 수 있을까?
2. **조건을 바꾸면:** 숫자 HTTP에서 이름 HTTPS로 바뀌면 정상 기준·관찰 위치·복구 확인에 무엇을 더할까?
3. **앞 개념을 다시 쓰면:** 13주 정책·14주 분산·15주 자동 기록 중 이번 성공 세 줄로 확인되지 않는 운영 근거는 무엇인가?

중심 질문을 먼저 설명하고 나머지는 짧은 후속 질문으로 사용한다. [분리 해설](ANSWERS.md)과 실제 근거를 대조하되 답을 본 시도와 독립 설명을 구별한다. 개인 공부에서 마친 정상 실습을 전부 반복하지 않고, 막힌 항목과 한 조건 변경·복구를 각자 확인한다.

## 이번 주에 할 일

**중심 질문: 요청이 실패했다. 무엇을 먼저 확인해야 두 원인 가설을 구별할 수 있을까?**

13주차의 서비스·양끝 로그, 14주차의 정상 기준·분산/복구, 15주차의 제한 반복 점검을 이어 쓴다. 새 앱을 만들거나 전체 환경을 다시 구축하지 않는다. 처음 보는 사례란 배운 개념으로 풀되 해당 주입·정답을 미리 보지 않은 사례다. 같은 사례를 따라 복구한 뒤 다시 성공한 것은 독립 진단과 구별한다.

| 순서 | 읽거나 실행할 자료 | 확인할 것 |
| --- | --- | --- |
| 1 | [함께 찾을 질문](WORKSHEET.md) | 앞 개념 복습·경쟁 가설·관찰 선택 |
| 2 | [핵심 교재](CONCEPTS.md)와 [공식 지정 절](SOURCES.md) | 증거가 말해 주는 범위·최소 변경·복구 기준 |
| 3 | [학습자 실습](LINUX.md) | 정상 → 미리 보지 않은 단일 장애 → 조사 → 변경 → 복구 |
| 4 | [공통 종료 점검](CHECKPOINT.md) | C16·O01\~O05와 앞선 필수 수행의 근거·보충 |

[진행자 안내](FACILITATOR.md)는 준비·시간 배치·판정 방법이다. 학습자는 실습 전 정답을 찾아 읽지 않고 증상·허용 범위만 받아 시작한다. 공개 교재의 해설은 학습을 돕지만 그것을 읽었다는 사실이 독립 이해를 증명하지는 않는다.

## 필수와 선택

필수는 두 묶음이다. **A:** Linux 한 대에서 정상 기준과 처음 보는 단일 장애 하나를 직접 조사·복구한다. **B:** 앞서 보관한 계산·코드 읽기·필수 실습과 O01\~O05 근거를 연결하고 막힌 항목만 새 조건으로 확인한다. 자세한 근거는 개인 파일에 한 번 보관하며 새 팀 기록·개인 마무리 양식은 요구하지 않는다.

VM 간 경로·정책 사례는 이미 해당 환경에서 직접 수행한 경우에 선택한다. 복합 장애·부하 시험·큰 서비스 설계·Ansible/Terraform 자원 변경은 후속 범위다. 관리 SSH·공용망을 바꾸거나 유료 자원을 추가하지 않는다. 제공 자료만 분석했다면 직접 복구는 보충으로 남긴다.
