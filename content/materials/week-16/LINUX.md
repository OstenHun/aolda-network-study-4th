# 16주차 학습자 실습 · 증상에서 복구까지

요약: 기존 Linux 한 대의 HTTP 서비스를 같은 입력으로 점검한다. 정상 기준 뒤 처음 보는 단일 장애를 받아 두 가설·구별 관찰·허가된 최소 변경·복구를 각자 설명한다. 제공 분석과 도움받은 수행은 직접 독립 진단과 나눈다.

## 준비 · 같은 VM과 기존 파일

본인에게 허가된 Linux VM 한 대·Python 3.10 이상·curl·ss와 셸 두 개를 사용한다. 셸 A는 본인의 테스트 서버, 셸 B는 요청/조회용이다. 13\~15주차 개인 폴더와 정상 파일을 우선 재사용한다. 파일이 없으면 다음 세 파일을 같은 개인 폴더에 둔다. 기존 파일을 덮어쓰지 않는다.

- <a download href="../../labs/week-01/server.py">1주차 server.py · HTTP Handler</a>
- <a download href="../../labs/week-13/cloud_service.py">13주차 cloud_service.py · 같은 Handler 실행기</a>
- <a download href="../../labs/week-15/check_http.py">15주차 check_http.py · 제한 반복 점검</a>

아래 명령은 모두 **같은 Linux VM·같은 개인 폴더**에서 실행한다. 관리 SSH·공용망·외부 공개·유료 자원·접근 정책은 이번 기본 사례의 변경 대상이 아니다. sudo나 패키지 설치는 요구하지 않는다.

```bash
python3 --version
curl --version
command -v ss
python3 -m py_compile server.py cloud_service.py check_http.py
ss -ltn 'sport = :18081'
```

이미 사용 중인 포트면 소유자를 확인하고 타인의 프로세스는 종료하지 않는다. 진행자와 다른 미사용 비특권 포트를 정해 모든 서버/클라이언트 명령을 맞추거나 별도 격리 호스트로 옮긴다. 준비가 안 되면 앞 주차의 가공 사례로 관찰을 연습하고 직접 진단/복구는 보충한다. 그 분석을 실측으로 바꾸지 않는다.

## A1 · 먼저 정상 기준을 만든다

셸 A에서 기존 13주 실행기를 **루프백만** 바인딩해 실행한다. 외부 테스트를 위해 쓰던 실제 주소·인증서는 이 기본 사례에 필요하지 않다. 기존 원격 서버를 변경하지 말고 개인 폴더의 별도 테스트 프로세스를 사용한다.

```bash
python3 -u cloud_service.py --bind 127.0.0.1 --port 18081
```

셸 B에서 실행한다. 파일명은 정상/장애/복구 단계별로 다르게 쓴다. `>`는 기존 파일을 덮어쓰므로 보존할 파일이 있으면 이름을 바꾼다.

```bash
curl --noproxy '*' -sS -i --connect-timeout 1 --max-time 3 'http://127.0.0.1:18081/echo?message=c16'
echo "exit=$?"
python3 check_http.py --port 18081 --path '/echo?message=c16' --count 3 > normal.jsonl
echo "exit=$?"
cat normal.jsonl
```

정상 기준은 curl 종료 0·HTTP200·본문 `{"message": "c16"}`, 자동 `http_success` 3줄·종료 0·같은 message다. 셸 A의 `listening` 주소·포트와 같은 경로의 `response` 로그를 비교한다. 수동 1회와 자동 3회는 별개의 요청이므로 이 구간의 서버 응답은 4개다. 로그에 시각이 없으므로 단계별 구간과 요청 순서도 보관한다. 로그의 쓰기 완료만으로 클라이언트 수신을 증명하지 않는다.

## A2 · 처음 보는 단일 장애를 받는다

진행자가 정상 기준을 확인한 뒤 허가된 테스트 범위의 조건 하나를 바꾼다. 학습자에게는 **실행 호스트·원래 URL/기대 본문·현재 증상·관찰 가능한 위치·변경 허용 범위·중단/복구 지원 경로**만 전달한다. 원인 이름·주입 명령·정답이 들어간 파일은 먼저 읽지 않는다. 이미 본 사례면 그 사실을 알리고 다른 단일 사례로 바꾼다.

1. A1과 **동일한 curl/자동 입력**을 다시 실행한다. 자동 파일명만 `incident.jsonl`로 바꾸고 종료 코드·본문·오류·시간을 읽는다. 입력을 바꿔 성공시키기 전에 원래 증상을 보존한다.
2. 서로 다른 원인 가설 두 개를 말한다. 각 가설이 맞다면 어떤 관찰이 나올지 예상한다. 같은 원인을 표현만 바꿔 두 개로 세지 않는다.
3. 두 예상이 달라지는 관찰을 스스로 고른다. 아래는 도구 목록이며 정답 순서가 아니다. 아직 허가받지 않은 자원을 변경하지 않는다.
4. 관찰 뒤 어떤 가설이 지지/배제됐는지, 무엇이 미확인인지 설명한다. 변경할 한 값·이유·원복 방법을 진행자와 확인하고 본인이 실행한다.

### 필요할 때 찾을 관찰 도구

| 도구·위치 | 질문 |
| --- | --- |
| 셸 B의 `ss -ltnp` | 요청 대상의 로컬 주소:포트는 누가 대기하는가? 프로세스 정보가 안 보이면 권한을 높이지 않고 본인 전경 셸과 대조한다 |
| 셸 A의 본인 서버 로그·현재 실행 인자 | 어떤 위치에 바인딩했으며 원래 요청이 어느 코드까지 왔는가? 주입 당시 정답 설명은 조회하지 않는다 |
| 제한된 `curl -v` 또는 헤더/본문 | 연결·HTTP 상태·본문 중 어디까지 확인됐는가? 비밀값 없는 루프백 URL만 사용한다 |
| 기존 `check_http.py`의 JSON 줄 | 수동 결과와 status/outcome/error/elapsed_ms가 일치하는가? |

이 루프백 숫자 주소 HTTP 사례에서 DNS·TLS·외부 방화벽을 이미 검증했다고 쓰지 않는다. 원격 이름·정책 사례를 선택했다면 [13주차의 양끝·허가·복구 조건](../week-13/LINUX.md)을 먼저 충족해야 한다. 조사 중 예상 밖 두 번째 장애·타인 프로세스·권한 문제가 보이면 멈추고 진행자에게 알려 사례를 다시 준비한다.

## A3 · 원래 요청으로 복구를 확인하고 정리한다

허가된 변경 뒤 **A1과 같은 URL·포트·본문 조건·count 3**으로 수동과 자동을 다시 실행한다. 자동 파일은 `restored.jsonl`에 보관한다. 변경 전후 설정과 리스너·HTTP 상태·기대 본문·서버 로그를 비교해 원래 실패가 해소됐는지 설명한다. 실패하면 무작정 변경을 더하지 않고 방금 변경을 원복하거나 진행자의 복구 지원을 받는다.

상세 증거는 개인 파일에 한 번만 둔다. 두 가설·선택한 관찰·최소 변경 이유·복구 근거·받은 도움을 기존 기록에서 찾을 수 있으면 된다. 새 팀 기록 양식은 없다. 공식 문서/명령 도움말을 조회할 수 있지만 AI/진행자가 알려 준 답이나 명령을 그대로 따라 한 부분은 **도움 후 보충 필요**다. 다른 처음 보는 조건에서 독립 수행을 다시 확인한다.

셸 A에서 Ctrl+C로 **본인의 테스트 프로세스만** 종료한다. 셸 B의 `ss -ltn 'sport = :18081'`로 리스너가 사라졌는지 본다. 진행자가 다른 허가된 테스트 포트를 사용했다면 그 포트도 정리한다. 공유 서비스의 중지는 정리 범위가 아니다.

## B · 앞 근거를 재사용해 C16을 확인한다

[공통 종료 점검](CHECKPOINT.md)에서 기존 계산·코드·직접 수행을 찾는다. [14주 계산](../week-14/CONCEPTS.md)과 [15주 코드 지도](../week-15/LINUX.md#code-reading)를 다시 작성하지 않는다. 막힌 항목만 진행자가 새 작은 조건을 주어 확인한다. 별도 앱·환경 재구축·일괄 재실습은 요구하지 않는다.

## 재사용 코드 읽기 · 입력에서 결과까지

| 파일·읽을 단계 | 입력 → 판단 → 실행 → 출력 | 실패·정리와 설명할 것 |
| --- | --- | --- |
| `cloud_service.py` main | bind/port → 주소/인자 검사 → ThreadingHTTPServer → listening | `from server import Handler`가 같은 폴더의 1주 Handler를 가져온다. 잘못된 주소/포트·중복 리스너는 실패. Ctrl+C와 with로 정리 |
| `server.py` Handler.do_GET | URL 분리 → /echo 또는 그 외 → JSON/Content-Length → 응답 로그 | message/상태·UTF-8 byte·Connection:close. 응답 쓰기와 클라이언트 수신/업무 성공 구별 |
| `check_http.py` check_once/main | port/path/count → 범위 검사 → 순차 GET·본문 → JSON과 종료 | 최대5회·간격0.2초·재시도없음. 개별 블로킹 timeout, 본문64KiB 상한/잘림 분리, finally close |

코드 자체는 앞 주차 정본을 그대로 쓴다. 소켓의 부분 recv·LF·EOF·수신 마감은 [15주 코드](../week-15/LINUX.md#code-reading)에서 확인한다. LF 키트는 연결당 한 메시지·본문 최대256 UTF-8 byte이며 지속 연결을 지원하지 않는다. 이번 HTTP Handler도 명시적으로 연결을 닫지만 현대 HTTP 전체의 제약으로 일반화하지 않는다.
