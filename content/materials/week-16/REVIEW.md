# 16주차 복습 · 근거와 한계를 설명하기

요약: 증상·가설·관찰·복구의 연결을 자기 말로 확인한다. 계산·코드 문제는 앞 근거가 부족한 부분만 새 조건으로 사용한다. 실제 단일 장애의 원인 정답은 포함하지 않으며 해설과 독립 수행은 구별한다.

## Q1. 서로 다른 두 가설

요청 실패에 ‘서버 프로세스가 없다’와 ‘서버가 종료됐다’를 두 가설로 제시했다. 왜 구별 관찰을 고르기 어려운가? 배운 범위에서 원인이 다른 가설 한 개로 바꾸고, 각 가설 아래 예상이 달라질 관찰을 설명한다. 실제 주입 사례의 정답을 추측하는 문제가 아니다.

## Q2. 로그가 없으면

클라이언트가 오류를 기록했는데 지금 연 서버 로그 파일에는 해당 요청이 없다. 무엇이 확인됐고 무엇은 미확인인가? 관찰 위치와 로그를 찍는 코드 위치를 고려해 다음 확인 두 가지를 고른다.

## Q3. 복구와 정상 기준

여러 설정을 한꺼번에 바꾼 뒤 다른 URL에서 HTTP200이 왔다. 원래 장애를 복구했다고 판단하기에 무엇이 부족한가? 최소 변경과 같은 입력의 관점으로 설명한다.

## Q4. 지연·병목 계산 · 보충할 때

가공한 단순 모형이다. 패킷 1,500 byte가 20 Mbps와 10 Mbps 링크를 store-and-forward로 한 번씩 지난다. 전파 지연 합은 5 ms, 처리 지연 합은 1 ms, 큐잉·헤더 오버헤드·손실은 0이다. 한 패킷의 마지막 bit 도착까지 지연과 연속 흐름의 이상적인 병목 상한을 계산한다. 왜 `패킷 크기/전체 지연`을 장기 처리량으로 단정할 수 없는가?

## Q5. BDP와 윈도 상한 · 보충할 때

대역폭 40 Mbps·RTT 50 ms·유효 윈도 100,000 byte의 가공 모형이다. BDP를 bit/byte로, `W/RTT`를 Mbps로 계산한다. 대역폭과 윈도 중 어느 상한이 작은가? 실측 처리량으로 쓰기 전에 어떤 제외 조건을 밝혀야 하는가?

## Q6. 소켓 코드 읽기 · 보충할 때

15주 `read_line`이 본문 일부를 받은 뒤 `recv`에서 `b''`를 받았다. 아직 LF가 없었다면 왜 정상 메시지가 아닌가? 연결당 메시지 수·본문 상한·UTF-8 처리·수신 마감과 HTTP 점검기의 timeout 범위를 구별해 설명한다. 앞 실습의 입력/종료 조건 변경·복구 근거를 재사용한다.

## Q7. HTTP 성공과 운영 근거

자동 점검 세 줄이 모두 `http_success`지만 본문의 message는 기대값과 다르다. 무엇을 정상으로 판정할 수 없는가? O01\~O05 가운데 이 세 줄만으로 확인할 수 없는 실제 운영 행동을 두 가지 고른다.

## Q8. 처음 보는 사례와 도움

진행자의 정답·복구 명령을 읽고 같은 사례를 성공시켰다. 독립 진단과 어떻게 나누어야 하는가? 제공 분석·실제 Linux 수행·참가자 독립 이해·전체 공통 완료를 각각 어떤 근거로 판단할지 설명한다.
