# 5주차 · DNS와 DHCP를 구별하기

요약: DNS의 재귀·권한 역할과 주소 레코드·캐시 수명을 설명하고 DHCP의 임대·설정 옵션을 읽는다. 이름 해석·서비스 응답과 호스트 설정을 구별하며 제공 예제의 조건과 실제 관찰 범위를 확인한다.

[개인 공부 정리](README.md#personal-notes)에서는 이 교재의 핵심·혼동 구별을 주요 질문과 내 답에 연결한다. 먼저 설명하고 해설과 비교한 뒤, 확인한 근거와 고친 이해를 기존 개인 노트에 보완한다.

## 앞선 통신에 이름과 설정을 더하기

2주차에는 주소와 마스크로 망을 나누고, 3주차에는 경로에서 다음 홉을 찾았다. 4주차에는 IP와 포트로 프로그램 사이에 데이터를 전했다. 이번에는 그 목적지 주소를 이름으로 찾는 과정과 내 호스트의 주소·경로·DNS 설정을 받는 과정을 추가한다.

| 질문 | 맡는 기능 | 별도로 확인할 것 |
| --- | --- | --- |
| 이 이름의 IPv4/IPv6 주소는? | DNS A/AAAA 질의 | 그 주소까지의 경로·포트·서비스 |
| 내 호스트가 어떤 주소·설정을 쓸까? | DHCPv4 임대 또는 정적 설정 등 | 실제 적용된 주소·경로·이름 해석 설정 |
| 웹 서버가 요청을 처리했을까? | TCP/TLS/HTTP 등 | 요청 결과·응답·필요한 서버 로그 |

DNS와 DHCP는 서로 다른 서버일 수 있다. DHCP가 알려 준 DNS 서버 주소로 이름을 질의할 수 있지만, DHCP 자체가 매 웹 요청의 목적지 이름을 찾아 주는 것은 아니다.

<span id="dns-roles"></span>
## W05-K1 · 이름의 정본과 답을 찾아 주는 역할

**권한 서버는 담당 영역(zone)의 데이터를 답하고, 재귀 리졸버는 클라이언트 대신 답을 찾는다.** zone은 한 권한 경계에서 관리하는 DNS 데이터 범위다. 내 프로그램은 보통 OS의 간단한 리졸버를 거쳐 설정된 재귀 리졸버에 묻는다.

캐시에 필요한 정보가 없는 경우의 단순화한 흐름이다. 화살표마다 질의와 응답이 있으며 HTTP 요청은 아직 없다.

```text
프로그램 → OS 리졸버 → 재귀 리졸버
                         ├→ 루트: 해당 최상위 도메인의 서버 안내
                         ├→ 최상위 도메인 서버: 권한 서버 안내
                         └→ 권한 서버: 해당 이름의 레코드
프로그램 ← OS 리졸버 ← 재귀 리졸버의 최종 응답
```

재귀 요청은 “최종 답 또는 오류까지 찾아 달라”는 요청이다. 재귀 리졸버가 다른 서버에 하는 질의는 흔히 반복 질의로, 다음 서버를 안내받으며 진행한다. 캐시된 답·위임 정보가 있으면 일부 단계를 생략한다. 모든 질의가 루트부터 시작하지 않는다. 같은 소프트웨어가 두 역할을 지원해도 이번에 어떤 역할로 답했는지는 구별한다.

### A와 AAAA 응답 읽기

아래는 **직접 측정하지 않은 설명용 출력**이다. `api.example`과 문서용 주소를 사용하며 실제 접속 대상이 아니다.

```text
;; status: NOERROR
;; flags: qr rd ra; QUERY: 1, ANSWER: 1
;; QUESTION SECTION:
;api.example.          IN A
;; ANSWER SECTION:
api.example.  300      IN A     192.0.2.20
;; SERVER: 192.0.2.53#53

; 별도의 AAAA 질의에 대한 응답
api.example.  300      IN AAAA  2001:db8::20
```

- `A`는 IPv4 주소, `AAAA`는 IPv6 주소 레코드다. `IN`은 인터넷 클래스이며 `300`은 이 응답에서의 TTL(초)이다. A만 확인해서 IPv6 경로까지 성공했다고 말할 수 없다.
- `SERVER`는 이 도구가 응답을 받은 DNS 서버다. 웹 서버 주소나 최종 권한 서버라고 단정하지 않는다. 로컬 stub 주소가 나올 수도 있다.
- `rd`는 재귀 요청, `ra`는 서버의 재귀 제공 가능 표시다. `aa`는 권한 응답 표시다. 위 예제에 `aa`가 없다는 사실만으로 캐시 적중을 확정할 수는 없다.
- `NOERROR`여도 해당 형식의 주소가 없을 수 있다. 존재하지 않는 이름의 `NXDOMAIN`, 처리 실패 `SERVFAIL`, 응답을 못 받은 시간 초과는 서로 다르다. 별칭 CNAME이 있으면 응답에 주소까지 이어지는 이름이 추가될 수 있다.

일반 DNS는 UDP 53을 많이 사용하지만 TCP도 사용한다. “UDP니까 모든 DNS가 UDP뿐”이라고 외우지 않는다. 이번에는 암호화 DNS·DNSSEC·권한 서버 구축을 필수로 다루지 않는다. 근거: [RFC 1034 §4.3.1·§5.3.3](SOURCES.md), [RFC 1035 §3.4.1·§4.1](SOURCES.md), [RFC 3596 §2](SOURCES.md).

## W05-K2 · 캐시는 응답을 재사용하고 TTL은 수명을 제한한다

**양성 응답의 TTL은 레코드를 캐시에 보관할 수 있는 시간의 상한이다.** DNS TTL은 IP 패킷의 홉 제한 TTL과 다른 필드다. 아래는 같은 단일 캐시가 최초 응답을 받은 뒤, 갱신·퇴거·미리 가져오기 없이 시간을 세는 **제공 모형**이다.

| 경과 시간 | 재귀 리졸버 상태 | 클라이언트에게 답할 주소·남은 TTL |
| --- | --- | --- |
| 0초 | 권한 데이터에서 A를 받아 캐시에 보관 | 192.0.2.20 · 300초 |
| 120초 | 같은 캐시를 재사용 | 192.0.2.20 · 180초 |
| 300초 이후 | 만료해 다시 질의, 권한 A가 .30으로 바뀐 조건 | 192.0.2.30 · 새 TTL 300초 |

120초 시점의 원문을 짧게 쓰면 다음과 같다.

```text
api.example. 180 IN A 192.0.2.20
```

권한 서버의 값을 바꿔도 이미 유효한 캐시가 즉시 사라지지는 않는다. TTL을 지금 줄여도 예전에 긴 TTL로 받아 간 캐시의 수명이 소급해 줄지는 않는다. TTL 0은 이 단순 모형에서 재사용할 캐시 수명을 주지 않는 조건이다. 실제 구현의 예외 정책과 장애 때 오래된 답 제공은 심화에서 다룬다.

연속 dig의 TTL·질의 시간이 기대대로 줄지 않을 수 있다. 서로 다른 캐시 노드, 캐시 초기 상태·갱신·네트워크 지연이 다를 수 있기 때문이다. 두 번 빨랐다는 사실만으로 캐시 적중이나 전체 웹 요청 성능을 증명하지 않는다. 앱·OS의 이름 캐시, HTTP 응답 캐시와 이미 열린 TCP 연결도 별개다. 근거: [RFC 1034 §3.6·§5.3.2](SOURCES.md).

<span id="dhcp"></span>
## W05-K3 · DHCP는 주소와 네트워크 설정을 임대한다

**DHCPv4는 주소 사용 기간과 설정을 전달한다. 주소·마스크·라우터·DNS는 각자 역할이 다르다.** 임대는 주소를 영구 소유하는 것이 아니라 일정 기간 사용할 수 있도록 할당받는 것이다. 서버는 UDP 67, 클라이언트는 UDP 68을 사용한다.

<span id="dhcp-trace"></span>
### 처음 주소를 받는 제공 trace

아래는 RFC 2131의 초기 할당 절차를 바탕으로 만든 **가공한 필드 trace**다. pcap 실측이 아니며 재전송·릴레이·충돌 검사는 생략했다. 클라이언트는 아직 주소가 없고, 서버는 같은 실습 링크에 있으며 브로드캐스트 응답을 요청한 조건이다. 문서용 192.0.2.0/24를 사용한다.

| 시각 | 방향 · UDP | 메시지 | 같은 거래 ID 0x050005에서 볼 필드 |
| --- | --- | --- | --- |
| 0.00초 | 0.0.0.0:68 → 255.255.255.255:67 | DISCOVER | 사용할 설정 탐색, broadcast flag=1 |
| 0.10초 | 192.0.2.1:67 → 255.255.255.255:68 | OFFER | yiaddr=192.0.2.100, server identifier=192.0.2.1 |
| 0.20초 | 0.0.0.0:68 → 255.255.255.255:67 | REQUEST | requested IP=192.0.2.100, 선택한 server identifier=192.0.2.1 |
| 0.30초 | 192.0.2.1:67 → 255.255.255.255:68 | ACK | yiaddr=192.0.2.100, mask=255.255.255.0, router=192.0.2.1, DNS=192.0.2.53, lease=3600초 |

DISCOVER → OFFER → REQUEST → ACK를 줄여 DORA라고 부른다. OFFER는 제안이며 REQUEST에서 선택한 서버·주소를 알려 주고 ACK가 할당을 확인한다. `yiaddr`는 서버가 제안/할당하는 클라이언트 주소 필드다. 여러 서버의 OFFER를 받은 상황이나 릴레이가 있는 망은 위 한 거래와 다르다.

### 옵션을 기존 개념에 대응하기

| 필드·옵션 | 이 예제에서 받은 값 | 호스트에서 쓰는 곳 |
| --- | --- | --- |
| yiaddr | 192.0.2.100 | 자기 인터페이스의 IPv4 주소 |
| 1 · subnet mask | 255.255.255.0 = /24 | 주소의 네트워크 범위 판단 |
| 3 · router | 192.0.2.1 | 다른 망으로 가는 기본 경로 구성에 사용 |
| 6 · DNS server | 192.0.2.53 | 이름 질의 대상으로 사용 |
| 51 · lease time | 3600초 | 주소 사용 기간 관리 |

`.100/24`와 `.53`은 같은 /24 주소 범위이며 다른 망의 주소는 기본 경로를 사용할 수 있다. 실제 경로 선택은 적용된 경로표를 읽어 확인한다. 라우터·DNS 서버·DHCP 서버가 우연히 같은 주소일 수 있어도 역할은 같지 않다.

임대 갱신은 처음 DORA 네 단계를 매번 반복하지 않는다. 기본 T1=임대의 50%, T2=87.5%라면 이 예제는 1800초에 원래 서버로 갱신을 시도하고, 갱신되지 않으면 3150초에 재바인딩 단계로 간다. 서버가 다른 타이머를 줄 수 있다. 만료 때까지 갱신되지 않으면 주소 사용을 중단한다. 이 설명을 확인하려고 접속 중인 VM의 임대를 해제하지 않는다. 근거: [RFC 2131 §3.1·§4.4.5](SOURCES.md), [RFC 2132 §3.3·§3.5·§3.8·§9.2](SOURCES.md).

Linux에 주소가 있다는 사실만으로 DHCP라고 판단하지 않는다. 정적 설정·가상 환경의 주입 설정 등 출처가 다를 수 있다. `/etc/resolv.conf`의 nameserver도 로컬 stub일 수 있으므로 적용된 링크별 DNS와 관리 도구의 설정을 함께 조회한다. [실습 B](LINUX.md#experiment-b)에서 조회만 한다. DHCPv6와 IPv6 자동 설정은 이번 DHCPv4 trace의 범위 밖이다.

## 헷갈리는 구별 두 가지

### 이름 해석 성공과 서비스 성공

dig에서 A 응답을 받았다는 것은 그 질의가 주소를 얻었다는 증거다. 해당 주소의 TCP 포트가 열렸는지·TLS 신원이 맞는지·HTTP 요청이 처리됐는지는 별도다. HTTP 404를 받았다면 HTTP 응답까지 받은 것이고, 연결 실패·시간 초과와 같은 결과가 아니다.

URL을 이름에서 IP로 바꾸면 HTTP의 `Host`나 HTTPS의 SNI·인증서 호스트명 검증 조건이 바뀔 수 있다. 같은 IP가 여러 이름을 서비스할 수 있다. 이름을 유지하고 목적 주소만 지정하는 `curl --resolve`로 비교하면 한 조건을 더 잘 고정할 수 있다. 이는 그 요청에서 DNS 조회를 우회하므로 DNS 정상의 증거로 쓰지 않는다. 인증서 검증을 끄는 `-k`를 해결책으로 사용하지 않는다. [실습 A](LINUX.md#experiment-a)는 이를 로컬 HTTP로 먼저 확인하고 TLS 세부는 6주차로 연결한다.

### DHCP 설정 전달과 DNS 질의

DHCP의 DNS 옵션이 틀려도 호스트의 주소·경로는 있을 수 있다. 반대로 DNS를 올바르게 받아도 경로·접근 정책·서버 상태가 나쁘면 요청은 실패한다. “DHCP 성공이니 인터넷도 정상”이라고 단정하지 않고 주소 → 경로 → 이름 질의 → 요청을 각각 확인한다.

## 개발 상황으로 설명하기

- **W05-D2:** 권한 서버의 A를 바꿨는데 일부 클라이언트만 예전 IP를 쓴다. 캐시 모형에서 가능한 이유와 바꿔 비교할 조건은?
- **W05-D3:** DHCP ACK의 주소·마스크·라우터는 그대로이고 DNS만 다른 값이다. 실제 설정을 바꾸지 않고 어떤 출력과 요청을 비교해 원인을 좁힐까?
