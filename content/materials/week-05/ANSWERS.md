# 5주차 · DNS·DHCP 분리 해설

요약: 복습과 공동 질문의 필수 답안 요소·조건·흔한 오해를 비교한다. DNS 응답과 서비스 성공을 나누고 캐시·DHCP 제공 분석을 직접 실행 근거와 구별한다.

먼저 [복습 문제](REVIEW.md)에 답한 뒤 읽는다. 문장 일치보다 역할·조건·근거를 자기 말로 설명하는지 확인한다. 제공 출력만 읽었다면 실제 Linux 직접 수행으로 기록하지 않는다.

<span id="inquiry"></span>
## 중심 질문 · DNS 성공 뒤 남은 단계

이름 질의에서 주소를 얻어도 그 주소의 경로·접근 정책·포트·TLS 신원·서비스 처리는 아직 모른다. A/AAAA 응답은 질의의 증거, TCP 연결은 전송 연결의 증거, HTTP 상태와 본문은 서비스 응답의 증거다. dig가 사용하는 서버와 앱의 이름 해석 경로가 다를 수 있으므로 실행 위치·설정도 붙인다.

필수는 “DNS가 됐다”라는 말 대신 어느 질의가 누구에게서 어떤 레코드를 받았는지 말하고 curl의 오류/상태·원격 IP를 따로 보는 것이다. 흔한 오답은 “DNS 성공이면 서버도 정상”이다. 근거는 [교재의 구별](CONCEPTS.md#distinctions), [실습 A](LINUX.md#experiment-a), [RFC 1034·curl 공식 안내](SOURCES.md)다.

<span id="q1"></span>
## Q1 · 재귀·권한 역할

OS 리졸버는 앱의 요청을 받아 설정된 DNS 경로를 사용한다. 재귀 리졸버는 대신 답을 찾거나 캐시로 답하고, 권한 서버는 자신의 zone에 대해 답한다. 캐시가 없으면 루트→최상위 도메인→권한 서버의 안내를 따라갈 수 있다. 캐시된 최종 답이나 위임 정보를 쓰면 단계를 줄인다.

필수 요소는 역할·캐시 조건·안내와 최종 답의 차이다. “재귀 리졸버가 모든 이름의 정본이다”, “내 PC가 항상 루트에 묻는다”는 오답이다. [W05-K1](CONCEPTS.md#dns-roles)·RFC 1034 §4.3.1·§5.3.3을 확인한다.

<span id="q2"></span>
## Q2 · 응답 필드

192.0.2.20은 질의한 이름의 IPv4 주소이며 .53은 이 도구가 질의 응답을 받은 서버다. 180은 초 단위 DNS TTL, A는 IPv4 레코드다. AAAA는 IPv6 주소를 알려 주지만 IPv6 경로·서비스 정상까지 증명하지 않는다. NOERROR의 빈 답은 그 형식의 레코드가 없을 수 있는 조건이며, NXDOMAIN은 이름이 존재하지 않는다는 응답이다. timeout은 응답을 못 받았으므로 이름의 존재 여부를 확정하지 못한다.

필수는 두 주소의 역할과 응답 상태의 구별이다. `SERVER`를 웹 서버·최종 권한 서버로 단정하거나 TTL을 홉 수로 읽으면 보충한다. [A/AAAA 예제](CONCEPTS.md#dns-roles)에서 필드를 짚는다.

<span id="q3"></span>
## Q3 · TTL과 변경

300−120=180초다. 기존 캐시가 유효하므로 권한의 t=100 변경 후에도 t=120에 예전 주소를 답할 수 있다. 다른 캐시에서 새로 질의하면 새 주소를 받을 수 있다. TTL 감소는 레코드 보관 수명의 모형이며 모든 사용자에게 동시에 적용되는 배포 타이머가 아니다.

필수 요소는 단위·단일 캐시·갱신 없음이라는 가정과 기존 캐시의 유효성이다. “TTL을 줄이면 이미 퍼진 응답도 즉시 바뀐다”, “두 번째가 빠르니 캐시 적중 확정”은 오답이다. [W05-K2](CONCEPTS.md#cache)의 전제와 실제 다중 캐시·지연 변동을 함께 설명한다.

<span id="q4"></span>
## Q4 · IP와 이름 조건

제공 서버는 세 요청 모두 같은 루프백 IP·포트에서 TCP 연결과 HTTP 요청을 받는다. URL 이름을 IP로 바꾸면 Host가 `lab.test:18405`에서 `127.0.0.1:18405`로 바뀌어 이 예제의 조건에 맞지 않는다. 421도 HTTP 응답이며 연결 자체 실패가 아니다. 처음 이름으로 돌아가 200을 확인하면 이 실험의 복구다.

`--resolve`는 해당 curl 요청의 주소 매핑을 주므로 DNS 조회 성공 근거가 아니다. HTTPS의 IP URL은 SNI·인증서 호스트명 검증 조건도 바뀔 수 있다. 인증서 검증을 끄지 않고 이름을 보존하는 비교를 사용한다. TLS 세부는 6주차다. “같은 IP니까 항상 같은 웹 응답”은 오답이다. [실습 A2 코드와 본문](LINUX.md#experiment-a)·curl --resolve가 근거다.

<span id="q5"></span>
## Q5 · 초기 임대와 갱신

DISCOVER(탐색) → OFFER(제안) → REQUEST(선택 요청) → ACK(확인)다. 클라이언트 UDP 68과 서버 UDP 67, 같은 거래 ID, REQUEST의 server identifier, ACK의 yiaddr·옵션을 짚는다. OFFER만으로 할당 절차를 마쳤다고 하지 않는다.

기본 타이머를 가정하면 T1=3600×0.5=1800초, T2=3600×0.875=3150초다. 원래 서버로 갱신을 시도하다 응답이 없으면 다른 서버에도 재바인딩을 시도한다. 서버가 타이머를 따로 제공할 수 있으며 갱신은 처음 DORA를 항상 반복하지 않는다. 임대가 만료되면 그 주소 사용을 중단한다. 이 동작을 보기 위해 접속 중인 VM의 임대를 해제하지 않는다. [제공 trace](CONCEPTS.md#dhcp-trace)·RFC 2131 §3.1·§4.4.5를 확인한다.

<span id="q6"></span>
## Q6 · 주소·경로·DNS 옵션

주소는 자기 호스트, /24는 망 범위, .1은 라우터, .53은 DNS 질의 대상이다. .54가 DNS에 응답하지 않으면 주소·경로가 남아 있어도 새 질의가 시간 초과 날 수 있다. 캐시된 이름과 이미 열린 연결에서는 증상이 가려질 수 있다.

필수는 실제 적용된 주소·경로·링크별 DNS 조회와 질의 결과를 나누는 것이다. 이름을 유지한 주소 지정 요청을 비교하면 서비스까지의 경로와 DNS 의존을 나눌 단서가 생긴다. 그 요청의 성공만으로 정상 DNS를 입증하지 않는다. IP URL로 바꿔 실패하면 Host/TLS 조건도 바뀌었는지 본다. “DHCP ACK가 왔으니 모든 통신 정상”은 오답이다. [옵션 표](CONCEPTS.md#dhcp)·[실습 B](LINUX.md#experiment-b)·RFC 2132가 근거다.

<span id="q7"></span>
## Q7 · 설정 출처

127.0.0.53은 로컬 stub일 수 있다. 해당 관리자 환경에서 `resolvectl status` 또는 `nmcli -f GENERAL,IP4,DHCP4 device show`로 링크별 설정과 DHCP 정보를 읽는다. 도구가 없으면 설치·출처를 확인할 때까지 미확인으로 남긴다. 정적 설정·주입 설정 등도 있으므로 IP만 보고 DHCP라고 단정하지 않는다.

필수 요소는 확인된 적용 값과 미확인 출처를 구분하는 것이다. 제공 trace는 DHCP 원리를 분석하는 근거이며 자기 VM의 실제 교환 증거가 아니다. 직접 조회·질의가 막히면 도구·권한·허가 대상과 보충 행동을 남긴다. 임대 해제·서비스 재시작을 보충 방법으로 고르지 않는다.

<span id="development"></span>
## Q8 · W05-D1~D3 개발 사례

| 질문 | 필수 답안 요소·다음 관찰 | 흔한 오답 |
| --- | --- | --- |
| D1 · 질의 성공 뒤 연결 실패 | A/AAAA·SERVER와 curl의 remote/error를 따로 읽고, 포트 대기·경로/정책 등 경쟁 가설을 세움 | DNS 응답만으로 서버 정상 확정 |
| D2 · 일부만 예전 주소 | 질의 시각·TTL·응답 서버·실행 위치를 맞추고 같은/다른 캐시 조건을 비교 | 권한 변경 즉시 모든 캐시 삭제 |
| D3 · DNS 옵션만 변경 | 실제 적용 DNS를 조회하고 새 이름 질의와 이름 보존 주소 지정 요청을 비교, 정상 trace로 되돌려 설명 | 실제 VM의 임대를 끊어 장애 만들기 |

예를 들어 “캐시의 예전 주소”와 “현재 주소의 서비스 포트 미대기”는 다른 가설이다. 질의 응답의 주소를 요청 원격 IP와 대응하고, 이름·프로토콜·포트를 고정해 하나씩 비교한다. 공용 설정을 바꾸지 않고 본인 로컬 예제의 이름→IP→이름 복구를 쓴다. 모르는 서버 내부 상태는 모른다고 남긴다.

이는 O02의 이름 해석과 서비스 연결을 배우는 선수 활동이다. TLS 신원·실제 클라우드 서비스까지 확인하지 않은 상태를 O02 전체 완료로 바꾸지 않는다. 설명과 제공 분석·본인 직접 수행을 따로 확인한다. [교재](CONCEPTS.md) · [실습](LINUX.md) · [전체 개념 색인](../CONCEPT_INDEX.md).
