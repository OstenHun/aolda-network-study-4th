# 5주차 · 이름과 설정 복습

요약: DNS 역할·주소 레코드·TTL과 서비스 요청을 구별하고 DHCP 순서·옵션을 읽는다. 먼저 자기 말로 답한 뒤 분리 해설에서 근거·조건·흔한 오해를 비교한다.

## 답하기 전에

답안은 필요할 때 입력하고 Markdown으로 내려받을 수 있다. 자동 저장되지 않는다. 직접 실행한 원출력은 개인 파일에 한 번 보관하고 여기서는 필요한 근거만 설명한다. [교재](CONCEPTS.md) · [실습](LINUX.md) · [분리 해설](ANSWERS.md).

## Q1. 누가 어떤 답을 찾을까?

프로그램 → OS 리졸버 → 재귀 리졸버 → 권한 서버의 역할을 설명한다. 캐시가 없는 경우의 루트·최상위 도메인·권한 서버 안내와, 캐시가 있는 경우 생략할 수 있는 단계를 비교한다. 모든 질의가 루트까지 가야 할까?

## Q2. DNS 출력에서 무엇을 알까?

제공 응답 `api.example. 180 IN A 192.0.2.20`과 `SERVER: 192.0.2.53#53`의 두 주소·180·A를 풀이한다. 별도 AAAA 응답이 있으면 무엇을 더 알며 무엇을 아직 모를까? NOERROR이고 ANSWER가 비어 있을 때와 NXDOMAIN·timeout도 구별한다.

## Q3. TTL을 계산하고 반례 찾기

한 캐시가 t=0에 TTL 300초인 A를 받았다. 갱신·퇴거 없이 t=120초에 같은 답을 준다면 남은 TTL은? t=100초에 권한 A가 바뀌었다면 t=120초 응답은 반드시 새 주소일까? 질의 시간이 짧다는 사실만으로 캐시 적중이라고 말할 수 있을까?

## Q4. 같은 IP면 같은 요청일까?

[실습 A2](LINUX.md#experiment-a)의 이름 URL은 200, IP URL은 421, 이름 URL 재요청은 200이다. TCP·HTTP·Host 중 무엇이 달라졌는지 설명한다. `--resolve` 요청을 DNS 질의 성공 근거로 쓸 수 있을까? HTTPS에서는 추가로 어떤 이름 조건을 생각해야 할까?

## Q5. DHCP의 제안과 확정

[제공 trace](CONCEPTS.md#dhcp-trace)의 네 메시지를 순서대로 그리고 포트·선택 서버·yiaddr를 짚는다. OFFER를 받으면 모든 할당 절차가 끝났을까? 3600초 임대, 기본 T1/T2 조건에서 갱신·재바인딩 시각을 계산한다. 갱신할 때도 항상 네 단계를 반복할까?

## Q6. 설정 하나만 잘못되면?

ACK에 주소 192.0.2.100, 마스크 /24, 라우터 .1, DNS .53이 있다. 각 값의 역할을 설명한다. DNS만 .54로 바뀌고 .54가 응답하지 않는다면 어떤 조회·새 이름 질의·주소 지정 요청을 비교할까? 실제 VM 설정은 바꾸지 않는다.

## Q7. 실제 설정 출처와 관찰 한계

Linux의 주소·기본 경로·`/etc/resolv.conf`를 읽었다. nameserver가 127.0.0.53이다. 이 값이 원격 권한 서버라는 뜻일까? 주소가 있다는 이유로 DHCP 할당을 확정해도 될까? 다음 읽기 전용 조회와 직접 수행이 막혔을 때 남길 보충을 말한다.

## Q8. 배포 뒤 일부 요청만 실패한다면?

W05-D1~D3를 한 사례로 연결한다. 이름 질의는 되는데 요청이 실패하고, 일부 사용자는 예전 주소를 받는다. DNS·서비스·호스트 설정에서 서로 다른 가설 두 개를 세우고, 한 조건만 바꿔 비교할 관찰과 복구 기준을 고른다. 아직 모르는 부분도 말한다.
