# NAT·접근 정책 · 주소와 허용 조건을 따로 읽기

요약: NAT/PAT는 주소·포트 대응을 만들고 접근 정책은 패킷을 허용하거나 차단한다. 관찰 위치·왕복 방향·상태·규칙 순서를 표시해 서비스 실패의 원인을 좁힌다.

[개인 공부 정리](README.md#personal-notes)에서는 이 교재의 핵심·혼동 구별을 주요 질문과 내 답에 연결한다. 먼저 설명하고 해설과 비교한 뒤, 확인한 근거와 고친 이해를 기존 개인 노트에 보완한다.

## 앞선 통신 흐름에 두 질문 더하기

6주차에서 HTTP 응답과 연결 실패를 나눴고 7·10주차에서 왕복 경로를 확인했다. 여기에 **이 위치에서 패킷의 주소는 무엇인가**, **이 패킷을 어떤 규칙이 판단하는가**를 더한다. NAT·방화벽·라우팅이 한 장비에 있어도 역할은 구별한다.

<span id="w11-k1"></span>
## W11-K1 · PAT에서는 주소와 포트의 대응을 함께 읽는다

NAT(Network Address Translation)는 IP 주소를 변환한다. Basic NAT는 주소를 대응시키고, NAPT 또는 흔히 PAT라 부르는 방식은 TCP/UDP 포트도 대응에 이용한다. **여러 내부 호스트가 같은 외부 주소를 써도 각 흐름을 구별할 수 있다.** 실제 할당·재사용 정책은 구현에 따라 다르며 포트가 매번 반드시 바뀌는 것은 아니다. [RFC3022 §2~2.2](https://www.rfc-editor.org/rfc/rfc3022.html#section-2).

패킷의 5튜플은 `프로토콜, 출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트`다. 다음 표는 학습용으로 만든 **한 NAT 장치의 SNAT/PAT 대응**이다. 캡처나 실제 계정 정보가 아니다. 외부 예제 주소는 문서용 대역이다. CSV 형식의 텍스트도 [내려받을 수 있다](../../labs/week-11/nat-table.txt).

| 흐름·프로토콜 | 안쪽 출발지 | 바깥쪽 출발지 | 원격 목적지 |
| --- | --- | --- | --- |
| A · TCP | 10.11.0.11:51000 | 198.51.100.20:40001 | 203.0.113.80:443 |
| B · TCP | 10.11.0.12:51000 | 198.51.100.20:40002 | 203.0.113.80:443 |
| C · UDP | 10.11.0.11:53000 | 198.51.100.20:41001 | 203.0.113.53:53 |

흐름 B를 양쪽에서 보면 다음과 같다. 화살표 오른쪽은 패킷의 목적지다.

```text
요청 · 안쪽: TCP 10.11.0.12:51000 -> 203.0.113.80:443
요청 · 바깥: TCP 198.51.100.20:40002 -> 203.0.113.80:443
응답 · 바깥: TCP 203.0.113.80:443 -> 198.51.100.20:40002
응답 · 안쪽: TCP 203.0.113.80:443 -> 10.11.0.12:51000
```

B에서는 요청의 출발지가 바뀌고, 돌아오는 응답의 목적지가 대응표에 따라 복원된다. 원격 서버는 이 예에서 내부 주소를 보지 않는다. 같은 외부 주소·다른 포트로 구별한 A와 B를 서로 바꾸지 않아야 한다. UDP에도 포트가 있으므로 C를 TCP 연결과 섞지 않는다.

SNAT는 출발지 변환, DNAT는 목적지 변환을 뜻한다. 포트 전달은 외부 목적지 주소·포트를 내부 서비스로 대응시키는 예다. **변환이 있다고 수신 허용·서버 대기·반환 경로가 자동으로 보장되지는 않는다.** 동적 대응이 사라진 뒤의 패킷을 과거 표만 보고 같은 내부 호스트로 보내겠다고 단정하지 않는다. 정적 대응·필터링 조건은 따로 확인한다.

이 주의 표는 한 가지 구성이며 모든 NAT의 연결·필터링 동작을 정의하지 않는다. 실제 구축과 다중 NAT·ALG·타임아웃 상세는 선택이다.

## W11-K2 · 규칙은 관찰 위치·방향·주소·포트·순서로 읽는다

ACL(Access Control List)은 접근 조건을 규칙으로 나열하는 방식이다. 방화벽은 이런 패킷 조건과 상태 등을 사용해 허용·차단을 구현한다. 제품마다 적용 위치와 평가 방식이 다르므로 ‘ACL이면 항상 이 순서’라고 일반화하지 않는다.

실습의 A=172.30.111.11, B=172.30.111.12, 서버=172.30.111.20은 같은 격리망에 있다. NAT 표의 주소와는 별도다. 서버에서 자신에게 도착하는 패킷은 **input**, 다른 호스트로 중계하는 패킷은 **forward**, 자기 프로세스가 보내는 패킷은 **output** 경로에서 본다. input은 물리 케이블의 방향 이름이 아니다. [nft 주소군·hook 표](https://www.netfilter.org/projects/nftables/manpage.html).

실습의 한 input 체인은 위에서 아래로 다음을 검사한다. 체인은 규칙을 담는 목록이고, hook은 패킷 처리 중 그 목록이 실행되는 위치다.

| 순서 | 조건 | 처리 |
| --- | --- | --- |
| 1 | loopback 인터페이스로 도착 | accept |
| 2 | 추적 상태 established 또는 related | counter → accept |
| 3 | IPv4 출발지 .11, 목적지 .20, TCP 목적지 포트8080 | counter → allow에서는 accept, block에서는 drop |
| 4 | 나머지 TCP 목적지 포트8080 | counter → drop |
| 끝 | 위 규칙에 해당하지 않음 | 기본 정책 drop |

새 A 요청의 첫 SYN은 3번, B 요청은 4번에서 판단된다. `counter`는 규칙에 도달해 조건을 만족한 패킷·바이트 수를 센다. 카운터 자체가 HTTP 요청 수는 아니다. 재전송도 센다. 이 단일 체인에서 3·4번을 뒤집으면 A도 넓은 DROP에 먼저 걸린다. 다만 nft의 accept가 다른 체인·이후 hook의 DROP까지 무효로 만드는 것은 아니다. [nft verdict·counter](https://www.netfilter.org/projects/nftables/manpage.html).

새 요청 `A:51000 → 서버:8080`의 서비스 포트는 목적지8080이다. 응답 `서버:8080 → A:51000`에서는 목적지51000이 된다. 상태 없는 양방향 규칙을 읽을 때 응답에도 목적지8080을 쓰는 오류를 피한다. 실제 임시 포트 범위는 OS·설정에 따라 확인한다.

### NAT와 정책이 함께 있으면

패킷이 정책 위치에 도달하기 전에 변환되었는지 표시한다. 예를 들어 위 NAT 표의 안쪽에서 보는 출발지는10.11.0.12지만 바깥에서 보는 출발지는198.51.100.20이다. DNAT 뒤의 전달 규칙이라면 변환된 목적지를 볼 수 있다. Linux의 구체적인 hook·우선순위와 클라우드의 적용 위치를 확인하고, 원래/변환된 값을 참조하는 기능이 있는지도 구별한다. 그림의 ‘안쪽 주소’를 모든 위치의 규칙에 그대로 쓰지 않는다.

## W11-K3 · 연결 추적은 상태를 제공하고 규칙이 허용을 결정한다

연결 추적(conntrack)은 패킷이 어느 흐름의 어느 방향·상태에 해당하는지 커널이 관리하는 기능이다. NAT의 왕복 대응에도 상태가 필요할 수 있다. 추적되었다는 사실 자체가 서비스 접근 권한은 아니다. **실습에서는 `ct state established,related accept`라는 규칙을 명시했기 때문에** 그 상태의 패킷을 허용한다. [nftables 상태 추적](https://wiki.nftables.org/wiki-nftables/index.php/Matching_connection_tracking_stateful_metainformation).

- `new`는 추적 관점에서 새 흐름의 패킷이다. 모든 패킷이 매번 새 연결은 아니다.
- `established`는 양방향 통신을 본 흐름의 상태다. HTTP 로그인 성공이나 앱의 정상 처리를 뜻하지 않는다.
- `related`는 기존 흐름과 관련 있다고 추적되는 별도 트래픽이다. 예를 들어 관련 ICMP 오류가 있다. 모든 별도 연결이 자동으로 related가 되는 것은 아니다.

실습에서 3번 accept를 drop으로 바꿔도 앞선 2번이 기존 established 흐름을 먼저 허용할 수 있다. **규칙 변경 후에는 새 curl 프로세스로 새 TCP 연결을 만들어 비교한다.** 기존 연결 종료를 강제하거나 호스트 전체 추적 표를 비우지 않는다. 실습의 서버 응답은 별도 output 체인으로 막지 않으며 클라이언트에도 추가 필터가 없다. input의 상태 규칙만 보고 모든 양방향 방화벽을 검증했다고 하지 않는다.

### 클라우드로 옮겨 읽을 때

| AWS 예 | 적용과 평가 | 응답 방향 |
| --- | --- | --- |
| Security Group | 연결된 자원의 네트워크 인터페이스에 적용, 허용 규칙을 모아 평가. 명시적 deny·번호순 첫 일치 방식이 아님 | 상태 기반이어서 허용된 흐름의 응답은 자동 허용되는 동작을 문서에서 확인 |
| Network ACL | 서브넷 경계, 작은 번호부터 첫 일치의 allow/deny | 상태를 저장하지 않으므로 응답 방향도 별도 허용 필요 |

[AWS SG](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-security-groups.html)와 [NACL](https://docs.aws.amazon.com/vpc/latest/userguide/vpc-network-acls.html)의 구별이다. 같은 서브넷 안의 두 컨테이너 INPUT 실습을 NACL 실험으로 부르지 않는다. 추적 예외·규칙 변경 후 기존 연결 수명·다른 공급자 동작까지 같다고 추정하지 않는다. 실제 O01/O03 운영 근거는 본인 자원에서 따로 확인한다.

## 헷갈리는 두 구별

| 섞기 쉬운 말 | 조건을 붙여 설명하기 |
| --- | --- |
| NAT가 내부를 숨기므로 방화벽이다 | 주소 변환과 허용 정책은 다른 역할이다. 정적 매핑·접근 규칙·서버·왕복 경로를 각각 확인한다 |
| 타임아웃이면 서버가 꺼졌다 | DROP·경로 손실·반환 차단 등도 가능하다. 이 실습의 허용 상태에서 서버 중지는 보통 연결 거부, DROP은 제한 시간 실패로 비교하되 메시지만으로 일반화하지 않는다 |

## 개발 질문 · 어디부터 좁힐까?

**W11-D1 · 이유:** 이름 해석과 경로 조회가 성공했는데 HTTP는 실패한다. 아직 확인하지 못한 두 조건과 이를 구별할 관찰은 무엇인가?

**W11-D2 · 조건 변경:** 새 요청만 막고 싶은 규칙을 established 허용 뒤에 넣었다. 열려 있던 연결까지 즉시 끊길 것이라고 예상해도 되는가?

**W11-D3 · 다음 진단:** 서버의 INPUT 카운터가 증가하고 대기 포트도 있다. HTTP 로그는 늘지 않는다. NAT 재구축부터 할 것인가, 어떤 규칙·어떤 요청인지 먼저 비교할 것인가?

자체 설명 연습이며 특정 기업 기출이 아니다. [분리 해설](ANSWERS.md#development)에서 필수 요소와 오답을 확인한다. 다음 단계에서 VLAN·경로·변환·접근 정책 중 어느 것이 실패를 설명하는지 다시 묻는다.
