# 함께 찾을 질문 · 경로가 있는데 왜 막힐까?

요약: 같은 HTTP 서버에 한 클라이언트만 접속하는 이유를 함께 찾는다. NAT 관찰 위치와 접근 규칙을 구별하고, 각자 설명한 뒤 조건을 바꿔 실습으로 확인한다. 모임에서는 근거를 비교한다.

## 중심 질문 · 필수

테스트 서버의 경로와 대기 포트는 정상이다. A의 새 HTTP 요청은 성공하고 B의 새 요청은 제한 시간에 끝난다. 두 클라이언트가 같은 서버·포트를 사용한다는 사실만으로 서버 장애라고 할 수 있을까? **어느 위치에서 무엇을 비교하면 정책 가설을 좁힐 수 있을까?**

1. 앞선 6주차의 HTTP 상태·서버 로그, 7주의 왕복 경로, 10주의 경로 설치를 떠올려 두 가설을 고른다.
2. [nft 매뉴얼](https://www.netfilter.org/projects/nftables/manpage.html)의 `IPV4/IPV6/INET ADDRESS FAMILIES` 표에서 input과 forward를 찾는다. 이어 `VERDICT STATEMENTS`의 accept/drop과 [교재 K2](CONCEPTS.md#w11-k2)를 함께 읽는다.
3. 각자 패킷 방향·주소·포트와 판단 순서를 설명하고 서버가 보게 되는 출발지를 예상한다. 모임에서는 각자의 근거를 비교한다.
4. [실습 A](LINUX.md#lab-a)에서 같은 서버의 규칙 한 항목을 각자 바꾼다. 새 요청과 서버 측 근거를 비교한 뒤 복구한다.

검색이 막히면 `saddr=보낸 쪽`, `daddr=받는 쪽`, `dport=이번 패킷의 목적지 포트`를 먼저 표시한다. 답의 필수 요소는 [분리 해설](ANSWERS.md#development)에서 확인한다.

## 보조 질문 · NAT 표에서 돌아오는 응답 찾기

[RFC3022 §2.2](https://www.rfc-editor.org/rfc/rfc3022.html#section-2.2)의 첫 문단과 Figure3을 보고 [제공 표](CONCEPTS.md#w11-k1)의 B 응답을 안쪽까지 따라간다. 외부 포트 40002가 40001로 바뀌면 어느 대응을 찾게 되는가? 두 호스트가 같은 내부 포트 51000을 쓴다고 왜 같은 연결이 아닌가?

이 예에서는 하나의 SNAT/PAT만 있고 원격 서버는 변환하지 않는다고 가정한다. 실제 NAT 구축이나 임의 외부 요청은 필요하지 않다.

## 보조 질문 · 순서를 바꾸면?

교재 K2의 좁은 허용 규칙보다 넓은 DROP 규칙을 앞에 두면 A의 새 SYN은 어디서 끝날까? 이미 허용되어 추적 중인 연결의 패킷은 같은가? [상태 추적 설명](CONCEPTS.md#w11-k3)을 읽고 연결 상태라는 조건을 덧붙인다.

## 설명에서 실습으로

정답을 외우는 대신 관찰 위치 하나와 다음 검증 하나를 말한다. 각자 찾은 근거로 설명하고 모임에서 해석과 막힌 지점을 비교한다. 규칙 변경 권한이 없으면 표와 설정 분석을 진행하되 직접 수행 보충을 남긴다. 자세한 출력·개인 메모는 별도로 한 번 보관한다.
