# 분리 해설 · 같은 실패를 다른 근거로 좁히기

요약: NAT 표·정책·상태·HTTP 실패 문항의 필수 요소와 오답을 설명한다. 제공 분석, 격리 실습, 실제 클라우드 변경과 참가자 독립 이해는 별도 근거로 확인한다.

## Q1 · B의 왕복 대응

필수 요소는 프로토콜·양끝 IP·포트와 관찰 위치다. B의 왕복 대응은 다음과 같다.

```text
바깥 요청: TCP 198.51.100.20:40002 -> 203.0.113.80:443
바깥 응답: TCP 203.0.113.80:443 -> 198.51.100.20:40002
안쪽 응답: TCP 203.0.113.80:443 -> 10.11.0.12:51000
```

A는40001, B는40002로 구별한다. ‘내부 포트가 같아 충돌한다’는 오답이다. 이 표의 특정 두 할당을 설명한 것이며 모든 NAT가 포트만으로 전역 유일한 연결 ID를 만든다는 뜻은 아니다. [K1](CONCEPTS.md#w11-k1).

## Q2 · C는 UDP

```text
바깥 응답: UDP 203.0.113.53:53 -> 198.51.100.20:41001
안쪽 응답: UDP 203.0.113.53:53 -> 10.11.0.11:53000
```

프로토콜도 대응 조건이다. ‘DNS는 무조건 UDP’라는 일반화까지 답에 붙이지 않는다. 이 제공 사례가 UDP다.

## Q3 · 매핑과 요청 성공

DNAT 뒤 서비스가 대기하는 주소·포트, 그 위치의 접근 규칙과 왕복 경로를 별도로 확인한다. 앞단에서는 외부 목적지, 변환 뒤에서는 내부 목적지를 볼 수 있으므로 **정책의 실제 적용 위치**를 먼저 고른다. ‘포트 전달이 있으니 방화벽도 열렸다’는 오답이다. 특정 공급자의 변환·필터 구현을 추측하지 않는다.

## Q4 · 목적지 포트는 방향에 따라 달라진다

실습의 새 요청 input 규칙은 `saddr=172.30.111.11`, `daddr=172.30.111.20`, TCP `dport=8080`을 검사한다. 응답은 서버8080에서 A51000으로 간다. 상태 없는 반환 방향의 목적지 포트는 이 예에서51000이다. 서비스 포트8080은 응답의 출발지다. 실제 규칙의 임시 포트 범위는 클라이언트 OS·실제 관찰과 대조한다.

실습은 서버 output에 별도 제한을 두지 않았다. 본인 클라우드에 그대로 복사할 규칙 집합이라는 뜻은 아니다. [K2](CONCEPTS.md#w11-k2).

## Q5 · 먼저 끝내는 규칙

새 SYN은 established에 해당하지 않으며 넓은8080 DROP에서 끝난다. 뒤의 좁은 허용에 도달하지 못한다. 이미 앞쪽 established 허용에 일치하면 이 체인의 뒤 규칙까지 내려가지 않는다. ‘허용 규칙이 하나라도 있으므로 항상 통과’는 이 순서 있는 체인에서 틀리다. nft accept 뒤에 다른 base chain/hook이 남을 수 있다는 예외도 유지한다.

## Q6 · 새 연결로 비교

실습은 established/related 허용을 앞에 남겼으므로 기존 연결은 통과할 수 있다. 새 curl 프로세스로 새 TCP 연결을 만들어 같은 목적지를 요청하고, 변경된 규칙·카운터와 대조한다. 추적 상태 자체가 권한인 것이 아니라 상태에 일치하는 accept 규칙이 근거다. ‘모든 규칙 변경은 기존 연결을 즉시 끊는다’와 ‘상태 기반이면 어떤 새 연결도 허용된다’는 둘 다 오답이다. [K3](CONCEPTS.md#w11-k3).

## Q7 · 본인 실행에서 확인할 것

정상 A200/B 제한 시간 실패→block에서 새 A 제한 시간 실패·LISTEN 유지·.11 DROP 증가·새 GET 없음→allow 복구 후 A200·새 GET을 자신의 출력과 비교한다. 오류 번호만으로 판단하지 않는다. 카운터는 정책 교체마다 초기화되며 요청 수가 아닌 패킷 수다. HTTP 로그는 service 재시작 전까지 누적이므로 과거200을 새 성공으로 세지 않는다.

제공한 정상 기준을 그대로 옮기면 직접 수행 증거가 아니다. 본인 환경에서 설정·새 요청·서버 근거·복구를 확인하고 설명해야 한다. 권한이 없으면 개념/분석 확인과 직접 수행 보충을 분리한다. C12에서 역할 구별에 재사용하되 다른 주차 실습의 누락을 대신하지 않는다.

## Q8 · 증상과 가설

이 격리망의 allow 상태에서 서버 중지는 LISTEN 없음·연결 거부, 정책 DROP은 LISTEN 있음·규칙 카운터 증가·시간 제한 실패가 기준이다. 그러나 REJECT도 연결 거부를 만들고 경로 손실도 타임아웃을 만든다. 대기 포트·바인딩, 같은 시점의 규칙·로그·클라이언트 경로를 조회해 구별한다.

HTTP404를 받으면 적어도 그 요청은 TCP 연결과 HTTP 응답까지 도달했다. 파일 경로·서버 로그를 조사한다. 단, 한 요청의404가 다른 출발지나 모든 서비스의 허용을 증명하지는 않는다. [실습 B1](LINUX.md#b1-같은-정책에서-서버만-중지복구).

## Q9 · 공급자 동작의 경계

AWS SG는 연결된 자원의 인터페이스에 적용되는 허용 규칙 집합이고 상태 기반 응답을 처리한다. NACL은 서브넷 경계에서 작은 번호의 첫 일치 allow/deny로 판단하며 상태가 없어 응답 방향도 필요하다. 같은 서브넷 컨테이너의 INPUT은 NACL 재현이 아니다.

컨테이너 실습은 실제 Linux 커널 정책의 직접 수행 근거가 될 수 있지만 자신의 클라우드 자원에서 O01/O03을 수행한 근거는 아니다. 실제 자원·정책·왕복·변경/원복은 허가된 환경에서 별도로 확인한다. [공식 비교](SOURCES.md#클라우드-비교와-선택-참고).

## 개발 질문 해설 · 이유→조건 변경→다음 관찰

| 질문 | 필수 답안 요소·근거 | 흔한 오답 |
| --- | --- | --- |
| W11-D1 | 이름/경로 뒤에도 바인딩·대기·정책·반환이 남음. 서버 ss와 출발지별 새 요청/규칙/로그로 두 가설을 구별 | route get 성공을 HTTP 정상으로 확대 |
| W11-D2 | established 허용 위치와 기존/새 연결을 구별. 새 curl을 사용하고 변경 전후·복구를 비교 | NAT 또는 전체 추적 초기화부터 수행 |
| W11-D3 | 어떤 규칙의 어떤 패킷이 증가했는지 확인. DROP과 앱 미도달, 누적/재설정 카운터를 구별한 뒤 최소 변경 | 카운터 증가를 HTTP 처리 성공으로 해석 |

답안을 가리고 다른 출발지·포트·규칙 순서의 작은 사례로 다시 설명한다. 참가자의 실제 독립 이해·도움 여부는 본인 설명을 듣고 확인하며 교재 열람만으로 판정하지 않는다.
