# 4주차 · TCP와 UDP는 무엇을 맡는가

요약: 소켓·TCP 연결·RTT에서 출발해 바이트 스트림과 UDP 데이터그램을 비교한다. SEQ/ACK·재전송·종료와 흐름/혼잡 제어의 역할을 설명하고 전달과 애플리케이션 처리 성공을 구별한다.

- 선수 개념: [IP·포트·요청](../week-01/ESSENTIALS.md), [다음 홉과 관찰 범위](../week-03/ESSENTIALS.md)
- 읽기: 소켓과 끝점 → RTT → 핸드셰이크 시간축 → 스트림/데이터그램 → 신뢰적 전송 → 개발 질문 → [분리 해설](ANSWERS.md). 계산은 설명 모형이며 실제 참가자 측정값이 아니다.

## W04-K1 · 소켓에서 연결 수립으로

1주차에서 curl과 Python 서버는 IP·포트로 요청과 응답을 주고받았다. 운영체제의 소켓은 프로그램이 이런 통신을 사용하는 창구다. 서버의 대기 소켓과 연결된 소켓을 구별하고, TCP 흐름은 양쪽 IP·포트의 조합으로 읽는다. 포트 하나를 프로세스 ID처럼 취급하지 않는다.

**기억 문장:** 서버가 포트에서 기다리는 것과 클라이언트와 TCP 연결을 수립한 것은 서로 다른 상태다. 일반적인 연결 수립에서는 SYN → SYN-ACK → ACK로 양쪽 초기 시퀀스 번호를 확인한다. 이 메시지 순서와 다음 절의 대기 시간을 함께 읽는다. [RFC 9293 §3.3.2·§3.5](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.5).

## W04-K2 · RTT로 왕복 구간 읽기

**RTT(Round Trip Time)는 보낸 지점에서 대응 응답이 돌아올 때까지의 왕복 시간이다.** 측정 메시지·시작과 끝·목적지·단위를 함께 적는다. ping의 Echo 왕복, TCP의 데이터/ACK 표본, HTTP 요청 전체 경과 시간은 같은 측정값이 아니다. RTT에는 경로와 응답 생성 과정의 지연이 반영될 수 있으며 순수 전파 시간만 뜻하지 않는다. [ping(8)](https://man7.org/linux/man-pages/man8/ping.8.html), [RFC 6298 §2](https://www.rfc-editor.org/rfc/rfc6298.html#section-2).

| 구별 | 기억할 문장 |
| --- | --- |
| 편도와 왕복 | 양방향 지연이 같다는 가정 없이는 편도를 RTT/2라고 단정할 수 없다 |
| 대역폭·처리량과 지연 | 전송 용량·실제 전달률을 높여도 왕복 대기 비용이 없어지는 것은 아니다 |
| 객체 전송 시간 | 크기 L bit를 속도 R bit/s로 직렬화하는 단순 비용은 L/R s다. RTT와 단위·역할이 다르다 |
| 응답 전체 시간 | 연결·TLS·서버 처리·대기·본문 전송 등 측정 구간 안의 비용을 포함할 수 있다 |

예를 들어 RTT 100ms인 경로에서 작은 요청을 앞 응답 뒤에 순서대로 시작하면, 전송량이 작아도 왕복 대기가 누적될 수 있다. 이 예시는 계산 모형이며 실제 성능은 별도 측정한다.

## W04-K3 · 3-way인데 연결 준비가 왜 1 RTT인가

일반적인 TCP 능동/수동 연결 수립을 가정한다. TCP Fast Open·재전송·TLS는 제외하고 양방향 편도 50ms, 호스트 처리·직렬화 지연은 무시한다. SYN을 보내는 순간이 0ms다.

| 시각 | 클라이언트 | 서버 |
| --- | --- | --- |
| 0ms | SYN 전송, SYN-SENT | LISTEN |
| 50ms | SYN-ACK을 기다림 | SYN 수신, SYN-ACK 전송, SYN-RECEIVED |
| 100ms | SYN-ACK 수신, ESTABLISHED로 전이, 마지막 ACK 전송. 데이터를 이어 보낼 수 있음 | 마지막 ACK를 기다림 |
| 150ms | 추가 확인을 기다릴 필요 없음 | 마지막 ACK 수신 후 ESTABLISHED |

**3-way는 메시지 교환 단계 수다. 1 RTT는 클라이언트가 SYN을 보낸 뒤 데이터를 보낼 수 있을 때까지 기다리는 비용이다.** 서버가 마지막 ACK를 받는 시점은 위의 대칭 모형에서 시작 후 1.5 RTT다. 비대칭 경로에서는 그 시점을 고정된 1.5 RTT로 일반화할 수 없다. 마지막 ACK에 데이터를 함께 싣거나 바로 이어 보낼 수 있으므로 ACK에 대한 별도 확인을 한 왕복 더 기다리지 않는다. [RFC 9293 §3.5·Figure 6](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.5).

이후 평문 HTTP 요청과 첫 응답을 기다리는 비용은 [6주차 HTTP 교재](../week-06/CONCEPTS.md#request-cost)에서 연결한다. TCP 연결 준비와 HTTP 요청·응답을 한 단계로 섞지 않는다.

## 헷갈리는 부분 두 가지

| 섞기 쉬운 설명 | 구별할 기준 |
| --- | --- |
| 메시지가 세 번이니 3 RTT 또는 항상 1.5 RTT다 | 메시지 수와 왕복 대기는 다르다. 시작 시점·클라이언트/서버 관점·양방향 지연 가정을 붙인다 |
| ping RTT나 프로그램 경과 시간이 곧 API 응답 시간이다 | 어떤 메시지의 시작/끝을 쟀는지 구분한다. 서버 처리·연결·본문 전송이 포함되는지 별도 확인한다 |

## TCP 스트림과 UDP 데이터그램

TCP는 연결 안에서 **순서가 있는 바이트 스트림**을 제공한다. 앱이 두 번 쓴 경계가 상대 앱의 두 번 읽기와 일치한다고 보장하지 않는다. `recv(3)`은 최대 세 바이트를 돌려주므로 더 짧게 받을 수도 있다. 앱은 고정 길이·길이 헤더·구분자 같은 규칙으로 메시지의 끝을 정한다. [Python 소켓 HOWTO](https://docs.python.org/3.12/howto/sockets.html#using-a-socket).

이번 [실습 코드](LINUX.md#code-reading)는 `hello`와 `network\n`를 나누어 쓰고 개행이 나올 때까지 누적한다. 작은 수신 버퍼로 여러 번 읽는 것은 앱의 읽기 조건이며 실제 TCP 세그먼트 분할을 입증하지 않는다. `sendall` 성공도 상대 앱의 처리 완료 확인이 아니다.

UDP는 메시지별 데이터그램을 보낸다. TCP식 연결 수립·순서 보장·재전송을 UDP 자체가 제공하지 않는다. 그러나 손실이 반드시 발생하거나 모든 용도에서 더 빠르다는 뜻도 아니다. 앱에 필요한 응답·재시도·중복 처리·혼잡 대응은 별도 설계해야 한다. [RFC 768](https://www.rfc-editor.org/rfc/rfc768.html).

| 관찰 기준 | TCP | UDP |
| --- | --- | --- |
| 앱이 받는 단위 | 바이트 스트림의 일부. 메시지 경계는 앱이 정함 | 데이터그램 하나. 수신 버퍼가 작으면 잘릴 수 있음 |
| 시작 | 보통 connect와 연결 수립, 서버 listen/accept | 이 예제는 bind 후 recvfrom, 클라이언트 sendto |
| 전달 실패 | 연결 오류·시간 초과·중단을 앱이 처리 | 전송 호출 성공만으로 상대 도착을 확인할 수 없음 |
| 소켓 구별 | 일반 TCP 연결은 양쪽 IP·port 조합으로 구별 | 로컬 IP·port와 수신 데이터그램의 발신 주소·port를 읽음 |

UDP 소켓에도 `connect()` API가 있지만 TCP 핸드셰이크를 만드는 것은 아니다. 이번 코드에서는 사용하지 않는다. TCP 대기 소켓은 새 연결을 받으며 `accept()`가 돌려준 별도 소켓에서 데이터를 읽는다. 클라이언트는 보통 운영체제가 고른 임시 포트를 쓴다. 같은 서버 포트에 여러 연결이 가능하므로 포트 번호를 프로세스 ID로 보지 않는다.

## SEQ·ACK·재전송을 시간축으로 읽기

아래는 **학습을 위해 만든 가상 패킷 예제**다. 실제 캡처나 본인 실행 결과가 아니다. 연결 수립 이후, 한 방향의 첫 데이터 SEQ=1001, 길이=4 byte, 순서 밖 데이터·번호 순환·SACK은 생략한다. ACK는 다음에 기대하는 바이트 번호이며 1001~1004를 받았다면 ACK=1005다.

| 순서 | 송신자 → 수신자 | 수신자 → 송신자 | 읽을 근거 |
| --- | --- | --- | --- |
| 정상 1 | SEQ=1001, LEN=4 전송 | | 송신자는 확인 전 데이터를 보관 |
| 정상 2 | | ACK=1005 | 연속된 네 바이트를 수신한 확인 |
| 비교 1 | SEQ=1001, LEN=4 전송 | ACK=1005가 경로에서 손실 | 수신했지만 송신자는 확인을 못 받음 |
| 비교 2 | 재전송 타이머 만료 후 같은 범위 전송 | ACK=1005 재전송 | 이미 받은 바이트를 구별해 앱에 중복 전달하지 않음 |

데이터 자체가 손실된 경우에도 확인을 못 받아 재전송할 수 있다. ACK가 없다는 관찰만으로 데이터 손실과 ACK 손실을 구별할 수는 없다. 번호는 순서·중복을, ACK는 수신 확인을, 타이머는 확인이 없을 때 다시 시도할 계기를 제공한다. 실제 TCP는 중복 ACK 등으로 더 일찍 복구할 수도 있으며 위 모형은 모든 손실 복구 알고리즘이 아니다. [RFC 9293 §3.4](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.4), [RFC 6298 §5](https://www.rfc-editor.org/rfc/rfc6298.html#section-5).

SYN과 FIN은 각각 시퀀스 공간 하나를 사용한다. 데이터 길이가 0인 순수 ACK는 그 이유만으로 번호 하나를 소비하지 않는다. 패킷 도구가 상대 번호로 보여 주는지 먼저 확인한다. TCP ACK는 수신 측 TCP의 바이트 수신 확인이며 앱이 읽었거나 데이터베이스에 저장했다는 확인은 아니다.

## 하나씩 기다리기와 미리 여러 개 보내기

교육용 stop-and-wait 모형은 A를 보내고 확인을 받은 뒤 B를 보낸다. 파이프라이닝은 A의 확인이 오기 전에 허용 범위에서 B·C를 보낼 수 있다. 둘 다 번호·확인·실패 처리가 필요하며 실제 TCP를 단순 모형 하나와 동일시하지 않는다.

| 모형 | 같은 시점에 확인을 기다리는 데이터 | 생각할 비용 |
| --- | --- | --- |
| stop-and-wait | 한 단위 | 왕복 응답을 기다리는 동안 전송이 멈출 수 있음 |
| 파이프라이닝 | 여러 단위 | 미확인 데이터를 보관하고 수신 가능량·망 상태를 고려해야 함 |

이번에는 이 역할과 시간 순서만 설명한다. GBN/SR의 재전송 범위는 8주차, 윈도 크기와 처리량 계산은 14주차에서 이어간다.

## 흐름 제어와 혼잡 제어

**흐름 제어**는 수신 버퍼가 감당할 양을 넘지 않도록 송신량을 조절한다. **혼잡 제어**는 경로의 혼잡을 고려해 송신량을 조절한다. 수신 앱이 늦게 읽는 경우와 경로 큐가 붐비는 경우를 섞지 않는다. 송신에는 수신 윈도와 혼잡 윈도 등 여러 제한이 함께 작용한다. [RFC 5681 §2](https://www.rfc-editor.org/rfc/rfc5681.html#section-2).

“수신 버퍼를 늘리면 모든 네트워크 혼잡이 해결된다”는 설명은 성립하지 않는다. 이번 주에는 제어의 대상을 구별하며 혼잡 알고리즘 종류·튜닝·성능 수치는 다음 범위로 둔다.

## 종료·오류와 앱이 확인할 증거

FIN은 한 방향에서 더 보낼 데이터가 없음을 알린다. 양방향이 독립적으로 닫히므로 FIN/ACK가 항상 정확히 네 패킷으로 보이는 것은 아니다. RST는 연결 중단을 나타내며 정상적인 끝과 구별한다. [RFC 9293 §3.6](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.6).

TCP `recv()`의 `b''`는 읽을 바이트를 모두 받은 뒤 상대가 송신 방향을 닫았다는 EOF다. 메시지가 끝나기 전에 EOF가 왔으면 앱 프로토콜 기준으로 불완전하다. 시간 초과는 정해진 시간 안에 읽기가 끝나지 않았다는 뜻으로 EOF와 다르다. UDP의 길이 0 데이터그램은 TCP EOF와 같은 의미가 아니다.

증거는 단계별로 읽는다. `sendall` 반환 → TCP ACK → 앱의 응답/로그 → 업무의 완료 근거를 모두 같은 의미의 성공으로 보지 않는다. HTTP 404 응답도 TCP 연결 실패와 다르다. 재시도가 필요하다면 서버에서 이미 처리했을 가능성도 생각해야 한다. 멱등성 설계는 후속 코드·운영 학습으로 이어간다.

2. **W04-D2 · 조건 변경:** 클라이언트→서버 30ms, 반대 방향 70ms라면 두 시각은 어떻게 바뀌는가?
3. **W04-D3 · 진단:** 1주차 키트의 `elapsed_ms`만으로 연결 수립 RTT를 측정했다고 말할 수 있을까? 어떤 패킷 구간·환경을 확인해야 할까?
