# 4주차 · 분리 해설

요약: 공동 질문과 복습에서 소켓·전달 증거·메시지 경계·SEQ/ACK를 확인한다. 연결 수립 계산은 가정을 붙인 모형이며 해설 열람과 본인의 직접 실습·독립 설명을 구별한다.

- 먼저 [4주차 교재](CONCEPTS.md)의 개발 질문을 설명한다.

## W04-D1 · 같은 편도 지연

SYN이 0ms에 출발하면 서버는 50ms에 받고 SYN-ACK을 돌려보낸다. 클라이언트는 100ms에 받고 마지막 ACK와 데이터를 보낼 수 있다. 서버가 그 ACK를 받는 시점은 150ms다. 1 RTT는 클라이언트의 데이터 전송 전 대기 기준이다. 메시지가 세 번이라는 이유로 세 왕복을 기다리지 않는다.

## W04-D2 · 비대칭 경로

왕복은 30+70=100ms다. 마지막 ACK가 서버에 도착하는 시점은 100+30=130ms다. 1.5 RTT라는 수치는 양방향 편도가 같다는 모형에만 맞는다.

## W04-D3 · 측정 근거

프로그램 경과 시간에는 실행·연결·응답 처리 등 다른 비용이 섞일 수 있다. 클라이언트 쪽 캡처에서 같은 TCP 흐름의 SYN 송신과 SYN-ACK 수신을 짝지어 연결 준비 구간을 읽고, 인터페이스·시각·재전송·측정 환경을 적는다. 순수 TCP 데이터/ACK RTT 표본과도 목적을 구별한다. 루프백 결과를 PC→VM 경로 지연으로 일반화하지 않는다.

**흔한 오답:** 3-way=3 RTT, 서버 수립까지 항상 1 RTT, 비대칭이어도 서버 수립은 1.5 RTT, elapsed_ms=순수 RTT. 본인 실행은 별도 패킷·환경 근거로 확인한다.

## 중심 질문 · 전달과 처리의 근거

필수 요소는 증거의 단계다. sendall 반환은 로컬 송신 API의 완료이며 TCP ACK는 수신 TCP가 연속 바이트를 받았다는 근거다. 앱이 읽기·업무 처리를 마쳤는지는 앱의 응답·로그·저장 상태 같은 해당 프로토콜의 근거로 확인한다. “ACK=주문 저장 성공”은 범위를 넘어선 결론이다.

포트가 잘못되면 서버의 정상 수신 자체가 없을 수 있다. 반대로 앱이 받고 응답 전에 멈추면 클라이언트의 대기만으로 이미 처리했는지 알 수 없다. 두 경우를 같은 재시도로 덮기 전에 서버 대기·양쪽 포트·앱 로그를 나누어 본다. [공식 근거와 읽을 범위](SOURCES.md), [교재의 종료·증거 설명](CONCEPTS.md#종료오류와-앱이-확인할-증거).

## Q1. 대기와 연결

대기 소켓은 새 연결을 받는다. accept가 돌려주는 연결 소켓은 특정 상대와 데이터를 주고받는다. 보통 클라이언트마다 임시 포트가 달라 같은 서버 IP·port에 연결해도 양쪽 IP·port 조합이 다르다. 포트를 PID라고 하거나 한 포트에 한 연결만 가능하다고 하면 보충한다. 근거는 양쪽 getpeername/getsockname 출력과 [W04-K1](CONCEPTS.md)이다.

## Q2. 메시지 경계

recv(3)은 최대 세 바이트이며 한 번에 전체 13바이트가 오지 않는다. 이 예제는 개행까지 누적하고, 그 전에 EOF가 오면 불완전한 메시지로 판단한다. 청크 수는 조건에 따라 달라지며 두 sendall과 두 recv가 대응한다고 가정하면 안 된다. UDP는 두 데이터그램을 각각 읽으며 수신 버퍼가 메시지보다 작으면 잘릴 수 있다. 이번 버퍼 64는 고정 메시지에 충분하다. [코드 읽기](LINUX.md#code-reading), [Python HOWTO](https://docs.python.org/3.12/howto/sockets.html#using-a-socket).

## Q3. 왕복 시간

W04-D2와 같은 모형이다. SYN-ACK은 30+70=100ms에 클라이언트에 도착하고 마지막 ACK는 130ms에 서버에 도착한다. 클라이언트 대기 비용은 1 RTT이며 서버의 시각은 비대칭 조건을 반영한다. 메시지 셋을 세 왕복으로 세지 않는다. 실제 측정값처럼 적거나 TLS·재전송을 포함했다고 하면 조건을 다시 확인한다.

## Q4. SEQ와 ACK

네 바이트는 1001~1004이므로 다음 기대 번호는 ACK=1005다. 같은 범위 재전송은 중복으로 구별해 앱에 다시 전달하지 않는다. ACK 손실과 데이터 손실 모두 송신자가 확인을 못 받게 할 수 있어 ACK 부재만으로 손실 방향을 단정하지 않는다. ACK를 “마지막 받은 번호 1004”라고 하면 다음 기대 번호라는 정의를 다시 읽는다. [설명용 합성 trace](CONCEPTS.md#reliability)는 실제 관찰이 아니다.

## Q5. 기다림과 제어

stop-and-wait는 한 단위의 확인 뒤 다음을 보내며 파이프라이닝은 허용 범위에서 여러 단위를 미리 보낸다. 기다림을 겹칠 수 있지만 미확인 데이터·순서·실패 처리가 필요하다. 수신 버퍼를 넘지 않게 하는 흐름 제어와 경로 혼잡을 다루는 혼잡 제어를 구별한다. “파이프라이닝이면 항상 빠르다”, “버퍼를 늘리면 모든 혼잡이 해결된다”는 조건을 빠뜨린 답이다. [제어 역할](CONCEPTS.md#흐름-제어와-혼잡-제어), [RFC 5681 §2](https://www.rfc-editor.org/rfc/rfc5681.html#section-2).

## Q6. 전달과 앱 성공 · C04 연결

주문 저장 완료는 앱의 응답 의미·서버 업무 로그/저장 근거로 확인한다. HTTP 404는 HTTP 서버가 자원에 대한 응답을 보냈다는 뜻이고 TCP 연결 실패는 HTTP 응답 자체를 받지 못한 경우다. 200도 해당 API가 정의한 의미 이상으로 일반화하지 않는다. 기존 1주차의 정상·404·연결 실패 근거를 재사용하고 본인 IP·port·다음 홉 설명과 조건 변경/복구를 함께 확인한다. 해설 열람만으로 C04 통과가 되지 않는다.

## Q7. 포트 변경

알려진 조건은 서버가 18404에 bind하고 클라이언트만 빈 18405로 향했다는 것이다. TCP는 보통 거절, UDP는 무응답에 따른 시간 초과 또는 운영체제 오류를 보일 수 있다. 오류 문자열을 고정 정답으로 요구하지 않는다. 서버 포트·실행 호스트·실제 bind/accept 출력으로 가설을 좁히고 18404로 되돌려 정상 송수신을 다시 확인한다. “UDP 전송 성공=도착”, “무응답=반드시 패킷 손실”은 근거가 부족하다. [실습 B](LINUX.md#experiment-b).

## Q8. 종료와 측정 범위

TCP b''는 상대 송신 방향의 정상 종료 뒤 EOF이며 시간 초과는 정해진 시간 안에 읽기가 끝나지 않은 것이다. FIN은 방향별 종료, RST는 연결 중단으로 구별한다. 실제 패킷 수는 종료 방식·ACK 결합 등에 따라 달라진다. 루프백 측정은 같은 호스트 내부 경로의 증거이고 PC→VM의 경로 RTT를 대신하지 않는다. 작은 recv 청크 수로 패킷 수를 추론하지 않는지도 확인한다.

## Q9. 내 주소·다음 홉

Q9에서는 같은 VM의 루프백 주소·임시 포트·서버 포트를 Python 출력과 `ss`에 대응한다. Linux에서 `ip -4 route get 127.0.0.1`로 로컬 경로와 lo를 확인할 수 있다. 이전 원격 요청은 그 요청의 실제 대상에 대한 경로 조회에서 dev·via·src와 클라이언트/패킷의 포트를 구별한다. 모든 원격 요청에 게이트웨이가 있는 것은 아니며 같은 망이면 직접 전달할 수 있다. 이전 조회 근거가 없는데 실제 경로를 지어내면 안 된다.
