# 4주차 · TCP와 UDP 복습

요약: 소켓·연결·메시지 경계와 전달 증거를 설명하고 조건을 바꾸어 확인한다. 계산과 제공 시간축은 실측과 구별한다. 답안은 개인 파일로 내려받을 수 있으며 자동 저장·제출되지 않는다.

## Q1. 대기와 연결

TCP 서버가 127.0.0.1:18404에서 LISTEN 중이다. 클라이언트 두 개가 연결되면 서버 포트가 같아도 어떻게 연결을 구별할까? `accept()`가 반환하는 소켓과 대기 소켓의 역할도 설명한다.

## Q2. 메시지 경계

TCP에서 `sendall(b'hello')`, `sendall(b'network\n')`를 호출했다. `recv(3)` 한 번에 전체 메시지가 올까? 완성 여부와 정상 종료를 어떤 기준으로 판단해야 할까? UDP의 두 데이터그램과 비교한다.

## Q3. 왕복 시간 계산

SYN 출발은 0ms, 클라이언트→서버 30ms, 반대 70ms다. 처리·직렬화·손실·TLS·Fast Open은 무시한다. 클라이언트가 데이터를 보낼 수 있는 시각과 서버가 마지막 ACK를 받는 시각을 구한다. `3-way = 3 RTT`를 검토한다.

## Q4. SEQ와 ACK

연결 수립 이후 송신 데이터의 첫 SEQ가 1001이고 길이가 4 byte다. 수신자가 순서대로 받았을 때 다음 기대 ACK는? ACK가 사라져 타이머 뒤 같은 범위가 재전송되면 수신 앱에 두 번 전달해야 할까? [제공 시간축](CONCEPTS.md#reliability)으로 확인한다.

## Q5. 기다림과 제어

한 덩어리를 보내고 ACK를 기다리는 모형과 여러 덩어리를 먼저 보내는 모형을 비교한다. 수신 앱이 천천히 읽는 경우와 경로의 큐가 붐비는 경우는 어떤 제어가 각각 다룰까? 알고리즘 이름이나 성능 수치 암기는 요구하지 않는다.

## Q6. 전달과 처리 성공

클라이언트의 sendall 성공과 TCP ACK가 보였다. 주문 저장 성공을 확정할 수 있을까? HTTP 404를 받았을 때와 TCP 연결 자체가 실패했을 때도 구별하고 다음에 확인할 증거를 고른다. 기존 1주차 실행 근거를 재사용할 수 있다.

## Q7. 포트를 바꾸어 진단하기

서버는 18404, 클라이언트는 사용하지 않는 18405를 향한다. TCP 연결 오류와 UDP 무응답/오류가 나오면 각각 무엇까지 알 수 있을까? 직접 바꾼 조건·정상 복구·아직 모르는 원인을 설명한다. 실행하지 않았다면 예상이라고 적는다.

## Q8. 종료와 관찰 범위

TCP `recv()`가 `b''`를 반환한 경우와 시간 초과는 같은 뜻일까? FIN과 RST도 구별한다. VM 내부 루프백의 핸드셰이크 시간을 PC→VM RTT로 보고할 수 있을까?

## Q9. 내 주소·다음 홉 · C04

같은 VM 안의 127.0.0.1:18404 통신과 이전에 실행한 원격 HTTP 요청을 비교한다. 자신의 실행 위치·출발/목적 IP와 port·선택 인터페이스·다음 홉을 각각 어떤 출력에서 확인할까? 루프백에 기본 게이트웨이가 안 쓰인다는 사실을 원격 통신에도 일반화할 수 있을까? 기존 출력이 없으면 직접 확인할 항목을 말하고 미확인으로 남긴다.
