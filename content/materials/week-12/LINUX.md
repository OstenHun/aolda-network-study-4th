# 12주차 실습 · 제공 무선·VPN 자료와 작은 망

요약: 네 개의 가공 자료를 읽어 무선 연결·경합·VPN 경로를 비교하고 작은 망 구성도를 그린다. 필수는 제공 분석이며 선택 직접 조회와 앞 주차 필수 직접 수행의 상태를 구분한다.

## 실행 환경과 파일

필수 활동은 브라우저와 텍스트를 읽을 도구, 그림을 그릴 종이나 편집기로 가능하다. 아래 파일은 실제로 내려받아 읽을 수 있다. Linux 명령 형식은 출력 읽기를 위한 것이며 학교 장비에서 그대로 실행할 설정이 아니다.

| 파일 | 제공하는 입력 |
| --- | --- |
| <a download href="../../labs/week-12/wifi-state.txt">wifi-state.txt 내려받기</a> | AP 연결·주소·경로·HTTP·정책·서버 로그 A/B/C |
| <a download href="../../labs/week-12/medium-access.txt">medium-access.txt 내려받기</a> | 기본 DCF의 서로 다른/같은 백오프와 ACK 예 |
| <a download href="../../labs/week-12/vpn-routes.txt">vpn-routes.txt 내려받기</a> | Linux 형식 V0~V4 경로·안팎 주소·정책·요청·복원 조건 |
| <a download href="../../labs/week-12/design-brief.txt">design-brief.txt 내려받기</a> | 장비·주소·VLAN·SSID·접근 요구사항. 직접 그릴 설계 입력 |

모두 자체 교육용 가공 자료다. 실제 패킷 캡처나 참가자 실측으로 인용하지 않는다. `.txt`의 명령과 결과는 읽을 대상이다. 임의 VPN 설치·관리 경로 변경·타인 무선 캡처는 수행하지 않는다. 풀이를 먼저 시도하고 [분리 해설](ANSWERS.md)을 연다.

## A · 무선 연결과 매체 접근 분석

### A1 · 동일한 서버 요청을 위치별로 읽기

`wifi-state.txt`에서 A를 기준으로 삼는다. `Connected`와 SSID/BSSID, 주파수·신호·tx bitrate를 찾고 주소와 다음 홉을 읽는다. 요청은 같은 IP의 TCP8080 `/health`다. `GET`은 서버가 HTTP 요청을 읽었다는 로그이며 프레임 수와 같은 단위가 아니다.

1. A와 B에서 변한 입력은 무엇인가? -48/-76 dBm 중 더 강한 쪽을 고르고 두 요청의 성공 여부를 말한다. 한 번의 가공 지연값으로 성능 원인을 확정할 수 있는지도 설명한다.
2. A와 C에서 **정책 한 항목** 외 조건을 고정했다. C의 연결 표시·로컬 경로·서버 LISTEN은 무엇을 지지하며 무엇을 지지하지 않는가? GW DROP 카운터와 새 GET 유무를 함께 읽는다.
3. C의 해당 규칙을 복원하는 조건 카드에서 예상할 요청·로그를 말한다. 실제 복구를 실행한 것으로 기록하지 않는다. B의 원래 위치 복원도 측정 대신 확인할 조건을 설명한다.

정상 기준은 A의 연결·경로·HTTP200·GET이다. 이 자료의 C는 정책 차단 근거를 제공한다. 실측에서 timeout과 GET 없음만 있다면 경로·정책·서버 등 여러 원인이 남으므로 추가 관찰이 필요하다.

### A2 · 남은 백오프를 따라가기

`medium-access.txt` M1에서 각 유휴 슬롯 뒤 A/B의 남은 수를 손가락으로 따라간다. A 송신 동안 B가 감소를 멈추는 위치와 재개 시점을 찾는다. 기다리는 이유를 혼잡·충돌 가능성과 연결한다.

M2에서는 B의 첫 선택만 4→2로 바꿨다. 첫 송신의 결과와 다음 경쟁 A=1/B=3의 순서를 설명한 뒤 첫 선택을 복원해 M1과 비교한다. 실제 시간 계산이나 모든 802.11 기능 재현은 요구하지 않는다.

마지막으로 M3만 보았다고 가정한다. ACK 없음의 원인을 두 가지 이상 제시하고 ‘CSMA/CA면 충돌이 없다’는 주장에 반례를 든다. 같은 순서를 전이중 스위치 링크에 적용해도 되는지도 구별한다. A1/A2의 필수 근거는 **가공 분석이라고 표시한 비교와 자기 설명**이다.

## B · VPN 전후 경로와 작은 망

### B1 · 목적지별로 전달 경로 고르기

`vpn-routes.txt`의 V0/V1을 나란히 읽는다. `via`는 다음 홉, `dev`는 나가는 인터페이스, `src`는 이 조건에서 선택한 출발 주소다. `tun0`는 이번 가상 사례의 터널 이름이며 모든 VPN이 그 이름이나 같은 경로 방식을 쓰는 것은 아니다.

| 목적지 | 각자 찾을 것 |
| --- | --- |
| 서버 10.60.30.20 | V0/V1의 일치 접두사·다음 홉·dev·src와 요청 결과 |
| VPN 끝점 198.51.100.20 | 접속 뒤에도 바깥 경로가 유지되는 이유 |
| 외부 서비스 203.0.113.80 | 분할 터널에서 어느 경로를 쓰는지, 이 VPN의 보호 범위인지 |

안쪽 요청과 응답의 IP·포트를 반대로 짝짓고 서버→기본 GW→VPN 사용자 반환을 그린다. 바깥 단말 LAN과 복호화 뒤 GW에서 볼 수 있는 헤더를 구별한다. 암호화 여부는 경로 행만으로 증명하지 않으므로 V1의 별도 설정 가정을 함께 읽는다.

V2에서는 정책 한 항목만, V3에서는 서버망 경로 한 항목만 바꿨다. 두 실패를 구별할 관찰을 고른 뒤 각각의 복원 카드와 V1을 비교한다. VPN 종료 V4에서는 원래 eth0/default가 유지되는지 V0와 대조한다. 이것은 제공 분석의 복원 비교다.

조건 변경 카드의 `/25`는 V1의 `/24`보다 구체적이다. 목적지 `.20`의 새 경로를 계산한다. 전체 IPv4 터널 카드에서는 외부 서비스와 VPN 끝점을 각각 고른다. DNS·IPv6와 실제 암호화 범위가 자료에 없는 경우 ‘모든 통신 보호’로 확대하지 않는다.

### B2 · 작은 망을 직접 그리기

`design-brief.txt`의 요구를 사용해 **본인 구성도**를 그린다. 도식은 종이·자유로운 편집기로 충분하며 새 발표 양식은 없다.

1. 유선 PC·직원 무선·게스트 무선·AP·스위치·GW·서버를 놓는다. VLAN/서브넷·SSID 매핑·각 게이트웨이와 터널 양끝을 표시한다.
2. 직원 또는 VPN 사용자→서버 TCP8080의 요청·응답 경로를 표시한다. 게스트→서버 차단 위치를 같은 그림에서 찾는다.
3. VPN 암호화가 시작/끝나는 위치를 표시하고 GW 이후 HTTP 구간을 설명한다.
4. AP·스위치·GW 중 한 장치가 고장 났을 때 영향을 받는 경로를 고른다. 구성도와 요구사항을 대조하고 빠진 연결을 고친다.

SSID 이름만 다르게 적거나 VLAN만 그려 놓고 모든 접근 차단이 완성됐다고 하지 않는다. 서버 반환 경로·응답 허용도 확인한다. 기본 예시는 [해설](ANSWERS.md#design-answer)에 있지만 먼저 자기 그림으로 설명한다. B1 비교·B2 구성도가 필수 근거이며 실제 장비 구축 완료를 뜻하지 않는다.

## C12 · 기존 활동 15~20분을 바꾸어 점검하기

별도 시험·발표·팀 기록을 추가하지 않는다. 기존 본인 출력과 복구 근거를 열고 필요한 설명만 확인한다. 아래 항목은 합산 점수가 아니며 빠진 직접 수행은 보충으로 남긴다.

| 시간 추정 | 재사용할 근거와 할 일 |
| --- | --- |
| 0~5분 | [9주차](../week-09/LINUX.md)의 본인 STP 전달/차단 전후·복구, LACP 멤버 단절·복구를 열어 VLAN·STP·LACP 역할을 구별한다. CRC의 오류 검출과 인증·암호화도 구별한다 |
| 5~10분 | [10주차](../week-10/LINUX.md)의 본인 OSPF Full·양방향 metric20→50→20·요청/복구를 설명한다. LS/DV: A-B=2, B-C=3, A-C=9일 때 A→C 비용과 경로를 구하고 B의 C비용 광고가 3→8이면 한 번의 DV 비교를 한다. AS·IGP·eBGP/iBGP의 역할과 정책이 최단 AS 개수보다 우선할 수 있음을 설명한다 |
| 10~15분 | [11주차](../week-11/LINUX.md) 본인 accept→drop→allow의 새 요청·카운터·LISTEN·로그를 사용해 NAT/PAT와 허용 정책을 구별한다. A2의 CD/CA·전이중 예외와 B2의 암호화 경계를 말한다 |
| 필요 시 5분 | 막힌 항목의 조건 하나만 바꿔 설명한다. 새 구성도에서 경로 비용과 접근 정책을 구별한다. 직접 수행 근거가 없으면 해당 앞 주차 실습을 보충할 환경·행동을 정한다 |

비용은 같은 단위의 가상 링크 비용이며 B를 통한 비용은 `A-B + B의 C비용`으로 비교한다. 새 표의 답을 읽었다고 9·10주차 전환/복구나 11주차 규칙 변경을 직접 수행한 것은 아니다. 분석·독립 설명·직접 수행을 각각 확인한다.

## 선택 · 이미 허가된 환경에서 직접 조회

무선 NIC가 있는 본인 Linux에서만 `iw dev`로 장치 이름을 확인하고 `iw dev wlan0 link`를 **본인 인터페이스 이름으로** 조회한다. 연결/위치가 달라진 뒤 같은 필드를 재조회하되 학교 공유기 설정·monitor mode는 바꾸지 않는다. 무선 NIC가 없는 VM에서 이 출력이 나올 것으로 기대하지 않는다. [공식 iw 사용법](https://wireless.docs.kernel.org/en/latest/en/users/documentation/iw.html#getting-link-status)을 따른다.

이미 사용할 권한이 있는 테스트 VPN은 접속 전/후/정상 종료 뒤 `ip route show`와 `ip route get 본인_허가_대상_IP`를 비교한다. **자리 표시를 실제 허가된 IP로 바꾸고** 기존 관리 SSH가 VPN에 의존한다면 별도 콘솔·복구 없이 종료하지 않는다. 키·인증 정보는 기록하지 않는다. 경로 조회는 로컬 선택만 보여 주므로 요청·반환·로그·실제 보호 설정은 별도로 확인한다. 새 VPN 설치와 공용망 변경은 이 선택 활동에 포함하지 않는다.

선택 직접 조회는 제공 분석과 구별해 조건·시각·위치를 개인 파일에 남긴다. 이번 필수 분석에는 스크립트·설치·자원 정리가 필요하지 않다.
