# 12주차 분리 해설 · 관찰 위치로 경계를 확인하기

요약: 복습·개발 질문의 필수 요소와 흔한 오답을 설명한다. 가공 자료의 분석·작은 망 설계·기존 본인 직접 수행을 구분하고 경로·암호화·정책별 근거와 한계를 확인한다.

## Q1 · 연결과 요청의 근거

A/C의 `Connected`·SSID/BSSID는 해당 무선 연결을 지지한다. 주소/로컬 경로는 단말의 설정과 다음 홉 선택을 보여 준다. C의 서버 LISTEN은 TCP8080에서 기다린다는 조건이다. 어느 하나도 왕복 HTTP 성공을 증명하지 않는다.

C에서는 다른 조건을 고정하고 GW의 해당 요청 DROP 카운터 증가·새 GET 없음·timeout을 함께 제공했다. 따라서 이 가공 사례에서는 GW 정책 차단으로 설명할 근거가 있다. timeout만으로 같은 결론을 내리면 안 된다. 해당 규칙 복원 후 A와 같은 HTTP200/새 GET을 확인하는 것이 복구 기준이다. 실제 복구 실측은 이 자료에 없다.

## Q2 · 강한 신호와 보호의 범위

-48 dBm이 -76 dBm보다 수신 전력이 강하다. B도 HTTP200이므로 약한 신호를 연결 불가와 동일시할 수 없다. B의 낮은 tx bitrate는 링크 정보이며 앱 처리량과 같지 않다. 한 번 만든 0.020/0.180초만으로 위치 변화가 실제 평균 지연을 얼마나 바꿨는지 측정했다고 하지 않는다. 실제 비교에는 같은 요청·서버·부하·반복·잡음/재시도 등 추가 근거가 필요하다.

채널은 사용하는 주파수 위치이고 폭이 겹치거나 같은 무선 시간을 경쟁할 수 있다. 이름 변경·숨김은 접근 보호를 대신하지 않는다. 적절한 WPA2-AES/WPA3는 무선 인증·암호화에 관한 것이며 HTTPS는 서버까지의 TLS 신원/전송 보호에 관한 것이다. SSID만으로 상대 신뢰·VLAN 분리·서버 권한을 추정하는 것이 흔한 오답이다.

## Q3 · 유휴 슬롯만 센다

M1은 두 유휴 슬롯 뒤 A=0/B=2다. A 송신·AP ACK 동안 B는 2에 멈추고 다시 필요한 유휴 간격을 지난 뒤 남은 슬롯을 줄인다. 처음부터 4를 새로 센다고 읽지 않는다.

M2에서는 첫 두 슬롯 뒤 양쪽 0이라 동시에 송신하고, **이 모형이 명시한 AP 해독 실패**로 ACK가 없다. 다음 경쟁 A=1/B=3은 한 유휴 슬롯 뒤 A가 먼저 보내고 B=2에 멈춘다. 뒤에 B가 남은 슬롯으로 전송한다. 첫 선택 A=2/B=4 복원 시 M1의 순서다. 실제 ACK 없음은 충돌·데이터 손실·ACK 손실 등 원인이 남으므로 단독으로 충돌을 확정하지 않는다. MAC ACK를 TCP ACK나 HTTP 성공으로 읽지도 않는다.

## Q4 · 적용 조건부터 구별한다

CD는 반이중 공유 Ethernet에서 송신 중 충돌 감지→중단→무작위 대기→재시도다. CA는 무선에서 유휴 확인·간격·백오프와 유니캐스트 ACK/실패 후 재시도로 경합을 줄인다. 같은 슬롯·숨은 단말 등으로 충돌이 남을 수 있다. 현대 전이중 점대점 스위치 링크는 CD를 쓰지 않으며 양방향 동시 송수신한다. 그래도 스위치 큐 혼잡·물리 오류·다른 구간 손실은 가능하다. 모든 유선망이 CD, 모든 최신 무선 전송이 단일 DCF 절차라는 설명도 과도하다.

## Q5 · 목적지마다 고르는 행이 다르다

| 목적지·조건 | 경로와 해석 |
| --- | --- |
| V0 서버 | 일치하는 구체 경로가 없어 default→192.168.50.1/eth0, src192.168.50.10. 이 LAN GW는 서버망으로 전달하지 않는다는 별도 조건 때문에 요청 실패 |
| V1 서버 | /24→10.250.0.1/tun0, src10.250.0.2. default보다 구체적인 경로를 선택 |
| V1 VPN 끝점·외부 서비스 | 둘 다 default→192.168.50.1/eth0. 서버망만 VPN인 분할 터널이며 외부 서비스는 이 VPN 보호 밖 |
| V2 | V1과 로컬 경로·터널이 같고 GW 복호화 뒤 TCP8080 DROP 근거가 있음. 해당 정책 복원이 필요 |
| V3 | 서버망 /24가 없어 default/eth0. 정책을 더 열어도 사라진 VPN 경로를 복구하지 못함 |
| /25 추가 카드 | .20은10.60.30.0/25에도 포함. /24보다 긴 /25→192.168.50.1/eth0를 선택. 표의 뒤에 적힌 행이 우선인 것이 아님 |
| 전체 IPv4 터널 카드 | 외부203.0.113.80은 default/tun0, 끝점198.51.100.20은 /32/eth0. 터널을 운반할 바깥 경로를 유지 |

V2는 해당 정책을, V3는 서버망 경로를 원상 복원하고 V1의 목적지별 route get·HTTP200·새 GET을 다시 비교한다. V4는 tun0/설치 경로 제거와 기존 eth0/default 보존을 V0와 비교한다. 제공된 복구 카드는 예상이며 실제 변경·복구한 경험이 아니다. 로컬 경로표만 보고 중간 전달·반환·암호화까지 성공했다고 단정하지 않는다.

## Q6 · 보호가 끝나는 곳과 반환 경로

안쪽 요청은 `10.250.0.2:51000 → 10.60.30.20:8080 TCP`, 응답은 `10.60.30.20:8080 → 10.250.0.2:51000 TCP`다. 단말 LAN의 바깥 IP는 `192.168.50.10 → 198.51.100.20`이며 이후 집 라우터 NAT 상세는 생략했다. 안쪽 주소와 LAN 바깥 주소를 한 패킷 관찰 위치처럼 섞지 않는다.

서버의 default는10.60.30.1이며 GW가10.250.0.0/24 반환과 응답을 허용한다. 이 흐름에는 NAT가 없으므로 서버가 VPN 사용자 출발 주소를 본다는 가정이다. NAT를 도입하면 관찰 주소·반환 해석도 달라진다.

별도 설정 카드가 단말↔GW 암호화·무결성/피어 인증을 가정한다. 경로표 자체가 이를 증명하지 않는다. GW 복호화 뒤 HTTP 서버 구간은 이 VPN 보호 밖이다. 전체 IPv4 터널 카드도 DNS·IPv6·예외나 종단 앱 보호를 증명하지 않는다. 원격 접속은 단말↔GW, 사이트 연결은 두 망의 GW↔GW 구간을 보통 그리며 각 사이트 내부·정책·반환을 추가 확인한다.

## Q7 · 작은 망의 한 가지 풀이

아래는 입력을 만족하는 개념도다. 실제 포트 설정·중복장비·관리 VLAN은 생략했다. 요청과 응답의 방향을 본인 그림에 더해 설명한다.

```text
직원 PC ─ VLAN10 ─┐
                 │
직원 Wi-Fi ─ AP ─ 스위치 ─ GW(L3/정책/VPN) ─ 인터넷
게스트 Wi-Fi ─┘   │           ║
                 │       암호화 터널 ─ 원격 단말
서버 ─ VLAN30 ──┘

AP: Staff→VLAN10, Guest→VLAN20 (업링크가 두 VLAN 전달)
GW: VLAN10=10.60.10.1, VLAN20=10.60.20.1, VLAN30=10.60.30.1
서버: 10.60.30.20/24, default GW 10.60.30.1
VPN: 공개끝점198.51.100.20, 원격사용자10.250.0.2
```

직원 무선→AP/VLAN10→스위치→GW 허용→스위치/VLAN30→서버 TCP8080, 응답은 서버 GW를 거쳐 직원으로 돌아간다. VPN 사용자는 암호화 터널→GW 복호화·허용→VLAN30 서버, 응답은 GW를 거쳐 같은 사용자 터널로 돌아간다. 게스트→서버는 VLAN20→GW에서 차단하며 내부 직원망도 차단한다. 인터넷용 NAT가 있다고 내부 접근 정책이 완성되지는 않는다.

게스트 인터넷 요구는 지정 DNS·외부 HTTPS·응답 허용이다. 같은 게스트 VLAN 안 단말 격리를 원하면 별도 AP/스위치 정책을 검토한다. SSID 이름/VLAN만으로 이 격리가 자동 생긴다고 하지 않는다. AP 고장은 두 무선 경로에, 스위치 고장은 유선·AP·서버 연결에, GW 고장은 망 간 전달/인터넷/VPN에 영향을 준다. 같은 VLAN 내 통신이 GW 없이 가능한 경우와 서버에 가는 경로를 구별한다. 이번에는 단일 고장 지점을 설명하고 이중화 구축을 추가하지 않는다.

## Q8 · C12의 필수 요소

VLAN은 L2 범위 분리, STP는 L2 루프를 막는 전달 경로 선택, LACP는 여러 물리 멤버를 논리 링크로 묶는다. OSPF는 AS 내부 링크 상태를 교환하고 비용 경로를 계산·설치한다. NAT/PAT는 주소/포트 대응, 정책은 통과 허용을 맡는다. CRC/FCS는 손상 검출이며 인증·암호화·권한이 아니다. K2의 무선 회피와 반이중 검출·전이중 예외를 이 기능들과 구별한다.

LS의 A→C는 직접9보다 A-B-C의2+3=5가 작다. 한 번의 DV 비교에서 B가 C까지8을 광고하면 B 경유2+8=10과 직접9를 비교해 직접9를 고른다. 이는 그 업데이트의 작은 계산이며 전체 망 수렴·루프 없음의 증거는 아니다. AS는 공통 관리/정책의 라우팅 영역, IGP는 AS 내부, eBGP는 AS 사이·iBGP는 같은 AS의 BGP 정보 교환이다. 정책은 단순 AS 경로 개수보다 우선할 수 있다. 실제 모든 BGP 비교 순서를 이번 숫자에 대입하지 않는다.

본인 STP 전달/차단 변화·복구, LACP 멤버 단절·복구, OSPF 양방향 경로/요청20→50→20,11주차 규칙 변경·새 요청/로그의 기존 근거를 짚어 설명해야 한다. 없으면 각 앞 주차의 준비된 구성으로 직접 수행을 보충한다. 이번 제공 표·작성자 실행·해설 열람으로 완료 처리하지 않는다. C12는 활동 15~20분을 대체하며 합산 점수로 필수 직접 수행 결손을 상쇄하지 않는다.

## Q9 · W12-D1~D3 개발 사례

- **D1 설명:** V1 서버는 tun0/서버망 경로, 외부 서비스는 eth0/default다. 보호 가정은 단말↔GW 터널 구간이다. 요청·반환 경로·정책·서버 LISTEN/GET과 실제 보호 설정을 더 확인한다. 흔한 오답은 연결 표시만으로 모든 트래픽 암호화/권한을 확정하는 것이다.
- **D2 조건 변경:** V2는 터널·경로·LISTEN을 유지하지만 GW DROP이 증가하고 새 GET/HTTP 응답이 없다. 서버 재시작은 이 차단 원인을 바꾸지 않는다. 허가된 정책의 해당 항목을 복원한 뒤 같은 요청200/새 GET을 비교한다. 공용망 정책을 임의로 여는 조치로 확대하지 않는다.
- **D3 다음 진단:** 우선 단말의 고정 목적지 route get/dev/src로 V3의 경로 누락 가설을 확인한다. GW의 복호화 뒤 해당 흐름 카운터·정책과 서버 LISTEN/새 GET으로 V2를 구별한다. 실제 환경에서 이 둘 외의 원인이 남으면 반환 경로·상대 인증·서버 상태를 더 본다. 복구 후 같은 출발지/목적지/포트·요청·반환·로그를 다시 비교한다.

필수 요소는 **관찰 위치·한 조건·결론의 한계**다. 모든 실패를 ‘Wi-Fi 문제’ 또는 ‘VPN 문제’ 한마디로 묶지 않는다.
