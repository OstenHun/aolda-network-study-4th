# 12주차 개념 · 무선·망 구성·VPN

요약: AP 연결과 서비스 도달성을 나누고 공유 매체의 대기·재시도를 설명한다. 작은 망에서 장치·분리·고장 지점을 찾고 VPN의 전달 경로·암호화 구간·접근 정책을 각각 확인한다.

[개인 공부 정리](README.md#personal-notes)에서는 이 교재의 핵심·혼동 구별을 주요 질문과 내 답에 연결한다. 먼저 설명하고 해설과 비교한 뒤, 확인한 근거와 고친 이해를 기존 개인 노트에 보완한다.

## W12-K1 · AP 연결은 서버 성공의 증거가 아니다

**기억 문장:** 무선 연결은 로컬 무선 구간의 상태이며 인터넷·서버 도달성은 추가로 확인한다.

AP(access point)는 무선 단말을 네트워크에 연결하는 장치다. 이 예의 AP는 무선 프레임과 유선 LAN 사이를 잇는다. [Cisco의 AP 소개 도입과 Root access point](https://www.cisco.com/site/us/en/learn/topics/small-business/what-is-an-access-point.html)에서 이 역할을 확인한다. 가정용 공유기는 AP·스위치·라우터·NAT·DHCP 기능을 한 상자에 담기도 한다. 기능이 함께 있다고 역할까지 같아지지는 않는다.

SSID는 사용자가 고르는 무선 네트워크 이름이다. BSSID는 개별 BSS(무선 기본 서비스 집합)를 식별하며 보통 MAC 주소 형식이다. 한 AP가 여러 SSID/BSSID를 제공하거나 여러 AP가 같은 SSID를 제공할 수 있다. 이름만으로 같은 장치·같은 VLAN·신뢰할 상대라고 판단하지 않는다. [Cisco FAQ의 SSID·다중 SSID 설명](https://www.cisco.com/c/en/us/support/docs/smb/wireless/cisco-small-business-100-series-wireless-access-points/smb5305-wireless-access-points-frequently-asked-questions.html)을 참고한다.

| 필드 | 읽는 방법 | 이것만으로 모르는 것 |
| --- | --- | --- |
| 주파수 대역 | 2.4/5/6 GHz처럼 사용하는 주파수 범위 | 더 높은 대역이면 모든 방에서 더 빠르다는 결론 |
| 채널·폭 | 대역 안에서 쓰는 주파수 위치·범위. 2437 MHz는 2.4 GHz 채널6 예시 | 채널 번호가 다르면 서로 절대 간섭하지 않는다는 결론 |
| 신호 dBm | 수신 전력의 로그 단위. 같은 기준에서 -48은 -76보다 강함 | 잡음 대비, 혼잡도, 손실 원인, 애플리케이션 속도 |
| tx bitrate | 해당 링크의 송신 전송률 정보 | HTTP 본문이 그 속도로 전달된다는 보장 |
| 보안 방식 | WPA2-AES/WPA3 등 로컬 무선 인증·암호화 조건 | AP 이후 서버까지의 종단 보호·서비스 권한 |

같은 채널의 단말은 무선 시간을 나누어 쓰며 인접 채널·다른 장비의 간섭도 영향을 준다. 채널 폭을 넓히면 가능한 전송률이 늘 수 있지만 간섭·경합 조건도 달라진다. 국가·장비·클라이언트 지원에 따라 사용 가능한 채널과 대역이 다르다. 특정 채널을 학교 장비에 일괄 설정하지 않는다.

WPA3 등 적절한 인증·암호화를 사용하고 상대 네트워크를 확인한다. SSID 숨김이나 MAC 목록은 암호화를 대신하지 않는다. 무선 구간을 보호해도 AP 이후의 HTTP 평문까지 자동 보호하지 않는다. [Apple 안내의 Security·Bands·Channel·Channel width](https://support.apple.com/en-us/102766)는 제품 운용 권고이며 모든 환경의 성능 보장이나 전체 무선 표준은 아니다.

```text
단말 -- 무선 연결 --> AP -- VLAN/게이트웨이 --> 경로/정책 --> 서버
       링크 조회       주소/DHCP 확인          요청·양쪽 로그
```

성립 조건은 제공 자료에 표시된 단일 연결·고정 대상이다. 신호가 약해도 작은 요청은 성공할 수 있고 신호가 강해도 정책에서 차단될 수 있다. [실습 A](LINUX.md#analysis-a)에서 같은 요청의 위치별 근거를 비교한다. `iw` 필드는 [Linux Wireless의 Getting link status](https://wireless.docs.kernel.org/en/latest/en/users/documentation/iw.html#getting-link-status)에 연결한다.

## W12-K2 · 공유 매체에서는 보내기 전후의 조정이 필요하다

**기억 문장:** CSMA/CD는 공유 반이중 Ethernet에서 충돌을 감지해 재시도하고, CSMA/CA는 무선에서 경합을 줄이도록 대기·백오프한다.

CS는 carrier sense, 즉 매체가 사용 중인지 살피는 것이다. MA는 여러 장치가 같은 매체에 접근한다는 뜻이다. 두 장치가 비어 있다고 판단한 뒤 동시에 보내거나 서로의 신호를 못 듣는 상황에서는 충돌이 생길 수 있다.

| 조건 | 매체 접근과 실패 뒤 행동 |
| --- | --- |
| 공유 반이중 Ethernet의 CSMA/CD | 사용 중이면 기다린다. 송신 중 충돌을 감지하면 송신을 중단하고 무작위 백오프 뒤 재시도한다 |
| 기본 802.11 DCF의 CSMA/CA | 필요한 유휴 간격을 기다리고 무작위 슬롯 수로 백오프한다. 다른 송신으로 매체가 바빠지면 남은 수를 멈췄다가 다시 경쟁한다 |
| 현대의 전이중 스위치 점대점 Ethernet | 양방향 동시 송수신이 가능해 CSMA/CD 충돌 검출을 사용하지 않는다. 혼잡·큐 손실·물리 오류까지 없다는 뜻은 아니다 |

백오프(backoff)는 경쟁하는 장치가 다시 시도할 시점을 분산하는 대기다. 무선에서는 송신 중 다른 신호를 확실히 구별하기 어려우므로 Ethernet식 충돌 검출을 그대로 쓰지 않는다. 기본 유니캐스트에서는 수신자의 MAC ACK를 기다리고 ACK가 없으면 실패로 보고 재시도할 수 있다. **ACK 없음은 충돌 확정이 아니다.** 데이터나 ACK의 잡음·손실도 가능하다. MAC ACK는 TCP ACK·HTTP 성공과 계층과 의미가 다르다.

```text
유휴 간격 → A=2, B=4 선택 → 두 유휴 슬롯 → A 송신, B=2에서 멈춤
                                      → ACK·간격 → B가 남은 슬롯 대기
동일 슬롯 선택 또는 숨은 단말 → 충돌 가능 → ACK 없음 → 다시 백오프
```

이는 기본 DCF를 설명하는 모형이다. 실제 마이크로초 타이밍·재전송 한도·WMM 우선순위·OFDMA 스케줄링 전체를 모사하지 않는다. 현대 Wi-Fi의 모든 프레임이 항상 이 한 절차만 쓴다고 일반화하지 않는다. 회피는 확률을 줄이며 충돌 0을 보장하지 않는다. [RFC8325 §6.1](https://www.rfc-editor.org/rfc/rfc8325.html#section-6.1)과 [Cisco의 반이중 적용 조건·What Are Collisions?](https://www.cisco.com/c/en/us/support/docs/interfaces-modules/port-adapters/12768-eth-collisions.html)를 대조한다. 슬롯 분석은 [실습 A](LINUX.md#analysis-a)에서 한다.

## W12-K3 · 망의 분리·VPN 경로·암호화·권한을 따로 그린다

**기억 문장:** 터널은 전달 형태, 암호화는 보호, 정책은 허용 범위를 정한다.

터널은 원래 패킷을 다른 전달 단위 안에 넣어 두 끝 사이로 운반하는 방식이다. 바깥 헤더는 터널 끝으로 가고 안쪽 헤더는 최종 내부 목적지를 가리킨다. VPN은 원격 사용자를 연결하거나 두 사이트의 망을 연결할 수 있다. 원격 접속은 단말↔게이트웨이, 사이트 연결은 보통 게이트웨이↔게이트웨이의 경계를 그린다.

암호화가 구성된 VPN은 지정된 터널 구간의 내용을 보호한다. 터널이라는 말 자체가 암호화 증거는 아니며 실제 프로토콜·협상·설정을 확인해야 한다. [RFC4301 §4.1](https://www.rfc-editor.org/rfc/rfc4301.html#section-4.1)의 IPsec 모드와 [RFC4303 §1](https://www.rfc-editor.org/rfc/rfc4303.html#section-1)·[§3.1.2](https://www.rfc-editor.org/rfc/rfc4303.html#section-3.1.2)의 ESP 보호 범위를 일반적인 터널 개념과 구별한다. ESP도 선택한 보안 서비스에 따라 보호가 다르다.

### 작은 망에서 장치별로 맡기는 일

| 기능 | 이번 설계에서 맡는 일 | 다른 기능과 구별 |
| --- | --- | --- |
| AP·스위치·VLAN | 유선/무선을 잇고 직원·게스트·서버의 L2 범위를 분리 | SSID 이름만 바꿔 격리가 완성되지는 않음 |
| 라우터·L3 게이트웨이 | 서로 다른 서브넷으로 전달 | 경로가 있다고 통과 권한이 생기지 않음 |
| 방화벽 정책 | 출발지·목적지·프로토콜·포트·상태에 따라 허용/차단 | VLAN·NAT가 모든 차단을 대신하지 않음 |
| VPN 게이트웨이 | 터널 종료·상대 인증·보호 처리, 내부로 전달 | 종료 뒤 서버 구간의 별도 보호·정책 필요 |
| DHCP·DNS | 주소 설정 전달·이름 해석 | AP 연결·IP 경로·앱 성공과 별도 |

서브넷마다 게이트웨이를 정하고 VLAN과 SSID의 실제 매핑을 적는다. 게스트→서버는 L3 정책으로 막고 같은 VLAN 안 단말 간 격리는 AP/스위치의 별도 기능을 검토한다. 이번 과제는 그 초기 설정을 실제 장비에 적용하는 작업이 아니다. 장치 한 대가 AP·스위치·라우터를 겸하면 그 한 대의 고장이 여러 구간을 함께 끊을 수 있다.

### VPN 전후의 경로와 신뢰 경계

```text
원격 단말                 인터넷                 VPN GW         서버망
안쪽 10.250.0.2 ── [암호화한 터널 구간] ──> 복호화·정책 ──> 10.60.30.20
바깥 경로는 기존 로컬 게이트웨이로 VPN 공개 끝점 198.51.100.20에 도달
```

예의 분할 터널(split tunnel)은 `10.60.30.0/24`만 VPN으로 보낸다. 나머지 IPv4 목적지는 기존 기본 경로다. 전체 터널(full tunnel)은 기본 경로 등 더 넓은 범위를 터널로 보내도록 구성하지만 VPN 끝점에 닿을 바깥 경로도 유지해야 한다. DNS·IPv6·예외 경로는 별도 확인한다. IPv4 기본 경로 변경 하나를 모든 통신 보호의 증거로 쓰지 않는다.

경로는 7주차의 최장 접두사로 고른다. 서버에는 VPN 사용자 대역으로 돌아오는 경로와 반환 정책이 필요하다. 복호화 뒤 서버까지 HTTP 평문이라면 그 구간은 VPN 암호화 범위 밖이다. 종단 HTTPS를 쓰려면 6주차의 TLS 신원 검증도 필요하다. [RFC4301 §4.4.1](https://www.rfc-editor.org/rfc/rfc4301.html#section-4.4.1)은 보호·우회·폐기 정책을 구별하며 터널 연결 자체를 모든 접근 허용으로 다루지 않는다.

## 헷갈리는 구별 두 가지

- **연결과 도달성:** AP 연결·VPN 터널 수립은 각각의 연결 상태다. 주소 설정·가는 경로·반환 경로·정책·서버 대기와 요청 로그까지 확인해야 서비스 성공을 설명할 수 있다.
- **오류 검출과 보호·허용:** 9주차 CRC/FCS는 우발 손상을 검출하는 수단이다. 상대 인증·암호화·서비스 허용을 제공하지 않는다. 암호화가 있어도 접근 정책의 허용은 따로 필요하다.
