# 14주차 · 느린 요청과 서버 분산을 근거로 설명하기

요약: 지연 네 성분·병목·BDP·윈도 제한을 계산하고 고전 혼잡 그래프를 읽는다. 같은 HTTP 요청의 정상·서버 지연을 비교한 뒤 준비된 프록시와 두 서버에서 분산·제외·복구를 직접 확인한다.

<span id="weekly-study"></span>

## 개인 공부와 오프라인 확인

오프라인 모임 전까지 아래 범위를 공부하고 실습을 시도한다. 모임은 그 주의 학습을 마무리하는 자리로, 막힌 이유와 조건을 바꾼 결과를 설명하고 남은 보충을 정한다. [공동 질문](WORKSHEET.md)은 개인 공부의 출발점으로 쓰고, 모임에서는 근거를 비교한다. 별도 사전 모임이나 발표 자료는 필요하지 않다.

- **개념·문제:** 지연 성분·병목·BDP·cwnd/rwnd·고전 혼잡 그래프, 상태 확인/실제 요청, 평균/꼬리 지연·연결 자원의 관찰. [교재](CONCEPTS.md) → [공식 지정 절](SOURCES.md) → [복습](REVIEW.md) 순서로 읽고, 먼저 답한 뒤 [해설](ANSWERS.md)과 비교한다.
- **실습·분석:** 두 계산 묶음과 제공 분포/연결 사례 분석, A 정상/지연/복구, B 분산/제외/정지/복구. 자원 고갈·고부하 실험은 추가하지 않음. [실행 안내](LINUX.md)의 필수/선택과 제공 분석/직접 수행 구분을 따른다.
- **모임에 가져올 것:** 본인의 근거에서 고른 출력·풀이와 아직 설명이 막힌 질문. 개인 학습 노트에 한 번 정리하고 원시 로그·pcap은 파일 링크로 연결해도 된다. 새 제출 양식은 만들지 않는다.

<span id="personal-notes"></span>

### 개인 공부를 정리할 때

기존 개인 학습 노트에 아래 세 가지를 중심으로 정리한다. 모임 전에는 현재 답과 막힌 지점을 남기고, 모임 뒤에는 확인한 차이와 보충할 부분을 고친다. 정해진 개수·분량이나 새 제출물은 없다.

- **주요 질문과 내 답:** [공동 질문](WORKSHEET.md)과 아래 확인 질문에 먼저 내 말로 답한다. 이유·성립 조건과 공식 자료·실습 근거를 연결하고, [분리 해설](ANSWERS.md)은 시도 뒤에 비교한다.
- **헷갈리는 개념 비교:** [핵심 설명](CONCEPTS.md)에서 망 RTT와 전체 요청 시간, rwnd와 cwnd의 역할·관찰 위치·성공 범위를 비교한다. 두 개념이 다른 결론을 내는 예를 들어 본다.
- **이번 주 꼭 기억하고 이해할 핵심 개념:** [핵심 정리](CONCEPTS.md)의 W14-K1~K3를 길잡이로 용어·역할·동작 순서를 추린다. 필요한 공식은 식·단위·성립 조건과 적용 이유를 함께 설명한다. 예제 주소·일회성 출력값을 외우는 목록으로 만들지 않는다.

실습 근거는 해당 질문·개념 아래에 예상·실제 관찰·수정한 이해와 함께 연결한다. 제공 분석과 직접 실행을 구별하고 관찰하지 않은 결과는 채우지 않는다. 입력 화면을 썼다면 이동 전에 답안을 내려받는다. [전체 개념 색인의 정리 방법](../CONCEPT_INDEX.md#personal-study)은 다른 주차에도 같은 방식으로 쓸 수 있다.

### 오프라인에서 확인할 질문

1. **중심 질문:** TCP 연결 시간은 비슷한데 첫 응답만 느리다면 서버/망 가설을 무엇으로 나눌까?
2. **조건을 바꾸면:** 평균이 같은 두 분포에서 느린 사용자 경험도 같은가? 제공 표의 p95/p99와 함께 설명해 보자.
3. **앞 개념을 다시 쓰면:** 6주 재사용·11주 상태를 떠올려 기존 연결은 되는데 새 연결만 실패하는 두 원인과 다음 관찰을 고르자.

중심 질문을 먼저 설명하고 나머지는 짧은 후속 질문으로 사용한다. [분리 해설](ANSWERS.md)과 실제 근거를 대조하되 답을 본 시도와 독립 설명을 구별한다. 개인 공부에서 마친 정상 실습을 전부 반복하지 않고, 막힌 항목과 한 조건 변경·복구를 각자 확인한다.

### 같은 개념을 더 깊게 연결하기

4·8주 전송 원리를 속도/관측으로 발전시킨다. 15주에는 이 측정 경계와 전체 시간 예산을 자동 점검/재시도에 적용한다. [핵심 개념의 단계별 연결](../CONCEPT_INDEX.md#operations-progression)에서 앞뒤 학습을 찾는다.

## 이번 주의 질문

**요청이 느리면 네트워크가 느린 걸까? 서버 하나를 제외하면 서비스가 정상으로 돌아올까?** [6주차 HTTP 시간](../week-06/CONCEPTS.md)과 [13주차 양끝 요청·로그](../week-13/LINUX.md)를 재사용한다. TCP가 연결되거나 상태 확인이 성공했다는 사실만으로 실제 요청까지 정상이라고 판단하지 않는다.

## 함께 공부하는 순서

1. [공동 질문 W14-D1](WORKSHEET.md)에서 먼저 비교할 관찰을 고른다.
2. [교재 K1\~K3](CONCEPTS.md)와 [짧은 공식 지정 절](SOURCES.md)을 함께 읽는다. 두 작은 계산 묶음과 제공 그래프를 설명한다.
3. 각자 근거로 설명하고 윈도나 서버 대기 조건 하나를 바꿔 확인한다. 모임에서는 각자 시도한 근거와 해석을 비교한다.
4. [실험 A](LINUX.md#delay-lab)에서 같은 요청을 정상→서버 대기→정상으로 제한 반복한다. [실험 B](LINUX.md#proxy-lab)에서 두 서버의 응답 분산·한 서버 제외·복귀와 정지·복구를 직접 대조한다.
5. [복습 문제](REVIEW.md)를 먼저 풀고 [분리 해설](ANSWERS.md)에서 조건·근거를 대조한다. [진행자 안내](FACILITATOR.md)는 막힐 때 돌아갈 설명과 시간 배치를 제공한다.

## 필수와 선택

| 구분 | 이번에 할 일 |
| --- | --- |
| 필수 계산·제공 분석 | 지연 성분·L/R·병목, BDP·이상화한 W/RTT의 두 묶음과 cwnd/rwnd·고전 혼잡 그래프 |
| 필수 직접 수행 A | 동일한 짧은 HTTP GET을 각 단계 5회, 정상·서버 대기 0.2초·복구로 비교. 상태·시간·서버 로그를 대조 |
| 필수 직접 수행 B | 준비된 프록시/서버 두 프로세스 조회·실행, 식별자별 요청 수·상태·시간, 한 서버 제외·복귀와 정지·복구 |
| 선택·후속 | 독립 프록시 초기 구축, Nginx 등 운영 제품, 대규모 부하·p99·재시도 증폭·관측 플랫폼 |

필수 실험은 자기 허가된 Linux 한 대의 루프백에서 가능하다. 서로 다른 포트의 두 프로세스는 호스트 장애 검증이 아니다. 접속·실행이 안 되면 [제공 사례](../../labs/week-14/observations.txt)로 분석하되 직접 수행은 보충한다. 한 사람의 시연·제공 출력만으로 각자의 분산·전환이나 O04/O05 운영 확인을 마치지 않는다.
