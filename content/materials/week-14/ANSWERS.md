# 14주차 · 분리 해설

요약: 계산·혼잡 그래프·지연 관찰과 프록시 전환의 필수 답안 요소를 설명한다. 가정·단위·관찰 위치를 보존하고 제공 분석과 본인 직접 수행을 구별한다. 실제 기업 기출이나 운영 성과를 뜻하지 않는다.

## Q1\~Q2 · 지연과 병목

Q1: L=1,500×8=12,000bit. 전송은 1.2ms·0.12ms, 전파는 각 1ms다. 처리/큐잉은 두 노드 합 1ms이므로 전체는 **4.32ms**다. 출발 처리 시작→목적지 마지막 bit 도착의 모형이다. 목적지 처리·연결 설정·ACK 왕복을 임의로 더하지 않는다.

Q2: R2의 전송만 0.012ms가 되어 **4.212ms**다. 긴 패킷열의 병목은 여전히 R1=10Mbps다. “전체가 10배 빨라진다”는 오답이다. 링크 속도·첫 패킷 도착 시간·충분히 긴 전송의 정상상태 처리량은 다른 값이다. [K1](CONCEPTS.md#delay)의 가정과 공식 계산 자료를 함께 본다.

## Q3\~Q4 · 크기와 전송률

Q3은 크기와 전송률을 나누어 계산한다.

- BDP: 100Mbps×0.1s = 10Mbit. 8로 나누면 1,250,000byte, 즉 **1.25MB**다.
- W: cwnd와 rwnd의 작은 쪽인 **80,000byte**다.
- 윈도 상한: 80,000×8/0.1 = 6,400,000bit/s, 즉 **6.4Mbps**다. 링크100Mbps보다 작다.
- 추가 송신 여유: 80,000−30,000 = **50,000byte**다. W 전체를 추가로 더 보낼 수 있는 양으로 쓰면 안 된다.

Q4: rwnd가 40,000byte이면 W도 40,000byte, **3.2Mbps**다. 이후 RTT가 0.05s이면 **6.4Mbps**다. BDP는 같은 100Mbps에서 RTT가 반이면 0.625MB가 된다. 짧은 요청·앱 대기·윈도 증가·손실·오버헤드·다른 병목을 생략했으므로 실제 속도 보장이 아니다. `W/RTT`를 byte/s로 계산했다면 bit/s 전환×8을 붙인다. [K2](CONCEPTS.md#window).

## Q5 · 그래프의 조건

0\~3은 충분한 새 데이터 ACK 아래 빠르게 증가하는 slow start다. 3\~7은 문턱 8에서 혼잡 회피를 택해 대략 라운드당 1SMSS 증가한다. 7→8은 세 중복 ACK를 신호로 빠른 재전송/복구 후 cwnd를 6으로 낮춘 경계다. 복구 중의 임시 팽창을 그린 것이 아니다. 10→11은 타임아웃 뒤 cwnd 1·ssthresh 4로 재시작한 모형이다. 1→2→4 뒤 완만해진다.

rwnd가 4SMSS이면 미확인 데이터는 그 한도에도 제약받는다. cwnd와 실제 FlightSize는 항상 같지 않다. 그림은 손실 전만 같다고 가정했다. 중복 ACK는 재정렬에서도 나올 수 있고, 초기1/문턱 8과 그래프는 자체 교육값이다. 모든 현대 TCP가 같은 상수·궤적을 쓴다는 설명은 오답이다. [RFC5681 지정 절](SOURCES.md)과 CSV 형식의 원본을 대조한다.

## Q6 · 시간과 가설

제공 latency는 각 5회·HTTP200 다섯 개·HTTP 오류0·통신 실패0이다. total_s 범위는 normal 0.003\~0.005, delayed 0.203\~0.205, recovered 0.003\~0.005다. 이는 가공한 설명값이며 실제 측정이 아니다. 자기 실험의 다른 값은 조건/원인을 확인하고 보존한다.

서버 처리 대기 증가와 경로/혼잡 증가를 가설로 나눌 수 있다. 같은 method·경로·본문/연결 조건을 유지하고 time_connect/first_s/total_s와 같은 식별자의 backend_done을 대조한다. 서버 처리 구간이 늘면 앱 가설을 지지하지만 망의 모든 문제를 배제하진 못한다. first_s−connect_s에도 요청 전송·서버 대기·응답 전송/스케줄링이 있으므로 순수 RTT나 정확한 앱 처리 시간은 아니다. health 경로는 대기하지 않아 여전히200일 수 있다.

## Q7\~Q8 · 설정·상태·실제 요청

Q7: b는 살아 있지만 관리상 후보에서 제외됐다. b의 직접 health200·b를 제외한 설정·프록시 후보 a·사용자 GET 6회 a를 맞춘다. a/b 목록을 복원하고 health/eligible 두 서버·6회 실제200/식별자 분산·양쪽 로그·오류/시간까지 확인해야 복귀다. 제외만으로 서비스 용량이나 호스트 내결함성을 입증하지 않는다.

Q8: `/status`는 조회를 성공했지만 실제 전달 후보가 없어 `/echo`는503이다. 두 서버 프로세스/LISTEN·설정/health·직접 요청·프록시 실제 요청 순으로 복구를 확인한다. 상태 조회 직후 선택한 서버가 멈추면 실제 요청502도 가능하다. 이 프록시는 자동 재시도하지 않는다. 단순히 프록시 리스너가 열렸거나 status200이라고 복구를 선언하지 않는다. [K3](CONCEPTS.md#proxy)·[실험 B](LINUX.md#proxy-lab).

## Q9 · 각자의 수행 범위

확인한 것은 한 호스트 안의 프로세스·포트 단위 분산/전환이다. 호스트·전원·공통 NIC 장애는 검증하지 않았다. O04에는 본인 실행의 정상 분산→제외→복귀/정지→재시작과 식별자·상태·오류/시간이 필요하다. O05에는 정상 기준·두 원인 가설·구별할 관찰·최소 변경·복구 설명을 붙인다. 서버 GET 로그와 프록시/클라이언트의 같은 message를 대응한다. health 추가 요청은 클라이언트가 보낸 GET 수와 구별한다. 제공 자료나 다른 사람의 시연만 읽었다면 개념 분석과 직접 수행 보충을 따로 남긴다.
