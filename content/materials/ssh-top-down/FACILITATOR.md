# 진행자 안내 — VM 준비부터 첫 SSH 로그인까지

요약: 정상 준비·접속·성공한 이유 설명을 중심으로 진행한다. 접속되면 HTTP 실습으로 이어가고 오류가 있는 참가자만 증상별로 확인한다. NAT 실패 사례는 선택 자료이며 60분 순서는 조정안이다.

## 모임 전에 확인할 것

[교재](LESSON.md) → [기록지](QUESTIONS.md) → 아래 해설 순서로 준비한다. 목표는 **자신의 설정으로 접속하고 연결 이유를 설명하는 것**이다. 오류가 없으면 진단 과제를 추가하지 않는다. NAT 사례를 이해하거나 재현해야 기본 학습이 끝나는 것은 아니다.

SSH 접속에는 본인에게 허용된 계정과 인증 방식을 사용한다. [교재 S7](LESSON.md#s7)에서 서버 호스트 키 확인과 사용자 인증을 서로 다른 단계로 설명한다.

시작 전 본인에게 허용된 VM·사양·접속 방법을 확인한다. 기존 자원은 다시 만들지 않는다. 새 자원이 필요하면 할당량·권한을 먼저 확인한다.

VM·접속 준비와 HTTP 실습은 준비 속도에 맞춰 나누어 진행한다.

## 60분 진행안

| 경과 시간 | 활동 | 남길 증거 |
| --- | --- | --- |
| 0~5분 | S0. 목표·본인 준비 상태 확인 | 오늘 할 일과 직접 실행 여부 |
| 5~20분 | S1~S4. 자원·망·라우터·VM 준비 또는 기존 값 확인 | 설정 카드·콘솔 OS 결과 |

| 35~43분 | S8. 성공한 경로를 그려 서로 설명 | 설정의 역할과 이번 접속으로 확인한 것 |

생성 대기나 인증 준비가 길어지면 해당 시간에 기존 자원 읽기로 전환하거나 다음 회차로 나눈다. 모든 생성·접속·HTTP를 한 번에 완료했다고 표시하지 않는다. HTTP 전체는 [기존 진행안](../week-01/FACILITATOR.md)으로 이어간다. 이미 VM·접속이 준비된 사람은 앞부분을 설정 설명으로 줄이고 HTTP에 시간을 쓴다.

## 접속한 사람과 막힌 사람을 함께 진행하기

**접속했다면** hostname·whoami 결과와 설정 카드를 대조하고 “왜 이 주소로 연결됐나?”를 설명하게 한다. 이어 두 셸·파일 전달·HTTP 실습으로 간다. 설정을 일부러 잘못 바꾸거나 NAT 장애를 재현시키지 않는다.

**접속이 막혔다면** S7의 증상표에서 현재 단계를 고른다. 5분 이상 막히면 시연·제공 자료 분석으로 전환하고 직접 실행 보충을 남긴다. 시간 초과에 경로·정책·서비스를 확인하며, 이미 사용자 인증까지 왔다면 계정·인증을 먼저 확인한다.

더 살펴보고 싶다면 [선택 NAT 질문 해설](#nat-answers)로 주소 변환과 정책의 관계를 비교한다.

## 설명이 막힐 때 던질 질문

“무엇을 설정할까?” → “이 값이면 무엇을 예상하나?” → “어느 출력으로 확인했나?” → “예상과 같거나 다른 이유는?” → “다음 VM에서도 설명할 수 있나?”

초보자가 막히면 진행자가 주소 표 한 칸을 읽어 주고 다음 칸을 참가자가 채우게 한다. 용어 암기보다 현재 그림의 위치와 역할부터 설명한다. 짝 안에서 실행하고, 출력을 읽고, 설명하는 역할을 바꿔 본다. 한 사람이 실행한 결과는 그 사람의 기록으로 남긴다.

## 기본 질문 해설

| 질문 | 해설·작은 재확인 |
| --- | --- |
| Q0 | Active와 TCP 응답만으로 셸 사용은 확인되지 않는다. 로그인 뒤 원격 대상·계정·명령 결과를 본다. |
| Q1 | 이미지는 OS 기반이고 IP는 네트워크·주소 할당 결과다. 새 VM의 실제 IP를 따로 확인한다. |
| Q2 | /24는 앞 24비트가 같은 범위, /32는 한 주소다. 포함된 주소여도 이미 사용 중이면 임의 할당하지 않는다. |
| Q3 | 게이트웨이는 다음 홉이고 접속 목적지는 VM에 연결한 주소다. 라우터 외부 주소를 VM 주소로 대신하지 않는다. |
| Q4 | 웹 콘솔은 관리 경로로 VM의 화면과 키보드를 제공한다. SSH는 VM의 TCP 22로 들어간다. LISTEN은 서버가 기다리고 있다는 뜻이므로 PC 경로와 보안 그룹까지 확인한 것은 아니다. |
| Q5 | Floating IP가 내부 IP에 연결되고 VM은 기본 게이트웨이를 통해 다른 망으로 보낸다. 각각 자기 값으로 설명하게 한다. |
| Q6 | 가상 포트는 VM의 네트워크 인터페이스를 망에 붙이는 자원이고 TCP 22는 SSH 서버의 통신 끝점 번호다. ingress 출발지 범위는 규칙이 적용되는 지점에서 보이는 주소와 맞아야 한다. |
| Q7 | 호스트 키는 서버 신원을 확인하고 계정의 인증 수단은 사용자 로그인을 인증한다. 지문 확인만으로 로그인이 끝난 것은 아니다. |
| Q8 | 지금 사용한 경로·대상·포트·계정에서 해당 접속이 성공했다. 모든 사용자·서비스 접근의 증거는 아니다. |
| Q9 | 접속 대상·hostname·whoami를 함께 대조하고 각 셸의 pwd와 원격 ls를 본다. 이름 하나만으로 동일 VM을 보장하지 않는다. |
| Q10 | 원격 curl의 루프백은 VM 자신이다. 404도 HTTP 응답이며 TCP 연결 실패와 다르다. |

## 짝에게 설명할 질문 해설

1. VM이 바뀌면 주소·계정·서버 키를 모두 다시 확인한다. 같은 배포판이어도 같은 서버 신원이 아니다.
2. 두 창은 같은 VM의 다른 셸일 수 있다. 작업 폴더는 셸마다 따로 확인한다.
3. SSH 성공은 TCP 22의 그 접속에 대한 증거다. 다른 포트의 리스너·정책은 별도다.
4. 127.0.0.1은 명령이 실행되는 호스트 자신이다. PC와 VM은 다르다.

## 마무리할 때 확인할 것

설정 카드·본인 경로 설명·실제 SSH 로그인 증거와 짝 변형 답을 확인한다. 장애 경험은 채점하지 않는다. 기존 자원 사용자는 새 VM 생성과 구분한다. 환경 미준비자는 이해 활동과 직접 실행 미완료를 함께 기록한다.

## 선택 NAT 질문 해설

- **D1:** 캡처 시점·필터·위치가 맞아도 VM에 도달하기 전 정책에서 막혔을 수 있다. 경로와 정책을 모두 확인해야 한다. 사용자 인증에 도달했다는 근거가 없으므로 비밀번호부터 바꾸는 것은 현재 증상을 구분하는 데 도움이 되지 않는다.
- **D2:** 같은 NAT 주소를 공유하는 다른 사용자도 이 주소 조건에 일치할 수 있다. /32는 주소 하나를 뜻하며 사람 한 명을 인증하지 않는다.
- **D3:** PC 송신 패킷을 캡처하지 않아 알 수 없다. NAT는 주소뿐 아니라 포트도 바꿀 수 있다.
- **D4:** 앞서 SYN·SYN/ACK·ACK와 SSH 교환이 있었다. RST 하나로 중단 원인을 확정하지 않는다. 호스트 키 검사에서 멈췄다면 신뢰할 수 있는 경로로 서버 지문을 대조한 뒤 사용자 인증 여부를 별도로 확인한다.

## 사이트의 주소 예시

주소와 VM 이름은 설명용 예시다. 본인에게 허용된 주소·계정·인증 방식은 환경 안내에서 확인한다. 비밀번호·개인 키·실제 접속 정보는 공유 답안에 넣지 않는다.
