# 13주차 · 진행자 준비와 시간 배치

요약: 개인 공부에서 개념·문제·실습을 준비하고 오프라인 한 번에서 설명·조건 변경·직접 수행을 확인한다. 준비·복구와 제공 분석의 경계를 지키며 막힌 필수 항목을 보충한다.

## 시작 전 준비

[실습의 허용 조건](LINUX.md#preflight)을 실제 환경에서 먼저 확인한다. 현재 허가/접속·자원·할당량·정책 소유권·별도 콘솔/복구를 과거 성공 기록만으로 확정하지 않는다. 자료 제작 때문에 VM/유료 자원을 새로 만들지 않는다. 기존 두 VM 또는 허가된 PC→기존 VM 중 가능한 경로 하나를 고른다.

테스트 전용 보안 그룹은 정책 소유자가 **미리** 준비한다. 대상 port에 연결되고 다른 자원과 공유하지 않으며 관리 SSH 규칙과 분리되어야 한다. 모든 적용 그룹/remote group을 읽어 8080의 중복 허용을 배제한다. 호스트/클라이언트 egress는 실험을 허용하고 별도 콘솔에서 복구할 수 있어야 한다. 불명확한 허용을 지우거나 전체 인터넷 허용으로 넓혀 실험을 맞추지 않는다.

1주차 server.py와 새 cloud_service.py를 같은 폴더에 준비한다. [코드 읽기](LINUX.md#code-reading) 순서대로 원래 HTTP 처리와 바인딩/TLS 실행기의 역할을 구별한다. 사용하지 않는 8080/8443과 실제 서버 IPv4를 확인한다. 기존 서버가 쓰는 port를 강제로 비우지 않는다. 다른 port를 택하면 명령·URL·규칙·예상을 모두 같이 바꾼다.

TLS 초기 준비는 [6주차 tls-setup](../week-06/FACILITATOR.md#tls-setup)을 재사용한다. 사용할 날 CA/서버 인증서·유효기간/SAN·신뢰 경로를 확인하고 개인키는 공유하지 않는다. 새 실행기로 같은 VM 주소:8443에 대기하며 해당 출발지만 허용한다. DNS는 기존 5주 근거와 준비된 테스트 이름/현재 목적지를 연결한다. 이름이 없으면 강제 매핑 비교와 실제 DNS 근거를 분리하고 빠진 확인을 보충한다. 초기 구축은 참가자의 새 필수 과제가 아니다.

## 리허설 정상·실패·복구

A1 자원/왕복 그림→A2 본인 8080 rule 생성·정상 200/같은 message의 양끝 로그→A3 본인 rule 제거·새 요청 비교→동일 조건 복구·새 200/로그→A4 TLS 정상/틀린 이름/복구→서버 종료·본인 임시 rule 정리 순서다. 실패가 반드시 timeout이어야 하는 것은 아니다. 실제 오류와 설정을 대조한다. 삭제 뒤 계속 200이면 중복 그룹·다른 port·상태/전파를 먼저 확인한다.

본인 rule ID/조건을 show로 대조한 뒤에만 제거한다. 복구의 create가 실패하면 별도 콘솔/정책 소유자에게 복구를 맡긴다. 관리 경로·그룹 전체·공용망·연결 추적을 지우지 않는다. 참가자별 직접 수행은 본인 결과로 확인하며 진행자의 시연만으로 완료 처리하지 않는다.

## 공식 절과 용어 풀이

[출처표](SOURCES.md)의 필수 약 10분을 기존 공동 탐색에 배치한다. port=망 연결 객체, ingress/egress=그 port 기준 들어옴/나감, fixed/floating=할당 주소/외부 대응 주소, DF=단편화 금지, PTB=너무 큰 패킷 통보를 풀이한다. 영문 검색이 막히면 K1 자원표·K2 관찰표·K3 크기 식으로 돌아온다. 공식 문서 전체 필독·장기 발표 준비는 추가하지 않는다.

## 한 주의 개인 공부와 오프라인 확인

개인 준비는 [학습 홈의 정리 안내](README.md#personal-notes)에 따라 주요 질문과 내 답·헷갈리는 개념 비교·꼭 기억하고 이해할 핵심을 살핀다. 노트 분량을 평가하지 않고 이유·조건 변경·관련 실습 근거로 확인한다. 모임 뒤에는 틀린 설명과 남은 보충만 기존 개인 노트에서 고치며 중복 제출을 요구하지 않는다.

[학습 홈의 개인 공부 범위와 세 확인 질문](README.md#weekly-study)을 오프라인 모임 전까지 준비한다. 모임은 그 주 학습을 마무리하고 남은 보충을 정하는 자리다. 개념·공식 지정 절·복습과 준비된 실습의 정상→변경→복구는 개인 공부에서 시도한다. 모임 전 완성 답안·발표 자료를 요구하지 않으며 막힌 질문과 본인 근거를 가져오게 한다. 진단 원인을 가리는 과제는 정상 기준과 도구까지만 준비한다.

오프라인은 한 번의 모임에서 **설명 → 새 조건 → 본인 실습/분석 확인 → 보충 결정**으로 진행한다. 아래 60분은 시간 배분 예시이며 모임 길이나 추가 회차를 확정하는 표가 아니다.

| 시간 예시 | 진행자가 확인할 것 |
| --- | --- |
| 0~10분 | 개인 공부에서 막힌 질문과 2~4학습 단위 전 개념 하나를 골라 근거로 설명 |
| 10~25분 | 학습 홈의 중심 질문 → 조건 변경. 각자 시도한 근거·막힌 이유 비교 |
| 25~50분 | A 자기 자원 조회·양끝 요청·테스트 전용 규칙 한 조건 변경/복구와 DNS/TLS 근거 연결, B 제공 크기 분석. 이미 수행했다면 근거를 보고 다른 한 조건의 판단·변경·복구 확인 |
| 50~60분 | 정상 복구·받은 도움·미완료 구분, 개인 학습 노트에 필요한 보충과 다음 질문 연결 |

개인 학습 시간을 고정된 2~3시간으로 제한하지 않는다. 필수 범위를 먼저 공부하고 실제 막힘에 따라 시간을 배분한다. 주차를 미리 분할하거나 필수 기준을 낮추지 않으며, 개인 공부 후에도 해결되지 않는 항목만 보충한다. C04/C08/C12/C16은 해당 주 기존 설명·실습을 대체하고 점검을 별도로 더하지 않는다. 한 사람의 답·팀 합의·파일 제출은 개인 이해/직접 수행의 증거가 아니다.

## 환경이 막힐 때와 다음 질문

가공 cloud-case C0\~C4와 mtu-cases M0\~M4를 분석하고 11주의 준비된 격리 정책 실습을 재사용한다. 분석/시뮬레이터 직접 수행과 실제 클라우드 직접 운영 미완료를 구별한다. 보충할 대상·허가·정상→한 조건→복구·양끝 로그를 정한다. 자료가 있다는 사실을 수행·이해로 기록하지 않는다.

O01\~O03 근거를 기존 5\~6·11주와 연결하고 O04/O05는 14\~16주로 넘긴다. 다음 기존 복습에서 “정상 200 뒤 한 서버가 느려지면 어디의 시간/오류를 봐야 할까?”를 묻는다. 프록시/분산·자동화의 본문/새 코드는 이번에 미리 추가하지 않는다.
