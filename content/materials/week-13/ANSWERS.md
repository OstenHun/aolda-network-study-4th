# 13주차 · 자원·요청·크기 분리 해설

요약: 복습 9문항과 개발 질문의 필수 답안 요소·흔한 오답·확인 근거를 정리한다. 계산/가공 분석과 실제 자기 환경의 운영을 구별하며 O01~O03에 빠진 직접 수행은 보충한다.

## Q1 · 연결 객체와 전송 계층 번호

Neutron port는 VM NIC 등을 가상 network에 연결하는 객체이며 fixed IP·MAC·적용 그룹을 갖는다. TCP 8080은 그 VM의 로컬 주소에 프로그램이 대기하는 서비스 번호다. VM→port ID→fixed IP를 확인하고 ip·ss의 로컬 주소:8080과 대응한다. 두 port의 번호나 이름이 같다고 답하는 것은 오답이다. 근거는 [K1](CONCEPTS.md#cloud-objects)·실습 A1이다.

## Q2 · 선택된 왕복 경로

C0의 두 주소는 192.0.2.0/24 안에 있으며 제공 route get은 직접 연결 dev/src다. 같은 subnet 요청은 해당 가정에서 gateway를 다음 홉으로 쓰지 않는다. router가 있다는 사실만으로 경유를 그리지 않는다. 외부 floating IP198.51.100.20을 쓴다면 fixed IP192.0.2.20으로의 DNAT와 반환/역변환·정책 관찰 위치를 따로 그린다. 이 주소들은 문서용이고 실제 대상이 아니다. 자기 환경은 양쪽 경로와 자원/요청 근거로 확인해야 한다.

## Q3 · 관찰로 가설 나누기

예를 들어 원격 주소에서 서비스가 대기하지 않는 가설과 경로/접근 정책에서 막힌 가설을 나눈다. 서버 ss의 주소/포트·프로세스와 로컬 사설 주소 요청을 먼저 확인하고, 클라이언트 route/src·실제 목적지 및 port의 모든 그룹·호스트 정책·반환을 대조한다. 루프백127.0.0.1만 대기하면 원격 사설 주소 요청을 받지 못한다. GET 로그 없음은 HTTP까지 안 왔다는 단서이며 보안 그룹 차단의 단독 증거가 아니다. DNS 성공·VM 실행 중·ping 성공만으로 HTTP 정상을 단정하지 않는다.

## Q4 · 합쳐진 허용과 상태

모든 적용 그룹에서 TCP 8080·포트 범위·전체 프로토콜·넓은 CIDR·remote group 허용을 찾는다. Neutron 그룹은 허용을 합치므로 한 그룹의 삭제가 다른 그룹의 허용을 덮지 않는다. 새 프로세스로 요청했는지, 실제 port/규칙을 바꿨는지, 반영/상태 추적 조건도 확인한다. 관리 규칙·보안 그룹 전체·연결 추적을 삭제하는 답은 오답이다. 본인 rule의 원래 속성을 복구하고 새 요청/양끝 로그로 확인한다. [공식 Security groups](https://docs.openstack.org/neutron/latest/admin/intro-os-networking.html#security-groups)·A3에 연결한다.

## Q5 · 같은 조건과 새 근거

C1은 w13-before의 0/200/로그, C2는 rule 제거 뒤 새 w13-block의 28·HTTP 없음/LISTEN 유지/해당 로그 없음, C3은 w13-after의 0/200/새 로그다. 제공 사례의 28을 모든 구현의 필수 오류 코드로 일반화하지 않는다. 방향·주소족·프로토콜·8080·remote IP·group이 같으면 정책 조건 복구를 비교할 수 있고 rule ID는 새로 생긴다. 예전 로그만으로 복구를 확인하지 않는다. 이는 가공 분석이며 자기 클라우드/O03의 실제 변경·복구 근거가 아니다. 직접 수행은 A3의 본인 출력으로 따로 확인한다.

## Q6 · 강제 매핑과 신원

--resolve는 DNS를 우회해 실제 접속 주소를 지정한다. URL 이름/SNI/검증 이름을 유지한 연결은 확인하지만 DNS 질의 성공을 증명하지 않는다. 실제 이름 해석은 DNS 응답/리졸버·캐시/NSS 근거로 분리한다. 같은 CA/주소에서 wrong.test만 바꾸면 SAN에 그 이름이 없어 검증 실패(보통60), HTTP 미수신·해당 GET 로그 없음이 예상이다. TCP/TLS 시도까지 없었다는 뜻은 아니다. 정상 이름으로 복구해 0/200/새 로그를 확인한다. -k는 신원 검증 복구가 아니다. [6주 TLS](../week-06/LINUX.md#tls-lab)와 A4를 재사용한다.

## Q7 · 같은 기준으로 바이트 빼기

M0에서 내부 1500+추가 50=외부 1550으로 1500을 넘는다. 내부 IP 한도는 1450이다. 옵션 없는 IPv4/TCP 데이터는 1450−20−20=1410bytes, IPv6/TCP는1450−40−20=1390bytes다. IPv4 TCP 옵션 12bytes를 실제 넣는 세그먼트의 데이터 예산은 1398bytes다. RFC6691의 MSS **광고값**은 고정 헤더만 빼고, 실제 송신 데이터는 옵션 등을 반영한다. 이 예산이 모든 세그먼트/HTTP 본문의 크기는 아니다. H=50은 주어진 가정이며 실제 터널의 종류/오버헤드를 확정하지 않는다. [K3](CONCEPTS.md#packet-size)·M0/M4가 근거다.

## Q8 · 조각과 오류 통보

첫 조각 total=1444(20+1424), 둘째 76(20+56), payload 합 1480으로 원래 값과 같다. 둘째 offset=1424/8=178이다. 첫 조각 MF=1·마지막 MF=0이며 조각 total 합 1520에는 IP 헤더 하나가 추가되어 있다. DF=0에서 가능한 구성이지 유일한 분할 크기는 아니다. DF=1이면 해당 라우터는 너무 큰 패킷을 버리고 ICMPv4 type3/code4·다음 홉 MTU를 알린다. IPv6 라우터는 단편화하지 않고 ICMPv6 PTB를 보내며 출발지가 크기 조절/필요한 단편화를 맡는다. 목적지의 재조립과 라우터의 역할을 섞지 않는다.

## Q9 · 크기 의존은 단서

MTU/PMTUD 문제 외에 서버 처리 지연·응답 방향 정책·손실도 가능하다. 같은 경로/프로토콜/방향을 유지한 크기 비교와 양끝 패킷 길이·관련 ICMP/재전송, 서버 요청/응답 시점·상태를 함께 본다. HTTP 본문 길이와 개별 IP 패킷 길이를 동일시하지 않고 호스트 offload 관찰도 구분한다. 공용 ICMP·MTU를 임의 변경하지 않는다. 게스트의 eth0 MTU만으로 물리 호스트 VXLAN/설정을 확정할 수 없으므로 권한 있는 설정 근거가 필요하다. 제공 사례 분석과 실제 측정을 구별하면 된다.
