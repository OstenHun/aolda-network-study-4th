4. ARP로 첫 이웃의 MAC 찾기

IPv4 Ethernet에서 ARP는 다음 홉의 IPv4 주소에 맞는 링크 주소를 알아낸다. 이웃 캐시에 정보가 있으면 새 ARP 요청은 보이지 않을 수 있다.

목적지 IP를 아는데 왜 ARP가 필요한가

IP 주소는 어디로 끝내 보낼지 또는 어느 이웃을 먼저 찾을지 결정하는 데 쓰인다. Ethernet 프레임은 현재 링크에서 받을 상대의 MAC도 필요하다. Linux는 경로를 먼저 고른 뒤, 선택한 다음 홉의 IPv4 주소와 MAC의 대응을 이웃 정보에서 찾는다. 없으면 해당 링크에서 ARP 요청을 보낼 수 있다.

아래는 직접 연결된 두 호스트를 가정한 설명용 흐름이다. 실제 아올다 패킷이 아니다. 192.0.2.0/24는 문서용 주소다.

A 192.0.2.10 / MAC 02:00:00:00:00:0a
        |                                  B 192.0.2.20
        |                                  MAC 02:00:00:00:00:0b
        |                                  |
        | -- ARP request (broadcast):      |
        |    Who has 192.0.2.20?           |
        | <-- ARP reply: 192.0.2.20        |
        |     is at 02:00:00:00:00:0b      |
        | -- IP packet in Ethernet frame -->|
             dst IP 192.0.2.20, dst MAC 02:00:00:00:00:0b

ARP 요청의 프레임 목적지는 브로드캐스트 MAC이고, 질문 안의 대상 IP는 찾고 있는 이웃의 IPv4다. 해당 IP를 가진 쪽이 자기 MAC을 답하면 보낸 쪽은 대응을 저장할 수 있다. 앞 주제처럼 다른 망 목적지는 먼 서버 IP가 아니라 게이트웨이 IP의 MAC을 찾는다. 따라서 캡처의 ARP 대상 IP와 HTTP 요청의 최종 목적지 IP가 다를 수 있다.

Linux의 ip -4 neigh show는 IPv4 이웃 정보를 조회한다. 예를 들어 192.0.2.20 dev ens3 lladdr 02:00:00:00:00:0b REACHABLE이라는 줄은 설명용 출력이다. lladdr가 링크 주소다. REACHABLE, STALE, INCOMPLETE, FAILED는 이웃 정보의 서로 다른 상태이고, 한 순간의 표기만으로 전체 통신 결과를 판정하지 않는다. 이웃 정보가 이미 있으면 다음 통신에서 새 ARP 요청이 보이지 않을 수 있다. 따라서 “캡처에 ARP 없음”만으로 ARP를 쓰지 않았다고 결론낼 수 없다. 캐시 삭제는 현재 SSH 경로에 영향을 줄 수 있으므로 이번 읽기 과제에는 넣지 않는다.

IPv6의 주소 탐색은 별도 **Neighbor Discovery Protocol(NDP)**을 사용한다. 이 설명은 Linux의 IPv4 over Ethernet에 한정한다. lo에는 이 Ethernet ARP 흐름을 적용하지 않는다.

예측과 확인

다른 망의 목적지 198.51.100.20으로 보내고 경로 조회에서 via 192.0.2.1이 나왔다면 ARP 요청의 대상 IP를 예상한다. 그 다음 ip -4 neigh show에서 어느 주소를 찾아야 하는지도 적는다.

확인 질문: ping 패킷은 보이는데 같은 시점의 새 ARP 요청은 안 보인다. 가능한 이유 하나와, 실제 판단을 위해 더 확인할 증거 하나를 적는다.
