# 1. 지난 두 주의 질문을 이어 보기

요약: 1주차의 프로그램·주소·포트와 2주차의 접두사·경로를 복습한다. 이번 주에는 목적지 IP를 정한 뒤 첫 링크에서 누구에게 프레임을 보낼지 묻는다.

[이번 주 핵심 정리](../ESSENTIALS.md)에서 다음 홉·ARP·도구별 관찰을 연결한다. 진단 뒤 기존 개념 읽기 안에서 되짚고 관련 공통 질문에 개발 사례를 사용한다.

## 이미 본 통신에서 출발

[1주차 개념](../../week-01/concepts.html)에서는 **클라이언트** `curl`이 **서버** Python 프로그램에 HTTP 요청을 보냈다. `127.0.0.1`은 요청을 받을 호스트, `8080`은 그 안에서 대기하는 프로그램의 포트였다. SSH로 VM에 들어가는 일은 실습 준비였고, VM 안에서 `127.0.0.1`로 보낸 HTTP 요청은 개인 PC와 VM 사이의 SSH 통신이 아니었다. VM의 `lo`에서 캡처한 것은 **한 호스트 내부**의 통신이다. 여기서 Ethernet 주소나 ARP를 찾으려 하면 관찰 위치부터 어긋난다.

[2주차 개념](../../week-02/concepts.html)에서는 IPv4 주소와 `/24`, `/26` 같은 CIDR 접두사로 주소 범위를 계산했다. 같은 범위로 계산되는지와 Linux가 실제로 선택한 경로는 다른 질문이다. 기본 게이트웨이는 다른 망으로 보낼 때 첫 번째로 맡길 수 있는 라우터 주소다. 이번 주는 그 판단 다음 단계로 간다.

각 주제의 예측·확인 질문은 읽기를 돕는다. 팀 활동에서는 핵심 질문 세 개를 각자 생각한 뒤 설명자를 바꿔 말하고, 서로 질문·보충한 다음 실제 본문·출력·패킷과 대조한다. 예상은 생각하거나 짧게 말하고 자세한 메모는 선택한다. 실제 실습 명령·출력·패킷 증거는 **개인 기록**이나 별도 파일에 보관한다.

## 시작 진단 — 8분

먼저 각 질문에 한두 문장으로 답해 본다. 모르는 항목은 표시하고 필요한 앞 주차 설명으로 돌아간다. 시험 점수를 매기거나 상세 답안을 모두 작성하는 활동은 아니다.

1. VM 안에서 `curl http://127.0.0.1:8080`을 실행했다. 클라이언트와 서버 프로그램은 각각 무엇이며, IP와 포트는 무엇을 가리키는가? 이 HTTP 요청과 PC에서 VM으로 접속한 SSH 경로는 같은가?
2. `HTTP 404`와 `Connection refused` 중 서버의 HTTP 응답을 받은 결과는 어느 쪽인가? 두 결과를 구별할 증거는 무엇인가?
3. 1주차 패킷을 `lo`에서 캡처했다. 그 자료로 VM의 가상 NIC에서 쓰는 Ethernet MAC이나 ARP를 확인할 수 있는가? 관찰 위치를 근거로 답한다.
4. `192.0.2.10/26`과 `192.0.2.70/26`은 같은 주소 범위인가? 각 범위를 계산한 뒤, 실제 전달 경로를 확인할 Linux 명령을 말한다.
5. 아래 설명용 조회에서 목적지 IP, 선택 인터페이스, 첫 전달 상대 IP를 구별한다. 첫 IP 패킷을 담을 Ethernet 프레임에는 누구의 MAC이 필요한가? MAC 값을 이 출력만으로 알 수 있는가?

```text
# 설명용 출력: 실제 VM에서 얻은 결과가 아니다.
192.0.2.70 via 192.0.2.1 dev ens3 src 192.0.2.10
```

1~3번이 막히면 [1주차 개념](../../week-01/concepts.html), 4번이 막히면 [2주차 개념](../../week-02/concepts.html)을 다시 확인한다. 5번은 이번 주 [다음 홉](03-next-hop.md)과 [ARP](04-arp.md)에서 설명을 완성한다. 주소 범위 계산과 실제 선택 경로를 같은 근거로 취급하지 않는다.

```text
HTTP 요청:  client program -> server program
IP 판단:   destination IP -> route -> outgoing interface / next hop
첫 링크:   sender NIC -> Ethernet frame -> next link peer
```

여기서 **목적지 IP**는 끝까지 도착하려는 호스트의 주소다. **다음 홉**은 지금 연결된 링크에서 먼저 받을 이웃이다. 목적지와 다음 홉은 같은 호스트일 수도, 다른 호스트일 수도 있다. Linux가 선택한 결과는 허용된 목적지에 대해 `ip -4 route get <목적지 IPv4>`로 조회한다. `<...>`는 그대로 입력하는 문자열이 아니라 실제로 허용된 주소를 넣으라는 자리 표시다. 아직 자기 VM의 경로를 조회하지 않았다면 예시를 실제 아올다 구성이라고 말하지 않는다.

## 먼저 예측

두 Linux 호스트가 같은 Ethernet 링크에 있고 직접 전달 경로가 선택되었다고 가정하자. A가 B의 IP와 HTTP 포트를 안다면, IP 패킷을 담은 Ethernet 프레임의 받는 쪽 주소도 IP만으로 채울 수 있을까? 다른 망의 웹 서버 IP를 안다면 첫 **IP 패킷을 담은 프레임**의 받는 쪽은 웹 서버일까, 게이트웨이일까? 각자 예상을 생각하거나 짧게 말하고 다음 세 주제에서 그림을 고쳐 보자.

**확인 질문:** 1주차 `lo` 캡처에서 ARP가 없었다는 사실이 “VM의 가상 NIC에서도 ARP를 쓰지 않는다”는 결론을 뒷받침하는가? 관찰한 인터페이스를 근거로 답한다.
