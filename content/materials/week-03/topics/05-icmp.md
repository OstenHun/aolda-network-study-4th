# 5. ICMP Echo로 무엇을 확인할까

요약: ping의 ICMP Echo 요청·응답은 한 경로의 반응을 관찰한다. 응답 실패만으로 HTTP 서버 중지나 ARP 실패를 단정할 수 없다.

## 같은 목적지, 다른 질문

`ping`은 보통 ICMP **Echo Request**를 보내고 **Echo Reply**를 기다린다. IPv4에서 요청 Type은 8, 응답 Type은 0이다. ICMP 메시지는 IP 패킷 안에 담긴다. 이 실험은 “상대 또는 중간 경로가 이 요청에 어떻게 반응했는가”를 묻는다. 1주차의 `curl`은 HTTP 요청에 대한 서버의 응답을 확인했다. SSH 접속은 별도의 TCP 서비스다. 세 결과는 서로 대체되지 않는다.

```text
설명용 관찰 질문
ping: A -- ICMP Echo Request --> B -- Echo Reply --> A ?
HTTP: A -- TCP + HTTP request --> B:8080 -- HTTP response --> A ?
```

Linux에서는 [실습 절차](../../../labs/week-03/LINUX.md)에 따라 승인된 실제 IPv4에 `ping -4 -n -c 2 -W 2 -w 8 "$TARGET"`을 한 번만 실행한다. 총 2패킷·전체 기한 8초이며 대상·경로·인터페이스를 먼저 확인한다. 함께 `ip -4 route get <허용된 IPv4>`로 경로를, `ip -4 neigh show`로 첫 이웃 상태를 조회하면 실패 해석의 폭이 좁아진다. 다음 중 어떤 증거를 실제로 얻었는지 **개인 실습 기록**에 구분해 남긴다.

| 관찰 | 말할 수 있는 것 | 아직 모르는 것 |
| --- | --- | --- |
| Echo Reply 수신 | 해당 시각에 요청·응답 경로가 작동했다 | HTTP 서버가 8080에서 대기하는지 |
| Echo 응답 없음 | 이 시도에서 응답을 못 받았다 | 상대 전원·HTTP 서버 상태·실패 위치 |
| ICMP 오류 수신 | 오류 종류와 보낸 장치에 관한 단서 | 다른 프로토콜까지 모두 실패하는지 |

ping 실패는 ICMP 차단, 경로·정책, 상대의 응답 설정 등 여러 원인으로 생길 수 있다. 응답이 없다면 먼저 대상·경로·이웃 정보와 정책을 확인하고, HTTP 상태는 별도 HTTP 요청·서버 로그로 판단한다. 반대로 ping 성공도 HTTP 200을 보장하지 않는다. 1주차의 **404는 HTTP 응답이 도착한 결과**, 서버 중지 때의 **연결 거부는 HTTP 응답 전의 TCP 실패**였다. ICMP Echo 실패를 둘 중 하나로 바로 번역하지 않는다.

## 예측과 확인

“ping은 실패했지만 `curl`은 HTTP 200을 받았다”는 설명용 상황을 생각해 보자. 모순인가? 각 도구가 검사한 메시지와 가능한 정책 차이를 적는다. 실제 Linux VM에서 같은 결과가 나왔다면 시각·목적지·명령·출력을 함께 남겨야 한다.

**확인 질문:** `ping` 두 번에 응답이 없을 때 “서버 프로그램이 중지됐다”를 확인하려면 어떤 별도 증거가 필요한가? 최소 두 가지를 적는다.
