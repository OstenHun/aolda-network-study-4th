# 3주차 참가자 Linux 안내 — 누구의 MAC을 찾는가

요약: 승인된 Linux VM에서 경로·이웃 조회와 허용된 IPv4의 짧은 ping을 직접 수행한다. 패킷은 제한된 캡처 또는 제공 trace로 분석하며 두 근거를 구분한다.

패킷을 읽을 때는 스터디 팀원이 만든 [WireSalmon](https://taerim0.github.io/WireSalmon/)을 사용해 보기를 권장한다. Wireshark를 사용해도 좋다. WireSalmon 공개 웹에서 내장 샘플이나 저장한 `.pcap`·`.pcapng` 파일을 열어 대화 흐름과 개별 패킷의 근거를 함께 살펴본다. 공개 웹은 실시간 캡처를 지원하지 않으므로 캡처는 아래 실습 절차를 따른다. 내장 샘플 분석과 본인이 직접 수행한 결과는 구분한다.

## WireSalmon에서 먼저 볼 샘플

[WireSalmon](https://taerim0.github.io/WireSalmon/)에서 언어를 **한국어**로 고른 뒤 상단 **샘플 열기**에서 아래 이름을 선택한다. 대화 목록에서 볼 대화를 고르고 **대화 흐름**을 따라간다. 패킷을 누르면 **봉투 구조**에서 주소와 필드를 펼쳐 볼 수 있다. **전체 패킷**에서는 다른 대화와의 시간 순서도 확인한다.

### 먼저 보기 · ARP 다음에 ping

**링크 계층 → ARP로 MAC 주소 알아내기**를 연다.

1. **MAC 주소 찾기: 192.168.0.1** 대화의 ARP 요청·응답을 누른다. Ethernet 목적지가 요청의 `ff:ff:ff:ff:ff:ff`에서 응답의 요청자 MAC으로 달라지는지 확인하고, ARP가 묻는 대상 IP와 응답이 알려 주는 MAC을 짝짓는다.
2. **핑: 192.168.0.1** 대화를 고른다. ICMP Echo 요청·응답의 출발/목적 IP, 식별 번호와 순번을 비교한다. **전체 패킷**에서 ARP 요청 → 응답 → Echo 요청 → 응답의 순서를 찾는다. 이 예제는 게이트웨이 자체가 IP 목적지인 경우다.
3. 아래 실제 조회·ping 결과와 비교한다. 샘플은 새 ARP가 있는 사례이며, 본인 캡처에는 캐시 때문에 새 ARP가 없을 수 있다. ARP가 안 보였다는 이유로 실패나 ARP 미사용을 단정하지 않는다.

### 선택 비교 · IP 목적지와 링크의 다음 상대

**한눈에 보기 → 와이파이에 접속해서 웹사이트 열기**에서 **핑: 8.8.8.8**의 Echo 요청을 누른다. IPv4 목적지는 `8.8.8.8`이지만 Ethernet 목적지는 앞선 **MAC 주소 찾기: 192.168.0.1**에서 알아낸 게이트웨이 MAC인지 대조한다. 이 샘플에서는 최종 목적지 IP와 다음 홉 MAC의 주인이 다르다. ICMP Echo에는 TCP/UDP 포트가 없다는 점도 확인한다. 샘플 주소로 직접 ping하지 않으며, 실제 실습은 아래에서 허용된 대상만 사용한다.

샘플은 기존 패킷 분석 시간에 필요한 것만 골라 본다. 같은 근거를 본인 캡처나 제공 trace로 확인했다면 반복하지 않아도 된다. 샘플은 코드로 만든 분석 예제다. 아래 Linux 직접 실습의 완료 근거로 바꾸어 적지 않는다. 필요한 패킷을 근거로 한 사람이 설명하고, 다른 사람은 조건 하나를 바꾸어 질문한다. 추가 기록 양식은 없다.

## 시작 전에

[실행 절차](../../labs/week-03/LINUX.md)를 옆에 열고 [개인 기록지](../../labs/week-03/PERSONAL_RECORD.md)를 준비한다. 예상은 짧게 말하거나 메모하고, 실제 출력과 비교한다.

`ip -4 route get TARGET`에서 `dev`와 `via`를 본다. `via`가 있으면 링크의 다음 상대는 그 게이트웨이이고 IP 패킷의 최종 목적지는 TARGET이다. `via`가 없으면 TARGET이 다음 상대 후보다. `dev lo`이면 루프백이라 Ethernet ARP 관찰에 적합하지 않다. `ip -o link show dev IFACE`에서 `link/ether`를 확인한다. VM에 보이는 가상 NIC의 MAC과 개인 PC NIC의 MAC을 섞지 않는다.

## 두 필수 실험

| 단계 | 실행 전 예측 | 남길 근거 |
| --- | --- | --- |
| A. 주소·경로·이웃 조회 | 내 IP/MAC, 선택 `dev`, `via` 유무, 다음 상대와 이웃 행을 예상 | `ip -br -4 addr`, `ip -4 route`, `ip -o link show`, `ip -4 route get`, `ip -4 neigh`의 실제 읽은 값과 출처 |
| B. 짧은 ping·패킷 분석 | 응답·이웃 상태와 ARP 관찰 조건을 예상 | 승인 대상 ping 2회·전후 이웃 상태. 패킷은 최대 12초·16패킷 직접 캡처 또는 제공 trace 분석 |

직접 캡처할 때만 셸 A에서 캡처가 시작된 뒤 셸 B에서 ping한다. 캡처 도구·권한이 없으면 작업 셸 하나에서 허용 대상의 ping·이웃 조회를 수행하고 패킷은 제공 trace로 분석한다. 직접 조회·ping과 제공 패킷 분석을 마쳤다면 직접 캡처를 필수 보충으로 요구하지 않는다. 명령과 변수 설정, 중지·실패 대안은 [실행 절차](../../labs/week-03/LINUX.md)에 있다. 그 페이지의 `TARGET`과 `IFACE`는 **출력·허용 범위를 확인한 다음** 실제 값으로 바꿔야 한다. 관리 NIC·IP·경로·방화벽·SSH·이웃 캐시를 변경하지 않는다. 캡처 필터는 ARP와 **허가한 대상의 ICMP**이며 SSH를 포함하지 않는다.

## 읽는 질문

1. 이웃 행의 IPv4가 TARGET인가, `via`의 게이트웨이인가? 보이는 MAC이 최종 목적지의 것이라고 말할 수 있는가?
2. ARP 요청이 없었다면 캐시·캡처 시각을 먼저 확인했는가? 이웃 행이 `INCOMPLETE`·`FAILED` 또는 없음이라면 어떤 점이 미확인인가?
3. Echo reply가 없으면 알 수 있는 사실과 아직 가설인 원인을 나눌 수 있는가? 1주차의 HTTP 성공·404·연결 실패와 ping 결과는 각각 다른 관찰이다.
4. `lo`에서 본 HTTP 패킷만으로 Ethernet ARP를 설명할 수 있는가? VM에서 보이지 않는 물리망의 트래픽을 보았다고 말하지 않는다.

직접 조회·ping에 필요한 접속·도구·허용 대상이 없으면 [가상 패킷 예제](../../labs/week-03/sample-trace.txt)의 A01~A06과 B01~B04를 읽는다. 같은 링크와 게이트웨이 사례에서 Ethernet MAC·IP 목적지·ARP 대상·ICMP 결과를 구분한다. 이는 실제 캡처가 아니며 자신의 직접 실행 항목을 완료 처리하지 않는다. [함께 찾을 질문](WORKSHEET.md)에서 공동 탐색한 답을 한 명이 설명하고 조건을 바꾸어 확인한다. 필요한 근거를 보여 주며 메모는 자유롭게 한다. 상세 예상·명령·패킷은 개인 기록과 원파일에 보관한다.
