LAN · MAC · ARP · ICMP

3주차 복습 해설

복습 8문항과 개발 사례의 판단 근거를 제공한다. 최종 IP·다음 홉·이웃 상태·서비스 응답을 구별하며 제공 예제와 본인 직접 관찰은 구분한다.

1. 복습 진단2. LAN·MAC3. 다음 홉4. ARP·캐시5. ICMP·ping

대조하는 방법

문제의 답을 먼저 쓴 뒤 읽는다. 조건·근거·한계가 맞는지 확인하고 프로토콜 근거는 출처와 대조한다. 아래는 자체 작성 해설이다.

Q1 — 앞선 관찰의 범위

③만 말할 수 있다. 제시된 자료는 한 학습자의 VM 내부 통신에 대한 근거다. 다른 사람의 수행 여부나 PC↔VM SSH 경로를 보여 주지 않는다. loopback 내부 전달에는 Ethernet 이웃을 찾는 ARP가 필요하지 않다. 이 관찰을 Ethernet LAN 전체의 동작으로 일반화하지 않는다.

Q2 — IP·port·MAC의 역할

IPv4는 이 예제의 최종 목적지 호스트 주소, TCP port는 그 호스트에서 통신할 서비스의 소켓을 구분하는 번호다. MAC은 현재 Ethernet 링크에서 프레임을 받을 상대의 링크 주소다. 같은 링크면 직접 상대, 경로가 게이트웨이를 가리키면 게이트웨이의 MAC을 사용한다.

HTTP 404는 요청한 자원이 없다는 응용 응답이다. 응답을 받았으므로 HTTP 통신이 성립한 근거가 있다. 서버 중지 뒤 연결 거부와 구분해야 한다. 실제 프록시 등이 있으면 응답한 장치·서비스를 추가 확인한다.

Q3 — 같은 링크의 상대

주어진 조회에는 via가 없으므로 이 Ethernet 모형에서 다음 상대는 B다. 매핑이 없다면 ARP는 192.0.2.70의 MAC을 묻고 요청 프레임은 ff:ff:ff:ff:ff:ff로 브로드캐스트한다. 일반적인 응답 뒤 Echo Request의 목적지 IP는 B의 IP, 목적지 MAC은 배운 B의 MAC이다. 문제에 B의 MAC 값은 없으므로 임의의 값을 실측처럼 적지 않는다.

두 주소는 /24 계산상 같은 범위다. 실제 경로표·NIC·가상 망 분리·허가·접근 정책과 응답 여부는 별도다. 두 참가자 VM의 접두사가 같다는 이유로 서로 ping을 보내지 않고 허용된 상대부터 정한다.

Q4 — 다른 망의 상대

ARP 대상은 게이트웨이 192.0.2.1이다. 첫 IP 패킷을 담은 프레임 목적지 MAC은 02:00:00:00:00:01, IP 목적지는 198.51.100.20이다. 이미 사용 가능한 매핑이 있다면 새 ARP 요청 없이 보낼 수 있다.

ARP는 로컬 링크의 다음 상대를 찾는다. 원격 서버의 MAC을 라우터 너머로 직접 질의하지 않는다. 라우터는 다음 링크에 맞는 새 프레임으로 전달한다. 이 설명은 NAT 없는 단순 모형이며 실제 주소 변환 여부·호스트 물리망 전체 경로는 이번 출력으로 알 수 없다.

Q5 — 캐시가 있으면

결론을 내릴 수 없다. 캡처 이전에 얻은 매핑을 사용했거나 캡처 시점·인터페이스·필터가 달랐을 수 있다. REACHABLE은 최근 도달성 확인을 반영하는 이웃 상태이며 HTTP 서비스 정상의 증거가 아니다. STALE은 유효한 매핑이 있으나 최근 도달성이 확인되지 않은 상태다. 사용 시 Linux의 추가 확인이 뒤따를 수 있으며 서버 중지를 뜻하지 않는다.

기본 실험은 캐시를 지우지 않는다. ARP 미관찰도 실제 결과로 기록하고 조회와 비교한다. ARP 순서를 읽는 학습 목표는 설명용 trace로 보충하되 직접 캡처로 표시하지 않는다.

Q6 — 관찰이 막히면

조건 확인·기록
INCOMPLETE 매핑 해결 중이다. 선택 경로·이웃 IP·NIC·승인된 대상이 맞는지 읽고 이후 상태·응답을 비교한다. 원인 확정은 보류한다.
local·lo 자기 호스트 내부 경로다. Ethernet 대상 실험 조건과 다르므로 lo를 필수 ARP 캡처로 사용하지 않는다.
캡처 권한 없음 기본 조회·허용된 ping과 제공 자료 분석으로 전환하고 직접 캡처는 미완료로 적는다. 정책을 임의 변경하지 않는다.
자신의 가상 NIC 흐름만 보임 VM의 인터페이스 관찰 범위다. 스위치의 다른 포트·물리 호스트·클라우드 fabric 전체를 봤다고 쓰지 않는다.

FAILED는 이웃 도달성 확인 실패 상태다. HTTP 프로세스 중지까지 증명하지 않는다. 경로·L2 전달·정책·대상 상태 등 추가 근거가 필요하다. 비 Ethernet 장치·특수 경로는 단순 모형에서 분리한다.

Q7 — ping과 HTTP

HTTP 404가 관찰됐으므로 해당 요청에 대한 응답이 돌아왔다. Echo Reply가 없다는 것은 제한된 ping 관찰 결과다. ICMP 제한·손실·경로 차이 등은 가설로 두고 근거 없이 한 원인으로 확정하지 않는다.

ping 응답은 그 시점의 ICMP 왕복 근거이며 TCP port의 대기·응용 정상까지 말해 주지 않는다. curl 연결 거부가 있으면 정확한 대상 IP·port·바인딩·대기 소켓·관련 정책을 허가된 조회로 확인한다. 1주차처럼 서버 로그·ss·curl 출력이 판단 근거다. ICMP Echo는 TCP/UDP port를 사용하지 않으며 identifier·sequence로 요청·응답을 대응한다.

Q8 — 독립 설명과 증거

정답 그림의 값은 사람마다 다르다. 다음 기준으로 확인한다.

  1. 출처가 본인 직접 관찰인지, 진행자 시연인지, 제공 설명 자료인지 표시했다.
  2. 경로 출력의 dev·src·via 여부로 다음 홉을 선택했다. 문제의 기본 경로를 실제 경로표 대신 쓰지 않았다.
  3. 같은 링크/라우팅 모형에서 IP 목적지와 프레임 목적지 MAC을 구분했다. MAC을 모르면 미관찰로 적었다.
  4. 이웃 행과 ARP/ICMP의 근거 줄을 연결하거나 보이지 않은 이유를 가설로 적었다.
  5. 캐시·ping·가상 NIC의 관찰 한계를 설명하고 개인 미완료를 남겼다.

짝의 그림을 자기 실측으로 복사하지 않는다. 보충 뒤 기록이 갱신돼야 직접 수행 상태를 바꿀 수 있다.

개발 질문 해설

핵심 정리의 자체 문항을 먼저 설명한 뒤 비교한다.

  1. W03-D1: HTTP 응답은 수신했지만 요청한 자원은 404로 표현됐다. ICMP는 이번 시도에 Echo Reply가 없고 원인은 미확인이다. 새 ARP가 없다는 사실은 캐시·관찰 시점과 함께 해석한다. REACHABLE 이웃은 다음 홉의 최근 도달성 단서이며 원격 HTTP 앱이 정상인지 알려 주지는 않는다.
  2. W03-D2: 아니다. STALE은 해당 매핑의 도달성 확인이 오래됐다는 상태이며 서버 프로세스가 종료됐다는 뜻은 아니다. 허가된 서비스 요청·로그·경로 등으로 확인한다.
  3. W03-D3: 요청 대상·프록시 구성·서버 로그를 맞추고, 경로의 다음 홉과 캡처 NIC·이웃표·시각을 대조한다. 캐시 초기화를 기본 과제로 추가하지 않는다. 확인하지 못하면 추정으로 남긴다.

흔한 오답: ‘ping 실패=서버 중지’, ‘ARP 미관찰=ARP 불필요’, ‘게이트웨이 MAC=최종 서버 MAC’. 설명 확인: 도구별 관찰과 한계를 구분하고 다음에 볼 증거를 제시한다. 실제로 실행하지 않은 사례는 자체 실측으로 기록하지 않는다.
