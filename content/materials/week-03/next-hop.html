두 주소를 구분해 보기

문서용 주소의 설명 모형입니다. 실제 패킷을 보내지 않습니다. A는 192.0.2.10/24, 게이트웨이는 192.0.2.1이며 NAT가 없는 Ethernet 경로를 가정합니다.

Ethernet 프레임의 목적지

B의 MAC · 이웃 IP 192.0.2.70

안쪽 IP 패킷의 목적지

192.0.2.70 · B

매핑이 없으면 192.0.2.70의 MAC을 ARP로 묻습니다. 캐시에 있으면 새 ARP가 없을 수 있습니다.

같은 주소 범위 계산 다음에 할 일

2주차에는 접두사로 “같은 서브넷처럼 보이는가”를 계산했다. 이제 Linux가 실제로 어느 인터페이스와 다음 홉을 선택하는지 확인한다. ip -4 route get <목적지 IPv4>의 결과에 via가 있으면 그 주소가 다음 홉으로 제시된다. dev는 나갈 인터페이스다. 아래 값은 설명용 출력이며 실제 아올다 VM의 설정이 아니다.

$ ip -4 route get 192.0.2.20
192.0.2.20 dev ens3 src 192.0.2.10

$ ip -4 route get 198.51.100.20
198.51.100.20 via 192.0.2.1 dev ens3 src 192.0.2.10

첫 줄은 이 예시에서 직접 연결 경로가 선택된 경우다. IP 목적지 192.0.2.20이 첫 링크의 이웃이다. 둘째 줄은 게이트웨이 192.0.2.1을 거치는 경우다. 첫 IP 패킷을 담은 Ethernet 프레임을 받는 쪽은 게이트웨이 MAC이고, 프레임 안 IP 패킷의 목적지는 여전히 198.51.100.20이다. 이웃 매핑이 없다면 그보다 먼저 ARP 요청 프레임이 나갈 수 있다. 여기서는 NAT가 없는 단순 경로를 가정한다. NAT를 적용하는 장치를 지나면 주소가 바뀔 수 있으며 그 조건은 별도로 확인해야 한다.

설명용: A(192.0.2.10) -- Ethernet --> G(192.0.2.1) -- ... --> D(198.51.100.20)
첫 IP 패킷을 담은 프레임: dst MAC = G의 MAC
안쪽 IP:   dst IP  = D의 IP (이 예시에서 NAT 없음)

이 구분 때문에 먼 서버의 MAC을 내 VM에서 ARP로 찾지 않는다. 내 Ethernet 링크에서 실제로 받을 게이트웨이의 IP에 대응하는 MAC을 찾는다. 주소를 안다고 자동으로 도달하는 것은 아니다. 경로가 있어도 가상망 연결, 방화벽·클라우드 접근 정책, 상대 서비스의 대기 주소와 포트가 통신을 막을 수 있다. 반대로 같은 /24라는 계산만으로 같은 L2 구간에 있다고 단정할 수도 없다.

먼저 예측

A가 198.51.100.20:8080의 HTTP 서버에 요청한다고 가정하자. 첫 IP 패킷을 담은 프레임의 목적지 MAC은 누구 것인가? 패킷 안의 목적지 IP는 무엇인가? ip route get에 via가 없는 예시라면 답이 어떻게 달라지는가? 각자 예상을 생각하거나 짧게 말한 뒤 ARP로 넘어간다.

확인 질문: “두 주소가 같은 /24”와 “ip route get이 직접 경로를 선택했다”와 “HTTP 200을 받았다”는 각각 같은 주장인가? 각 문장이 확인하는 범위를 한 줄씩 구분한다.
