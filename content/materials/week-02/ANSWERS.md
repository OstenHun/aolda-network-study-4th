# 2주차 복습 해설과 확인 포인트

요약: 공동 질문·카드 C1/C2·복습 8문항·개발 사례의 분리 해설이다. 접두사 계산·경로 선택·실제 응답을 나눠 설명하고 흔한 오답과 다음 확인 방법을 살펴본다. 자기 답을 설명한 뒤 비교하며 열람만으로 통과하지 않는다.

## 비교 방법

[문제](REVIEW.md)에 답을 먼저 적고 비교한다. 틀린 계산은 지우지 말고 어느 비트·경계·가정이 달라졌는지 덧붙인다.

## 공동 질문 해설

[중심/선택 질문](WORKSHEET.md)에 대한 자기 설명을 먼저 마친 뒤 비교한다. 아래 계산은 문서용 카드이며 아올다 VM의 실측이 아니다.

### W02-Q1 · IP가 비슷한 두 VM은 같은 망으로 바로 통신할까?

**답에 포함할 내용:** 접두사로 양쪽 범위를 계산하고, 각 호스트의 경로 조건을 따로 읽으며, 주소 계산·경로 조회·실제 응답을 서로 다른 근거로 구분한다.

| 조건/호스트 | 네트워크·전체 범위 | 일반 호스트 범위 | 상대를 자기 범위에 포함하는가? |
| --- | --- | --- | --- |
| C1 A `.10/24` | `192.0.2.0/24`, `.0~.255` | `.1~.254` | B `.70` 포함 |
| C1 B `.70/24` | `192.0.2.0/24`, `.0~.255` | `.1~.254` | A `.10` 포함 |
| C2 A `.10/26` | `192.0.2.0/26`, `.0~.63` | `.1~.62` | B `.70` 미포함 |
| C2 B `.70/24` | `192.0.2.0/24`, `.0~.255` | `.1~.254` | A `.10` 포함 |

`/24`는 2^8=256개, `/26`은 2^6=64개 주소다. 카드의 일반 서브넷에서는 네트워크·브로드캐스트 두 주소를 제외한다. 이 호스트 수 규칙을 `/31`·`/32`나 클라우드 플랫폼의 실제 예약 규칙에 무조건 적용하지 않는다.

C2에서 A에는 직접 연결 `/26` 경로 외에 기본/별도 경로가 없다는 가정이므로 B를 향한 경로가 없다. B가 A를 자기 `/24`에 포함한다고 해서 A의 전송·응답 경로가 생기지는 않는다. A를 `/24`로 복구하면 범위 판단은 달라지지만 실제 링크·정책·상대 서비스까지 정상인지는 별도 확인해야 한다.

자기 VM에서는 `ip -br -4 addr`, `ip -4 route`, `ip -4 route get`의 실제 줄을 읽는다. `dev`는 선택된 장치, `via`는 표시된다면 다음 홉, `src`는 선택된 출발지 주소다. 필드가 없거나 경로 오류가 나면 그 사실을 그대로 남긴다. 이 조회는 실제 패킷 왕복·상대 응답을 확인하지 않는다.

**흔한 오답:** 주소 앞 세 묶음만 보고 같은 망이라고 함, B의 판단으로 왕복을 보장함, `/26`을 무조건 64개 호스트라고 함, 경로 출력으로 서비스 정상까지 단정함.

**다음에 확인할 것:** 양끝 주소/접두사·목적지 경로·선택한 인터페이스를 대조한다. 실제 도달성은 허가된 대상/절차에서 별도 확인하고, 추가 정책·서비스·링크 증거가 없으면 원인을 단정하지 않는다. SSH 관리 설정을 즉석에서 바꾸지 않는다. 이번 주 P1/P2는 조회·계산이므로 실제 응답을 받았다는 기록을 만들어 넣지 않는다.

### W02-Q2 · lo와 다른 인터페이스가 함께 보이는 이유

한 VM 안에도 여러 인터페이스·주소가 있다. VM 안에서 실행한 curl의 `127.0.0.1`은 그 VM의 루프백을 가리킨다. 두 SSH 창은 같은 VM의 두 셸일 수 있고, 터미널 수가 호스트 수는 아니다. 실제 NIC에 붙은 주소와 특정 목적지의 전달 경로는 나눠 읽는다. 자기 주소를 목적지로 조회하면 로컬 경로가 선택될 수 있으므로 주소가 붙은 NIC로 반드시 송신한다고 단정하지 않는다. 실제 조회 줄이 근거다.

### W02-Q3 · 사설 주소와 기본 경로가 있으면 서비스가 정상일까?

RFC 1918 범위·기본 경로의 존재는 주소/경로 정보다. 서비스 대기·정책·왕복 전달·상대 응답은 별도다. 더 구체적인 경로가 있으면 목적지 경로 조회로 실제 선택을 확인한다. 이번 주는 모르는 조건을 나누고 다음 관찰을 고르면 충분하며 방화벽/NAT·서버를 새로 구성하지 않는다.

### 선택 격리 실험의 예상·실제 비교

선택 실행을 한 경우에만 정상 `/24`→A만 `/26`→`/24` 복구의 실제 주소·경로·A→B 요청과 정리를 비교한다. 격리된 직접 링크가 정상이고 다른 경로가 없다는 조건에서 중간 단계의 A는 B로 향한 경로가 없을 것으로 예상한다. 오류 문구·요청 수·실제 응답은 출력으로 확인한다. 예시를 본 것·진행자 시연·본인 실행을 구별하며 선택 실험을 하지 않아도 필수 실습은 완료할 수 있다.

이제 [질문](WORKSHEET.md) 또는 [P1/P2](../../labs/week-02/LINUX.md)로 돌아가 바뀐 설명·남은 수행을 정리한다.

## 복습 8문항 해설

### Q1. 주소와 포트

`127.0.0.1`은 요청을 실행한 **그 호스트의 루프백 주소**, `8080`은 그 호스트의 목적지 서비스 포트다. 개인 PC에서 실행하면 PC의 루프백을 가리켜 VM 서버를 가리키지 않는다. 포트가 같아도 주소가 가리키는 호스트가 다르다.

### Q2. /24

마스크 `255.255.255.0`, 네트워크 `192.0.2.0`, 브로드캐스트 `192.0.2.255`, 일반적인 사용 가능 호스트 `192.0.2.1–192.0.2.254`다. `.70`은 이 `/24`에 포함된다. 이 범위는 문서 예시용이므로 인터넷의 실제 공인 호스트를 뜻하지 않는다.

### Q3. /26

`/26` 마스크는 `255.255.255.192`이고 한 구간은 64개 주소다. 네 네트워크 주소는 `192.0.2.0`, `.64`, `.128`, `.192`다. `.70`은 `192.0.2.64/26`에 있으며 브로드캐스트는 `.127`, 일반적인 사용 가능 호스트는 `.65–.126`이다. 64개 중 네트워크와 브로드캐스트를 제외하면 62개다.

### Q4. A의 관점

둘 다 `/24`이면 A에서 B는 `192.0.2.0/24` 안에 있다. A가 `/26`으로 바뀌면 A의 구간은 `192.0.2.0–.63`이고 `.70`은 밖이다. A에는 이 직접 연결 경로 외에 다른 경로가 없다는 조건이므로 B를 향한 경로를 찾지 못한다. B가 `/24`이므로 B의 판단은 A와 다를 수 있다. 주소 계산만으로 양방향 통신 결과를 단정하지 않는다.

### Q5. 주소 용도

`10.1.2.3`, `172.31.255.1`, `192.168.2.9`는 RFC 1918 사설 주소다. `127.0.0.1`은 루프백, `192.0.2.10`은 문서 예시용이다. `172.32.0.1`은 RFC 1918 사설 대역 밖이며 이 문제의 분류에서는 “그 밖”이다. 할당·경로·정책·상대 상태를 모르므로 인터넷 도달이나 실제 사용 가능성을 보장할 수 없다. 특히 `172.16.0.0–172.31.255.255`가 사설 범위의 경계다.

### Q6. 출력에서 경로 읽기

주소는 `10.24.8.21/24`, 직접 연결 경로는 `10.24.8.0/24 dev eth0`, 기본 게이트웨이는 `10.24.8.1`이다. `.70`은 같은 `/24`이므로 제시된 경로 중 직접 연결 경로와 일치한다. 기본 경로가 보인다고 같은 망 목적지도 항상 게이트웨이를 통과하는 것은 아니다. 실제 선택과 전달은 `ip route get 10.24.8.70`과 허용된 관찰로 확인한다.

### Q7. 같은 서브넷과 도달성

두 주소의 `/24` 네트워크 값은 `10.24.8.0`으로 같다. 이것은 주소·접두사만으로 가능한 판정이다. 링크 연결, 양끝 설정, 이웃 주소 확인, 방화벽·보안 그룹, ICMP 처리 때문에 ping 결과는 달라질 수 있다. 예를 들어 양쪽 `ip -4 addr`·`ip -4 route`를 대조하고, 허가된 환경에서 `ping` 결과 또는 `ip neigh` 상태를 비교한다. 출력이 실제로 없으면 관찰 결과를 써 넣지 않는다.

### Q8. /26의 경계

`10.24.8.70/26`은 `10.24.8.64–10.24.8.127` 구간이다. 네트워크는 `.64`, 브로드캐스트는 `.127`, 일반적인 호스트 범위는 `.65–.126`이다. 따라서 `.64`와 `.127`은 이 일반적인 `/26` 호스트 주소로 배정하지 않는다. 다른 접두사나 특수한 링크의 주소 규칙까지 일반화하지 않는다.

## 진행자가 확인할 설명

`/26`은 마지막 옥텟을 64씩 나눈다는 계산과 “같은 구간이면 통신된다”는 주장을 구별한다. Q4에서는 **A의 관점**과 경로가 없다는 조건을 설명한다. Q7에서는 계산으로 아는 것과 직접 관찰해야 아는 것을 구별한다. [RFC 4632 §3.1](https://www.rfc-editor.org/rfc/rfc4632#section-3.1)의 접두사 정의와 [IANA 특수 목적 주소 등록부](https://www.iana.org/assignments/iana-ipv4-special-registry/iana-ipv4-special-registry.xhtml)를 확인 근거로 썼다.

## 개발 질문 해설

[핵심 정리의 자체 문항](ESSENTIALS.md)을 먼저 설명한 뒤 비교한다.

1. **W02-D1:** A의 `/26`은 `.0~.63`, B의 `/24`는 `.0~.255`다. A는 B를 자기 범위 밖으로, B는 A를 안으로 본다. 주어진 A에는 B를 향한 경로가 없으므로 이 조건에서 A의 전송 경로를 고를 수 없다. B의 판단만으로 왕복 성공을 주장할 수 없다.
2. **W02-D2:** 양쪽 주소 범위 판단은 같아지지만 실제 링크·가상망 정책·서비스 대기·양방향 전달은 별도 확인이 필요하다. 계산 결과를 실제 ping/HTTP 결과로 쓰지 않는다.
3. **W02-D3:** 양쪽 `ip addr`, 목적지별 `ip route get`, 사용 인터페이스와 정책·서비스 증거를 대조한다. SSH 관리 인터페이스의 주소·경로를 즉석에서 바꾸지 않고 기존 조회·주소 카드나 준비된 격리 실험을 사용한다.

**흔한 오답:** ‘B가 A를 같은 망으로 보니 왕복 성공’, ‘/26은 무조건 호스트 64개’, ‘사설 주소끼리는 자동 연결’. **설명 확인:** 양쪽 범위와 경로·실측의 구별을 말한다. 계산 정답은 실제 통신 성공의 증거가 아니다.
