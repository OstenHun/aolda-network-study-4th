P1은 기존 VM 주소·경로 조회, P2는 C1/C2 손계산·Python 검산이다. 공동 질문의 답을 자기 출력·계산으로 확인하고 분리 해설과 비교한다. P1·P2에서는 관리 설정을 바꾸지 않으며 격리 변경은 별도 권한을 확인한 뒤 선택한다.

질문·핵심 개념에서 이어오기

함께 찾을 질문과 핵심 K1~K3로 만든 임시 답을 확인한다. P1(1~2단계)은 자기 VM 관찰, P2(3~4단계)는 계산·검산과 조건 변경이다. 둘을 필수로 하고 5단계 격리 데모는 선택한다. 각자 실행하며 설명자나 짝의 출력을 자신이 실행한 결과로 기록하지 않는다.

P1에서 자신의 실제 주소·접두사·선택 인터페이스/다음 홉과 모르는 구간을 작은 그림으로 표시한다. P2의 문서용 주소를 그 그림에 실제 VM 주소처럼 넣지 않는다. 이 그림으로 기본 클라우드 구조를 설명한다. 정책·NAT·서비스가 정상인지는 별도로 확인해야 한다.

준비와 안전 범위

1주차에 사용한 승인된 Linux VM에 다시 접속해 VM 안의 셸에서 실행한다. 먼저 지난주 http://127.0.0.1:8080/echo의 IP·포트 역할과 lo 캡처 위치를 떠올린다. 이번에는 같은 VM에서 lo와 다른 인터페이스의 주소·경로를 읽는다. 새 VM 생성이나 서버 재설치가 필요하지 않다. 지난주 SSH 성공이 이번 주 ip·Python 사용이나 직접 실습 완료를 보증하지는 않으므로 각자 확인한다.

아래 명령의 $ 표시는 프롬프트 예시이며 입력하지 않는다. 프로젝트 사본을 Linux에 옮겼다면 그 폴더에서 pwd와 ls labs/week-02로 위치를 확인한다. 온라인에서는 Python 검산기를 내려받아 허가된 방법으로 Linux VM에 옮긴다. Python 파일만 받았다면 파일이 있는 폴더에서 ls subnet_check.py로 확인하고 python3 subnet_check.py ...로 실행해도 된다. Windows의 이 프로젝트 작업 폴더에서 Linux 명령을 실행하는 안내가 아니다.

필수 1~4단계는 조회와 Python 계산만 한다. SSH에 쓰는 관리 인터페이스의 주소·마스크·경로를 바꾸지 않는다. IP와 경로 출력은 접속·설계 정보를 드러낼 수 있으므로 공유본에는 실제 IP, 사용자명, VM 이름 등 팀이 정한 민감 정보를 가리고, 가렸다는 사실을 기록한다. 가려야 할 값도 개인 원본에는 남겨 비교한다.

uname -s
pwd
command -v ip
python3 --version
ls labs/week-02/subnet_check.py  # 프로젝트 사본을 옮긴 경우

Linux, ip의 위치, Python 버전, 자신이 옮긴 파일의 경로가 보이면 시작한다. 프로젝트 사본 대신 Python 파일만 받았다면 위 마지막 줄 대신 ls subnet_check.py로 확인한다. ip 또는 Python이 없으면 설치를 임의로 진행하지 말고 제공 예제를 사용한다. 실제 Linux 접속·명령 사용 가능 여부는 참가자별로 확인해야 한다.

1. 자기 인터페이스와 경로를 읽기

실행 전에 예측한다. 내 IPv4 주소는 어느 인터페이스에 붙어 있을까? lo의 127.0.0.1과 VM의 다른 IPv4 주소가 같은 상대를 뜻할까? 기본 게이트웨이가 보일까?

ip -br -4 addr
ip -4 route

ip -br -4 addr에서 인터페이스 이름, 상태(UP 등), 주소/접두사를 읽는다. lo는 같은 Linux 안에서 돌아오는 루프백이며 127.0.0.1은 다른 VM을 지정하지 않는다. 지난주 VM 안에서 실행한 curl의 127.0.0.1:8080은 VM 내부 Python 서버를 향했으며, 그 lo 패킷은 VM 바깥 인터페이스의 통신 증거가 아니다. 주소가 여럿이거나 lo만 나올 수 있다. ip -4 route에서 default via ... dev ...가 있다면 기본 경로의 다음 전달 대상과 인터페이스를 표시한다. 기본 경로가 없는 환경도 있다. 192.168.../24 dev ... scope link처럼 보이는 직접 연결 경로는 자신의 접두사 범위에 대한 경로다. 실제 출력의 인터페이스 이름을 예시의 eth0으로 바꿔 적지 않는다.

질문 기록할 실제 근거
내 VM의 IPv4 주소와 접두사는? ip -br -4 addr의 인터페이스·주소/접두사 줄
같은 Linux 안의 주소는? lo의 IPv4 줄
범위 밖 목적지의 기본 다음 전달 상대는? ip -4 route의 default 줄 또는 없음

2. 목적지 경로 조회 — 패킷 전송이 아님

ip route get은 목적지에 대한 현재 커널 경로 선택을 조회한다. 아래 문서용 주소는 실습 카드의 계산 대상이다. 임의의 공인 서버로 ping이나 HTTP 요청을 보내지 않는다.

ip -4 route get 127.0.0.1

local 127.0.0.1 dev lo 같은 결과를 예상하되 실제 줄을 적는다. ip -4 route get은 패킷 왕복이나 상대의 응답을 검증하지 않는다. 자기 VM의 기본 경로를 살펴볼 때는 진행자가 허용한 목적지에 한해 추가로 조회한다. 출력의 dev는 나가는 장치, via는 표시된다면 다음 전달 상대, src는 선택된 출발지 주소다. via가 없다고 목적지의 응답이 보장되는 것은 아니다.

3. /24와 /26을 손으로 계산하고 코드로 검산

실제 VM 주소 대신 문서용 192.0.2.0/24를 사용한다. /24는 앞 24비트가 네트워크, 뒤 8비트가 주소 범위다. /26은 앞 26비트가 네트워크, 뒤 6비트가 주소 범위다. 마지막 옥텟을 기준으로 /24 경계는 0·256, /26 경계는 0·64·128·192·256이다. 아래 두 카드에서 먼저 각 주소의 네트워크·범위 끝(브로드캐스트)·일반 호스트 범위·상대 포함 여부를 종이에 적는다.

카드 A B 먼저 예측할 것
C1 192.0.2.10/24 192.0.2.70/24 두 주소가 양쪽 범위에 들어가는가?
C2 192.0.2.10/26 192.0.2.70/24 A·B에서 바라본 포함 여부가 같은가? 
python3 labs/week-02/subnet_check.py 192.0.2.10/24 192.0.2.70/24
python3 labs/week-02/subnet_check.py 192.0.2.10/26 192.0.2.70/24

출력의 양쪽 네트워크·마스크·범위 끝·일반 호스트 범위를 본인 손계산과 비교한다. C2는 A만 접두사가 바뀌므로 두 방향을 따로 계산한다. 풀이를 먼저 설명한 뒤 C1/C2 분리 해설에서 완성 값·흔한 오답과 비교한다.

코드는 계산기다. 이 결과만으로 실제 상대가 존재하는지, 링크·방화벽·왕복 경로·서비스가 정상인지 알 수 없다. 192.0.2.0/24는 문서 예제용 예약 주소이며 이 실습에서 공인 인터넷 주소로 사용하지 않는다. RFC 1918의 사설 범위(10/8, 172.16/12, 192.168/16), 루프백(127/8), 문서용 주소, 공용 인터넷에서 사용할 수 있도록 할당된 주소는 구분한다. 공용 주소를 가진 것과 외부에서 접근 가능한 것도 다른 판단이다.

계산만 하는 주소 분류 카드 분류 확인할 이유
10.3.4.5, 172.20.1.9, 192.168.10.23 RFC 1918 사설 주소 세 범위 중 하나에 포함
127.0.0.1 루프백 같은 호스트 안으로 돌아옴
192.0.2.70 문서용 RFC 5737 TEST-NET-1
8.8.8.8 공용으로 할당된 주소의 예 분류 카드만 읽고 이 주소로 요청·탐침을 보내지 않음

4. 주소 카드와 실제 도달성 구분하기

다음 문장을 예상·근거·남은 미확인으로 나누어 답한다.

  1. 두 주소가 /24에 속하면 ping 응답이 반드시 오는가? 직접 연결 경로 외에 확인할 조건 두 가지를 적는다.
  2. C2에서 A에 게이트웨이와 별도 경로가 없다면 A는 .70으로 향할 경로를 찾을 수 있는가? B의 /24 계산만으로 왕복이 완성되는가?
  3. 자기 VM에서 default via가 없으면 무슨 정보가 부족한가? 있으면 상대의 실제 응답까지 확인한 것인가?

필수 실습을 마친 뒤에는 실제 명령 출력, C1·C2 손계산과 검산, 카드나 검산기의 입력 조건 하나를 바꿔 직접 푼 결과를 보관한다. 소그룹에서는 이 근거를 보여 주며 1~2분 동안 설명하고 출력을 읽는다. 개인 실습 증거 보관에 원본이나 파일 위치를 한 번 남기고 함께 찾을 질문을 설명할 때 필요한 근거를 보여 준다. 추가 메모는 자유롭게 한다. 도구나 접속이 없으면 제공 예제에서 읽은 값에 예제 분석이라고 표시하고 직접 조회·검산은 미완료로 남긴다. 읽기 전용 경로 조회는 실제 패킷 응답 확인이 아니다.

5. 선택: 두 격리 노드에서 접두사 한 조건만 바꾸기

선택 실험을 하지 않아도 필수 P1/P2는 완료할 수 있다. 참여하려면 아래 사전 조건을 확인하고, 실행하지 않았다면 선택하지 않음·실행하지 않음·제공 자료 분석 중 해당하는 것으로 표시한다.

실행 전 셸 코드 읽기에서 두 공간·가상 케이블·세 실험을 먼저 읽고, 같은 문서의 실패·정리 설명까지 확인한다. 코드 해석만 했다면 직접 실행과 구분한다.

진행자가 격리 Linux의 관리자 권한·ip·ping·네트워크 네임스페이스 사용 가능 여부를 확인한 경우에만 실행한다. 스크립트는 실행별 이름으로 네임스페이스 두 개와 veth 한 쌍을 만들고, 종료 시 자신이 만든 자원만 지운다. 드문 이름 충돌이 나면 기존 자원을 덮어쓰거나 지우지 않고 실패한다. 기본 호스트의 관리 주소, 기본 경로, 방화벽은 변경하지 않는다. 관리 VM의 관리자 권한이 허가되지 않았거나 기능이 없으면 실행하지 않고 카드 분석으로 대체한다.

예측: A 192.0.2.10/24와 B 192.0.2.70/24가 직접 연결된 경우 → A만 /26으로 변경하고 게이트웨이 없음 → A를 /24로 복구한 경우, 각 단계의 ip route get과 ping이 어떻게 달라질까?

sudo bash labs/week-02/isolated_demo.sh

스크립트 출력에서 각 단계의 명령, 경로 유무, ping 송수신 수·종료 상태를 읽는다. 예상과 달라도 결과를 고치지 말고 실제 설정·오류를 기록한다. 실행 뒤 선택 실험 해설과 가정을 대조한다. 기본 데모가 관찰한 A→B 외의 방향을 직접 측정했다고 쓰지 않는다.

스크립트는 종료 시 자신이 만든 자원을 정리한다. 삭제가 실패하면 종료 상태를 실패로 표시하고 확인할 정확한 네임스페이스·veth 이름을 출력한다. 중단이나 비정상 종료 뒤에는 첫 줄 또는 정리 오류에 출력된 이번 실행 이름과 ip netns list를 대조한다. 잔여 자원이 있을 때는 진행자와 함께 그 이름이 이 실행 소유인지 확인한 다음에만 제거한다. 다른 네임스페이스를 일괄 삭제하지 않는다.
