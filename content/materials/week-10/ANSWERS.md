# 10주차 분리 해설 · 비용, 정보, 요청을 나누어 설명하기

요약: 계산의 한 차례 갱신과 수렴을 구별하고, OSPF의 이웃·경로·ICMP와 서비스 응답을 각각 해석한다. 아래 예상 기준은 본인의 실습 결과를 대신하지 않으며 미완료 직접 수행은 보충한다.

먼저 [복습 문제](REVIEW.md)에 답하고 읽는다. 필수 요소는 답안을 외울 문장 수가 아니라 이유와 관찰 범위다. [교재](CONCEPTS.md) · [실습](LINUX.md) · [출처](SOURCES.md) · [색인](../CONCEPT_INDEX.md).

## Q1 · 누가 경로 정보를 고치는가

정적 경로 자체는 지정된 목적지·다음 홉을 유지한다. 로컬 인터페이스 down이면 관련 경로가 제거될 수 있지만, 멀리 있는 R2-R3 장애를 R1이 자동으로 아는 것은 별도 기능 없이 보장되지 않는다. OSPF는 장애를 발견한 뒤 바뀐 연결 정보를 전하고 각 라우터가 재계산·설치한다. 필수 요소는 **로컬 링크 상태와 원격 도달 정보의 차이**다. “정적은 어떤 경우에도 절대 변하지 않는다”도 지나친 단정이다.

## Q2 · 후보를 낮추고 작은 것부터 확정한다

확정 순서는 A0→B2→C3→D4다. C는5→3, D는∞→7→4로 바뀐다. A→D=A→B→C→D, 비용4, A의 다음 홉 B다. C에서 D로 갈 때 다음 홉은 D다. A-C 직접 비용5는 A-B-C의3보다 크다. 홉 수나 그림의 선 길이를 cost로 대신하지 않는다. 교재 [K1 표](CONCEPTS.md#W10-K1)에서 각 갱신을 대조한다.

## Q3 · 첫 갱신은 최종값이 아닐 수 있다

`min(2+5,5+1)=6`, 다음 홉 C다. 주어진 초기 광고만 사용해야 한다. B가 나중에 C를 경유하는 비용2를 광고하고 A가 받으면 비용4·다음 홉 B로 바뀔 수 있다. 필수 요소는 **초기 광고의 시점과 한 차례 갱신**이다. Q2 결과4를 바로 쓰면 이번 입력에서 요구한 한 차례 갱신을 건너뛴 것이다. DV의 식과 RIP 구현의 제한·타이머는 구별한다.

## Q4 · 같은 지도에서도 출발점이 다르다

LS는 연결·비용을 나누어 각자 자신을 출발점으로 경로를 계산한다. DV는 이웃이 광고한 목적지별 거리에 이웃까지의 비용을 더해 갱신한다. LSDB가 같아도 R1과 R3의 다음 홉은 다를 수 있다. OSPF는 경로 정보를 유지하는 제어 프로토콜이며 HTTP 요청마다 Dijkstra를 다시 실행하는 앱 프록시가 아니다. 필요한 조건은 같은 영역에서 수렴한 데이터베이스라는 점이다.

## Q5 · 네 값을 같은 주소·비용으로 읽지 않는다

`2.2.2.2`는 Router ID, `Full`은 인접 데이터베이스 동기화 상태, `172.30.12.12`는 이 링크의 이웃 주소다. distance110은 FRR의 기본 OSPF 관리 거리, metric20은 이번 경로의 OSPF 누적 cost다. 하나의 영역0에 여러 `/24` 구간과 loopback `/32`가 있다. cost20은20ms·20홉이라는 뜻이 아니다. Full만으로 목적지 경로·왕복 성공을 증명할 수도 없다.

## Q6 · 본인 출력과 비교할 예상 기준

| 단계 | 이웃·경로의 예상 | 요청의 예상 |
| --- | --- | --- |
| 정상 | 모든 라우터 두 이웃 Full. R1→R3 lo는 metric20·172.30.12.12/eth12, R3→R1 lo는20·172.30.23.12/eth23 | R1 lo 출발 ping 응답 |
| R2 eth23 down·수렴 뒤 | R2-R3 Full 해제. R1→R3는50·172.30.13.13/eth13, R3→R1은50·172.30.13.11/eth13 | 전환 중 손실 가능. 안정 뒤 ping 응답 |
| no shutdown·재수렴 뒤 | R2-R3 Full 복귀, 양 방향 metric20·R2 경유 | 다시 ping 응답 |

위 표는 구성으로부터 예상하는 기준이다. 출력의 순서·타이머·첫 응답 시점은 환경에 따라 다르다. 본인 명령·이웃·양 방향 경로·요청·복구가 필수 근거다. 읽기만 했으면 분석과 직접 수행 미완료를 따로 남긴다. FRR 구성은 실제 패킷을 다루지만 참가자의 수행·독립 이해는 각자 확인한다. 12주차에는 이 근거를 재사용해 설명한다.

## Q7 · 경로 수렴과 요청 복구의 관찰 위치

각 라우터의 장애 발견·LSA 교환·SPF·설치는 시간차가 있다. ICMP 요청·응답은 별도의 관측이다. 드문 조회로 정확한 경로 설치 시각을 알 수 없고, 한 번 성공한 ping으로 이전 손실0을 증명할 수도 없다. 공통 시계·명령 시각·관측 간격·전후 출력을 남긴 조건에서만 범위를 말한다. “항상40초”는 Hello/Dead, 로컬 인터페이스 상태, LSA 전파·SPF 등을 무시한다. 이번 실험의 행정적 shutdown과 무응답 장애도 구별한다.

## Q8 · 경로의 존재와 선택·광고

주어진 Q 우선 정책에 따라 Q가 선택될 수 있다. AS 경로가 짧다는 것만으로 모든 정책을 덮어쓰지 않는다. 선택과 외부 광고는 별도 정책의 영향을 받으며 모든 이웃에게 반드시 광고하지 않는다. OSPF 같은 IGP는 AS 내부, eBGP는 서로 다른 AS, iBGP는 같은 AS 안에서 BGP 정보를 전달하는 관계다. iBGP와 IGP는 이름이 비슷해도 같은 프로토콜 분류가 아니다. 이 예로 BGP 속성의 전체 비교 순서나 실제 인터넷 정책을 추정하지 않는다.

## Q9 · W10-D1~D3 개발 사례

- **D1 설명:** R1의 경로 변경은 그 라우터에서 다음 홉이 바뀌었다는 근거다. R3의 역방향 경로와 출발 주소를 고정한 ping으로 왕복 전달을 확인한다. HTTP 성공은 추가로 확인해야 한다. 흔한 오답은 “Full이니 프로그램도 정상”이다.
- **D2 한 조건 변경:** ping이 복구돼도 해당 시점의 ICMP 왕복만 확인했다. HTTP 대상 주소·포트·바인딩·서버 대기·접근 정책, 이름과 TLS 조건을 나누어 요청 결과·서버 로그를 비교한다. 이 주차 실습은 HTTP 서버를 띄우지 않으므로 실제 HTTP 성공 로그를 만들지 않는다.
- **D3 다음 진단:** R1의 목적지 경로와 커널 설치, R3의 출발지로 돌아오는 경로, 실제 링크·중간 라우터의 경로를 확인한다. 두 가설을 구별할 관찰을 고른다. “핑 실패=OSPF 실패”나 “ICMP 차단일 것”을 출력 없이 확정하지 않는다.

## 코드 읽기 확인

정적 경로를 쓰지 않았는데도 커널 경로가 생기는 이유는 ospfd의 계산을 zebra가 설치하기 때문이다. `ping -I 192.0.2.1`은 출발 주소를 고정해 역방향 확인 대상을 명확히 한다. `no shutdown` 뒤 이웃·경로·ping을 다시 보는 것은 설정 복구와 통신 복구를 구별하기 위해서다. 종료 때 호스트의 기본 경로를 지우는 명령을 실행하는 것은 이 실습의 정리가 아니다. 자기 프로젝트의 `down`으로 정리한다.
