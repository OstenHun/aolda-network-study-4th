# 6주차 · 복습 문제

요약: HTTP 메시지·재사용/캐시·TLS 검증·SSH를 조건과 근거로 설명한다. 답을 먼저 쓰고 분리 해설과 비교한다. 입력은 자동 저장·제출되지 않으며 필요한 답안을 Markdown으로 내려받는다.

## Q1. 메시지와 전달

HTTP/1.1의 `GET /resource`, `Host`, `200`, `Content-Length`는 각각 무엇을 뜻할까? TCP ACK를 받았다는 사실과 HTTP 200을 읽었다는 사실의 차이를 설명한다.

## Q2. 새 연결과 재사용 계산

RTT=80ms, 작은 객체 3개를 응답 뒤 하나씩 요청한다. 첫 연결은 없고 DNS·TLS·처리·본문 전송·손실·병렬·파이프라이닝/다중화·캐시는 무시한다. 객체마다 새 TCP 연결, 첫 연결 뒤 재사용, 이미 열린 연결 재사용의 대기 비용을 각각 계산한다. 이 수치를 실제 HTTPS 페이지의 로딩 시간으로 써도 될까?

## Q3. 재사용을 확인할 근거

같은 curl 프로세스의 두 요청에서 X-Connection-ID가 같고 `num_connects`가 1·0이었다. 첫 경로만 `/close`로 바꾸면 무엇을 비교할까? 두 요청을 동시에 시작했다거나 로그인 상태가 유지됐다고도 말할 수 있을까?

## Q4. 304와 캐시

저장한 본문과 ETag `"study-v1"`가 있다. `If-None-Match: "study-v1"`을 보낸 GET에 304가 왔다. 본문은 어디에서 읽을까? 304를 받았으니 TCP 연결 비용이 없었다고 할 수 있을까? `no-cache`와 `no-store`도 구별한다.

## Q5. TLS가 확인하는 세 조건

신뢰 경로·호스트명·유효기간은 각각 왜 확인할까? 같은 IP·같은 CA인데 URL 이름만 `wrong.test`라면 어떤 근거를 보고 실패 단계를 나눌까? 복구 방법도 설명한다.

## Q6. 어디서 무엇을 볼까

TLS 1.3·ECH 없음·복호화 키 없는 중간 캡처를 가정한다. IP·포트·ClientHello SNI·서버 인증서·HTTP 메서드/경로/상태 중 평문으로 읽을 수 있는 것과 없는 것을 나눈다. curl은 왜 HTTP 200을 보여 줄 수 있을까?

## Q7. 서버 인증과 사용자 인증

인증서 검증은 통과했는데 HTTP 401이 나왔다. TLS가 실패한 것일까? SSH의 호스트 키 지문 확인·사용자 비밀번호/키 인증·원격 셸은 어떤 순서와 역할일까? SSH를 HTTPS와 같은 프로토콜이라고 해도 될까?

## Q8. 직접 수행의 범위

자신이 B를 실행했다면 정상→이름 변경→복구의 URL 이름·검증 결과·HTTP 결과·서버 로그를 근거로 설명한다. 아직 실행하지 않았다면 제공 예제에서 예상만 설명하고 필요한 환경을 말한다. CA 파일 읽기 오류·연결 거부·인증서 오류·HTTP 404 중 하나를 골라 다음 확인을 제시한다. 인증서 검증을 끄는 방법이 복구가 아닌 이유도 설명한다.
