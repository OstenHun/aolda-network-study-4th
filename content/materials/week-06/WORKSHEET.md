# 6주차 · 함께 찾을 질문

요약: 같은 IP에서 이름만 바꿨을 때 HTTPS가 달라지는 이유를 함께 찾는다. 공식 문서·교재·클라이언트 결과로 설명하고 연결 재사용·캐시·SSH를 필요한 보조 질문으로 연결한다.

## 먼저 짧게 복습하기

DNS가 IP를 알려 줬다는 사실만으로 HTTP 응답까지 보장할 수 있을까? [5주차 교재](../week-05/CONCEPTS.md)에서 근거를 찾는다. TCP ACK는 앱의 처리 완료인가? [4주차](../week-04/CONCEPTS.md)의 전달/처리 구별을 다시 설명한다.

## 중심 질문 · 같은 IP인데 이름이 다르면?

허가된 루프백 서버에 `https://study.test:8443/resource`로 요청한 뒤 같은 IP의 `https://wrong.test:8443/resource`로 요청한다. 한 이름만 인증서의 SAN에 들어 있다. 무엇이 같고 무엇이 달라지는지, 어디에서 실패를 확인해야 하는지 함께 찾아보자. 정답은 먼저 읽지 않는다.

1. [curl 인증서 검증 안내](https://curl.se/docs/sslcerts.html)의 **Verification**에서 기본 검증과 `--cacert`의 역할을 찾는다.
2. [RFC 9525 §6.3](https://www.rfc-editor.org/rfc/rfc9525.html#section-6.3)의 이름 비교를 [교재의 신원 확인](CONCEPTS.md#tls-identity)과 나란히 읽는다. 영문이 막히면 SAN·URL 이름 두 칸을 먼저 짚는다.
3. 각자 주소 선택·이름 비교·HTTP 도달 여부를 근거로 설명한다. “CA는 맞고 이름만 틀리다면?”으로 조건을 바꾼다.
4. [실습 B](LINUX.md#tls-lab)를 각자 실행하고 정상→실패→복구의 결과와 설명을 대조한다. 아직 실행하지 않은 내용은 예상으로 구별한다.

## 보조 질문 · 연결을 다시 쓰면 무엇이 줄까?

상품 응답을 받은 뒤 리뷰 요청을 보내는 코드가 있다. 같은 연결을 쓰면 두 요청도 동시에 처리될까? [RFC 9112 §9.3](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.3)의 도입 두 문단과 `In order to remain persistent`로 시작하는 문단에서 재사용 조건을 찾고 [교재의 RTT 표](CONCEPTS.md#request-cost)를 읽는다. RTT=80ms·객체 3개로 바꿔 계산한다. 캐시 재검증이 304를 받으면 새 연결 비용도 항상 없어지는지 묻는다.

시간이 남으면 [실습 A2](LINUX.md#reuse-lab)의 같은 프로세스/별도 프로세스·`/close`를 비교한다. 코드를 함께 시작하는 것과 실제 프로토콜의 다중화를 구별한다. 개발 사례 W06-D1~D3의 해설은 [별도 페이지](ANSWERS.md#development)에서 나중에 읽는다.

## 보조 질문 · SSH는 누구를 확인할까?

[교재의 제공 SSH 기록](CONCEPTS.md#ssh)을 읽고, 서버 지문 안내와 사용자 인증 요청의 순서를 설명한다. “호스트 키가 바뀌었다”는 경고를 비밀번호 오류로 처리해도 될까? 신뢰 경고를 없애기 위해 기록을 지우거나 검증을 끄는 행동 대신 확인할 근거를 고른다.

찾은 근거로 자기 설명을 확인하고 [복습](REVIEW.md)으로 돌아간다. 모임에서는 각자 시도한 근거와 막힌 이유를 비교한다. 메모는 자유롭게 하며 별도 발표 자료·정해진 기록을 만들지 않는다.
