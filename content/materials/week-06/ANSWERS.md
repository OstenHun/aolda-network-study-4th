# 6주차 · 분리 해설

요약: HTTP 메시지·RTT 계산·재사용/캐시·TLS/SSH의 필수 답안 요소와 흔한 오답을 대조한다. 실제 직접 수행은 본인의 출력으로 확인하며 제공 예제·계산·개발 사례는 자체 자료다.

- 먼저 [복습](REVIEW.md)과 [교재](CONCEPTS.md)의 W06-D1~D3을 설명한다.

## Q1 · 메시지와 전달

GET은 메서드, /resource는 요청 대상, Host는 서비스 이름/포트다. 200은 HTTP 상태 코드, Content-Length는 메시지 본문의 바이트 수다. TCP ACK는 상대 TCP의 수신 범위를 뜻하며 앱의 처리 완료·HTTP 200을 보장하지 않는다. **흔한 오답:** 패킷 하나가 메시지 하나다, 길이는 글자 수다. 교재의 24바이트 본문과 [실습 A1](LINUX.md)의 요청/서버 로그를 대조한다.

## Q2 · 대기 비용

객체마다 새 연결은 2×3×80=480ms, 처음 한 번 수립 후 순차 재사용은 (1+3)×80=320ms, 이미 열린 연결이면 3×80=240ms다. 필수 요소는 시작 시 열린 연결 여부·순차 요청·제외한 비용이다. **흔한 오답:** 재사용이 경로 RTT를 줄인다, TLS/브라우저 병렬 요청에도 같은 식을 그대로 쓴다. [교재의 가정](CONCEPTS.md#request-cost)을 붙인 자체 모형이며 실측이 아니다. 8주차 전체 흐름 계산에 다시 사용한다.

## Q3 · 재사용과 요청 순서

같은 ID와 새 연결 수 1·0은 이 서버/클라이언트 조건에서 재사용 근거다. /close는 첫 응답 뒤 연결을 닫으므로 다음 응답 ID가 달라지고 새 연결 수가 1·1이어야 한다. 정상 명령으로 돌아가 같은 ID/1·0을 재확인한다. 순차 재사용으로 동시 요청·다중화·사용자 로그인을 증명할 수 없다. **흔한 오답:** 두 curl 프로세스의 반복 호출도 연결 풀을 공유한다. [실습 A2](LINUX.md#reuse-lab)와 코드 setup의 호출 단위를 확인한다.

## Q4 · 캐시 재검증

304에는 메시지 본문이 없으므로 캐시가 저장한 본문을 사용하고 메타데이터를 갱신한다. 새 연결에서 재검증해도 304를 받을 수 있다. no-cache는 사용 전 검증을 요구하고 no-store는 저장하지 말라는 지시다. **흔한 오답:** 304는 오류라 빈 화면이다, 캐시는 TCP 연결 보관이다. [가공 흐름](CONCEPTS.md#캐시-재검증은-응답-내용을-다시-받을지-묻는다)과 실습 A3의 수동 검증자/브라우저 캐시 차이를 짚는다.

## Q5 · 신원 검증과 복구

신뢰하는 CA까지 경로/서명/용도, URL 이름과 SAN, 현재 시각과 인증서 기간을 확인한다. 같은 IP·CA여도 wrong.test가 SAN에 없으면 이름 검증에 실패할 수 있다. curl의 검증 오류·HTTP 미수신과 해당 요청의 HTTP 서버 로그 부재를 대조한다. 원래 study.test 명령으로 복귀해 검증을 켠 채 0·200·로그를 확인한다. **흔한 오답:** IP가 같으면 같은 신원이다, CN만 보면 된다, -k로 200이면 복구다. 검증 비활성화는 처음 확인하려던 보장을 제거한다. O02의 TLS 근거 일부이며 전체 운영 완료는 아니다.

## Q6 · 관찰 위치

주어진 조건에서는 IP·포트와 ClientHello SNI는 보일 수 있다. TLS 1.3 ServerHello 뒤의 인증서와 HTTP 메서드·경로·상태는 암호화되어 중간 캡처에서 평문으로 읽지 못한다. curl은 TLS 연결 당사자라 응답을 복호화해 200을 읽는다. **흔한 오답:** HTTPS가 IP와 모든 메타데이터를 숨긴다, TLS 1.3 인증서는 언제나 캡처에 평문이다. [관찰 표](CONCEPTS.md#암호화되면-무엇을-관찰할까)와 실제 협상 버전·키 보유 여부를 대조한다.

## Q7 · 인증 대상과 프로토콜

HTTP 401은 TLS 위에서 받은 HTTP 응답일 수 있다. 서버 신원 성공과 웹 사용자 인증 성공은 별개다. SSH는 전송 계층의 서버 호스트 키 확인→사용자 인증→연결 채널의 원격 셸 순서로 나눈다. SSH와 TLS는 별도 프로토콜이며 HTTPS는 HTTP over TLS다. **흔한 오답:** 호스트 지문은 사용자 키다, known_hosts 경고는 비밀번호를 다시 입력하면 된다. [SSH 제공 기록](CONCEPTS.md#ssh)에서 별도 신뢰 경로의 지문 대조와 변경 사유 확인을 설명한다.

## Q8 · 직접 근거와 다음 진단

본인 명령·출력에서 정상 200→잘못된 이름의 검증 실패/HTTP 미수신→정상 200을 확인한다. CA 파일 오류는 파일 경로, 연결 거부는 대기 포트·실행 위치, 인증서 오류는 신뢰/이름/기간, 404는 HTTP 경로를 본다. 실제 실행이 없으면 제공 분석과 필요한 Linux·서버·공개 CA·도구를 말하고 직접 수행을 보충한다. **흔한 오답:** 진행자 시연을 본인 실습으로 표시한다, 검증을 꺼 정상 처리한다. [실습 B](LINUX.md#tls-lab)의 결과와 복구 후 검증 기준을 재사용한다.

## W06-D1~D3 · 요청 순서와 연결 재사용

1. 연결 재사용은 새 연결 비용을 줄이지만 코드에서 앞선 응답을 기다리도록 정한 순서는 바꾸지 못한다. 실제 데이터 의존성이 없다면 두 요청을 일찍 시작할 수 있다.
2. 항상 절반은 아니다. 프로토콜·연결 수·서버 처리·자원 경쟁·캐시·전송량과 시작 시점에 따라 달라진다. 동시에 시작하는 코드가 프로토콜 다중화를 직접 켜는 것은 아니다.
3. 같은 조건에서 프로토콜·연결 재사용·요청 시작 시점·의존 관계·Timing과 응답 완료 시간을 대조한다. 이 예시에는 실제 브라우저에서 측정한 성능 결과가 없다.

**흔한 오답:** 지속 연결이 RTT 자체를 줄인다, HTTP keep-alive와 TCP/fetch keepalive는 같다, 요청을 함께 시작하면 항상 절반으로 빨라진다. 코드 의존성·연결·프로토콜·처리·전송 조건을 붙여 설명한다.
