# 6주차 · HTTP·TLS·SSH

요약: HTTP 메시지·연결 재사용·캐시를 구별하고 TLS가 보호하는 내용과 서버 신원 검증을 확인한다. 같은 IP의 이름을 바꿔 실패·복구를 비교하며 SSH의 호스트 확인과 사용자 인증으로 이어 간다.

## 이번 주에 설명할 질문

**같은 IP에 연결했는데 HTTPS는 왜 이름이 다르다고 거절할까? 암호화되면 무엇을 볼 수 있을까?** 먼저 [함께 찾을 질문](WORKSHEET.md)에서 필요한 근거를 찾고 한 명이 설명한다. 다른 사람은 이름 조건을 바꾸고 직접 요청해 비교한다. 질문·회차마다 설명자를 교대한다.

[4주차](../week-04/CONCEPTS.md)의 TCP 연결·RTT·전달과 앱 처리, [5주차](../week-05/CONCEPTS.md)의 DNS와 서비스 성공·URL 이름을 유지하는 `--resolve`를 다시 쓴다. “주소를 알아냈다”, “TCP가 연결됐다”, “서버 신원을 검증했다”, “HTTP 응답을 받았다”가 각각 어떤 근거인지 짧게 설명해 본다. 막히면 해당 교재로 돌아간다.

## 필수와 선택

필수 A는 HTTP 메시지·새 연결/재사용 RTT 계산·조건부 요청 제공 예제 분석이다. 실제 연결 재사용 실험 A2는 준비된 코드로 비교할 수 있다. 필수 B는 **각자 허가된 TLS 대상에 정상 요청→잘못된 이름→복구 요청**을 보내는 것이다. 진행자가 준비한 루프백 TLS 서버와 CA 공개 인증서를 사용하며 유료 도메인·외부 공개는 필요하지 않다. 준비가 막히면 제공 예제로 설명하고 직접 수행은 보충한다.

TLS 서버의 초기 구축, 추가 패킷 캡처, 새 SSH 접속·인증 방식 변경은 선택이다. 기존 SSH 경험 또는 제공 접속 기록에서 호스트 확인과 사용자 인증을 구별하는 설명은 필수다. 인증서 검증을 끄는 `-k`는 성공·복구 기준이 아니다. 전체 서비스 운영 능력은 이름·바인딩·정책 등 이후 근거까지 이어 확인한다.

## 무엇을 근거로 설명할까

HTTP의 메서드·경로·상태·헤더를 짚고, 재사용의 연결 식별자와 캐시 재검증의 ETag/304를 따로 읽는다. TLS는 URL 이름·신뢰 CA·SAN·유효기간·검증 결과와 정상 복귀를 보인다. 패킷에서 읽는 정보와 클라이언트가 복호화해 읽는 정보를 나눈다. SSH는 “서버를 믿을 근거”와 “사용자가 로그인할 근거”를 구별한다.

고정 팀 기록·개인 마무리 양식은 없다. 명령·출력은 개인 파일이나 노트에 한 번 보관하고 필요한 부분으로 설명한다. [전체 개념 색인](../CONCEPT_INDEX.md)에서 W06-K1~K3을 다시 찾는다.
